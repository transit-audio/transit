# E56: A lost graphics device froze the app in a plug-in's unload code

1. **Failure.** Build 7c1e744, Windows 11, AMD GPU (#104): transit was idle with two VST3 instruments loaded when the GPU changed power state. The UI thread panicked inside egui-wgpu ("Failed to create staging buffer for index data"), the window stayed on screen without responding, and the process never ended: one thread was left, sleeping inside an instrument's DLL unload.
2. **Mechanism.** Two defects. (a) No device-loss handling: wgpu reports a lost device only through `Device::set_device_lost_callback` (its error sink drops the error), and nobody registered one. egui-wgpu's buffer upload (`update_buffers`) then got `None` from `write_buffer_with` and panicked; its surface "Lost" recovery runs after that upload and would not re-create the device anyway. (b) No shutdown on a UI-thread panic: the panic unwound out of `eframe::run_native` (`apps/transit/src/main.rs`), so `on_exit` never ran: no input close and no `shutdown_plugin_hosts` (`crates/engine/src/lib.rs`). The C runtime's exit ran with plug-in binaries never exited. On Windows the exit first kills every other thread, then unloads the DLLs; the instrument's static destructor waited, with no time limit, for a worker thread that was already gone.
3. **Why checks missed it.** The module-exit tests (`crates/vst3-host/tests/module_exit*.rs`) covered the normal quit order and exit handlers, never a process that ends by a panic, and the VST3 fixture had no worker thread its unload waits for. Nothing exercised a lost wgpu device. The panic hook only logged. The quit order lived in `on_exit` alone, so any other way out of the event loop skipped it, and nothing bounded the exit.
4. **Regression tests.** `crates/ui-studio/src/emergency_tests.rs`, child processes with the VST3 fixture in its new unload mode (`VST3_FIXTURE_UNLOAD_WAITS_ON_WORKER`: the module entry starts a worker, the module exit stops it, a static destructor waits for it): `a_ui_thread_panic_with_a_plug_in_loaded_shuts_down_and_exits_within_the_bound` (exits with 70 after a clean shutdown), `a_binary_that_cannot_be_exited_is_terminated_instead_of_hanging_the_exit` (a leaked instance; terminated with 71 instead of hanging) and, on Windows, `without_the_shutdown_the_exit_hangs_in_the_plug_ins_unload`, which shows the pre-fix path (the C runtime's exit with the plug-in loaded) still hangs, so the fixture reproduces the defect. `apps/transit/src/shutdown.rs`: `a_lost_device_routes_the_next_frame_to_the_shutdown_path_before_the_paint` (a fake frame driver whose paint panics as egui-wgpu does) and, on Windows, `destroying_a_warp_device_fires_the_callback_and_flags_the_watch` (the real callback on a destroyed WARP device). `crates/engine/src/emergency.rs` and `crates/rt/src/process.rs` test the watchdog result and `terminate_process` (exit code, no exit handler).
5. **Gate class.** Every way out of the UI loop (quit, a lost device, a panic) runs the same bounded quit order, and the process exits normally only when plug-in hosting shut down cleanly (`shutdown_plugin_hosts` returns true, which now includes `soundcraft_vst3_host::modules_not_exited() == 0`); otherwise it is terminated without exit handlers (`transit_rt::terminate_process`). A watchdog (`soundcraft_engine::emergency::run_bounded`, 15 s) ends a shutdown that overruns. Plug-in teardown is tested against a fixture whose unload waits for its own thread, in a process that ends abnormally.
6. **Protocol change, owner, blind spot.** The plug-in hosts row of `docs/contributing/evidence/gates.md` now asks for the unload-mode fixture in a child process for changes to the quit order, plug-in teardown or process exit. ADR 0018 has an amendment on shutdown. Owner: plug-in host and app shell maintainers. Blind spots: the device is not re-created (K69: transit closes, keeping the autosave); a loss first seen inside egui-wgpu's upload still panics there and is shut down from the panic path; the time between the panic and the app's drop during unwinding is not under the watchdog; a crash (access violation) in plug-in code is still out of scope (ADR 0018, section 8); CLAP binaries are not counted by the cleanliness check; the "without the shutdown" hang is Windows-only (other platforms run exit handlers before killing threads).
