# E54: The Measure alignment guard was validated only on a lockstep fake

1. **Failure.** On Windows hardware (build 6f7670c, an External Instrument with Out = a KeyStep Pro MIDI port and Return = In 1), every Measure run ended with "Input alignment changed during the measurement: measure again." No run completed (#98).
2. **Mechanism.** `ExtProbe::note_backlog` (`crates/playback/src/external_probe.rs`, called from `External::measure` after the plan's pop in `player/audio.rs`) recorded the input ring's `buffered_input_frames` after every plan block, and `take_result` refused when the run's maximum and minimum differed by more than 2 frames. The snapshot is the ring's accepted minus retired count. With capture and render in one callback (native ASIO, the duplex fake) it is the aligned slack after every read. When the capture runs on its own callback (WASAPI's capture loop, cpal), the capture can push between the read and the snapshot. Each snapshot then reads the slack plus whatever arrived since: a sawtooth of up to a capture period (480 frames for a 10 ms capture under a 128-frame render), and a swing of a block when the two callbacks race for the same period. None of that moves the alignment, since the reader keeps reading the FIFO in order, but the extremes differed on every run. The guard now adds each snapshot to the current note's window and compares the windows' means, with a tolerance of half a plan block (`backlog_tolerance`). A block that gets ahead of the plan and stays moves the mean by the block and still refuses. Of the issue's hypotheses, (2) holds: an unpaired backend's count legitimately oscillates. (1) was close: the sample was always taken after the pop, but on an unpaired backend that point is not ordered against the capture. (3) did not apply: every value the guard compares is in input frames.
3. **Why checks missed it.** Every Measure test pumped the duplex fake in lockstep, capture then render, so the snapshot was constant by construction. The ADR's hardware evidence for a constant B came from native ASIO, which is paired. The hardware K22 test sampled B between callbacks and saw odd samples a block high ("caught between a capture push and the plan's read"), but it asserts only the minimum, so nothing checked the guard against that.
4. **Regression tests.** `player::device::external_measure_tests::an_unpaired_device_whose_callbacks_interleave_measures_in_every_order` pumps an unpaired fake (capture on its own stream) with capture 480 under render 128 and 64, and 192 under 192, in capture-first, render-first and pseudo-random order on ties. Every run measures 8 of 8 notes with spread 0. With the old extremes guard restored it fails at runtime (capture 480, render 128, capture-first: refused; 192 under 192, mixed order: refused). `an_unpaired_device_whose_input_shifts_by_a_block_mid_run_refuses` injects one capture block mid-run on the same fake and gets the refusal, with B moved by the block. `external_probe::tests::the_guard_takes_a_capture_sawtooth_and_refuses_a_step_that_stays` checks the same at the probe level. The paired test `a_backlog_that_changes_mid_run_refuses_and_the_note_is_released` passes unchanged.
5. **Gate class.** A guard validated only on a lockstep fake. A guard that reads a quantity another thread writes is tested on a fake whose callbacks interleave (own schedules, a capture period other than the render block, both orders on a tie), together with the real change it must still catch on the same fake.
6. **Protocol change, owner, blind spot.** `docs/contributing/evidence/gates.md` (test rules) carries the interleaving-fake rule. Owner: playback maintainers. The Measure log line (`External Instrument Measure at … Hz`, INFO) prints each note window's mean/min/max B and the tolerance, so a hardware run can be checked from transit.log. Blind spot: a callback order that flips and then holds for whole notes, or a real shift under half a block (K67). The hardware confirmation on the reporting device is a separate step.
