# ADR 0063: Clip tempo and Follow Tempo

- **Status:** accepted 2026-11-26 (proposed 2026-11-26; settled after five judging rounds with edits; the eight open questions decided on 2026-11-26 on the maintainer's delegation, after two rounds of a second review, listed under Decided; issue #336, milestone v0.8.0).
- **Date:** 2026-11-26
- **Implementation:** not started. Needs ADR 0056 slice 1 (the `anchor` field, #554) first; Smooth's release waits on the maintainer's listening verdict (Decided 8). Slices in the Slices section, kept as a checklist in #336.
- **Reopen when:** the quality check of slice 0 finds no acceptable Smooth algorithm under the license rule; ordinary Smooth loops exceed the render-before-play budget, or a tempo change during playback is heard in Smooth's stand-in for more than a moment, or the listening comparison of Decided 8 finds both the re-pitched stand-in and silence unacceptable (the trigger for a real-time stretcher); the render cache's memory budget is exceeded by ordinary sessions; warp markers need a mapping this record fixed differently; ADR 0056 changes `anchor` or the split representation this record builds on; or Ableton and Logic are found to agree on a behavior chosen differently here (claims marked unverified in Context).

## Context

The maintainer's case (2026-11-04): a 130 bpm project and a 133 bpm drum loop, and no way to make the loop follow the project tempo. Rulings already made on #336 and binding here: the stretch mode is a property of the clip with Keep Pitch (the default) and Re-Pitch, and Conform to Tempo and Follow Tempo use it without a prompt; Remove Pitch Shift stops being a separate command; the mode lives in the audio clip editor, the clip actions on the right-click menu, with no top-level Clip menu (2026-11-16); no tempo dance: detection happens on import, in the order `acid` tempo, file name, nearest whole-bar count, analysis, and the detected value is shown and can be typed over; the first version users get keeps the pitch; and before the mode is designed, a quality check of the existing pitch-preserving stretch on real material, recorded under `docs/benchmarks`. Standing rules: import makes no audible change the user did not ask for; the arrangement grid is one structure for tempo and meter; no interim surface; no migrations or shims while alpha.

### The code today (read at 5233b087)

- **`Clip::stretch`** (`crates/model/src/clip.rs:176-178`) is documented as "applied by rendered processing" but is a live varispeed: every read goes through `ClipReader::read` at `q = 1 / stretch` (`crates/model/src/disk/read.rs:113-132`), exactly the direct index at a stretch of 1 and the band-limited reader of ADR 0056 decision 8 otherwise, in memory, from the disk ring and offline alike (#604; `crates/mix/src/clips.rs:120-129`). The reader takes rates up to 32 and reads silence above (`crates/resample/src/read.rs:9`, `114-118`). Stretch bounds 1/32 to 32 (`clip.rs:105-110`), a stretch within 1e-9 of 1 stored as 1 (`clip.rs:112-117`). A clip's `length` may exceed its source while it loops (`clip.rs:186-189`), its content wrapping by `content_pos` (`clip.rs:132-137`).
- **The inherited commands.** `clip.conform_to_tempo` (`crates/engine/src/cmd/clip_more.rs:223-260`) sets `stretch = source_bpm / bpm` and rescales the length without rendering (`clip_more.rs:249-253`), keeping its memory in `edit.values` keys `clip.bpm.<id>` and `clip.len0.<id>`; it re-pitches. `clip.elastic_properties` (`crates/engine/src/cmd/clip.rs:141-147`, `214-258`) stores a varispeed without rendering when the track has no Elastic algorithm or has `"varispeed"` (`clip.rs:222-236`), and otherwise renders a pitch-preserving stretch into a new source, clones the clip onto it and resets `stretch` (`clip.rs:239-253`), remembering the original source, offset and length in `elastic.<id>.*` keys, which `clip.remove_warp` (`clip.rs:259-288`) restores. The algorithm is `Track::elastic` (`crates/model/src/track.rs:282-283`, serialized on every track, `null` when unset), set by `track.elastic` (`crates/engine/src/cmd/track.rs:207-219`). The renders go through `render_stretched` (`crates/engine/src/cmd/more_util.rs:143-198`), which sizes its input at up to ten times the output (#544); its callers are `clip.remove_pitch_shift` (`clip_more.rs:262-281`), Elastic on an Elastic track, and `edit.tce_to_timeline` (`crates/engine/src/cmd/edit_more.rs:224`, `749`). None of them is on a menu: the reachability gate lists them as undecided (`crates/ui-studio/tests/command_reachability/exceptions/undecided.rs:307-308`, `353-354`), and #728 was rescoped (2026-11-16) to leave them off until this record. `audiosuite.process` also offers `time_stretch` and `pitch_shift` renders (`crates/engine/src/cmd/audiosuite.rs:103-104`).
- **The stretcher.** `transit_dsp::offline::time_stretch` (`crates/dsp/src/offline.rs:231-327`) is a WSOLA with a 40 ms Hann window, half overlap and a 10 ms search on a mono guide shared by all channels, taking one scalar ratio clamped to 0.1..10. Its window is built with the standard library's `cos` (`offline.rs:245`), outside ADR 0055's portable math. The Time Stretcher built-in (`crates/dsp/src/plugins/time_stretcher.rs:1-40`) is a different thing: a port of a granular module's stretch mode as an insert effect, at 32 kHz on int16 frames; it is not a clip stretcher.
- **The transient detector** `detect_transients` (`offline.rs:382`) is already the one engine for the Sampler's Detect (`crates/engine/src/slice_detect.rs:248`, #267) and the clip transient analysis (`crates/engine/src/io.rs:438`).
- **Embedded tempo.** `transit_audio_io::wav_tempo` (`crates/audio-io/src/wav_cues.rs:337-344`) reads the `acid` chunk's tempo from a WAV's bytes. Its one caller, the Sampler's Slice to MIDI (`crates/engine/src/cmd/sampler_acid.rs:38`), reads the whole file and caches by path (#452). No other format's tempo is read.
- **Tempo and positions.** The tempo map holds step changes only (`crates/time/src/tempo.rs:43-46`); the Linear, Parabolic and S-Curve operations write step series at a resolution (`crates/engine/src/cmd/event_more.rs:34-50`). Clip positions are samples. On a tempo change `retime` works on ticks-timebase tracks only: it moves their clip starts and automation points, an audio clip keeping its length and a MIDI clip musical end to end (edges, fades, envelope, sync point, loop), and refuses a change that squeezes a clip or loop (`crates/engine/src/retime.rs:1-18`, `106-135`, `186-206`). Audio tracks default to the samples timebase (`crates/model/src/track.rs:337`), where neither clips nor automation move.
- **Undo and identity.** Undo swaps the whole document (`crates/engine/src/lib.rs:646-648`), the source pool and the id allocator `next_id` included (`crates/model/src/session.rs:399`, `505-510`), so a source id can be reused by a later import after an undo. The pool holds each source's audio as an `Arc<SourceAudio>` (`crates/model/src/source.rs:79-90`) and records no content identity.
- **Join** in the interface runs `edit.heal` on the range and then, when two or more clips remain, `edit.consolidate`, which renders them into one new clip (`crates/ui-studio/src/edit_tools.rs:190-197`). Heal compares source, offset continuity, loops and clip gain only, and never merges looped clips (`crates/engine/src/edit.rs:455-470`; #578).
- **ADR 0056** (audio clip editor, v0.8.0) owns the clip-to-source mapping: `offset` is the source frame read at clip time `anchor`, `x(c) = offset + s·(c − anchor)`; a split at `t` keeps `offset` and gives the later piece `anchor − d`, all integer and exact at any rate; pieces heal when their canonical forms say they play continuously (decision 5.3, 5.4). It reserves a clip key `warp: Option<...>` for this record with its own `needs` entry ("absent means decision 5's fixed-rate mapping"), and forbids new timing state in `edit.values`, any other meaning for `warp`, a source-time position anywhere but `offset` and the warp description, and a transpose that changes `stretch` (decision 12). Its decision 10.2 (accepted 2026-11-12, after the maintainer's #427 ruling of 2026-11-11 that loop cycles start on the tick grid) narrows that ruling: unwarped audio loops keep whole-sample cycles, and "a loop that follows the grid is the warping record's". Its slice 1 (`anchor`, the #554 fix) has not landed (`ClipContent::Audio` is still `{ source, offset }`, `clip.rs:85-87`).

### Conventions

From the issue (the maintainer's survey, not re-verified here): Ableton and Logic agree that a clip carries its original tempo, detected and editable; that a toggle makes it follow the project tempo (Live's Warp; Logic's Follow Tempo); and that markers fix the alignment where detection is off. They differ in algorithms (Live's Beats, Tones, Texture, Re-Pitch, Complex; Logic's Slicing, Rhythmic, Monophonic, Polyphonic, Speed) and in where the control lives (Live's clip panel, Logic's region inspector with Flex on the track). Both have a slicing mode and a speed mode among their algorithms. **Not verified, not relied on:** whether either switches following on by default for imported files and on what condition; where Logic stores the original tempo (file or region); whether either offers the toggle in a top-level Edit menu; what either plays while a stretch is being computed.

## Decision

### 1. Data model

1. **`Clip::tempo: Option<ClipTempo>`**, written only when set, with `ClipTempo { bpm: f64, from: TempoFrom, mode: StretchMode }`. `bpm` is the material's original tempo in quarter notes per minute, 5 to 1000 as the tempo map's (`valid_bpm`), further bounded while following (1.8). `from` is `File`, `Name`, `Bars` or `Typed` (decision 2), shown beside the value so a guess reads as a guess. `mode` is `Beats`, `Smooth` or `RePitch`: Keep Pitch is Beats or Smooth (the two pitch-preserving algorithms), Re-Pitch is speed and pitch together; the ruling's two values are kept, with Keep Pitch carrying an algorithm. The mode lives here, not in `warp`, so it survives Follow being switched off, as the ruling's "property of the clip" requires. A `clip_tempo` need when any clip has one (an older build would drop it on save; ADR 0023).
2. **Per clip, not per source.** A split copies it, so pieces agree; two clips of one file may differ (a trimmed region of a longer file). A per-source tempo would make Set Original Tempo change other clips, which neither convention requires.
3. **`Clip::warp: Option<Warp>`**, the key ADR 0056 decision 12.2 reserved, present exactly while the clip follows the project tempo: `Warp { looping: Option<TickLoop>, slices: Vec<Samples>, rate_one: Option<RateOne> }`. `looping` is the following loop (1.6); `slices` the Beats mode's slice points in source frames, ascending, at most 4,096, the whole list kept by every piece of a split (empty in the other modes); `rate_one` the Follow-off snapshot (1.7). A `clip_warp` need when any clip has one; an older build plays the clip at its fixed rate and warns, as decision 12.2 states. Warp markers join the structure later.
4. **The follow mapping builds on ADR 0056's.** `offset` stays the source frame read at clip time `anchor`. While following, the rate is replaced by musical time: with `P = start + anchor` (an absolute timeline sample, the anchor point), `T(x)` the session tempo map's tick position of timeline sample `x` (`samples_to_ticks_f`) and `F = 60 · R / bpm` source frames per beat (`R` the source's stored rate), clip time `c` reads source position `x(c) = offset + λ(c) · F / 960` with `λ(c) = T(start + c) − T(P)` ticks, wrapped by the loop when there is one (1.6). The clip's `length`, `start` and `anchor` stay stored integers in arrangement samples, so the playlist rule, the arrangement and the mix keep reading `start + length` as today.
5. **Edits are ADR 0056's, exactly.** A split at clip time `t` keeps `offset`, `looping` and `slices` and gives the later piece `anchor − t`; its `P` is the same absolute sample, so it reads the same positions as the whole, bit for bit. Lengths partition exactly (`t` and `length − t`). A start trim is the same; an end trim changes `length` only; a slip changes `anchor`. Heal merges two touching pieces that both follow with equal `tempo`, `offset`, `looping` and `slices` and the same anchor point `P` (`start_l + anchor_l = start_r + anchor_r`), looped or not: then splitting the merged clip gives both back, ADR 0056's heal rule. This replaces today's integer `offset` continuity test (`edit.rs:455-470`) for following clips only. Split then heal gives back every field of the following clip except `rate_one`, which the split cleared (1.7).
6. **A following loop is musical, in whole ticks.** `TickLoop { start: i64, end: i64 }` holds the loop in ticks relative to the anchor point, `end − start ≥ 1`. For `λ ≥ end`, `λ` wraps to `start + (λ − start) mod (end − start)`. Cycle `n` therefore starts at tick `T(P) + start + n·(end − start)`, converted to the sample nearest it once, never by summing cycles (the #427 rule): every cycle lands on its bar within half a sample at any `n`. Switching Follow on converts a clip loop `[ls, le)` to ticks by rounding each edge, `round((edge − anchor) · bpm · 960 / (60 · R))`: a one-bar loop cut at 86,617 frames of a 133 bpm file (3,840.02 ticks) becomes exactly 3,840 ticks, and its content runs half a frame past the cycle, which the next cycle cuts. ADR 0056 decision 10.2 governs unwarped loops; this governs following loops. While following, the clip's own `looping` is `None`.
7. **Follow off.** Switching Follow on stores `rate_one = RateOne { offset, anchor, length, looping }`, the clip's fixed-rate fields as they were, and derives the following form (`length` the arrangement span of the same material, `looping` in ticks). Any edit that changes the clip's edges, anchor or loop clears `rate_one`; a tempo change does not. Switching Follow off restores `rate_one` exactly when it is present; otherwise it writes the fixed-rate form in ADR 0056's normal form, rounded once: `offset = round(x(0))`, `anchor = 0`, `length = round(x(length) − x(0))` unlooped, loop edges from their ticks. **The stated limit:** after any edit, Follow off is exact only to that one rounding (a 48,001-frame clip at 120 bpm following 240 is 24,001 samples; split and healed, then switched off, it comes back as 48,002 frames). The snapshot is kept only for never-edited clips, because a piece of a split cannot know the whole's fixed-rate form and keeping copies on pieces would need a rule for which copy still applies. Set Original Tempo and Re-detect on a following clip are Follow off, the change and Follow on in one undo step, so the following form is derived afresh (the loop's ticks and the length measure the material in beats at the old tempo); a mode change alone moves nothing. Stored fades and the gain envelope are never rewritten by Follow on or off (1.10).
8. **The tempo domain while following.** For each tempo segment under a following clip, the ratio `ρ = (bpm_segment / bpm) · (R / session rate)` must lie in the mode's domain: Re-Pitch and Beats `[1/32, 32]` (the reader's bound); Smooth the renderer's (today's WSOLA 0.1 to 10; slice 0 states the chosen algorithm's). Switching Follow on, setting the tempo or the mode, and any tempo-map edit or retime that would put a following clip outside its domain is refused, naming the clip, as `retime` refuses a squeezed clip.
9. **Relation to `stretch` and the inherited commands.** `stretch` stays in the model, read and played as ADR 0056 composes it, so a session holding a stretch loads and sounds unchanged; after slice 1 no command writes it. Follow is refused on a clip with a stretch other than 1, with "reset the clip's speed first" (folding a varispeed into the following form would need a rate-aware conversion this record does not need for anything else). Slice 1 retires `clip.conform_to_tempo`, `clip.remove_pitch_shift`, `clip.elastic_properties`, `clip.remove_warp`, `edit.tce_to_timeline`, `track.elastic` and `Track::elastic`, with `render_stretched` (closing #544) and the `elastic.<id>.*`, `clip.bpm.<id>` and `clip.len0.<id>` keys: Follow Tempo in Re-Pitch is Conform to Tempo that keeps following; switching a clip from Re-Pitch to Keep Pitch is Remove Pitch Shift; a per-track Elastic algorithm is the inherited Pro Tools shape the maintainer declined (2026-11-04). Retiring them with the slice that creates following clips leaves no window in which an inherited render can repoint a following clip's source under its `warp`. Keys already in a session file are ignored (no migration). **What is lost:** a clip that Elastic already rendered keeps playing its rendered source, but the original source, offset and length its `elastic.<id>.*` keys remember can no longer be restored, and Follow off cannot recover them from the rendered file; re-importing the original is the way back. `audiosuite.process`'s `time_stretch` and `pitch_shift` stay, as offline renders that write a new file, refused on a following clip (decision 5).
10. **Fades and the gain envelope** stay in arrangement clip time (ADR 0056 decision 12.3). Their stored values are never clamped by Follow on or off; the clip gain evaluator clamps the **effective** fade lengths to the clip's current length at read, so a fade longer than a shortened clip plays shortened and comes back whole when the clip is long again, with nothing extra stored. A tempo change re-places them musically, as `retime` does for a MIDI clip. Envelope points past the end are kept, silent. **The loader keeps them too:** today `Clip::sanitize` clamps fades to the clip's current length (`clip.rs:383-386`, called at `clip.rs:412` from the session load, `crates/model/src/session.rs:794`), which would make a save and reopen lose what Follow on kept. For a following clip it bounds them to `0..MAX_POSITION` instead, as it bounds `whole_fades` (`clip.rs:400-403`), and the clamp at read does the rest. The other repairs of `sanitize` on a following clip: `start`, `length` (1 to `MAX_POSITION`), `sync_point`, envelope times and `offset` are bounds only, which no edit reaches, so they lose nothing; the clip's own `looping` is `None` while following; ADR 0056's load repair of an `anchor` outside ±2^46 (only a hand-edited file) moves `P` and so the mapping, said in its load note. New repairs: a `bpm` that is not finite or outside 5 to 1000 is clamped into it with a load note; a `TickLoop` with `end ≤ start` or edges past ±`MAX_POSITION` is dropped, as an invalid clip loop is; `slices` are sorted, deduplicated, bounded and cut to 4,096; `rate_one` gets the repairs of a fixed-rate clip (bounds, a valid loop or none), so Follow off never restores what a load would refuse; a `warp` without a `tempo` is dropped with a load note (the clip then plays at its fixed rate from its stored fields). A following clip outside its domain (1.8) keeps its fields and gets a load note.
11. **Transforms.** In the first slices Follow is refused on a clip that is reversed, transposed or fine-tuned (ADR 0056 decisions 6 and 7), and those transforms are refused on a following clip, each with its reason; an `anchor` alone is fine (it is the mapping's). Pitch at constant length (ADR 0056's "transpose under warp") is a later slice. Follow is refused on a disk-backed source (ADR 0035) until the cache can stream (slice 6).
12. **No migration, and what saves byte-identical.** A clip without `tempo` and `warp` is today's clip; both fields are skipped when absent, as `Clip::take` is (`clip.rs:194`). Removing `Track::elastic` in slice 1 changes the bytes of every saved session once: each track's `"elastic": null` (or an algorithm name, which no longer does anything) is no longer written. Beyond that one change, a session with neither new field saves as before.

### 2. Original tempo on import

1. **Order** (the maintainer's): (a) the file's `acid` tempo, from a read of the chunk headers only, through one reader the Sampler's Slice to MIDI also moves onto (fixing #452's first point; the cache keyed by size and modification time, its second); (b) a number in the file name from 60 to 200, decimals allowed, beside "bpm" (any case, with or without a space) or alone in brackets or between separators (`_`, `-`, space), as in "Melody[133]" or "Drums_131_"; when several qualify, the one beside "bpm" wins, else none (ambiguous); (c) the whole-bar count: with `L` the file's length in seconds, the project tempo `T` and the quarter notes per bar `n` at the import position, the bar counts `N` in 1, 2, 4, 8, 16, 32, the candidate `60·N·n / L` nearest `T` in ratio, accepted when it lies within 60 to 200 and within a ratio of 1.25 of `T` (outside that, half and double time are as likely as the guess); the result is a suggestion, shown as estimated and corrected by typing (Decided 2); (d) analysis, a later slice. The first that gives a value sets `tempo` with its `from`; none leaves `tempo` unset. Only `file.import_audio` (`crates/engine/src/cmd/file.rs:55`) detects; recordings and renders get no tempo in these slices.
2. **The maintainer's case.** Four bars of 133 bpm are 7.218 s; at 130 bpm in 4/4 the candidates are 66.5, 133 and 266, so (c) gives 133.0 (`from: Bars`), within 1.25 of 130.
3. **Follow Tempo is off on every import** (Decided 1). Detection stores a fact and changes nothing audible: an imported clip renders exactly as its file. The detected tempo is shown on the clip before Follow is on, with its provenance (decision 6), and the one Follow Tempo command uses that value with no prompt. Rejected: on by default for files from a loop-aware place (a file with an `acid` tempo or a tempo in its name) changes what an import sounds like without the user asking, which the standing ruling forbids; a per-import choice is a dialog on every import, a prompt the 2026-11-16 ruling avoided. An opt-in preference ("Imported loops follow the project tempo", off by default) is the user asking and can come later.
4. **Typed.** Set Original Tempo writes `from: Typed`. Follow on a clip without a tempo runs (a) to (c) first and is refused with "set the original tempo first" when none applies.

### 3. Playing a following clip

1. **Re-Pitch is a live read** through ADR 0056's reader at `x(c)`, the local rate being the segment's `ρ`. No render, no cache, no pending state.
2. **Beats is a live read too**, not a render. Beats plays source frames at rate 1 and only decides where each slice starts. A slice's **material** is source frames `s_i` up to the next slice point in `slices`, or up to the loop's end in a looped clip (the source position of its end tick, rounded down; the loop's start, rounded the same way, is always a slice point of each cycle), whichever comes first; the last slice's material runs to the end of the source. None of this depends on the clip's length, so a piece of a split has the same slices with the same materials as the whole. In clip time throughout: slice `i` starts at clip time `q_i = a_i − start`, where `a_i` is the timeline sample nearest tick `T(P) + (s_i − offset) · 960 / F` (wrapped per cycle by the loop: cycle `n` adds `n·(end − start)` ticks), and clip time `c` plays source frame `s_i + (c − q_i)` until its material ends (silence after it until the next slice starts) or the next slice starts, whichever comes first. **The only fade is on a trimmed tail:** when the next slice starts more than one sample before this slice's material ends, the last `round(0.002 · session rate)` samples before that start (96 at 48 kHz) fade linearly, the gain computed in `f64` from integer distances and rounded once to `f32`. A slice whose material ends first, a trim of one sample (two placements rounding apart) and the clip's edges cut with no fade: a clip edge cuts as every clip edge does, so a split adds no fade. At the clip's own tempo every `q_i` is exact and no slice is trimmed, so Beats then reads the file exactly as the fixed-rate clip does. The read depends on `slices`, `offset`, `P`, `bpm`, `R`, the loop's ticks, the tempo map, the source's length (the last slice's material) and the session rate (the fade's length), all read live from the clip, its source and the snapshot, nothing cached; a start trim moves `start` and `anchor` together and leaves `P`, so it moves no slice. That is a position map at rate 1 with a gain: the read is the direct index (ADR 0056 decision 5.3's fast path, no reader taps), the slice and cycle for a block are found by arithmetic on the tempo map and a binary search in `slices`, with no allocation, lock or IO, and every sample is a pure function of its timeline position, so the read is block-partition invariant. It holds on the audio thread under ADR 0029's rules for in-memory sources, which are the only ones that follow (1.11). A split piece places its slices from the same anchor point, so Beats splits null bit for bit.
3. **Play equals export for Re-Pitch and Beats, always**: the offline renderers call the same read.
4. **Smooth is the only rendered mode.** A render job runs off the control thread on a worker, the way Slice Detect does (`slice_detect.rs:1-20`), and its result joins the session's source pool as a rendered entry (an `Arc` of audio beside the sources, never serialized, never in the undo history), which the published snapshot maps from the clip, so the audio thread does one lookup per clip and reads it at rate 1 by clip time. Cycles under one tempo render once and are placed at each cycle start.
5. **The audio's identity.** Each `SourceAudio` gets an `audio_id: u64` from a process-wide counter when its audio is created (decoded, recorded or rendered), never reused within the process and never serialized. Undo and redo restore the same `Arc`, so the same identity; a later import that reuses a source id gets a new identity; re-importing the same file is a cache miss, which is harmless. A content hash was rejected: it reads the whole file to build a key.
6. **The key is the render's input.** The engine first resolves the clip's position map (3.7) off the audio thread: for clip times `0..length`, the pieces where the rate or the loop cycle changes, each as (its first clip time, an integer; the source position there, an `f64`; source frames per sample, an `f64`), closed by the terminal endpoint `length`, an integer, so the map says where it ends; a cycle start is a piece whose source position jumps back. The renderer reads that map, the audio (any frames its window needs around the mapped positions, before a trimmed start included, all of them in the audio the `audio_id` names) and nothing else of the session; it renders exactly `length` samples. The key is a hash over the `audio_id`, the resolved map's numbers bit for bit with its endpoint, the session rate and a renderer version (which covers the algorithm and its settings; Smooth is the only rendered mode, so the mode is implied, and a second rendered mode would join the key). Clip fades, gain and the envelope are applied after the read and are not in it; slices are Beats' and Smooth never reads them. Everything the mapping reads (the tempo history from `P` through the clip's end, `offset`, `anchor`, `bpm`, the loop) reaches the render only through the map, so two placements share an entry exactly when their maps are bit-identical: duplicates of a loop at constant tempo usually do, two placements whose tempo history before the clip differs (so their source positions at the clip start differ) never do, and undo or redo finds an earlier render still cached. Each piece of a split has its own key and render, so a Smooth seam is continuous in material and time but not bit-identical to the whole. Entries are evicted least recently used beyond a memory budget (slice 5 measures and sets it), never while the current snapshot maps them.
7. **Several tempos under one clip**: the renderer takes a monotone piecewise-linear output-to-source position map (one piece per tempo segment), not a scalar ratio; today's `time_stretch` scalar is its one-piece case. The tempo map has no continuous ramps, so pieces are exact.
8. **Pending Smooth renders.** Anything that changes a Smooth clip's resolved map (a tempo change it reads, Follow switched on, Set Original Tempo, an edit of the clip) makes its key new; until its render lands it is **pending**, drawn so in the arrangement (the design hand-off gives the state).
   - **Play waits for short renders, by work, not time.** Play and Locate compute the source frames of the pending Smooth renders the playhead reaches within the priming window. If their sum is at most the render-before-play budget (a number of frames, set in slice 5 from a measurement), they are rendered on the calling thread before the transport starts, as disk-backed rings are primed (ADR 0035 decision 4; `crates/model/src/disk.rs:725`). If it is more, nothing waits: the transport starts at once and those clips play the stand-in until the worker finishes them. The decision is made before any render starts, from the frame count alone, so it is the same on an idle and a loaded machine, and no render is cut short.
   - **What a pending clip plays** (after a change during playback, or past the budget; Decided 8) is its **Re-Pitch reading**, the working default: timing right at once, pitch off by the tempo ratio until the render arrives (133 to 130 is 0.39 semitone flat; a 10 percent change about 1.8 semitones), then a 5 ms linear crossfade to the render starting at a block boundary. Before Smooth is released, the maintainer compares it by ear against silence (the part dropping out until it is ready) in a development build of slice 5, the two behind a debug switch present in that build only, the worker held deterministically, on small and large tempo changes, repeated nudges, sustained vocals and pads, and several pending clips at once. That verdict decides which one ships and gates Smooth's release, not the earlier surface; if both are unacceptable, the reopen trigger for a real-time stretcher applies. The last finished render at the old tempo was rejected: its timing drifts off the grid by the tempo difference (at 133 against 130, about 170 ms by the end of four bars), and a clip that has just started following has none.
   - **The stated limit:** while a Smooth clip is pending, what plays is the stand-in and an export of that moment is the render, so the two differ until the render lands; the arrangement shows the clip pending for exactly that time. Offline paths (bounce, export, freeze, consolidate) render every missing entry synchronously first and never use a stand-in. Tests drive the worker deterministically (as they drive `DiskSource::pump`) and assert both sides of the rule: pending, the live read is the stand-in and the clip reports pending; finished, the live read equals the export bit for bit.
9. **Determinism.** The Smooth renderer computes its window and every transcendental through `transit-math` (ADR 0055). Beats uses copies and linear fades only, so its output is IEEE-exact.
10. **Undo** restores clip fields only; the cache is derived state, like peaks.
11. **Rejected for now: a real-time pitch-preserving stretcher on the audio thread.** It costs CPU per following clip per block, needs pre-roll on every locate and a latency report, is hard to keep block-partition invariant, and the only permissively licensed candidate seen (Signalsmith Stretch, a header-only C++ library, MIT by its published documentation) would need a new FFI crate under the unsafe policy. With Beats and Re-Pitch live, it would serve Smooth alone. ADR 0035's streaming is the path for long files (slice 6); the trigger is in Reopen when.

### 4. Beats and Smooth

1. **Beats**: `slices` are detected once by `detect_transients` (the Sampler's detector, one engine) when a clip first follows in Beats or Beats is chosen, and stored, so the read is reproducible on every machine and the slices are the seed of warp markers; Re-detect is an explicit action. The material's first frame is always a slice start, and so is each loop cycle's start, whether or not a transient is there. A slice shorter than its place on the grid ends where its material ends and silence fills the gap (Trim); a slice longer than its place is cut with the tail fade of 3.2; filling the gap by looping the slice tail is a later option.
2. **Smooth**: the pitch-preserving stretch slice 0 chooses (today's WSOLA as it is, an improved WSOLA, or another algorithm under the license rule, MIT, Apache, BSD or ISC only), taking the position map of 3.7.
3. **The default mode is Beats, fixed and permanent** (Decided 4): every clip whose `tempo` is first set gets Beats, whatever its material, and the user picks another mode per clip. Nothing chooses a mode by detection, and the arrival of Smooth changes no default and no stored clip. A mode is never stored before its slice lands, so slice 1, control channel only, stores Re-Pitch (the one mode it has); from slice 2 on, every newly set tempo gets Beats.
4. **The first user-visible cut ships Beats and Re-Pitch** (Decided 6). The maintainer's case is a drum loop, which a WSOLA smears; Beats is the transient-exact answer, IEEE-exact and live. Smooth joins later as one more Mode entry. Until then there is no continuous pitch-preserving treatment for sustained material: on a pad or a vocal, Beats leaves gaps when slowed and cuts tails when sped up, and Re-Pitch changes the pitch; the help and the user guide say so plainly.

## Consequences

- A loop follows the project tempo with its pitch kept, from one click; switching Follow off gives an unedited clip back exactly, looped length and fades included.
- Following clips are musical: they move with the grid on a tempo change even on a samples-timebase track, where the track's automation does not, and their loops never drift off the bar.
- Splits and heals of following clips are as exact as ADR 0056's at fixed rate, because they are the same operation.
- Re-Pitch and Beats always play what exports; once Smooth is released, a Smooth clip changed during playback is heard in its stand-in (re-pitched, unless the listening verdict of Decided 8 picks silence) until its render lands, and shows pending meanwhile.
- The inherited stretch commands and the per-track Elastic algorithm go with the first slice; an Elastic-rendered clip can no longer be restored to its original; `stretch` remains as a read-only legacy until a later record retires it; every saved session drops `"elastic"` once.
- The work waits for ADR 0056 slice 1. The first visible cut has no continuous pitch-preserving treatment for sustained material, and says so; Smooth renders cost memory when Smooth comes; long files cannot follow until slice 6.
- Every clip with a detected tempo shows it, qualified by where it came from, whether or not it follows.

## Alternatives rejected

- **The tempo on the source:** couples clips that the user may want to differ, and makes a split or a trimmed region inherit a value that may not fit it.
- **A parallel mapping in rounded rate-1 frames** (rounds 1 and 2): a split rounded the cut into source frames and moved the later piece's phase, whose derived length then overlapped its neighbor by a sample (a split at 47,902 of a 133-in-130 clip: source position 46,821.50, right offset 46,822, left length 47,903); loop cycles taken from a rounded frame count drifted (cycle four at 265,848 against bar four at 265,846); looped pieces could not heal; and Follow on clamped fades that Follow off could not restore. Building on `anchor` and ticks removes all four.
- **Rendering Beats:** it is a position map at rate 1 and needs no stretch processing, so a render would only add the pending state and a playback and export difference.
- **Follow as a fixed-rate `stretch` rewritten on every tempo change** (Conform to Tempo kept running): re-pitches, cannot hold two tempos under one clip, and keeps hidden state in `edit.values`, which ADR 0056 forbids.
- **The render as a new source in the document** (today's `render_stretched`): destructive by bookkeeping, saved files multiply, and toggling off depends on remembered keys.
- **A render keyed on the clip id or the source id:** duplicates re-render, undo loses the render, and a source id reused after an undo would hand one file's render to another.
- **A render-before-play budget in elapsed time:** the same session would start rendered on an idle machine and in the stand-in on a loaded one, and a test could not pin the branch.
- **Join falling through to Consolidate on following clips:** silently ends Follow and the way back to the original material.
- **Refusing the inherited commands on following clips until a later retirement:** refusal code written to be deleted; retiring them in slice 1 is simpler.
- **Beats detected afresh on every read:** the read could differ between machines (the detector's floating point), and markers would have nothing to start from.
- **A default mode chosen by detection** (Beats above a transient density, else Smooth): an unsupported inference from density to the right algorithm, and a default that would change when Smooth arrived.
- **Waiting for Smooth before the first visible cut:** holds the drum-loop case on a slice whose algorithm and stand-in are not settled yet.
- **Rubber Band and other GPL or LGPL stretchers:** license.

## Decided (2026-11-26, on the maintainer's delegation)

1. **Follow Tempo is off on every import.** The detected tempo is shown on the clip before Follow is on, with its provenance qualified ("133 BPM · estimated" for the whole-bar count), and the one Follow Tempo command uses that value (decisions 2.3 and 6).
2. **The whole-bar bounds as stated** (bar counts 1 to 32 in powers of two, 60 to 200 bpm, within a ratio of 1.25 of the project tempo). They produce a suggestion; its provenance stays visibly qualified and the value can be corrected (decision 2.1).
3. **The whole inherited family retires** in slice 1, `edit.tce_to_timeline` and `track.elastic` included (decision 1.9).
4. **No default by detection.** The default mode is Beats, fixed and permanent; the user picks another mode per clip (decision 4.3).
5. **AudioSuite and the clip renders are refused on a following clip** in the first cut, and the refusal changes nothing (decision 5).
6. **The first visible cut ships Beats and Re-Pitch.** Smooth is added later as one more Mode entry, changing no default and no stored clip; the help and the user guide say plainly that until then there is no continuous pitch-preserving treatment for sustained material: Beats leaves gaps or cuts tails on a pad or a vocal, Re-Pitch changes pitch (decision 4.4, slices 4 and 5).
7. **A following clip's start follows the grid on every track**, a time-locked clip excepted. The Tempo group says so where the user enables it: "Follow keeps this clip on the beat grid. Track automation on a samples-timebase track stays at its original time." The user guide too (decision 6).
8. **A pending Smooth clip plays the re-pitched stand-in** as the working default. Before Smooth is released, the maintainer compares it against silence by ear in a development build of slice 5 (both behind a debug switch in that build only; the worker held deterministically; small and large tempo changes, repeated nudges, sustained vocals and pads, several pending clips). That verdict gates Smooth's release, not the earlier surface; if both are unacceptable, the reopen trigger for a real-time stretcher applies (decision 3.8).
