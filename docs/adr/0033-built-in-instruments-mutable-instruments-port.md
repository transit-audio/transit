# ADR 0033: Built-in instruments: a port of the Mutable Instruments family

- **Status:** proposed 2026-10-29 (maintainer decision)
- **Date:** 2026-10-29
- **Reopen when:** the crates.io evaluation finds no acceptable starting point and the Rust port proves too costly to carry; the upstream license terms change; the null-test residual floor cannot be measured stably on CI hardware; or a product question asks for engines the family does not cover.

## Context

transit has no built-in instruments beyond what it inherited. The maintainer wants wavetable and granular synthesis. Writing generic engines from scratch would mean months of sound design with no reference to judge them against.

Émilie Gillet's open-source Mutable Instruments DSP (the `eurorack` repository on GitHub, code under the MIT license) is a coherent, proven family:

- Plaits: a macro oscillator with virtual analog, wavetable, FM, additive, physical-model and drum engines. Firmware 1.2 adds six-operator FM, wave terrain, string machine and chiptune.
- Rings and Elements: physical modeling.
- Clouds: granular texture synthesis.
- Warps: a meta-modulator, which is an effect.
- Marbles and Grids: random and drum sequencers, which are MIDI effects.

The modules were built to run on a Cortex-M4, so CPU cost is low, and they share one design language.

## Decision

Port the family as small, focused built-in instruments and effects. They are mono by design where the originals are. Users build bigger instruments by composition: a track chain (an instrument plus inserts) and a group of tracks, the rack of [ADR 0034](0034-racks-layering-instruments-through-track-groups.md).

Order: Plaits first, with a voice allocator and a small editor, as the first slice of v0.6.0. Then Rings, Clouds, Warps, then Marbles and Grids.

Rules, each agreed by the maintainer:

1. Port only from the original repository. Never port from VCV Rack's Audible Instruments, which is GPLv3 and would contaminate transit's MIT/Apache-2.0 licensing.
2. No Mutable Instruments branding on the instruments. They get descriptive names of transit's own (as VCV did with Macro Oscillator, Resonator and Texture Synthesizer). Credit Émilie Gillet explicitly, with her MIT notice, in the about box, in each instrument's help entry and in a third-party license file.
3. Polyphony, the editor window and the rack are transit's own work. Polyphony is a voice allocator around N mono engines with a note-to-macro mapping (pitch, harmonics, timbre, morph). The editor follows the ownership rules of [ADR 0030](0030-editor-window-cohesion.md).

### Implementation

A Rust port in a transit-owned crate with a descriptive, brand-free name (the Plaits port is `transit-macro-osc`; see the amendment below). The shipped app is pure Rust.

Before any port starts, evaluate the existing crates.io port (`mi-plaits-dsp`) for license and fidelity. The evaluation is a prerequisite, not a decision: it informs whether to adopt, fork or write the port, and this ADR does not pre-empt it.

### Gate

Null tests against her C++, wrapped as a dev-only oracle. The oracle is built with the `cc` crate for tests and CI only and is never linked into the app.

- Same model, seeded noise, fixed parameter sweeps, compared sample by sample at 48 kHz with her block size.
- The residual floor is measured first, with FP contraction and fast-math off. The gate is set at that floor with margin. A residual above the floor is an escape.
- The port is tested at the mono-voice level. The allocator, the editor and the rack get ordinary tests.

## Consequences

- A coherent instrument section with one design language and low CPU.
- The DSP risk is retired by the oracle; the design work moves to composition and UI.
- Every ported module adds its own oracle build to CI.
- Third-party license text and credits become a maintained deliverable of each release that ships a port.

## Alternatives considered

- Generic wavetable and granular engines from scratch: months of sound design and no reference to test against.
- The C++ via FFI inside the app: adds a toolchain and an unsafe surface. Rejected; the C++ stays in the test oracle.
- The VCV Rack ports: GPLv3, which conflicts with transit's licensing.
- Shipping under the original names: contrary to the branding request.

## Amendment 2026-10-29: crate naming and the Plaits source decision

Maintainer decision, 2026-10-29. This amendment supersedes the crate naming in Implementation above and records the outcome of the crates.io evaluation (#193).

**(a) Crate naming.** The rule `transit-mi-*` is replaced. The eurorack README asks derivative works not to keep the original module names, so crate names are descriptive and brand-free: each names what the crate does, not whose module it came from. The Plaits port is the crate `transit-macro-osc` (macro oscillator). Later modules take names that describe what they do, for example Rings is `transit-modal-resonator`, not `transit-rings`.

**(b) Source decision (#193, 2026-10-29): option (b), vendor the MIT Rust port.** The port is `mi-plaits-dsp-rs` by Oliver Rockstedt (GitHub `sourcebox`), vendored at commit `effe9864bb` into `transit-macro-osc`. Its terms:

- Rockstedt's MIT notice stays in the source and the crate.
- Émilie Gillet's full MIT notice from `eurorack` and `stmlib` is restored in the crate `LICENSE` and in the third-party license file.
- The source commit (`effe9864bb`) is recorded in the crate and in the third-party file.
- Before any engine ships, each one is corrected against the C++ oracle (#194): per-instance RNG; sample rate as a parameter, not a constant; an audit of the interpolate clamps; the VA auxiliary oscillator phase returned to firmware behavior; and the snare and VOSIM details.

**(c) Fallback.** If the vendored code needs more repair than it saves, port from the firmware instead (option c), behind the same oracle gate. The null tests compare output sample by sample, so the swap is invisible to users.

Related: #193 (the evaluation and this decision), #194 (the C++ oracle that gates each engine).

## Implementation note: oracle

The Gate oracle is `crates/macro-osc-oracle` (`transit-macro-osc-oracle`, #194): the upstream C++ vendored unchanged, dev-only (`cargo xtask layers` rejects any normal or build dependency on it), with its FFI `unsafe` confined to `src/ffi.rs`; the sweep, the residual and the measured floor are in [gates.md, Oracle null tests](../contributing/evidence/gates.md#oracle-null-tests).

## Oracle deviation note 2026-10-30: the six-op engine after shared RAM

The firmware's engines share one 16 KB RAM arena (`Voice::Init` frees the allocator before each engine's `Init`), and the six-op engine keeps its staggered-render accumulator there without clearing it in `Reset`. On the module, the first block after the voice returns to a six-op bank from the string machine, speech, swarm, particle noise or inharmonic string engine (or the wavetable engine, on a 64-bit host only) therefore adds that engine's leftover bytes, read as floats, to the output: arbitrary values up to a NaN, which the C++ cast turns into a full-scale -32768 click. The port's engines own their memory, so the six-op engine replays its own last partial sum, which is the module's output whenever nothing overwrote it; the port is never louder than the module there. Won't fix: on the module, the first 12-frame block (0.25 ms) after returning to a six-op bank from one of six engines adds that engine's leftover memory to the output, which can be a click; transit plays the six-op engine's own tail instead, as the module does after any other engine. Reproducing it would mean emulating every engine's byte layout and the host's pointer size to replay garbage. The voice gate pins the difference to that one block (`six_op_reentry_after_a_ram_sharing_engine` in `crates/macro-osc/tests/voice_scenarios_vs_oracle.rs`); every other frame of every voice scenario is compared at 0 LSB. This is an oracle deviation, not a transit known issue: no user can hit it, since nobody compares the DAW with the module (#195).

## Implementation note 2026-10-30: the Macro Oscillator instrument (tuning, names, MIDI)

The first instrument of the family ships as the built-in "Macro Oscillator" (`macro_oscillator`, in `transit-dsp` beside the other built-ins, over `transit-macro-osc`; `transit-dsp` takes the same-layer dependency and is no longer standalone, #195).

- **Tuning.** The firmware computes pitch against its corrected rate (47872.34 Hz, the module's codec clock), so the module plays in tune while the same arithmetic at a true 48 kHz plays 4.6 cents sharp. The instrument plays concert pitch by default (A4 = 440 Hz): `Voice::set_tuning(Tuning::Concert)` scales every frequency the firmware derives from its corrected rate (the voice's `a0`, the six-operator voices' reference, the speech formants) by 47872.34 / 48000, and divides the LPC speech pitch shift's corrected rate by the same factor, so A4 is 440 Hz on every path. The firmware's LPC path is pitched differently by design: in `lpc_speech_synth_controller.cc` the corrected rate cancels out of `pitch_shift` and the LPC clock is the raw sample clock / 6, so at a true 48 kHz the firmware's LPC speech is in tune while its other paths are 4.6 cents sharp (on the module, the other paths are in tune and LPC speech is 4.6 cents flat). `crates/macro-osc/tests/voice_pitch.rs` checks every path's absolute pitch at every rate ([E63](../escapes/E63-the-speech-model-played-out-of-tune-away-from-48-khz.md)). The port plays at concert pitch; the firmware's arithmetic is kept bit-exact in the crate (`Tuning::Firmware`, the crate default) for the null tests, and the module itself plays in tune because its audio clock runs at the corrected rate. So there is no switch back to the firmware's pitch: at a true 48 kHz it would only detune the instrument by 4.6 cents while claiming to match the hardware (a "Hardware Tuning" parameter existed briefly on the slice 3 branch and was removed before merge; a session that stored it loads, and the open logs the ignored id).
- **Names.** The 24 models are named by what they do, in the firmware's order: Filtered analog, Phase distortion, Six-op FM 1 to 3, Wave terrain, String machine, Chiptune, Virtual analog, Waveshaper, FM, Grain, Additive, Wavetable, Chord, Speech, Swarm, Filtered noise, Particle noise, Inharmonic string, Modal, Bass drum, Snare, Hi-hat. No module or brand name appears in a UI string or identifier.
- **MIDI.** The held note is the voice's V/OCT input, a note-on raises its trigger and sets its level input from the velocity, a note-off lowers both so the low-pass gate's decay is the release. Mono, last-note priority, legato as the module's trigger input behaves: a note under a held one changes pitch with no new trigger. A new phrase whose note-on shares a 12-frame block with the last note-off gets one low block first, so the voice sees the edge. A legato note sets the level input to its own velocity, so the level steps mid-phrase as the module's level CV does (Ableton and Logic keep the running envelope on legato; documented in the user guide). Sustain holds released notes; pitch bend spans a parameter range (2 semitones by default); the mod wheel adds to a chosen control (Timbre by default).
- **Blocks and output.** The voice renders 12-frame blocks (its envelopes are timed per block) whatever the host block, carrying rendered frames across host blocks, so any host block size renders the same bits; events take effect at the next 12-frame boundary. The int16 frames become floats as `(1 - s) / 32768`: polarity restored and the firmware's +1 truncation offset removed (silence is exactly 0), full scale one LSB under 0 dBFS (+1 reads 32767/32768, -1 reads -32766/32768; only the clip reads 32769/32768, +0.0003 dB); the default level is -6 dB.
- **Credits.** Émilie Gillet's MIT notices (eurorack, stmlib) and Oliver Rockstedt's are in ATTRIBUTION.md, NOTICE and Help > About transit; the panel and its help entries credit the original; the user guide says it is a port, not an emulation of the hardware's analog stages.
- **Rack-ready, not racked.** One mono voice, MIDI in, one audio output on every channel, parameters addressed by automation id (`plugin:instrument:<id>`). Unison and layering are ADR 0034's racks; polyphony inside the one instrument followed in #196 (next note).

## Implementation note 2026-10-30: voices, note-to-macro mapping, editor (#196)

- **Voices.** `voices` (1 to 16, default 8) firmware voices inside the one instrument, all built with the instance (the parameter can change on the audio thread without allocating). Voice `i` is seeded `Random::DEFAULT_SEED + i`, and a reset reseeds every voice, so exports and renders after a reset play the same bits. A note-on takes, in order: the voice already playing that key (held, under the pedal, or in its tail), the lowest-numbered free voice, the quietest voice in its release tail (a peak follower falling 0.5% per 12-frame block; the oldest phrase among equals), else the oldest held voice; a stolen held voice gets one low trigger block first, so it sees a new edge. A note-off leaves the voice's low-pass gate tail playing; a voice is free once it holds no key, its trigger is low and both outputs have stayed within one int16 LSB of silence (-90 dBFS) for 50 ms (six-op FM 2 settles on a ±1 LSB residue, never exact zero), and a free voice is not rendered; every model goes idle within the tail (`every_model_releases_to_an_idle_voice_within_the_tail`). The chiptune model bypasses the low-pass gate and, with no envelope set, holds its note for ever (on the module too, with the TIMBRE attenuverter at 0): a held key keeps it held, and after the note-off the voice sets its envelope from Decay (`chiptune_release`, silent in 0.15 s to 9 s), so its note ends as on the other models. This fixes a slice 3 defect (a chiptune note never ended). Voices above a lowered count release and play out. `voices` = 1 is the mono instrument above, bit for bit in its legato rules. The voices sum in voice order, so the instrument plays exactly the sum of independent mono voices (`n_voices_render_the_sum_of_n_mono_renders_bit_for_bit`). No unison and no automatic gain for wide chords: voices add, as in Ableton's and Logic's synths. The steal order follows the convention of both DAWs' stock synths (steal the oldest note), with a preference for released voices first, quietest first; a stolen held voice is silent for one 12-frame trigger block (0.25 ms at 48 kHz) so its envelopes restart on a clean edge.
- **Note-to-macro mapping.** Velocity (0..1) and the key (-1..1 around middle C, MIDI 60, which Live and Logic both name C3 and Live's key tracking is relative to; ±1 at 60 keys away) drive Harmonics, Timbre, Morph and Decay through a depth each (-100% to +100%, default 0) and a curve per source (Linear, Exponential, S-curve: the clip fades' curves, `FadeShape::gain` called directly). As in the MIDI Learn range model the source's travel spans a part of the target's travel (no change to `depth` for velocity, `-depth` to `depth` for the key) and a negative span inverts. The sum is clamped to 0..1, then the mod wheel adds; with every depth at 0 each target is its knob exactly, so the defaults play as #195 (velocity sets the level, as before). Key tracking of Timbre ships as the "Key Tracked Timbre" factory preset (`key_timbre` +50%).
- **Editor.** Every built-in editor in transit is an egui window inside the main window's viewport (`builtin_editor.rs`), not a separate OS window, so ADR 0030's outcome (minimize, restore and front with the main window, no taskbar entry, never duplicated) holds by construction and the `editor_group` requests do not apply; `ui.inspect` lists it as `builtin` (`the_macro_oscillator_editor_stays_with_the_main_window_and_is_never_duplicated`). Rather than a first viewport for one built-in, the panel grows in place: a Voices section with activity lights (read from the instrument's scope tap, `Plugin::voice_activity`, stored only while the panel is open) and the mapping grid (a row per source, a column per target).
- **Cost.** One voice costs 5 to 70 us per 256-frame block at 48 kHz (0.1% to 1.3% of one core; the median of the eight models measured is 26.6 us, 0.5%) on the development machine, measured by `crates/dsp/tests/macro_osc_cost.rs` (ignored, release); the figures are in the crate README for the rack budget.

## Implementation note 2026-10-31: the Macro Oscillator's shaper and modulation matrix (#243)

The shaper and the matrix are transit's addition, not part of the original module; the panel says so on the line that shows them. Both are off by default: with the shaper off and no active row, the instrument renders the bits it rendered before them, and the null tests against the oracle are untouched (the vendored port's numerics are not changed; everything below lives in `crates/dsp/src/plugins`).

Convention: Ableton's Wavetable and Logic's ES2 and Alchemy route modulation through a matrix of rows (source, destination, amount); the "via" (a second source scaling a row's amount) follows ES2's modulation router (Source, Via, Target), which Alchemy's modulation also has. The curves are the clip fades' shapes, as the note-to-macro mapping's were.

- **Where it sits.** Per voice, after the firmware's low-pass gate and the aux crossfade, before the level and the voice sum: drive (soft clip), the Filter insert's SVF sections (`filter/svf.rs` `Section` and `Coefs`; 12 dB one section, 24 dB a second Butterworth one), then the amp envelope's gain (the built-in instruments' `Adsr`). With the shaper on the gate's level input is held at 1 (open) and the amp envelope is the voice's envelope: a voice is free once no key holds it and its amp envelope has finished. Off, the low-pass gate's decay is the release, as before. Whether the shaper shapes a voice is taken when the voice's phrase starts and kept until the voice is free: a voice sounding when the shaper turns on keeps its gate and its idle rule until it ends, and a shaped voice keeps its amp release when the shaper turns off, so the switch does not click (`switching_the_shaper_on_keeps_the_sounding_voices_on_their_gate`, `switching_the_shaper_off_keeps_a_shaped_release`). The LFO is the Filter's, moved to `plugins/lfo.rs` as a pure move, then given a smooth random shape, a seed per instance and `set_phase`.
- **Evaluation order.** Once per voice per 12-frame block, so the firmware's block alignment stays and any host block size renders the same bits (`the_shaper_and_a_full_matrix_render_the_same_at_any_block_size_and_after_save_and_load`). In a block: a new phrase gates the envelopes, draws the note's random value and restarts or picks up the LFOs; a synced, free-running LFO takes its phase from the song position; the sources are read (envelope levels and LFO values as of the block start); the rows run in order, each adding `amount · via · curve(source)` to its destination (a row with source or destination Off, or amount 0, is dropped when the parameters change, and a matrix with no active row is not evaluated); the sums are applied; the filter's coefficients are worked out; the frames are shaped; the LFOs advance. The LFO amount sums act one block later (the LFOs feed the matrix). Fixed storage throughout: the probe with 16 voices, the shaper and every row active allocates nothing (`sixteen_voices_with_steals_the_shaper_and_a_full_matrix_allocate_nothing`).
- **Clamping.** Harmonics, Timbre, Morph and Decay: knob plus sum clamped to 0..1, then the mod wheel (capped at 1), exactly the mapping's rule, and a target no row moves is its knob exactly. Pitch: 24 semitones per unit, the note clamped to ±96. Level: gain `1 + sum` clamped to 0..2. Pan: a balance clamped to ±1 that leaves the near side at unity, so a centered voice's gains are exactly 1 and the voice sum is unchanged bit for bit; with any Pan row the instrument's output is stereo (first channel left, second right, any other their mean). Cutoff: six octaves per unit on top of key tracking and the filter envelope, clamped to 16 Hz .. 0.49·fs. Resonance: the knob's travel. Filter env amount: clamped to ±1. LFO rate: ×2^(4·sum), the sum clamped to ±1, for free-rate LFOs (a synced one follows the tempo). LFO amount: base plus sum clamped to 0..1.
- **Sources.** The rack's eight macros reach a member's instrument through `Plugin::reads_rack_macros` and `set_rack_macros`, which the mix calls each block with the macro knobs or their lanes' values (0 for a track not in a rack). Aftertouch, poly aftertouch and the note-off velocity are read from the instrument's events.
- **Tempo sync (#245).** A synced LFO with retrigger off counts its phase from an anchor (sample and song position) set when playback starts, jumps or changes tempo, in whole frames, so playback from bar 5 and an export from bar 1 place it the same and host block sizes agree bit for bit at a constant tempo; a tempo change re-anchors at the next host block start, the caveat #245 states for the Filter. The Filter's own LFO is unchanged here; `Lfo::set_phase` is the shared piece for #245. Known limit: the anchor places the phase, not the history, so Sample & hold and Smooth random (whose values depend on how many cycles came before) can play different values from bar 5 than an export from bar 1 plays there; the other four shapes match.
- **Migration.** The note-to-macro mapping of #196 is the matrix's first rows: `transit_model::legacy_mapping` rewrites an old session's Macro Oscillator (on load, so every open path applies it) and an old preset (on parse) as one row per depth that is not 0 or that something drives (velocity rows first, then key, each Harmonics, Timbre, Morph, Decay), in the first free rows; the depth becomes the amount, the source's curve the curve (the first three curves keep the mapping's indices). Automation lanes, MIDI mappings and rack macro targets move with them (a curve's lane and macro targets to every row of its source, its MIDI mapping to the first, its range rescaled from the old three curves to the five so the same travel picks the same curve). A track whose depths are all 0 with nothing driving them, which every v0.5 session with a Macro Oscillator stored, loses the old ids silently: no row, no load note, and the session opens unmodified. A track that gets a row or has something moved makes the session open as modified with one load note, which also says when a curve's MIDI mapping now drives only the first row of its source. The proof is two fixtures saved by the build before #243 (`crates/engine/tests/fixtures`): the note-mapping session, migrated, renders the golden hashes that build rendered, at 512 and 64 frames per block, and the plain session renders its golden with the new parameters absent or present at their defaults (`crates/engine/tests/macro_osc_matrix.rs`). The "Key Tracked Timbre" preset is rewritten as a Key to Timbre row and plays its old golden. The mapping's ten parameters and its panel grid are gone.
- **Parameters.** 123 in all (the module's 12, the shaper's 31 with both LFOs, five per row: `mod<n>_source`, `_via`, `_dest`, `_amount`, `_curve`), every one an automation target by its id. Parameter maps up to 128 entries are now tracked inline in a plug-in slot (`APPLIED_INLINE`), so the instrument's values reach it on the audio thread without prepared storage.
- **Cost.** 16 held voices per 128-frame block at 48 kHz (budget 2667 us), median of nine runs of 1600 blocks, Ryzen 9 5900X, `timing_shaper_and_full_matrix_at_128` (ignored, release): with the shaper and all sixteen rows active, Virtual analog 188 to 198 us (7.1% to 7.4% of one core), Six-op FM 1 160 to 164 us (6.0% to 6.2%), Wavetable 244 to 248 us (9.1% to 9.3%), Modal 644 to 659 us (24.1% to 24.7%); the shaper and matrix add about 25 to 36 us per block for the 16 voices (about 2 us per voice, 1% to 1.4% of the block), within run-to-run noise of about 30 us on the heaviest model. The Pi 5 figure waits for #237.

## Implementation note 2026-10-30: the resonator port (#198, slice 1)

- **Source: option (c), a port from the firmware.** No Rust port of this module exists to vendor (Oliver Rockstedt's repositories carry only the macro oscillator; crates.io and GitHub have none), so `transit-resonator` is transit's own port of `eurorack/rings/dsp` at `08460a69` and the stmlib helpers it uses, from her MIT C++ only (never from VCV's GPLv3 Audible Instruments). Its license chain is Émilie Gillet's MIT notices alone (`crates/resonator/LICENSE-THIRD-PARTY`, `VENDOR.md`). For the second module of this pair (slice 2), the one candidate for option (b) is `mutated-elements` (MIT, derived from the firmware, frozen upstream), pending a provenance and fidelity check.
- **Crate names.** The port is `transit-resonator`: it holds six models, not only the modal one, so the amendment's example name `transit-modal-resonator` would undersell it. The oracle stays one crate, `transit-macro-osc-oracle`, with a module per family (`resonator`, `resonator_sweep`, `cpp/resonator_oracle.cc`) sharing the build, the session lock, the residual and the floor; its name is brand-free, and a family-neutral rename is left for a quiet gap, since it would touch the in-flight instrument branches.
- **Gate.** All six models at polyphony 1 to 4 null bit-identical over the resonator sweep and the scenarios ([gates.md, Oracle null tests](../contributing/evidence/gates.md#oracle-null-tests)). The reference is the firmware's C++ as its desktop test harness builds it (flush-to-zero on, no fused multiply-adds), not the hardware's bits: the module runs with FZ off and its GCC build fuses multiply-adds. The oracle's flush-to-zero is reproduced by doing the port's arithmetic in an `f32` newtype that flushes every subnormal result, rather than at chosen spots; the sweep never reaches the subnormal range, the 20 s silences do.
- **Rate and pitch.** The firmware computes pitch against a true 48 kHz (`a3 = 440 / 48000`), so it needs no tuning switch: MIDI note 69 plays 440 Hz. The port runs at 48 kHz only, like the firmware; supporting other host rates (resampling, or a rate parameter with E63 pitch tests at every rate) is the instrument's decision in slice 3.
- **User-facing names (proposal).** The instrument over this port: "Resonator". Its models: Modal, Sympathetic Strings, Inharmonic String, FM Voice, Chord Strings (the quantized sympathetic strings), String and Reverb. The instrument over the second module of the pair: "Modal Voice". No module or brand name in a UI string or identifier.

## Implementation note 2026-10-30: the granular texture processor port (#199, slice 1)

- **Source: option (c), a port from the firmware.** No MIT Rust port derived from the firmware exists: crates.io has none, and the one GitHub file that names the module's playback modes (`tacogips/vactr`, MIT) declares every mode an "architectural adaptation" with no source port and no firmware table. `transit-granular` is transit's own port of `eurorack/clouds/dsp` at `08460a69` (its granular playback mode) and the stmlib helpers it uses, from her MIT C++ only, never from VCV's GPLv3 Audible Instruments; Émilie Gillet's MIT notices are its license chain (`crates/granular/LICENSE-THIRD-PARTY`, `VENDOR.md`). The oracle gained a module (`granular`, `granular_sweep`, `cpp/granular_oracle.cc`), as the resonator did.
- **Rate.** The firmware runs at 32 kHz, its codec's rate, and its grain sizes, feedback filter, diffuser and reverb are tuned for it; the low-fidelity qualities run the grains at 16 kHz behind the firmware's own 2:1 converters. The port runs at 32 kHz only, the one rate where the null tests mean anything, and a host at another rate resamples to and from 32 kHz at the edges, as the module's codec does. Running natively at the host rate would rescale every constant (a variant the oracle cannot check), so it is rejected; the converter, its latency report and pitch tests at every host rate belong to the device (slice 2).
- **Buffer.** The memory is a constructor parameter (`BufferSize`, the firmware's two blocks; `from_seconds` for a 16-bit stereo length), allocated once. Its range is the firmware's own, 0.768 s to 1.214 s in 16-bit stereo (the module: 1.02 s): a grain's read position is 16.16 fixed point in 32 bits, so no recording may exceed 131072 samples. Longer buffers need a wider phase, a deviation outside what the oracle can null.
- **Gate.** All four qualities null at 0 LSB over the granular sweep, a 60 s run per quality and the scenarios ([gates.md, Oracle null tests](../contributing/evidence/gates.md#oracle-null-tests)). The output is the firmware's int16, so no subnormal ever moves a sample: the tests pass with the port's flush-to-zero turned off as well. The flush is kept so the internal state matches the oracle's bits, but it is unverified by any oracle comparison; a float output path (slice 2) must bring a test that fails without it. The firmware reads one past an array in normal use (the grain window at its peak, the crossfade tables when the dry/wet ramp overshoots 1.0 by rounding, the freeze tail on every resume); the oracle's build pads those arrays so the C++ reads what the port's clamp reads, and it refuses memory sizes whose recording would overflow a grain's 16.16 phase (#199 review).
- **Upstream finding.** At `08460a69` the pitch-shifter / time-stretcher mode is silent: two commits each removed one of two duplicate `done_ = false;` lines in `clouds/dsp/window.h` and the merge `d1d8839` (2023-03-13) kept both removals, so no WSOLA window ever starts. The oracle restores the line on a build-time copy (`patches/all/`, VENDOR.md); `vendor/` stays upstream's bytes. Reported to the maintainer to post upstream. A second candidate: `Correlator::EvaluateNextCandidate` shifts a 32-bit word by 32 when a candidate is a multiple of 32 (undefined in C++; x86 scalar code keeps the word, SSE and the module's Cortex-M4 give 0); the oracle pins it to 0, the hardware's result, before slice 2 nulls against the stretch sweep.

## Implementation note 2026-10-31: the texture synthesizer port (#241, slice 1)

- **Source: option (c), a port from the firmware.** No Rust port derived from the firmware exists (crates.io's "beads" crates are issue trackers; GitHub code search finds only C++ copies of the upstream directory). `transit-texture` is transit's own port of `eurorack/beads/dsp` and `beads/gain_control.cc` at `f4cfa769` (the directory arrived in `d8f47391`, 2026-10-11; the README's footnote says the code builds on a desktop but is not verified on a module, which is our convention: the reference is the C++ as its desktop harness builds it) and the stmlib helpers at `e3bd7c9c`, from her MIT C++ only, never from VCV code. Émilie Gillet's MIT notices are its license chain (`crates/texture/LICENSE-THIRD-PARTY`, `VENDOR.md`). Included: the whole effect chain (four quality processors, grain and delay triggers, the multitap delay and its frozen slices, freeze, SEED, limiters, reverb, tape wow and flutter), the synth (wavetable oscillator and wavetable grains) and the input stage (automatic gain and soft clipping, part of what the chain hears on the module). Excluded: drivers, UI, CV reader and calibration, settings, buffer backup, factory test, and the main loop's glue.
- **Rate.** The brief assumed 48 kHz; the firmware runs its codec at the quality's rate (`ENABLE_HARDWARE_24K`): digital 48 kHz, vintage digital 32 kHz, clean tape 48 kHz with the grains at 24 kHz behind 2:1 converters, dirty tape 24 kHz; blocks are the rate / 4000 (12, 8, 6 frames). The port runs each quality firmware-exact at its own rate only (the synth at 48 kHz). The device (slice 2) needs no resampling for digital and clean tape in a 48 kHz session; every other case resamples at the edges with the latency reported, per quality.
- **Buffer.** A constructor parameter in seconds of 16-bit stereo at 48 kHz (`BufferSize`), allocated once: 4 s (the firmware's, also the shortest: the frozen delay cuts the buffer into slices of a clock interval that can reach 4 s) to 8 s. The top is the 22.10 fixed-point delay taps: the clean tape's mono controller sees 16/3 of the frames, and with the 68-sample minimum and the 1024-sample pitch window it must stay below 2^21 samples (393011 frames, 8.19 s). Sizes outside are refused (`BufferSize::new`, tested). The oracle nulls both ends: a second build of the chain at 8 s.
- **Gate.** Every quality, the synth and the input stage null bit for bit over their sweeps, a 60 s run per quality and the scenarios ([gates.md, Oracle null tests](../contributing/evidence/gates.md#oracle-null-tests)). The output is float, so the flush to zero is discriminated: unflushed, the oracle's tails differ (subnormals), and the port matches the flushed reference. The null is against the desktop reference as patched, not measured on hardware: argument order is pinned to GCC's rule for targets without push rounding (ARM among them), `partial_sort` ties to libstdc++, and flush-to-zero to on (the firmware's `SystemInit` sets FPSCR.FZ, but `Process` runs in an interrupt handler whose mode comes from FPDSCR, which the firmware never writes, so the module's own state is not established). These are our reading of the module's toolchain.
- **Pinned and defined on a build-time copy (`patches/all/0003` to `0006`), followed by the port.** Argument evaluation order for the grains' random draws (source order, the module's ARM GCC); `std::partial_sort`'s ties (libstdc++'s heap selection, the module's library); a frozen slice longer than the buffer (a negative density CV with SEED latched stretches the clock to about 13 buffers: an out-of-bounds read and a fixed-point overflow) and shorter than a sample (a division by zero at audio-rate SEED clocks; the module returns 0); the last wave of the last bank (one wave of zeros appended). Upstream candidates are on the maintainer's list (eurorack section).
- **Input stage.** Whether the device uses the input stage (automatic gain and soft clipping) is slice 2's decision.
- **User-facing name (proposal, final at slice 2).** "Texture" (the insert effect; the synth would be its instrument form, slice 3). No module or brand name in a UI string or identifier.

## Implementation note 2026-10-31: the Texture insert effect (#241, slice 2)

- **Device.** `texture` (`TextureFx` in `crates/dsp/src/plugins/texture.rs`, with `texture/path.rs` and `texture/resample.rs`), a built-in insert in the Delay group (not an offline process: it learns its input level and keeps a buffer). The name "Texture" is final. Émilie Gillet is credited under the panel, in the help entry `texture.credits`, in Help > About transit (the credit line and her notices from `crates/texture/LICENSE-THIRD-PARTY`), in `NOTICE` and in `ATTRIBUTION.md`.
- **Rate per quality.** Each quality runs firmware-exact at its codec rate (dirty tape 24 kHz, vintage digital 32 kHz, clean tape and digital 48 kHz). A 48 kHz session with digital or clean tape converts nothing: a test holds the device's output, 11 frames late, bit-equal to the crate's input stage and chain driven directly in 12-frame blocks.
- **Edge converters.** Streaming rational windowed-sinc converters from the family of the offline resampler (`offline::resample`: Kaiser window, beta 9, 32 zero crossings each side), the kernel tabulated at 512 steps per crossing with linear interpolation, cutting off at 0.91 of the lower Nyquist under a window whose length is the first design's (32 zero crossings of a 0.94 cutoff), so the latency table below is unchanged (see the fix-up bullet for the measured response). Timing is exact integer arithmetic on the rates' common tick, so the output does not depend on the host's block size (tested bit-equal for 64- and 512-frame blocks at 44.1 and 48 kHz, every quality, with parameter changes). The firmware's blocks are gathered across host blocks.
- **Latency.** The firmware block less one frame plus both converters' half lengths, padded to a whole number of session samples, reported per quality and rate (tests: the impulse delay of every path equals it; the dry path's at the device level too). In session samples: 44.1 kHz: dirty tape 137, clean tape 81, vintage digital 105, digital 81; 48 kHz: 149, 11, 115, 11; 88.2 kHz: 273, 148, 210, 148; 96 kHz: 297, 161, 229, 161. Dirty tape's wow and flutter (a modulated delay of 1 to about 172 codec samples after the chain) is the module's effect and is not compensated. A grain's pitch is the firmware's at 44.1, 48 and 96 kHz for every quality to 0.05 cent (E63's class: an absolute frequency, octave aliases refused); the firmware's 22.10 grain increment puts a +7 grain 0.30 cent under the tempered fifth at every rate.
- **Input stage on by default.** `Input Gain: Auto` runs the module's automatic gain (the firmware's processor expects its level); `Manual` maps `Input Level` (0 to 32 dB) onto the firmware's setting (1 to 255, a gain of `1 + 39·(s/255)⁴`). Session floats enter as the codec's 32-bit frames (full scale ±1, saturating). `Mono In` is the module's normalization: `Configure(media, mono)` and the right input copying the left.
- **Rebuild path (a deviation from the brief, for review).** The brief asked for the buffer rebuild outside the audio thread. A built-in receives parameter values only on the audio thread (no control-thread hook), and an asynchronous build would land the swap at a frame that depends on scheduling, so an offline render would not be deterministic. Instead the memory is allocated once, at construction, for the longest buffer (8 s: 3 MB), and `Texture::rebuild` rebuilds the chain in place to exactly what `Texture::new` builds (tested: same output and random state after a dirtied run, every quality, mono and stereo), deferring the lines' clears so the memory is filled once. It runs on the audio thread at the bottom of a 10 ms fade-out, then fades back in; measured informally at about 50 µs (release, this machine; a quality change's `Configure` about 100 µs). Quality and Mono In restart the same way (`Configure`, the codec rate's path, the input stage re-initialized keeping its learned gain). `reset` rebuilds too. A probe counts no allocation or free in the callback through every edit, a rebuild and a reset.
- **Controls.** Every knob with its attenuverter as a Random knob (the module's behavior with no CV patched), Density, Feedback, Dry/Wet, Reverb, Freeze, the SEED button (Seed held, Latch for the long press), the SEED input as `Trigger` with `Trig In` (patched), Quality, Length (4 to 8 s), Mono In, Mono Grains. Not exposed: the CV inputs (automation moves the knobs instead), the output gate setting (it turns the right output into a gate signal) and the Trim gesture.
- **Later.** The Pitch Shifter (#199 slice 2) is to share these edge converters. The instrument form (the synth, freeze and seed from MIDI) is slice 3.
- **Review fix-ups (2026-10-31).**
  - *Converter stopband.* The first design (cutoff 0.94 of the lower Nyquist) measured -0.29 dB at 0.89, only -26 dB at 0.985, and -90 dB from about 1.04 of the lower Nyquist: an input at 1.004 of it folded back at -43.6 dB (audible on Dirty Tape, whose Nyquist is 12 kHz). The cutoff is now 0.91 under the same Kaiser window (beta 9, the same half length, so every converter's length and the latency table stay as they were). Measured per down converter (96 to 48 kHz and 44.1 to 24 kHz, `resample.rs` tests): within 0.1 dB to 0.852 of the lower Nyquist, -3 dB at 0.896, -90.6 dB or lower at the Nyquist, and the worst alias of any input from 1.001 to 1.1 of it -91.1 dB. Content from 0.85 to 1.0 of a codec's Nyquist is rolled off (at Dirty Tape's 24 kHz, above about 10.2 kHz). Tests: tones at 1.004 and 1.02 of the lower Nyquist alias at or below -80 dB and 0.85 passes within 0.2 dB, on five down and three up pairs; the E63 pitch, latency, block-split and firmware-exact tests pass unchanged.
  - *Subnormals.* A resampled output, and the output during a restart's fade, is flushed to zero under 1e-25 (`util::flush`, a threshold compare). A steady equal-rate output is not touched, so the firmware-exact path stays a copy bit for bit. Before: 60 s of silence after a loud run put out 222 to 565 subnormal samples through the converters; now none (test).
  - *Restart cancel.* A setting that returns to the running value before the bottom of the fade cancels the restart: the fade turns round from its level and the recording stays (test: after the fade the output is the untouched device's, bit for bit).
  - *Span-only fill.* A rebuild or a `Configure` fills only the memory span the active buffer length uses (`DelayMemory::set_span`), so the default 4 s fills half of the 8 s memory. `Texture::new` allocates exactly its span, so the crate's output and the oracle nulls are unchanged; rebuild-equals-new is tested at 4, 6 and 8 s.
  - *Audio-thread rebuild cost (review measurements, release, before the span-only fill).* `Texture::rebuild` at 8 s: warm median 63 µs, max 84 µs; cold (cache thrashed) up to 683 µs. `Configure` over the 12 quality pairs: warm medians 90 to 106 µs; cold outliers up to 1.66 ms. A whole 64-frame block holding a restart: medians 60 to 120 µs on a quiet machine (a steady block costs 11 to 20 µs), 340 to 490 µs under memory contention. A Pi 5 (taken as 4x slower) would take 240 to 480 µs quiet, inside a 64-frame period at 48 kHz (1333 µs), and 1.4 to 2 ms loaded, which could overrun it. It stays on the audio thread for determinism: parameters reach a built-in only there, and a swap prepared off the thread would land at a frame that depends on scheduling, so an offline render would differ from run to run. The span-only fill halves the memory work at the default 4 s; automating Quality, Length or Mono In restarts the chain every change (a 20 ms dip each time; said in the help).
  - *Known limits, filed.* After a quality change mid-bounce the whole bounce sits behind the timeline by the latency delta (104 samples Digital to Vintage Digital, 138 to Dirty Tape at 48 kHz), because the offline render skips the latency once, at its first block (compressor lookahead automation behaves the same): #251. The recording is not session state, so a session saved with Freeze on reopens silent until something is recorded (#252; said in the Freeze help). Auto input gain learned over silence lets a following loud burst out at about +12 dBFS until the peak protection catches it, as on the module (said in the Input Gain help).
  - *Presets and Seed.* Frozen Pad no longer sets Freeze (a fresh instance froze an empty buffer and stayed silent); a test renders every preset non-silent on a fresh instance. The Seed button senses drags, so its hold lasts until the pointer button comes up even when the pointer leaves the button (test).

## Decision note 2026-10-30: the Macro Oscillator is the default instrument, the Subtractive Synth is removed (#234)

With polyphony in (#196), a new instrument track carries the Macro Oscillator (default model, 8 voices) and the built-in Subtractive Synth is removed outright: its code, plug-in id (`subtractive_synth`), editor panel, factory presets, help and README line. transit is alpha software, so there is no compatibility shim for the synth itself; the one rule below keeps old sessions opening. Drum Synth and Sampler are unchanged.

Convention: Logic opens a new software-instrument track with its default patch loaded and Ableton leaves a MIDI track empty; we keep Logic's "ready to play" default, which is what the Subtractive Synth gave until now. Every path that creates an instrument track (`track.new`, the Add Instrument Track menu and shortcut, MIDI file import, the demo) uses `transit_model::DEFAULT_INSTRUMENT`.

**Substitution rule on load.** An instrument slot that names `subtractive_synth` becomes a Macro Oscillator with defaults when the session loads (`transit_model::legacy_synth::retire_subtractive_synth`, called by `Session::from_json`, so every open path, recovery and session import apply it):

- the old synth's parameters and preset name are dropped, since they mean nothing to the new instrument; the slot's bypass and active flags carry over; the new instrument gets `level` = -19.5 dB instead of its -6 dB default, because the Macro Oscillator at its defaults plays about 13.5 dB louder than the old synth did (derivation below);
- the session's MIDI mappings, the track's automation lanes and the rack macro targets that addressed the old instrument's parameters (`plugin:instrument:<id>`) are dropped; mappings and lanes on inserts, and everything that addresses the slot as a slot (rack membership, zones, routing, volume, pan), keep working;
- the load report gets one line per track that lost something, then the status line "N track(s) used the retired Subtractive Synth and now carry the Macro Oscillator";
- the session opens as modified (the engine keeps the file's own content as the saved state), so the user sees the substitution on save; a saved session no longer names the old id and opens clean.

The corpus keeps the sessions released builds wrote with the old synth (`crates/model/tests/corpus`); `a_release_session_with_the_old_synth_opens_with_a_macro_oscillator_and_one_report` loads them, and the lossless round-trip tests read them with the id swapped. MIDI-mapping profiles are app-level, not session data, and are not rewritten: a profile mapping to an old instrument parameter finds no such parameter and does nothing.

**Level derivation.** The instrument plan-parity golden (`crates/mix/tests/golden/plan_parity/instrument.f32`) holds the same session rendered with the old synth and with the Macro Oscillator at its defaults: peak 0.0569 and 0.2680, a difference of 20 log10(0.0569 / 0.2680) = -13.46 dB (the held-notes golden: 0.271 and 1.346, -13.9 dB). The default level of -6 dB minus 13.5 dB gives -19.5 dB (`SUBSTITUTE_LEVEL_DB`), which lands a substituted track within about 2 dB of its old peak loudness on that golden. RMS differs more (-18 dB on that golden) because the timbres differ, so loudness is matched by peak, and a patch change will still sound different.

**Status line coverage.** Every open path applies the substitution, but only a normal open and open from bytes show the status line. Crash recovery drops the temporary engine's messages and session-data import shows only the video note; both predate this change.

The event queue and ADSR that lived in the synth's file stay, as `crates/dsp/src/plugins/instrument_queue.rs`: the Drum Synth and the Sampler use the queue and the Sampler the ADSR; the Macro Oscillator uses only the queue's two capacity constants (`MAX_EVENTS`, `RELEASE_RESERVE`), not the queue.
