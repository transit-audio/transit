# ADR 0046: Retire cpal from Windows builds (stage one of retiring cpal)

- **Status:** accepted 2026-11-06 (the maintainer's decision, #354); settled after two judging rounds
- **Date:** 2026-11-06
- **Amends:** [ADR 0016](0016-native-wasapi-backend.md): section 1.3 (selection and the cpal fallback); section 4, Threading ("On panic ... the Player falls back to cpal with a visible message"); the slice (c) gate ("fallback to cpal on every injected open failure"); slice (f) ("cpal fallback stays", and its switch back `AudioConfig.backend = Cpal`); step 4 of the exclusive-mode ladder (amendment of 2026-10-22); the "default features" amendment of 2026-10-24 ("`--no-default-features` still builds without them" no longer holds on Windows). The draft native ASIO amendment as recorded in [`docs/contributing/knowledge/asio-backend.md`](../contributing/knowledge/asio-backend.md): `:284-286` (without the feature "a saved `NativeAsio` opens cpal"), `:316-318` (the fallback to cpal, "using WASAPI shared") and `:332-333` (an input on demand opens through cpal if the native one fails).
- **Reopen when:** a Windows audio path transit needs cannot be served by native WASAPI or native ASIO (a device class only cpal opens, seen on a user's machine); the name-equality test of decision 2 fails on the maintainer's interfaces or a user's; or stage two or three finds a shared reason to keep cpal on every platform.

## Context

The maintainer decided on 2026-11-06 to remove cpal from Windows builds completely. Native WASAPI ([ADR 0016](0016-native-wasapi-backend.md)) and native ASIO (its draft amendment) are the shipped Windows backends; cpal remains on Windows only as the fallback when a native open fails, as the default `Auto` backend, and as the lister of the WASAPI system. This ADR is stage one of retiring cpal in stages: Windows now, Linux ALSA (with FreeBSD) next, macOS last. Verified against `main` at `52ab4c52` (paths from the repository root):

- **Pin and fork.** `Cargo.toml:63` pins `cpal = "=0.16.0"`; `Cargo.toml:112-114` patches it to the maintainer's fork at `31b5dd4`. The fork carries five commits over 0.16.0: three WASAPI worker-priority commits (`96c0d87`, `6bf6ff5`, `59ffcf7`, all under `src/host/wasapi/`), one build commit that pins `asio-sys` to `=0.2.6` (`873c252`, inert: cpal's `asio` feature is off and `asio-sys` is not in `Cargo.lock`), and one platform-neutral commit that normalizes negative fractional `StreamInstant` values (`31b5dd4`, `src/lib.rs` only). The timestamp fix serves ALSA and CoreAudio too, which is a reason to keep the fork for Linux and macOS.
- **Who pulls cpal on Windows.** `cargo tree --target x86_64-pc-windows-msvc --workspace --all-features -e normal,build,dev -i cpal` shows exactly two edges: `transit-playback` (normal) and `transit-audio-wasapi` (dev); `transit`, `transit-ui-studio` and `audio-bench` reach it only through `transit-playback`. `crates/playback/Cargo.toml:24` depends on cpal on every target and again at `:28-30` under `cfg(target_os = "windows")` with the `audio_thread_priority` feature; `-i audio_thread_priority` shows a single path, through cpal, and no `.rs` file names it. `crates/audio-wasapi/Cargo.toml:30` takes cpal as a Windows dev-dependency for `src/convert.rs`'s tests, whose module doc claims byte identity with the cpal adapter's conversion. `crates/rt/Cargo.toml:20` and `tools/audio-bench/Cargo.toml:19` only mention cpal in comments.
- **Thread priority without cpal.** Native WASAPI promotes its render and capture threads through `promote` (`crates/audio-wasapi/src/com.rs:1127-1128`, calling `transit_rt::promote_audio_thread()`, MMCSS "Pro Audio", `crates/rt/src/windows.rs`); native ASIO registers the buffer-switch thread itself (`crates/audio-asio/src/mmcss.rs`, `com.rs:654-675`). cpal's `audio_thread_priority` feature serves only cpal's own WASAPI streams.
- **Selection today.** `crates/playback/src/devices.rs:27-46`: `Backend { Auto, Cpal, NativeWasapi, NativeAsio, NativeJack }`, default `Auto`, and `Auto` is cpal on Windows (`native_on` is false for `Auto` and `Cpal`, `devices.rs:72-79`; `factory_for` returns `None`, `crates/playback/src/backend/native.rs:41-61`). ADR 0016's slice (f), native as the Windows default, never landed. `Player::open` (`crates/playback/src/player/device/open.rs:231-236`) tries the native factory with `CpalFactory` as the fallback; `open_native` (`open.rs:277-331`) opens cpal on any error the exclusive ladder does not answer (`open.rs:322-325`), except when an ASIO host thread is blocked (`open.rs:316-319`). A failed native ASIO open falls to cpal's default host, WASAPI shared, a different audio system (`native.rs:27-35`). Inputs: a native output's on-demand input falls back to a cpal input (`crates/playback/src/player/device.rs:966-971`), a non-native output's input opens through cpal (`device.rs:973`), and `Recorder::open` and `Recorder::open_with` are public cpal opens (`crates/playback/src/record.rs:320-336`).

- **Enumeration today (the largest piece).** On Windows the **WASAPI system is listed through cpal**: `devices::audio_systems()` (`devices.rs:511-516`) is `cpal_audio_systems()` plus the native ASIO and JACK systems; `cpal_audio_systems()` (`devices.rs:554-582`) walks `cpal::available_hosts()` with `HostTrait` and `DeviceTrait`, marks the default host's system `is_default` (`devices.rs:567`) and drops cpal's ASIO host when native ASIO is compiled. The **ASIO system is already listed natively** (`native_asio_system`, `devices.rs:542-551`, through `backend::native::asio_system`, `native.rs:130-161`: the registry driver names, only the selected driver probed). ## Decision

1. **Scope: no cpal on Windows targets.** On `cfg(windows)` cpal is not compiled: there is no `Backend::Cpal` choice, no fallback open and no cpal enumeration; native WASAPI and native ASIO are the only paths.
   - **The system decides the backend.** On Windows the ASIO system opens native ASIO and the WASAPI system (and the untouched default, `system: None`) opens native WASAPI, whatever backend value was saved. The crossed configuration (a saved `NativeAsio` with the WASAPI system, `diagnostics.rs:365-368`) opens native WASAPI.
   - **One resolver.** `Backend::effective(self, system: Option<&str>) -> Backend` returns, on Windows, `NativeAsio` for the ASIO system and `NativeWasapi` for any other, for every saved value (`Auto`, `Cpal`, either native variant); off Windows it returns `self` (ADR 0021's JACK rule stays in `factory_for`). Every site that tests a native variant reads it instead of the saved value: `factory_for` (`native.rs:46-56`); the exclusive-mode checkbox (`window.rs:364`), which moves out of the Backend-row block so it shows when the Backend row is hidden; "Paired input" (`window.rs:440-441`, `:468`); the ASIO "Calibration" line (`window.rs:442-443`, `:514`); `running_native_asio` (`audio_devices.rs:796`); and the system-change reset (`window.rs:349-351`), which on Windows has nothing to reset because the effective backend follows the new system. The saved value itself is not rewritten to a native variant (decision 2 has the one migration, `Cpal` to `Auto`), so a config written on Windows still reads correctly on another platform.
   - **The Backend row is hidden on Windows.** `Backend::offered` on Windows returns only the system's native variant, and the row is drawn only when more than one choice exists.
   - **A native open failure is a visible error, never a silent backend fallback.** When the ladder of ADR 0016 (its amendments of 2026-10-22) cannot answer an error, the Player opens nothing: the existing silent-runtime path with the backend's own reason (`Player::with_config`, `open.rs:10-18`). The status line and Audio Devices keep today's text, "The audio device did not open: <reason>." (`audio_devices.rs:589-593`, asserted on the status line at `audio_devices_tests.rs:1389`); the log keeps "<Native WASAPI|Native ASIO> did not open: <reason>". The device stays closed until the user changes a choice and applies, or presses Reconnect. The ladder's step 4 becomes this error.
   - **Every input path is native or an error on Windows.** The duplex input that fails with the output stays `HeldInput::Failed` (`crates/playback/src/lib.rs:180-182`), as today. The on-demand input (`device.rs:966-971`) returns the native backend's error to the caller instead of opening cpal. The `None =>` branch (`device.rs:973`, a silent runtime's input) opens through the native factory of the effective backend. `Recorder::open` and `Recorder::open_with` (`record.rs:320-336`) open through the native factory of the effective backend on Windows (`open_through` with that factory) and through `CpalFactory` elsewhere.
   - **A missing saved device is not a backend fallback.** A saved output or input name that matches no endpoint opens the system's default endpoint, as it did before this ADR (`devices.rs:1-4`), and says so: the existing note "Output “X” is not available; using “Y”." (and the input equivalent) is shown at startup and on apply, on the status line and in Audio Devices. Slice 3 adds the startup case where it is missing and tests both.
   - **32-bit Windows.** Native ASIO compiles only on 64-bit Windows; where it is not compiled the ASIO system is not listed, so the ASIO choice does not exist there. Only `windows-x86_64` is shipped (`release.yml:40`).
   - **Off Windows nothing changes** in this stage: Linux keeps cpal ALSA and ADR 0021's `Auto` rule, macOS keeps cpal CoreAudio, and both keep the native-or-cpal fallback.
2. **Enumeration: the native crates list their systems.** On Windows `devices::audio_systems()` is the native WASAPI system plus the native ASIO system (where compiled).
   - **WASAPI** is listed through `WasapiBackend::endpoints` (`audio-wasapi/src/lib.rs:141-144`) and `system_from_endpoints`, in a new `backend::native::wasapi_system()`. The WASAPI system is the default system on Windows: `system_from_endpoints` gains an `is_default` argument (true for WASAPI on Windows, false for ASIO and JACK, which keeps their behavior), so `pick_system(&audio_systems(), None)` (`audio_devices.rs:385-387`) finds it. A `list_endpoints` error becomes the system's diagnostic ("WASAPI: <error>"), not an empty list.
   - **ASIO** stays as it is (`native_asio_system`, the registry names, only the selected driver probed).
   - `cpal_audio_systems()` and the cpal helpers are compiled only off Windows. The settings window (`audio_devices.rs:708`) and the report (`diagnostics.rs:148`) call `devices::audio_systems()`, or a fast variant without the ASIO probe, instead of `cpal_audio_systems()`.
   - **Saved names stay valid; no rename migration.** The saved key is the device name, and the native list names endpoints by the same property key, from the same enumerator, filter and default role as cpal. This is proved, not assumed: **`cpal_and_native_wasapi_list_the_same_names`**, an ordinary (not ignored) Windows test in `transit-playback` added in slice 2 while cpal is still present, enumerates both per direction and asserts equal name sets and the same default name. It skips, printing its reason on stderr, when the enumerator fails or neither listing has an endpoint (a CI runner without audio). The maintainer runs it on both reference interfaces and files the output in `docs/contributing/evidence/`. A pass there is a precondition of slice 3, the first landing where saved names resolve through the native lookup for every user.
   - **The duplicate-name rule that ships:** the native rule, first match by name or id in default-first order (`audio-wasapi/src/lib.rs:147-156`). It can differ from cpal's enumeration-order rule only when two active endpoints share a friendly name; the slice 2 test lists any duplicate names it sees, and the native lookup logs a warning when a saved name matches more than one endpoint.
   - **One migration: the backend field.** The `Cpal` variant stays in the `Backend` enum on every platform so an existing `ui.json` with `"backend": "cpal"` still parses (an unknown variant would fail the whole `AudioConfig`). On Windows a loaded `Cpal` is rewritten to `Auto` and saved as `auto` on the next save; it is never offered.
3. **Vocabulary: no new shared types; the leftovers move into the adapter.** The shared vocabulary (`SampleFormat`, `Format`, `Endpoint`, `OpenRequest`, `Period`, `Mode`, `Stamp`) is already in `transit-audio-backend` (layer 0, standalone). The cpal-typed helpers still in `devices.rs` (`FORMATS`, `format_rank`, `describe`, `shared_host`, `host_named`, `cpal_system_for`, `find_device`, `buffer_size_on`, `buffer_size` and their tests) move into `crates/playback/src/backend/cpal.rs` (or a `backend/cpal/` folder if the file-size budget asks for it). `add_unlisted` stays in `devices.rs`: the native builder uses it (`native.rs:109`). `devices.rs` then holds only platform-neutral types (`Backend`, `AudioConfig`, `AudioSystem`, `DeviceInfo`, calibrations). `transit-audio-wasapi`'s conversion tests keep their byte-identity claim against a stored table: the golden values are captured once from cpal's conversion (`I16`, `I24`, `I32` from `f32` and back over the existing sample sets, plus the wire formats of `capture_conversion_matches_the_cpal_adapters_for_every_wire_format`) into `crates/audio-wasapi/src/convert_golden.rs`, whose header names the cpal version and fork commit; the tests compare against it and the cpal dev-dependency goes.
4. **Dependency gate.** A new xtask gate, `cargo xtask windows-deps`, runs `cargo tree --locked --target x86_64-pc-windows-msvc --workspace --all-features -e normal,build,dev --prefix none --format "{p}"`, the one shipped Windows target.
   - It **fails** when `cargo tree` exits nonzero or prints nothing; when any package line names `cpal` or `audio_thread_priority`, in the plain form or the deduplicated `... (*)` form; or when the **positive control** in the same output is missing: `transit-audio-wasapi` and `transit-audio-asio` must both appear, which proves the query saw the Windows graph and not a host-filtered one. Lines that are section headers (`[dev-dependencies]`, `[build-dependencies]`) are skipped.
   - The parsing is a pure function with unit tests in `xtask/src/tests.rs`: fixtures with a plain `cpal v0.16.0 (...)` line, a `cpal v0.16.0 (...) (*)` line, an `audio_thread_priority` line, header lines, empty output, and output without the native crates. Each forbidden or incomplete fixture must fail. **Live negative control,** once at landing: a scratch manifest line restoring `cpal.workspace = true` under `crates/audio-wasapi`'s Windows dev-dependencies makes the live gate fail; the run is recorded in the landing note.
   - **Where it runs:** a `- run: cargo xtask windows-deps` step in both the `linux` and `windows` jobs of `.github/workflows/ci.yml` (it needs no Windows host: `cargo tree` resolves any target), and `windows-deps` joins the gate list at `xtask/src/main.rs:321` and the dispatcher. The local Linux gate script lives outside the repository; its update is named in the landing note.
   - The `[patch.crates-io]` entry and the `=0.16.0` pin stay for Linux, macOS and FreeBSD; the patch comment becomes: "Linux, FreeBSD (ALSA) and macOS (CoreAudio) only since ADR 0046: the signed timestamp fix is platform-neutral; the WASAPI commits are unused and go with the fork in stage three."
5. **Staging.**
   - **Stage one (this ADR): Windows.** cpal leaves every Windows build.
   - **Stage two: Linux ALSA and FreeBSD**, its own ADR: decide whether ALSA direct is dropped in favor of JACK and PipeWire-JACK (ADR 0021) or kept through cpal until a native ALSA path exists, and whether FreeBSD (cpal's ALSA host over `alsa-plugins-oss`, packaged but not gated) keeps an audio path or its packaging is retired. Known issue KC6 is input to it.
   - **Stage three: macOS**, after a native CoreAudio backend, its own ADR. It needs access to a Mac, and CI cannot prove sound there, so it waits for hardware. When it lands and stage two has removed every other cpal user, the cpal dependency, the fork and the pin go from the workspace.
   - **Why macOS keeps cpal now:** the maintainer's download figures are about half Linux, a third Windows and a sixth macOS. A sixth of users is too many to leave without audio, and cpal's CoreAudio path is their only one.
6. **Consequences carried in the landings.**
   - **Features.** `native-wasapi` and `native-asio` stop being features: on Windows `transit-playback` depends on `transit-audio-wasapi` (all Windows targets) and `transit-audio-asio` (64-bit Windows) unconditionally, and the features are removed from `crates/playback/Cargo.toml`, `apps/transit/Cargo.toml` and `tools/audio-bench/Cargo.toml`. Without them a Windows build would have no audio path at all, so the switch only builds a broken app. `NATIVE_WASAPI_COMPILED` and `NATIVE_ASIO_COMPILED` become `cfg!(windows)` and `cfg!(all(windows, target_pointer_width = "64"))`; the hardware tests' `cfg(all(windows, feature = "native-wasapi"))` and `native-asio` gates (`crates/playback/src/player/device/tests.rs:532-609`) become `cfg(windows)` and the 64-bit form. `native-jack` stays a Linux feature (its build needs `jack.pc`). The CI lines (`ci.yml:58`, `:62`), the release line (`release.yml:40`) and the documented commands drop the two feature names in the same landing.
   - **audio-bench** on Windows loses `--backend cpal`; its default `--backend` becomes `wasapi` on Windows (`cpal` elsewhere), `--list-devices --system WASAPI` lists through the native backend, and `--system` is documented as the cpal system off Windows. `cli.rs`'s help text, the BENCH-README text (`release.yml:131`) and `release.yml:295` ("native WASAPI and native ASIO") follow. The committed cpal-shared baselines (ADR 0016 slice b, `docs/benchmarks/`) stay as history; a new cpal WASAPI comparison runs from a v0.6.x release's `audio-bench.exe`.
   - **Known issues:** K16's last sentence and K100's "(cpal)" say "on Linux and macOS"; K24 and K29 keep their measurements as history and drop "cpal WASAPI" as a current path ("measured through cpal's WASAPI backend before ADR 0046"); K29's workaround reads "choose Audio system ASIO" (no feature, no Backend choice).
   - **User docs:** the user guide's "Audio setup" gains a Windows paragraph (the backend follows the audio system; no Backend choice; a device that does not open stays closed with the reason until a choice changes or Reconnect is pressed; a missing saved device opens the default with a note). `docs/help/audio-devices.toml` says the same where it describes the open device. `docs/troubleshooting.md:38` names the backends per platform. `README.md:240-241` lose "pick it under Audio Devices > Backend", "then Backend > Native ASIO" and "with a cpal fallback"; `:265` says cpal is the Linux, FreeBSD and macOS adapter; the bench recipe at `:109-114` uses `--backend wasapi`.
   - **Contributor docs:** `docs/building.md:117-135` (no features, no Backend step, no `--no-default-features` opt-out of ASIO); `docs/contributing/evidence/hardware-and-ci.md:9`, `:25-26`, `:35` and `docs/contributing/evidence/gates.md:7`, `:9` (commands without the feature names; the new gate listed); `docs/contributing/knowledge/clocks.md:45-49` (the Windows rule); `docs/contributing/knowledge/asio-backend.md:284-286`, `:316-318`, `:332-333` (no cpal fallback); ADR 0016 gets a note that its cpal-fallback text and its "CPAL-shared" reopen conditions are superseded here. `crates/rt/Cargo.toml:20`'s comment stops naming cpal (windows-sys stays in the tree through winit and others).
   - **Release notes, Breaking:** "Windows: cpal is gone. Audio opens through native WASAPI or native ASIO, chosen by the audio system; a device that does not open says why and stays closed instead of falling back. A saved `cpal` backend reads as Auto. The `native-wasapi` and `native-asio` build features are removed."
   - **Thread priority:** nothing replaces cpal's `audio_thread_priority` on Windows, because nothing on the native paths used it.
   - **Gate classes:** none removed. The new gate is a dependency-graph class; if an escape later shows cpal or a fallback returning on Windows, its escape record names this gate.
7. **Gate: tests that prove the behavior, each with a negative control.**
   - **No cpal in the Windows graph:** `cargo xtask windows-deps` (decision 4). Controls: the fixtures, the positive control in every live run, and the one-time manifest line.
   - **No cpal choice on Windows:** a `transit-playback` unit test that `Backend::offered(Some("WASAPI"))` and `offered(Some("ASIO"))` on Windows contain only the system's native variant, and a `transit-ui-studio` layout test that the Audio Devices window on Windows shows no Backend row and no "cpal (legacy)" text (`audio_devices_tests.rs:313` is rewritten). Control: restoring `Cpal` to `offered` fails both.

## Implementation

Not started. Slices as in decision 8, each through the usual implementer, review and chain gates; slice 3 waits for the slice 2 name-equality evidence.

Slice 1 landed: the cpal helpers moved into `backend/cpal.rs`, the fitter tests run on a neutral stamp harness proven bit-identical to the cpal `Stamper`, and `transit-audio-wasapi` tests its conversion against `convert_golden.rs` without cpal.

## Gate

Decision 7 is the gate. In short: `cargo xtask windows-deps` passes with its positive control and its negative controls fail; Windows offers no cpal choice; the effective backend shows the native controls for `Auto` and former `cpal` users; WASAPI is the default system; a forced native open failure is a visible error with the device closed and no other open attempted; saved device names resolve to the same endpoint, proven against cpal on real endpoints before slice 3; the WASAPI conversion goldens pass without cpal; the fitter tests run on Windows on a harness proven bit-identical to the cpal one.

## Consequences

- Windows has one path per audio system, with its own clock, counters and error text; a native failure can no longer hide behind a working cpal stream.
- A Windows device that only cpal could open no longer opens. None is known: cpal's Windows host was WASAPI alone (its ASIO host was retired in ADR 0016's amendment of 2026-10-25), and the slice 2 test checks that the native backend lists the same WASAPI endpoints.
- Users who saved `cpal` or `Auto` move to native WASAPI on the next start; a user whose device misbehaves on native WASAPI now sees the error instead of sound through cpal. Shared mode stays the default (ADR 0016, amendment 2), so the common case opens the same mix-format stream cpal did.
- `transit-playback` keeps one cpal adapter for Linux, FreeBSD and macOS, so cpal-only code and tests carry `cfg(not(windows))` until stage three.
- Windows build time and binary size shrink by cpal and `audio_thread_priority`; the fork stays in `Cargo.lock` for the other targets.
- The `native-wasapi` and `native-asio` feature names disappear; scripts that pass them fail with "feature not found" and are updated in the same landing.

## Alternatives considered

- **Keep cpal as a hidden fallback.** Rejected: a silent fallback hid native failures (a failed native ASIO open played through WASAPI shared, another system, `native.rs:27-35`), and the fork's WASAPI patches are exactly what the native backend replaced.
- **Remove cpal everywhere now.** Rejected: macOS would lose audio; cpal CoreAudio is its only path, and Mac users are about a sixth of downloads.
- **Replace cpal's enumeration with a third crate.** Rejected: the native crates already own the device model (`WasapiBackend::endpoints` over `IMMDeviceEnumerator`, the ASIO registry list), and the open path already resolves their names and ids.
- **Keep `native-wasapi` and `native-asio` as features.** Rejected: once cpal is gone, a Windows build without them has no audio, so the switch could only produce a broken app; keeping them with a `compile_error!` when both are off adds a switch with one legal position.
- **Rewrite the saved backend value to the system's native variant on disk.** Rejected in favor of `Backend::effective`: a computed resolver keeps one rule for every site, and a config file moved to another platform keeps `auto`.
- **Map saved device names to endpoint ids in a migration.** Rejected as unneeded: the names come from the same property in both listings (tested in slice 2); the open path already accepts either a name or an id.
