# ADR 0046: Retire cpal from Windows builds (stage one of retiring cpal)

- **Status:** proposed 2026-11-06 (maintainer decision, #354); judging rounds pending
- **Date:** 2026-11-06
- **Amends:** [ADR 0016](0016-native-wasapi-backend.md) section 1.3 (selection and the cpal fallback), slice (f) ("cpal fallback stays"), step 4 of the exclusive-mode ladder (amendment of 2026-10-22), the "default features" amendment of 2026-10-24, and the draft native ASIO amendment's fallback to cpal WASAPI.
- **Reopen when:** a Windows audio path transit needs cannot be served by native WASAPI or native ASIO (a device class that only cpal opens, seen on a user's machine); the native WASAPI enumeration lists a different set of endpoints than cpal did on the maintainer's interfaces (the slice 2 evidence fails); or stage two or three finds a shared reason to keep cpal on every platform.

## Context

The maintainer decided on 2026-11-06 to remove cpal from Windows builds completely. Native WASAPI ([ADR 0016](0016-native-wasapi-backend.md)) and native ASIO (its draft amendment, [`docs/contributing/knowledge/asio-backend.md`](../contributing/knowledge/asio-backend.md)) are the shipped Windows backends; cpal remains on Windows only as the fallback when a native open fails, as the default `Auto` backend, and as the lister of the WASAPI system. This ADR is stage one of retiring cpal in stages: Windows now, Linux ALSA next, macOS last. Verified against `main` at `52ab4c52` (paths from the repository root):

- **Pin and fork.** `Cargo.toml:63` pins `cpal = "=0.16.0"`; `Cargo.toml:112-114` patches it to the maintainer's fork at `31b5dd4`. The fork carries five commits over 0.16.0: three WASAPI worker-priority commits (MMCSS registration retained and released per worker lifetime, its observation API, a test of the shared prologue), one build commit that pins `asio-sys` to `=0.2.6` (inert: cpal's `asio` feature is off and `asio-sys` is not in `Cargo.lock`), and one platform-neutral commit that normalizes negative fractional `StreamInstant` values (`src/lib.rs`). So not every patch is WASAPI-specific: the timestamp fix serves ALSA and CoreAudio too, which is a reason to keep the fork for Linux and macOS.
- **Who pulls cpal on Windows.** `cargo tree --target x86_64-pc-windows-msvc --workspace --all-features -i cpal` shows exactly two edges: `transit-playback` (normal) and `transit-audio-wasapi` (dev). Everything else (`transit`, `transit-ui-studio`, `audio-bench`) reaches it only through `transit-playback`. `crates/playback/Cargo.toml:24` depends on cpal on every target and again at `:28-30` under `cfg(target_os = "windows")` with the `audio_thread_priority` feature; `audio_thread_priority` 0.33 is in the Windows graph only through cpal (no `.rs` file names it). `crates/audio-wasapi/Cargo.toml:30` takes cpal as a Windows dev-dependency for `src/convert.rs`'s tests, whose module doc claims byte identity with the cpal adapter's conversion. `crates/rt/Cargo.toml:20` and `tools/audio-bench/Cargo.toml:19` only mention cpal in comments.
- **Thread priority without cpal.** The native backends promote their own threads: native WASAPI calls `transit_rt::promote_audio_thread()` (MMCSS "Pro Audio", `crates/audio-wasapi/src/com.rs:1126`, `crates/rt/src/windows.rs`); native ASIO registers the buffer-switch thread itself (`crates/audio-asio/src/mmcss.rs`, `com.rs:654-675`). cpal's `audio_thread_priority` feature serves only cpal's own WASAPI streams.
- **Selection today.** `crates/playback/src/devices.rs:27-46`: `Backend { Auto, Cpal, NativeWasapi, NativeAsio, NativeJack }`, default `Auto`, and `Auto` is cpal on Windows (`native_on` is false for `Auto`, `devices.rs:72-79`; `factory_for` returns `None`, `crates/playback/src/backend/native.rs:41-61`). ADR 0016's slice (f), native as the Windows default, never landed. `Player::open` (`crates/playback/src/player/device/open.rs:231-236`) tries the native factory with `CpalFactory` as the fallback; `open_native` (`open.rs:277-331`) falls back to cpal on any error the exclusive ladder does not answer (`open.rs:322`), except when an ASIO host thread is blocked (`open.rs:316-319`). A failed native ASIO open falls to cpal's default host, WASAPI shared, a different audio system (`native.rs:27-35`). A native output's input falls back to a cpal input (`crates/playback/src/player/device.rs:965-971`).
- **Enumeration today (the largest piece).** On Windows the **WASAPI system is listed through cpal**: `devices::audio_systems()` (`devices.rs:511-516`) is `cpal_audio_systems()` plus the native ASIO and JACK systems; `cpal_audio_systems()` (`devices.rs:554-582`) walks `cpal::available_hosts()` with `HostTrait` and `DeviceTrait` and drops cpal's ASIO host when native ASIO is compiled. The **ASIO system is already listed natively** (`native_asio_system`, `devices.rs:542-551`, through `backend::native::asio_system`, `native.rs:130-161`: the registry driver names, only the selected driver probed). The settings window and the report call `cpal_audio_systems()` directly (`crates/ui-studio/src/audio_devices.rs:708`, `crates/ui-studio/src/diagnostics.rs:146-155`). The native WASAPI crate **already enumerates by itself**: `WasapiBackend::endpoints` (`crates/audio-wasapi/src/lib.rs:142-145`) over `com::list_endpoints` (`com.rs:345-362`: `IMMDeviceEnumerator::EnumAudioEndpoints(flow, DEVICE_STATE_ACTIVE)`, default endpoint by `eConsole` first), with the endpoint id from `IMMDevice::GetId` and the name from `PKEY_Device_FriendlyName` (`com.rs:308-312`). Nothing in playback calls it for the settings list yet. A native WASAPI open resolves the saved device by name or id (`lib.rs:147-156`, `e.name == name || e.id == name`).
- **Device identity.** `AudioConfig.output` and `.input` hold the device **name** (`devices.rs:132-136`); cpal's WASAPI name is `DEVPKEY_Device_FriendlyName` (fork `src/host/wasapi/device.rs:272-283`), the same property key as the native backend's `PKEY_Device_FriendlyName`, from the same enumerator, with the same `DEVICE_STATE_ACTIVE` filter and `eConsole` default (fork `device.rs:867`, `:911`). The system name "WASAPI" is the same string in both (`audio-wasapi/src/lib.rs:33`). `input_pairing` and `system_audio_output` already hold native names or ids.
- **cpal use sites.** 146 lines with `cpal::` in the playback and audio-wasapi crates (190 occurrences), plus one in `tools/audio-bench/src/lib.rs` (`cpal_backend`, through `CpalFactory`). By role: the adapter `crates/playback/src/backend/cpal.rs` (76 lines); enumeration and adapter helpers in `devices.rs` (38: `FORMATS`, `format_rank`, `describe`, `shared_host`, `host_named`, `find_device`, `buffer_size_on`, `buffer_size`, and their tests); the adapter's entry points in `open.rs` (2), `device.rs` (1, a test-only `fill`), `record.rs` (1), `lib.rs` (1, `OutputCallback` re-export); tests only: `crates/playback/src/device_clock/tests.rs` (20: a `Stamper` harness feeding cpal callback infos into the fitter), `crates/playback/src/player/device/golden.rs` (5: the adapter's byte goldens), `crates/playback/tests/backend_time_contract.rs` (1: arithmetic of the fork's `StreamInstant`; it opens no stream and, as ADR 0016 section 3 says, gates no backend), `crates/audio-wasapi/src/convert.rs` (1). The common vocabulary already lives in `transit-audio-backend` (`crates/audio-backend/src/lib.rs`: `SampleFormat` at `:34`, `Format` at `:56`, `Endpoint` at `:188`, `OpenError` at `:246`, the `Backend` and `BackendFactory` traits at `:601` and `:696`); that crate is layer 0 and standalone in the layers xtask (`xtask/src/main.rs:60`, `:91`), not layer 1. The cpal types left outside the adapter are `cpal::SampleFormat`, `SupportedBufferSize` and `BufferSize` in `devices.rs`.
- **Builds.** `apps/transit/Cargo.toml:16` and `tools/audio-bench/Cargo.toml` make `native-wasapi` and `native-asio` default features. CI's `windows` job (`.github/workflows/ci.yml:37-62`) runs clippy and the workspace tests with `--features transit/native-wasapi,transit/native-asio`; `.github/workflows/release.yml:40` builds the Windows zip and MSI with both, and its notes (`release.yml:295`) say `audio-bench.exe` carries "native WASAPI, native ASIO and cpal WASAPI".
- **Docs that name cpal on Windows.** Known issues K16 (cpal capture has no discontinuity handling), K24 and K29 (cpal WASAPI measured beside native), K100 (cpal as a backend that neither fills nor flags a gap); `docs/contributing/knowledge/clocks.md:45-49` ("`Auto` is cpal", the fallback note); `README.md:109-114` (the cpal WASAPI bench recipe) and `:240` ("with a cpal fallback"); `docs/troubleshooting.md:38`. The label "cpal (legacy)" exists only in code (`devices.rs:53`, asserted in `crates/ui-studio/src/audio_devices_tests.rs:313`); the user guide's "Audio setup" section (`docs/user-guide.md:170`) does not name a backend.
- **Related decisions.** [ADR 0017](0017-clock-contract-annex.md) (the clock contract both adapters feed), [ADR 0021](0021-native-linux-audio-over-the-jack-client-api.md) (JACK and PipeWire-JACK as the Linux story, `Auto` still cpal ALSA when no server answers), [ADR 0032](0032-transit-ships-a-desktop-app-only.md) (desktop only), [ADR 0037](0037-adaptable-core-small-hardware.md) (tiers and the layers xtask), [ADR 0040](0040-inherited-built-in-effects-retired-in-stages.md) (retirement in stages, break in alpha).

## Decision

1. **Scope: no cpal on Windows targets.** On `cfg(windows)` cpal is not compiled: there is no `Backend::Cpal` choice, no fallback open and no cpal enumeration; native WASAPI and native ASIO are the only paths.
   - **`Auto` on Windows** opens the native backend of the chosen system: the ASIO system opens native ASIO, the WASAPI system (and the untouched default, `system: None`) opens native WASAPI. The system decides, not the saved backend, so the "crossed configuration" (a saved `NativeAsio` with the WASAPI system, `crates/ui-studio/src/diagnostics.rs:365-368`) opens native WASAPI.
   - **A native open failure is a visible error, never a silent fallback.** When the ladder of ADR 0016 (its amendments of 2026-10-22) cannot answer an error, the Player opens nothing: the existing silent-runtime path with the backend's own reason (`Player::with_config`, `open.rs:10-18`), shown in Audio Devices as "The audio device did not open: <reason>." (`crates/ui-studio/src/audio_devices.rs:589-593`) and on the status line as "<Native WASAPI|Native ASIO> did not open: <reason>". The device stays closed until the user changes a choice and applies, or presses Reconnect. The ladder's step 4 becomes this error. A native output's input that fails to open is the same kind of error on the input (`HeldInput::Failed`), not a cpal input.
   - **Off Windows nothing changes** in this stage: Linux keeps cpal ALSA and ADR 0021's `Auto` rule, macOS keeps cpal CoreAudio, and both keep the native-or-cpal fallback.
2. **Enumeration: the native crates list their systems.** On Windows `devices::audio_systems()` is the native WASAPI system plus the native ASIO system.
   - **WASAPI** is listed through `WasapiBackend::endpoints` (already `IMMDeviceEnumerator`, `audio-wasapi/src/lib.rs:142`) and `backend::native::system_from_endpoints` (`native.rs:100`), the same builder the ASIO and JACK systems use, in a new `backend::native::wasapi_system()`; default endpoint first, `is_default` on it.
   - **ASIO** stays as it is (`native_asio_system`, the registry names, only the selected driver probed).
   - `cpal_audio_systems()` and the cpal helpers move behind `cfg(not(windows))`. The settings window (`audio_devices.rs:708`) and the report (`diagnostics.rs:146`) call `devices::audio_systems()` (or its fast part without the ASIO probe) instead of `cpal_audio_systems()`.
   - **Saved device choices stay valid; no rename migration is needed.** The saved key is the device name, and the native list names endpoints by the same property key, from the same enumerator, with the same active-state filter and default role as cpal (Context, "Device identity"); the native open already resolves a saved name or id (`lib.rs:147-156`). Duplicate friendly names were ambiguous under cpal too; the native lookup takes the first match in its default-first order, and that rule is kept and named in the code.
   - **One migration: the backend field.** The `Cpal` variant stays in the `Backend` enum on every platform so an existing `ui.json` with `"backend": "cpal"` still parses (an unknown variant would fail the whole `AudioConfig`). On Windows a loaded `Cpal` reads as `Auto` and is written back as `auto` on the next save; it is never offered.
3. **Vocabulary: no new shared types are needed; what is left moves into the adapter.** The shared vocabulary (`SampleFormat`, `Format`, `Endpoint`, `OpenRequest`, `Period`, `Mode`, `Stamp`) is already in `transit-audio-backend` (layer 0, standalone). The cpal-typed helpers still in `devices.rs` (`FORMATS`, `format_rank`, `describe`, `shared_host`, `host_named`, `cpal_system_for`, `find_device`, `buffer_size_on`, `buffer_size`, `add_unlisted` and their tests) move into `crates/playback/src/backend/cpal.rs` (or a `backend/cpal/` folder if the file-size budget asks for it), so `devices.rs` holds only platform-neutral types (`Backend`, `AudioConfig`, `AudioSystem`, `DeviceInfo`, calibrations). `transit-audio-wasapi`'s conversion tests keep their byte-identity claim against a stored table: the golden values are captured once from cpal's conversion (`I16`, `I24`, `I32` from `f32` and back, over the existing sample sets, plus the wire formats of `capture_conversion_matches_the_cpal_adapters_for_every_wire_format`) into `crates/audio-wasapi/src/convert_golden.rs`, the tests compare against it, and the cpal dev-dependency goes. The table's header names the cpal version and fork commit it was captured from.
4. **Dependency gate.** A new xtask gate, `cargo xtask windows-deps`, runs `cargo tree --locked --target x86_64-pc-windows-msvc --workspace --all-features -e normal,build,dev --prefix none --format "{p}"` and fails when any line is the `cpal` package (or `audio_thread_priority`, which only cpal brings). It is cross-target, so it runs in the Linux CI job, the Windows CI job and the WSL gate alike; `cargo xtask ci` includes it. The parsing is a pure function with unit tests in `xtask/src/tests.rs`. **Negative control:** a fixture tree with a `cpal v0.16.0` line fails the function; and, once at landing, a scratch manifest line restoring `cpal.workspace = true` under `crates/audio-wasapi`'s Windows dev-dependencies makes the live gate fail, recorded in the landing note. The `[patch.crates-io]` entry and the `=0.16.0` pin stay for Linux and macOS; the patch comment becomes: "Linux (ALSA) and macOS (CoreAudio) only since ADR 0046: the signed timestamp fix is platform-neutral; the WASAPI commits are unused and go with the fork's retirement in stage three."
5. **Staging.**
   - **Stage one (this ADR): Windows.** cpal leaves every Windows build.
   - **Stage two: Linux ALSA**, its own ADR: decide whether ALSA direct is dropped in favor of JACK and PipeWire-JACK (ADR 0021), or kept through cpal until a native ALSA path exists. Known issue KC6 (the ALSA period under PipeWire) is input to it.
   - **Stage three: macOS**, after a native CoreAudio backend, its own ADR. It needs access to a Mac, and CI cannot prove sound there, so it waits for hardware. When it lands, the cpal dependency, the fork and the pin go from the workspace.
   - **Why macOS keeps cpal now:** the maintainer's download figures are about half Linux, a third Windows and a sixth macOS. A sixth of users is too many to leave without audio, and cpal's CoreAudio path is their only one.
6. **Consequences carried in the landings.**
   - Known issues: K16's last sentence and K100's "(cpal)" say "on Linux and macOS"; K24 and K29 keep their measurements as history and drop "cpal WASAPI" as a current path ("measured through cpal's WASAPI backend before ADR 0046").
   - User guide, "Audio setup": a short Windows paragraph: the backend follows the audio system (ASIO opens native ASIO, WASAPI opens native WASAPI), there is no Backend choice, and a device that does not open stays closed with the reason in Audio Devices until a choice changes or Reconnect is pressed. `docs/help/audio-devices.toml` says the same where it describes the open device. `docs/troubleshooting.md:38` names the backends per platform.
   - `README.md:240` loses "with a cpal fallback", `:265` says cpal is the Linux and macOS adapter, and the bench recipe at `:109-114` uses `--backend wasapi`. `docs/contributing/knowledge/clocks.md:45-49` is rewritten for the Windows rule. `crates/rt/Cargo.toml:20`'s comment stops naming cpal (windows-sys stays in the tree through winit and others).
   - **Features.** `native-wasapi` and `native-asio` stop being features: on Windows `transit-playback` depends on `transit-audio-wasapi` (all Windows targets) and `transit-audio-asio` (64-bit Windows) unconditionally, and the features are removed from `crates/playback/Cargo.toml`, `apps/transit/Cargo.toml` and `tools/audio-bench/Cargo.toml`. Reason: without them a Windows build would have no audio path at all, so the switch only builds a broken app. `NATIVE_WASAPI_COMPILED` and `NATIVE_ASIO_COMPILED` become `cfg!(windows)` and `cfg!(all(windows, target_pointer_width = "64"))`. `native-jack` stays a Linux feature (its build needs `jack.pc`). CI and release command lines drop the two feature names in the same landing.
   - `audio-bench` on Windows loses `--backend cpal` (it reaches cpal only through `transit-playback`). The committed cpal-shared baseline tables (ADR 0016 slice b, `docs/benchmarks/`) stay as history; a new cpal WASAPI comparison runs from a v0.6.x release's `audio-bench.exe`. `release.yml:295` says "native WASAPI and native ASIO".
   - Release notes, Breaking: "Windows: cpal is gone. Audio opens through native WASAPI or native ASIO, chosen by the audio system; a device that does not open says why and stays closed instead of falling back. A saved `cpal` backend reads as Auto."
   - Thread priority: nothing replaces cpal's `audio_thread_priority` on Windows, because nothing on the native paths used it (Context, "Thread priority without cpal").
   - No gate class is removed. The new gate (decision 4) is a dependency-graph class; if an escape later shows cpal or a fallback returning on Windows, its escape record names this gate. ADR 0016's reopen conditions that compare against "CPAL-shared" become historical and are marked so in an ADR 0016 note.
7. **Gate: tests that prove the behavior, each with a negative control.**
   - **No cpal in the Windows graph:** `cargo xtask windows-deps` (decision 4); control: the fixture and the one-time manifest line.
   - **No cpal choice on Windows:** a `transit-playback` unit test that `Backend::offered(Some("WASAPI"))` and `offered(Some("ASIO"))` on Windows contain no `Cpal`, and a `transit-ui-studio` layout test that the Audio Devices window on Windows shows no Backend row and no "cpal (legacy)" text (`audio_devices_tests.rs:313` is rewritten). Control: restoring `Cpal` to `offered` fails both.
   - **A forced native open failure surfaces and leaves the device closed:** a test hook (`ab::fake::FakeBackend` scripted to fail every open, through the existing `open_native` seam that `open_fake_native_asio` uses) asserts the Player is silent with `initial_error` equal to the backend's reason, that no other factory was asked to open (a counting fake in the old fallback position records zero calls), and that Audio Devices shows "The audio device did not open: <reason>." One test per kind (WASAPI after the full exclusive ladder, ASIO). Control: re-adding the fallback call makes the counting fake record a call and the test fail.
   - **Saved device choices still open the same device:** a unit test over a fake WASAPI endpoint list that a config saved by the current build (system "WASAPI", the endpoint's friendly name, `backend: "cpal"`) resolves to that endpoint's id and to `Backend::Auto` on load; control: a config naming a missing device fails the match. Before the cut, the maintainer runs one ignored Windows hardware test (`hardware_cpal_and_native_wasapi_list_the_same_names`, added in slice 2 while cpal is still present) that enumerates both and asserts equal name sets per direction and the same default; its result goes in `docs/contributing/evidence/` and is a precondition of slice 4.
   - **Conversion goldens:** `transit-audio-wasapi`'s conversion tests pass against `convert_golden.rs` with no cpal; control: flipping one bit of one table entry fails them.
   - **Clock contract on Windows:** the fitter tests in `device_clock/tests.rs` that only use cpal as a stamp generator (all but `cpal_stamp_sequences_match_the_captured_golden`, `timestamp_extraction_does_not_fabricate_host_time_and_checks_signed_range` and `noisy_and_millisecond_quantized_cpal_clocks_converge_and_retain_delayed_capture_coverage`) are moved onto a backend-neutral stamp harness (`Stamp` values straight into `Observer`) so they run on every platform; the three cpal-specific ones and `tests/backend_time_contract.rs` (fork arithmetic only, not a backend test) become `cfg(not(windows))`. On Windows the native timing contract stays where it is tested today: `transit-audio-wasapi`'s and `transit-audio-asio`'s stamp tests and `crates/playback/tests/publication_contract.rs`. Control: the harness move is checked by running the moved tests once against a fitter with the residual bound set to zero, which must fail them, before and after the move.
8. **Implementation plan: four slices, main green at each landing.**
   1. **Vocabulary move (pure move, `transit-playback`, `transit-audio-wasapi`).** The cpal helpers leave `devices.rs` for the adapter module; the device-clock harness becomes backend-neutral; the conversion goldens are captured from cpal into `convert_golden.rs` and the tests switch to them (cpal stays as a dev-dependency in this slice so the capture is reproducible, then goes at the end of it). No behavior change; existing tests unchanged except the moved ones.
   2. **Native WASAPI enumeration (`transit-playback`, `transit-ui-studio`).** `backend::native::wasapi_system()`; `audio_systems()` uses it on Windows; the settings window and the report use `audio_systems()`; the hardware comparison test is added and run by the maintainer while cpal still opens streams. cpal remains the `Auto` and fallback path in this slice.
   3. **Selection without fallback (`transit-playback`, `transit-ui-studio`).** `Auto` maps to the system's native backend on Windows; `Cpal` loads as `Auto`; the Backend row disappears on Windows; `open_native` and `open_input` stop falling back on Windows; `fallback_note` and the ladder's step 4 become the error; the forced-failure tests. A build of this slice still compiles cpal on Windows but never reaches it, so the Windows CI job proves the app works without it before the cut.
   4. **The dependency cut (`transit-playback`, `transit-audio-wasapi`, `apps/transit`, `tools/audio-bench`, `xtask`, CI, release, docs).** cpal moves to `[target.'cfg(not(windows))'.dependencies]`; the `audio_thread_priority` line goes; `backend/cpal.rs` and its call sites are `cfg(not(windows))`; the native features are removed and the native crates become unconditional Windows dependencies; `cargo xtask windows-deps` lands with its negative control; CI and release lines, docs and known issues as in decision 6. The Windows CI job must pass with the gate before the cut merges; the WSL gate (Linux) still builds and tests cpal, and the macOS job still builds it.
9. **Alternatives considered** are below.

## Implementation

Not started. Slices as in decision 8, each through the usual implementer, review and chain gates; slice 4 waits for the slice 2 hardware evidence.

## Gate

Decision 7 is the gate. In short: `cargo xtask windows-deps` passes and its negative control fails; Windows offers no cpal choice; a forced native open failure is a visible error with the device closed and no other open attempted; a saved device choice from the current build resolves to the same endpoint (unit test) and the maintainer's hardware comparison shows equal name sets before the cut; the WASAPI conversion goldens pass without cpal; the fitter tests run on Windows on a neutral harness.

## Consequences

- Windows has one path per audio system, with its own clock, counters and error text; a native failure can no longer hide behind a working cpal stream.
- A Windows device that only cpal could open no longer opens. None is known: cpal's Windows host was WASAPI alone (its ASIO host was retired in ADR 0016's amendment of 2026-10-25), and the native backend lists the same WASAPI endpoints.
- Users who saved `cpal` as their backend move to native WASAPI on the next start; a user whose device misbehaves on native WASAPI now sees the error instead of sound through cpal. Shared mode stays the default (ADR 0016, amendment 2), so the common case opens the same mix-format stream cpal did.
- `transit-playback` keeps one cpal adapter for two platforms, so cpal-only code and tests carry `cfg(not(windows))` until stage three.
- Windows build time and binary size shrink by cpal and `audio_thread_priority`; the fork stays in `Cargo.lock` for the other targets.
- The `native-wasapi` and `native-asio` feature names disappear; scripts that pass them fail with "feature not found" and are updated in the same landing (CI, release, the WSL gate).

## Alternatives considered

- **Keep cpal as a hidden fallback.** Rejected: a silent fallback hid native failures (a failed native ASIO open played through WASAPI shared, another system, `native.rs:27-35`), and the fork's WASAPI patches are exactly what the native backend replaced.
- **Remove cpal everywhere now.** Rejected: macOS would lose audio; cpal CoreAudio is its only path, and Mac users are about a sixth of downloads.
- **Replace cpal's enumeration with a third crate.** Rejected: the native crates already own the device model (`WasapiBackend::endpoints` over `IMMDeviceEnumerator`, the ASIO registry list), and the open path already resolves their names and ids.
- **Keep `native-wasapi` and `native-asio` as features.** Rejected: once cpal is gone, a Windows build without them has no audio, so the switch could only produce a broken app; `--no-default-features` builds keep working.
- **Map saved device names to endpoint ids in a migration.** Rejected as unneeded: the names come from the same property in both listings; the open path already accepts either a name or an id.
