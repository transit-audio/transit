# ADR 0064: Hosted MIDI plug-ins in the MIDI effect chain

- **Status:** proposed 2026-11-27 (issue #671; builds on ADR 0057 and ADR 0059, both accepted 2026-11-26).
- **Date:** 2026-11-27
- **Implementation:** not started. No code before this record is accepted (#671, Order). Slice cards in the Slices section; a contributor can take any slice whose needs have landed.
- **Reopen when:** the MIDI routing record named in decision 11 is written (it may change where a chain's output can go, never what a stage guarantees); ADR 0036's rack stage lands (decision 10 then admits hosted stages on racks); a supported plug-in is found to write its notes on an output bus or port other than the first and expects them merged (decision 3); a VST3 plug-in is found whose note output depends on an event output bus the host leaves inactive, or that writes output events outside `0..numSamples` on purpose (decision 3); a plug-in that qualifies by the capability rule is found to misbehave in the slot in a way the category would have predicted (decision 2); Audio Unit MIDI processors are wanted (Out of scope); the stage ledger (decision 5) is measured refusing notes in ordinary use; or Ableton Live and Logic Pro are found to agree on a behavior this record chose differently (claims marked "from memory").

## Context

**The request.** Issue #671: a third-party MIDI plug-in (a chord generator, an arpeggiator, a note processor) loads in transit, but the notes it produces go nowhere. A reported case (2026-11-26) adds two facts: the plug-in in question, a VST3 generative chord performer with no sound of its own, is listed by other hosts as an instrument, not a MIDI effect; and the user wants its notes to drive synths on other tracks. An outside contributor offered to build it, so this record is written as a specification to build from, slice by slice.

**What this record builds on.** [ADR 0036](0036-midi-effect-slot.md) made the slot and its host. [ADR 0057](0057-midi-devices-chord-arpeggiator-humanize.md) (accepted 2026-11-26) rebuilt the host's contract for its three devices, and its decision 16 lists what a hosted stage in the chain inherits, enforced by the host: final acceptance per hop (16.1), the host owning delivery to the instrument with its `out` table and refused-note accounting (16.2), every chain edit, Stop, panic and safety reset ending the chain's notes from the host's own table and releasing every pedal at an edit (16.3), ownership inside a stage being the stage's own (16.4), time and between-blocks rules (16.5), latency (16.6), capacity (16.7), refusal by the instrument (16.8, owned by [ADR 0059](0059-midi-event-delivery-under-refusal.md)) and Capture (16.9). Decision 16.2 states the hole this record must close or state: the host matches releases by identity and oldest-first, which proves an entry exists, not that a release answers it, so a hosted stage that writes an anonymous C on, its off, another C on and then a duplicate of the first off ends the second C early. This record inherits all of decision 16 and does not restate it; where it adds a rule, the rule is written here.

**What the code does today** (read on the branch carrying ADR 0057 and ADR 0059, head 40992792; line numbers are that tree's).

**What the formats say** (public documentation; quotes checked for this record on 2026-11-27).

- *VST3* (Steinberg's API reference and developer portal). `ProcessData::outputEvents`: "outgoing events for this block (optional)". `Event`: `busIndex`, `sampleOffset` ("sample frames related to the current block start sample position"), `ppqPosition`, `flags`, `type`; types `kNoteOnEvent`, `kNoteOffEvent`, `kDataEvent`, `kPolyPressureEvent`, `kNoteExpressionValueEvent`, `kNoteExpressionTextEvent`, `kChordEvent`, `kScaleEvent`, `kNoteExpressionIntValueEvent`, `kLegacyMIDICCOutEvent`. `NoteOnEvent`: `channel`, `pitch` (0 to 127), `tuning` (cents), `velocity` (0.0 to 1.0), `length` ("optional, Note Off has to follow in any case!"), `noteId` ("if not available then -1"); `NoteOffEvent`'s `noteId` is the "associated noteOn identifier (if not available then -1)". `LegacyMIDICCOutEvent` is "reserved for generating MIDI CC as output event for kEvent Bus during the process call", with `controlNumber` (the `ControllerNumbers` enum, 0 to 255: 0 to 127 are MIDI controllers, then `kAfterTouch`, `kPitchBend`, `kCtrlProgramChange`, `kCtrlPolyPressure` and others), `channel`, `value` and `value2` ("used for pitch bend (kPitchBend) and polyPressure (kCtrlPolyPressure)"). A MIDI port maps to a bus of media type `kEvent` ("About MIDI"); a bus's direction is `kInput` or `kOutput`; for an event bus `channelCount` is "the number of supported MIDI channels by this bus". `getBusCount` and `getBusInfo` are "Called after the plug-in is initialized"; `activateBus` and `setActive` are UI-thread calls. Categories are strings (`Fx`, `Instrument`, `Instrument|Synth`, `Fx|Generator`, `Fx|Instrument`, ...); no MIDI effect category exists. `setProcessing`: "this could be used to reset some buffers (like Delay line or Reverb)", callable "in the UI or in Processing Thread"; the call sequence page: it "may be called from real-time Audio Thread (must be lock-free and without memory allocation!)" and the "plug-in has to reset its inner processing state". Not stated anywhere read: whether output events must lie in `0..numSamples` or be sorted; whether `projectTimeSamples` may be negative. The bit order of a legacy pitch bend in `value`/`value2` and which of the two holds the key for `kCtrlPolyPressure` were not settled from the pages read (one generated summary contradicted the struct page); the slice settles them against the fixture and states the result in code.
- *CLAP* (the MIT-licensed headers, `include/clap/`). `note-ports.h`: `count(plugin, is_input)` and `get(plugin, index, is_input, info)`, both main-thread; `clap_note_port_info { id, supported_dialects, preferred_dialect, name }`; dialects `CLAP_NOTE_DIALECT_CLAP`, `_MIDI`, `_MIDI_MPE`, `_MIDI2`; "If the plugin does not implement this extension, it won't have note input or output"; ports change only while the plug-in is deactivated. `events.h`: `time` is the "sample offset within the buffer for this event"; "The plugin must insert events in sample sorted order"; `clap_event_note { note_id, port_index, channel, key, velocity }` with `-1` as "unspecified or wildcard" (a note-off with `note_id` -1 still matches; "Well constructed plugins will search for voices and notes using the entire tuple"); a note-on of velocity 0 "is valid and should not be interpreted as a NOTE_OFF"; `NOTE_CHOKE` "can be sent by the host to the plugin"; `NOTE_END` "is sent by the plugin to the host" to report a voice's end; note expressions (volume, pan, tuning, vibrato, expression, brightness, pressure); `CLAP_EVENT_MIDI`, `_MIDI_SYSEX`, `_MIDI2`; one note must not be sent both as a note event and as MIDI. `try_push` "returns false if the event could not be pushed to the queue". `plugin-features.h`: `note-effect` is "a note effect or a note generator/sequencer"; `instrument` "can process note events and then produce audio". `plugin.h`: `reset` "Clears all buffers, performs a full reset of the processing state ... and kills all voices" (audio thread, active); latency and ports "must remain constant, until deactivation". The transport has `CLAP_TRANSPORT_IS_LOOP_ACTIVE` and loop points; whether `song_pos_beats` may be negative is not stated.

**What other hosts do** (from memory, not verified for this record; nothing below relies on it unless it says so). Ableton Live hosts VST3 and Audio Unit MIDI effects in the MIDI effect position of a track's chain and lets a second track take another track's MIDI "Post FX" as its input. Logic Pro hosts Audio Unit MIDI FX in its MIDI FX slots and has no direct track-to-track MIDI routing for their output. A plug-in listed as an instrument (the reported case) is placed by both as an instrument, which is why the reported user cannot reach its notes there either way: in Live, a MIDI track set to receive from the instrument's track can take its MIDI output. So the two hosts do not agree on routing, and do not document a capability rule for the slot.

## Decision

### 1. Scope of the first cut

A hosted VST3 or CLAP plug-in that declares a note output can be a stage of an instrument track's MIDI effect chain, anywhere a built-in can sit, under every rule of ADR 0057 decision 16 and the rules below. Its notes go to the next stage or the instrument of the same track (decision 11 for other destinations). Audio Units are out of scope (Out of scope).

### 2. Which plug-ins qualify: capability, not category

1. **The rule.** A VST3 class qualifies when its component, initialized, reports at least one event bus in the output direction (`getBusCount(kEvent, kOutput) >= 1`). A CLAP plug-in qualifies when, created and initialized, it reports at least one output note port (`note_ports.count(plugin, false) >= 1`) whose first port supports the CLAP, MIDI or MIDI MPE dialect; a plug-in whose output ports speak only MIDI 2 does not qualify (transit carries no MIDI 2 message, decision 3). Whatever the plug-in calls itself: an instrument, an effect, a generator, a note effect.
2. **Categories are a hint and decide nothing.** VST3 sub-categories and CLAP features keep doing what they do today (the category and the instrument flag that place a plug-in in the instrument and insert menus); they never admit or exclude a plug-in from the MIDI effect slot. So the reported case (a VST3 class whose sub-category is an instrument, with an audio output bus and an event output bus) qualifies, and appears in both the instrument menu and the MIDI effects menu. A CLAP `note-effect` without an output port does not qualify (it cannot write notes the host reads).
3. **A declared output that stays silent is fine.** A plug-in that declares a note output and never writes to it passes nothing (decision 4: its output replaces its input). That is the user's choice to make, not the host's to guess.
4. **The scanner records the capability.** The scan child (already a separate process, so a plug-in that crashes while it is created takes only the child down) creates each class after reading the factory: VST3: `createInstance` of the component, `initialize` with the host context, `getBusCount` for event buses in both directions, `terminate`; CLAP: `create_plugin`, `init`, the note ports in both directions (count, and the first port's dialects), `destroy`. Nothing is activated, processed, or shown. The descriptors (`Vst3Descriptor`, `ClapDescriptor`) gain `note_output: Option<bool>` and `note_input: Option<bool>`: `Some` when the probe ran, `None` when it failed (logged with the reason, and counted in the scan summary under its own count, not as a failed file: the factory listing still succeeded, so the plug-in keeps its place in the menus it is in today). The cache's `VERSION` goes from 1 to 2, so every file is loaded once again by the first scan of a build with this slice: the existing mechanism, not a migration shim (alpha: no migrations). Cost: every class is created once per scan of a changed file; the child's timeout (`CHILD_TIMEOUT`, 120 s per file) bounds a plug-in that hangs while being created.
5. **Checked again at creation.** An instance made for a MIDI slot whose configured instance declares no note output (a plug-in updated since the scan) is kept in the slot with the state "does not write notes", passes its input through (decision 7) and is named in the card and the load note; the session keeps the slot unchanged.
6. **Where a qualifying plug-in appears.** In the MIDI effect group's "+" menu (ADR 0057, 14.7): built-in MIDI effects first, then VST3 and CLAP entries with `note_output == Some(true)`, grouped by vendor, through the existing `plugin_menu` with the list filtered; nothing else marks them. A plug-in whose probe failed (`None`) is not listed there; a rescan (Audio > Scan Plug-ins) probes again. The add command accepts a hosted id only when its cached descriptor says `note_output == Some(true)`; until the visibility slice, only through the control channel (decision 12, slice VH).

### 3. Reading note output

**Which bus or port.** Only the first output: VST3 event output bus 0, which the adapter now activates in `configure` beside the input bus (`activateBus(kEvent, kOutput, 0, true)`, UI thread, inactive component, as the input bus is); CLAP output note port index 0. Events on any other bus or port are dropped and counted (`other_port`). Transit has one note port per instrument, and a plug-in that writes several streams means them for several destinations, which is decision 11's question; merging them now would decide it by accident.

**When it is read.** After each native sub-call, before the next: the adapter takes that call's output events, adds the sub-call's start to each offset (`start` in `process_keyed`), and appends them to a fixed buffer of the instance's block output (capacity 1,024, the native list's; past it an event is dropped and counted). CLAP: the host's `try_push` writes into that buffer and returns `false` when it is full (the plug-in is told); VST3: `addEvent` already refuses at the list's capacity. A skipped call (main thread holds the instance, parked, inactive) produces no output for that block; the input it kept is delivered at offset 0 of the next actual call (ADR 0059, 3a).

**Offsets.** An event offset below 0 becomes 0 and one at or past the sub-call's frame count becomes that sub-call's last frame; both are counted (`offset_clamped`). Neither format documents the range (Context), and the host's carry is not used for hosted output: carrying an event the plug-in placed outside its call would act on an offset no format defines. The host then sorts the stage's output stably by offset (it does for every stage, `midi_fx.rs:526`), so events at one offset keep the plug-in's write order. A plug-in that writes a note-off ahead of its own note-on in time has that note-off consumed by the stage ledger (decision 5) and the note sounds until the next barrier (decision 6); Stop ends it.

**The translation table.** Every accepted event becomes a `PluginEvent` on the stage's output, channel 0 to 15 (an out-of-range channel or key drops the event, counted). Velocities: a format's float velocity `v` becomes `round(127 × v)`, rounding half away from zero, clamped to 1..=127 for a note-on and 0..=127 for a note-off. A format-native note-on (VST3, CLAP dialect) whose velocity rounds to 0 is a note-on of velocity 1, as both formats define it; a MIDI-byte note-on with velocity 0 is a note-off (MIDI's rule; ADR 0057, 2.2).

| Format event | Becomes |
|---|---|
| VST3 `kNoteOnEvent` | note-on (`tuning` and `length` ignored; `noteId` kept for the stage ledger) |
| VST3 `kNoteOffEvent` | note-off, matched by the stage ledger |
| VST3 `kPolyPressureEvent` | poly pressure `round(127 × pressure)`, given to the matching open note(s) (decision 5) |
| VST3 `kLegacyMIDICCOutEvent`, `controlNumber` 0 to 127 | `Control { cc, value }` |
| the same, `kAfterTouch` | `ChannelPressure` |
| the same, `kPitchBend` | `PitchBend` from `value` and `value2` (14 bits; the byte order settled against the fixture, Context) |
| the same, `kCtrlProgramChange` | `Program` |
| the same, `kCtrlPolyPressure` | poly pressure (key and pressure fields settled against the fixture) |
| the same, any other controller number | dropped, counted |
| VST3 `kDataEvent`, note expressions, `kChordEvent`, `kScaleEvent` | dropped, counted |
| CLAP `NOTE_ON` (port 0) | note-on; a wildcard channel or key (`-1`) is invalid for a note-on by the format's rule and is dropped, counted |
| CLAP `NOTE_OFF` and `NOTE_CHOKE` | note-off; a wildcard channel or key ends every open stage note matching the fields that are not wildcards (decision 5) |
| CLAP `NOTE_END` | ignored (it reports the plug-in's own voices, not a note it writes) |
| CLAP `NOTE_EXPRESSION`, pressure | poly pressure to the matching open note(s) |
| CLAP `NOTE_EXPRESSION`, any other | dropped, counted (transit carries no per-note tuning, volume, pan or brightness) |
| CLAP `MIDI` (port 0), any dialect | decoded as MIDI 1.0: 9n, 8n, An, Bn, Cn, Dn, En; MPE is carried as what it is on the wire, per-channel notes and controllers (ADR 0057, 2.10) |
| CLAP `MIDI_SYSEX`, `MIDI2` | dropped, counted |
| CLAP `PARAM_VALUE` | as today (editor edits, `ffi/events.rs:199` to `211`) |

What a user loses, stated in the help: per-note tuning and the other per-note expressions except pressure, system exclusive and MIDI 2. The drop counters are shown with the chain's counters (`MidiFxCounts`, `EventStatus::midi_fx`) and in the diagnostics report.

**The trait seam.** `Plugin` gains, with defaults that change nothing for any existing plug-in: `fn writes_notes(&self) -> bool` (false; the configured instance's capability, decision 2.5) and `fn take_note_output(&mut self, out: &mut dyn FnMut(u32, PluginEvent) -> bool)` (does nothing), which hands the block's translated events, in write order, with the plug-in's own note id in `note_id` (`-1` when it gave none), and clears the buffer. `Hosted` forwards both. The adapters' file budgets (`crates/vst3-host/src/plugin.rs` 1,340 lines, `crates/clap-host/src/plugin.rs` 1,337) mean the output path goes to new modules beside them.

### 4. What the plug-in hears, and what passes it

1. **Input.** The stage's input events go to the plug-in through the adapter's existing `Plugin::event`, exactly as an instrument receives them: VST3 notes and poly pressure on event input bus 0 with the chain's voice ids as `noteId`, controllers, channel pressure and pitch bend as points on the parameters the plug-in maps them to (`IMidiMapping`), program changes not delivered; CLAP notes on input port 0 in its dialect, controllers only as MIDI to a port that supports MIDI. A plug-in with no event input (a pure generator) hears no notes. Admission and refusal at this input are the adapter's, under ADR 0059's slice R1 when it lands; a refused input event is counted like any stage refusal.
2. **Output replaces input.** What the plug-in writes is the stage's whole output: an input event the plug-in does not write again (a note, a pedal, pitch bend) does not reach later stages. This is how a plug-in in a MIDI effect position behaves in other hosts (from memory) and the only rule under which a note generator with its own Thru setting means what it says. A pedal-down the plug-in passes and whose pedal-up it drops leaves the instrument's pedal down until the next barrier, which releases every pedal the instrument holds at an edit (ADR 0057, 2.13) and resets the instrument at Stop.
3. **Transport and tempo.** The same `Transport` the built-ins see (ADR 0057, 16.5): playing, recording, tempo, meter, sample position, quarters and bar start, which the adapters already map (Context). No loop or cycle information is passed (none exists in `Transport`); a loop wrap appears to the plug-in as a jump of the position. While stopped, playing is false and the position does not advance; whether the plug-in plays while stopped is its own behavior, not gated by the host (a chord performer must answer keys while stopped). The pre-count zone (ADR 0052) reaches it as negative positions, true values in both formats; neither format documents negative positions (Context), so a plug-in's behavior there is its own.
4. **Its audio.** The stage owns a scratch buffer, allocated when the stage's instance is prepared (two channels, the session's largest block), given to `Plugin::process` with the input marked silent (VST3 silence flags, CLAP constant flags, as today's `set_input_silent`); the output is computed and not used. A synth that also writes notes may sit in the slot: the capability rule admits it, and refusing it would refuse the reported case, which declares an instrument audio bus. A sidechain key is never routed to a MIDI stage. The card says "Audio from this plug-in is not used here" (decision 9). The plug-in's processing cost is paid in full; the help says so.
5. **Never suspended.** A hosted MIDI stage is not suspendable (a generator writes notes with silent input); its slot is created with `suspendable` false.
6. **Between blocks.** A hosted stage is never processed between blocks: a native call advances the plug-in's time, and ADR 0057's call "in which no time passes" (slice P2) has no native form. An event sent between blocks waits in the stage's input and is delivered at offset 0 of the next block's call, after the retained events of a skipped call and before that block's own events; its consequences (a release through a generator) are therefore one block later than for a built-in. Until P2 lands, the host's between-blocks call `run(plugin, 1, false)` skips hosted stages the same way.
7. **Offline rendering.** Bounce, freeze and Capture render with fresh instances restored from the stored state (`crates/mix/src/offline.rs`), through the same stage code. The VST3 process mode stays `kRealtime` in offline renders, as for every VST3 plug-in today (Context; changing it for all VST3 plug-ins is not this record's).

### 5. Note pairing and provenance: the stage ledger

ADR 0057 decision 16.4 leaves ownership inside a hosted stage to this record. The host puts a **stage ledger** at every hosted stage's output, between the translation and the stage's output buffer. It is host code, so the plug-in is held to it without being trusted.

1. **Re-identification.** Every note-on the stage writes opens a ledger entry `{ channel, key, plug-in note id or none, host id, seq: u64 }` and leaves the stage carrying a fresh **host id** in `note_id`, unique among the stage's open entries: a 31-bit counter, skipping `-1` and any id still open. Every note-off and poly pressure that matches an entry leaves with that entry's host id. So every note downstream of a hosted stage is identified, and every later stage, the host's `out` table and the instrument pair it exactly by identity.
2. **Matching.** A note-off with a plug-in note id closes the open entry of its channel, key and id, and nothing else. A note-off without one (`-1`) closes the oldest open entry of its channel and key, identified or not: that is the formats' wildcard meaning (CLAP: a note-off with `note_id` -1 still matches; VST3: `-1` is "not available"). A CLAP note-off or choke with a wildcard channel or key closes every open entry matching its other fields, each with its own note-off. Poly pressure goes to every open entry its fields match, each event with that entry's host id. A note-off or pressure that matches nothing is consumed and counted (`unmatched_releases`): it cannot belong to a note the stage let through.
3. **Capacity.** 256 open entries (`MIDI_FX_NOTES`). With 256 open, a further note-on is refused (not emitted, counted as a refused note-on); its later note-off matches nothing it should (an identified one finds no entry and is consumed; an anonymous one closes the oldest open entry of its key, ending that note early; the same fail-closed bound as ADR 0057's kit ledger: saturation can only shorten a note, never leave one sounding or write a note-off twice).
4. **The output buffer.** The stage's output is admitted by ADR 0057's P3b rule (16.1): a note-on is entered in the ledger only when the output accepted it, and a note-off is written only for an entry that exists. A note-on the output refuses is not entered, so its note-off is consumed.
5. **What the host guarantees.** For a stage under this ledger: no note-off leaves the stage for a channel and key with nothing open; every note-on that leaves has exactly one note-off from the stage or is ended by a barrier (decision 6); a note the plug-in identified is ended only by its own note-off, a wildcard of its fields, or a barrier; and downstream of the stage every pairing is exact.
6. **What it cannot guarantee.** An anonymous note-off carries no evidence of which note-on it answers. A plug-in that writes an anonymous C on, its off, another anonymous C on and then a duplicate of the first off ends the second C early, and its own later off is consumed: nothing is left sounding, a note is cut short. The ledger narrows ADR 0057's hole to that case (anonymous notes of one key from a plug-in that writes duplicate offs) and closes it for every plug-in that identifies its notes; a host cannot tell a duplicate from a release without the plug-in's identity. The help says that a plug-in which writes note ids pairs exactly and one which does not is paired oldest-first.
7. **Not `NotePairing`, not the kit ledger.** ADR 0057's kit ledger (K1) matches an anonymous note-off against anonymous entries only and records rejections; the formats' wildcard rule needs an anonymous off to close an identified entry, so the stage ledger is its own small table in the host (`crates/mix/src/midi_fx/hosted.rs`), with the same capacity and fail-closed bound.

### 6. Barriers: every way a stage stops owning its notes

Each event below is a **host barrier**: the host ends every note it delivered from the chain (`out`), releases every pedal at an edit and presses none again, resets every stage, clears every stage ledger and the delivery refused table, and starts a new epoch, exactly as ADR 0057's chain edit and reset barrier (2.13, P3a, P3b) do. This record adds to the list of events that cause one, never to what one does.

| Event | Barrier | Note |
|---|---|---|
| A hosted stage added, removed, moved, bypassed or un-bypassed | edit (ADR 0057, 2.13) | unchanged rule |
| A hosted stage replaced by another plug-in (decision 8) | edit | |
| Stop, the end of a play range, the All MIDI Notes Off action | as ADR 0057 2.14 and ADR 0059 4 | |
| A hosted stage's instance arrives in the plan, or leaves it (created after Loading, Retry after Not responding, a creation that failed, a plug-in removed from disk at the next load) | edit | the stage comparison in `begin` gains "instance present" |
| A hosted stage reports a processing error (decision 7) | edit, then the stage is failed until Stop | |
| A hosted stage restarts (VST3 `kLatencyChanged` or `kIoChanged` reactivation; CLAP `request_restart` and its reactivation) | edit | a reactivated plug-in has forgotten the notes it was holding, so their note-offs will never come |
| A state is loaded into a hosted stage (a preset recalled, an undo that restores its state, a state set through the control channel) | edit | the loaded state can drop what the plug-in held, for the same reason |
| A parameter change, from a lane, a hand, MIDI Learn or the plug-in's editor | none | each plug-in pairs its own notes across its own parameter changes; the ledger catches what it does not |

**The stage's own reset.** At a barrier a hosted stage is reset by its format's means before its next call: CLAP `reset` (requested and run before the next actual call, as today; documented to kill all voices); VST3 `setProcessing(false)` followed by `setProcessing(true)` on the audio thread before the next call, which the format documents as the place a plug-in resets its inner processing state and allows from the processing thread. That VST3 cycle is new and is done for hosted MIDI stages only, through a new trait method `Plugin::restart_processing` whose default calls `reset` and whose VST3 override performs the cycle; instruments and inserts keep ADR 0059's reset as written (3d). Whether a VST3 plug-in actually forgets pending notes at that cycle is the plug-in's; the host's guarantee does not depend on it, because the stage ledger is cleared at the barrier, so a note-off the plug-in writes afterwards for a note from before matches nothing and is consumed, except that an anonymous one can close a newer anonymous note of the same key opened since (decision 5.6's limit, at a VST3 plug-in that does not reset).

**Nothing hangs.** Every note a hosted stage let through to the instrument is ended by its own note-off or a wildcard (5.2), by the barrier that ends the chain's notes (above), or by the instrument's reset at Stop (ADR 0057, 2.14), within ADR 0059's limits for an instrument that refuses releases. A note-on the plug-in writes without ever writing its note-off sounds until the next barrier; Stop is always one.

### 7. Absent, missing, failed and unresponsive stages

1. **Absent passes through.** A hosted stage with no instance (Loading, Slow, Not responding, a creation that returned nothing, a plug-in not installed, or an instance that does not write notes, 2.5) passes its input through unchanged, as ADR 0036 already does for an id the build does not know and as bypass does. Its card names the state; its arrival is a barrier (decision 6). Rejected: muting an absent stage. A muted track gives no sound and no hint that anything is wrong while a session loads; pass-through is the rule the slot already has.
2. **Missing on load (#641).** A session whose MIDI effect slot names a plug-in that is not installed loads with the slot unchanged (id, parameters, state and pages written back on save as read), the stage passing its input through, and a load note naming the plug-in and the track: "<name> (MIDI effect on <track>) is not installed: its input plays through unchanged." The same note path serves #641's unknown built-in ids; `Session::needs()` lists `hosted_midi_effects` when any slot holds a hosted id, so an older build warns instead of passing through silently (ADR 0023). What a hosted *insert* shows today when its creation returns nothing was not read for this record; the slice reuses that slot state if one exists and adds the load note either way.
3. **Not responding.** A creation that runs past the plug-in host's budget shows "Not responding" with Retry (ADR 0018, `SlotLoad::NotResponding`), unchanged; meanwhile the stage is absent (7.1). Editor and state calls that stop responding are handled by the existing host-thread machinery, unchanged. A native `process` call that never returns hangs the audio thread; in-process hosting cannot prevent it (the VST3 host's crate documentation states the same limit for a plug-in that crashes), and this record does not claim otherwise.
4. **A processing error.** A VST3 `process` that returns an error or a CLAP `process` that returns `CLAP_PROCESS_ERROR` (the adapters' `process_errors` count grows during the stage's call; ADR 0059's R1 adds the count to VST3): the stage's output for that block is discarded, a barrier runs, and the stage is **failed until the next Stop**, during which it passes its input through (7.1) and its card and the status line say "<name> on <track> reported a processing error. Its input plays through until you press Stop." This follows ADR 0059's choice for instruments (contained until Stop) with pass-through instead of silence, for the reason in 7.1.

### 8. Session, parameters, automation, presets

1. **Model.** A hosted stage is a `MidiEffectSlot` with the plug-in's id in `plugin`, its state in `state` (base64, as the field was reserved for) and its host-set parameter values in `params`, stored as a hosted insert stores them; `pages` as for any device (ADR 0047). No new field. The state is read and written by the state jobs of [ADR 0025](0025-plug-in-state-jobs-and-preset-containers.md) at save, as for inserts.
2. **Instances through the plan.** A hosted stage's instance is an `InstanceSpec` made off the audio thread by the existing `Handles` path, restored and prepared there, and carried by the plan to the instrument's event state, where `begin` takes it into its stage instead of calling `Builtin::new`. Its slot key is in a reserved range the slice defines (eight keys, one per chain position), disjoint from insert indexes, `INSTRUMENT_SLOT`, `RACK_SLOT` and clip-effect slots, and recognized by `clip_fx_of_slot` as not a clip slot; its `uid` is the slot's `InsertUid`, so a moved stage keeps its instance as a moved insert does. A displaced instance retires like a replaced instrument (back to its host thread through `Hosted`'s drop). Built-ins stay values made in place (ADR 0036's alternative "MIDI effects as plan cells" is taken for hosted stages only, where it was to be revisited).
3. **Parameters and automation.** A hosted stage's parameters are its plug-in's (`PluginInfo::params` of the instance) and are automated exactly as a hosted insert's: each lane point through `set_param_at` at its offset (`send_points`), so automation is sample-placed and the same at every block partition; lanes use the stage's slot 240 + index, as today. Editor edits are reported and written to the session as for hosted inserts. MIDI Learn maps them as for any hosted parameter.
4. **Replace keeps the lanes.** A new command, `mix.midi_effect_replace {track?, index, plugin}`, puts another effect (hosted or built-in) in an existing slot in one undo step, keeping the slot's automation lanes; a lane that names a parameter the new effect lacks stays and is inert, as for a replaced insert (`automation.rs:182` to `190`), and works again if the original plug-in returns. Removing a slot still removes its lanes (`remove_midi_effect`, unchanged). The card's `⋯` menu gains Replace with the same menu as "+".
5. **Presets.** A hosted stage's presets are its plug-in's own preset files (`.vstpreset`, `.clappreset`) through the existing plug-in preset commands (`crates/engine/src/cmd/plugin_presets.rs`), whose slot address gains the MIDI effect positions (`midi1` to `midi8`, the same names the automation lane ids use). ADR 0057's JSON factory and user presets are for built-ins and do not apply (a hosted state is opaque). A preset recall is a state load, so a barrier (decision 6).
6. **Racks.** See decision 10.

### 9. The card, the editor window, the help

1. **Card.** A hosted stage is one card in ADR 0057's card row (K2a), at the shared height: the header every card has (power for bypass, the name, fold, `⋯` with Replace, Presets, Capture MIDI Effect Output, Remove), a button that opens the plug-in's editor window, the macro strip page when the stage has one (ADR 0047), a state line (Loading, Slow, Not responding with Retry, Not installed, Does not write notes, Failed until Stop, each with what passes) and the line "Audio from this plug-in is not used here". No parameter rows: a hosted plug-in's interface is its own window, as for a hosted insert.
2. **Editor.** The plug-in's own editor window through the existing editor machinery (`EditorOpened { track, slot }` with the stage's reserved slot key; ADR 0018, [ADR 0030](0030-editor-window-cohesion.md)), with the same header, not-responding handling and window state as an insert's editor. ADR 0057's decision 14.1 (MIDI effects are cards, not device windows) is about built-in devices' panels and is not changed.
3. **Help.** One help entry for hosted MIDI effects: what qualifies, that output replaces input, that its audio is not used, the drop list (decision 3), pairing (5.6), the barriers (6), pass-through states (7), that a plug-in with internal randomness cannot be made to repeat (decision 10.3), and that its notes stay on its track (decision 11).

### 10. Latency, racks, determinism

1. **Latency.** A hosted stage's reported latency (VST3 `getLatencySamples`, CLAP `latency.get`, already read by the adapters into `Plugin::latency`) enters ADR 0057's MIDI effect latency `L_midi` (decision 7, slice P4) as a stage's requested figure, read when the plan is built. The formats define latency for the plug-in as a whole and give no separate figure for its note output, so the host cannot tell a note generator that delays its notes from a synth whose audio path is late; it takes the plug-in's word. A change of a hosted stage's latency arrives only through a restart (both formats; Context), which is a barrier (decision 6); the new figure is requested at the next plan build and provisioned when that plan is adopted. Unlike a built-in, a hosted plug-in cannot play at its provisioned figure until then (ADR 0057's deferred activation, `set_provisioned_latency`), so between its restart and that adoption the track is compensated for the old figure: a stated limit, normally a few blocks.
2. **Racks: refused until the rack stage.** A rack's chain runs once per member until ADR 0036's rack stage exists (ADR 0057, 15), which for a hosted plug-in would mean one instance per member, each with its own internal state and its own processing cost. The add and replace commands refuse a hosted id on a rack ("Hosted MIDI effects go on an instrument track until racks run one chain for all members"); a session that has one (hand-edited) loads it absent (7.1) with a load note. Reopens with the rack stage, which also serves the reported "one generator, several synths" case without routing (decision 11).
3. **Play equals export, and what the host cannot do.** The host gives a hosted stage the same input, transport and parameter points at the same frames in playback and in an offline render, and re-identifies its output the same way; a plug-in that is a function of those gives the same notes. A plug-in with internal free-running or random state (a generative performer, a random arpeggiator seeded from the clock) can give different notes in every render, every playback and every loop pass, and no host can make it repeat. What the user has for that is **Capture MIDI Effect Output** (ADR 0057, decision 9, unchanged): it renders the range offline and writes what the instrument accepted as an editable MIDI clip on a new track. Two consequences are stated in the help and in Capture's result line when the source chain holds a hosted stage: the captured clip is the notes of the capture's own render, which for such a plug-in is a new performance, not the one heard while playing; and once captured, the clip is fixed and plays the same everywhere, so the way to keep a performance is to capture it and play or bounce the captured track. Recording what the chain plays live, so the heard performance itself can be kept, is a separate feature (Out of scope: it needs the routing record's tap or #330's retrospective capture).

### 11. Destination: the same track now, routing deferred to a named record

**Decision.** In every slice of this record a hosted stage's notes go to the next stage or the instrument of its own track, nowhere else. Routing a track's MIDI chain output to another track's input, or to an external MIDI port, is deferred to its own record, **"MIDI routing between tracks and to external ports"** (to be written; issue to be filed when the maintainer schedules it).

**Why defer.** Ableton and Logic do not agree here (from memory: Live lets a track take another track's post-effect MIDI as its input; Logic has no direct route for MIDI FX output), so there is no common convention to follow and the design is transit's to make. It touches more than this record does: the plan's render order (a destination must render after its source within one block, or the route costs a block and breaks partition independence), cycles, MIDI tracks with no instrument (today the chain is only on instrument tracks and racks; ADR 0036, ADR 0022), external ports and their clocking (ADR 0022, [ADR 0043](0043-hardware-sync-transport-and-clock.md)), and what barriers on the source do at every destination. Settling it inside this record would stall the stage, which is useful on its own track from the first slice.

**What the first slices must not preclude** (constraints for the routing record and for this record's builders).

1. The chain's output after the last stage is a per-block stream of identified events (every note from a hosted stage carries a host id, decision 5) that a second consumer could read without changing what the instrument receives; nothing in these slices may make the stage's output exist only inside the instrument's admission.
2. Ownership stays per hop: a destination will own what it accepted from the route by its own tables, never by the source instrument's.
3. Barriers on the source end the source's notes from the host's tables; nothing here may put a destination's notes in those tables.
4. The tap is after the chain's stages, before the source instrument's admission, so a destination does not depend on the source instrument's refusals; Capture's tap (what the instrument accepted) stays as it is.
5. No interim surface: no "send to track" control, no hidden route, no per-stage destination field in the model before the routing record is accepted. Until then, notes reach another track through Capture MIDI Effect Output (copy the captured clip to the synth's track), by putting the plug-in on the synth's own track, or, once the rack stage lands, by putting it on a rack (10.2).

### 12. Session format, commands, visibility

- `MidiEffectSlot` unchanged (8.1); `Session::needs()` gains `hosted_midi_effects` (7.2). Alpha: no migration of anything; the scan cache's version bump (2.4) is the existing mechanism.
- Commands: `mix.midi_effect` accepts a hosted id whose descriptor qualifies (2.6), refused on a rack (10.2); `mix.midi_effect_replace` (8.4); the existing remove, move, bypass, param and params commands apply unchanged (param addresses a hosted parameter by its id); `engine.midi_effects` lists hosted qualifying plug-ins only after the visibility slice.
- Until slice VH, a hosted id is accepted by the add and replace commands only through the control channel (a preview gate, as ADR 0057's preview table, 12), so tests and the maintainer's hands-on check can use it while no menu shows it.

## Out of scope

- Audio Unit MIDI processors (type `aumi`). The Audio Unit host has no MIDI output path (its MIDI is input only, and it reports no refusal, ADR 0059's R1 owns that), and an AU MIDI processor's output arrives through a callback the host does not register; not trivial, so not here.
- Routing to other tracks and external ports (decision 11's record). Recording what the chain plays live.
- More than one output bus or port per plug-in, and MIDI 2 and system exclusive output.
- Hosted stages on racks (10.2), until ADR 0036's rack stage.
- Per-note expression other than pressure.
- Running a hosted plug-in out of process.

## Consequences

- Any VST3 or CLAP plug-in that declares a note output can feed a track's instrument from the MIDI effect slot, including plug-ins other hosts list as instruments.
- Every note a hosted plug-in writes is re-identified at the stage, so everything downstream pairs exactly; only a plug-in that writes anonymous duplicate note-offs can cut a later note of the same key short, and nothing hangs past the next barrier.
- A scan creates every plug-in class once in the scan child; the first scan of a build with HM0 loads every file again.
- A plug-in in the slot costs its full processing, its audio is discarded, and its reported latency delays the track.
- Restarts and state loads of a hosted stage cut the track's sounding notes, like an edit.
- A missing, loading, failed or silent stage plays its input through, with a note saying so.
- A plug-in with internal randomness is not repeatable; Capture keeps one rendering of it as an editable clip.
- Notes stay on their track until the routing record.

## Alternatives rejected

- **Qualifying by category** (CLAP `note-effect`, a VST3 "Fx" sub-category). Excludes the reported case and every instrument-category note generator; categories are the vendor's label for menus, not a description of buses.
- **Probing the capability only when the plug-in is placed.** The menu could not list what qualifies without creating every plug-in in the app process; the scan child already isolates plug-in start-up.
- **Mixing a hosted stage's audio into the track, or refusing plug-ins with audio outputs.** Mixing makes the slot an instrument by another name and contradicts "before the instrument"; refusing excludes the reported case.
- **Passing input events through around the plug-in.** A generator with its own Thru control would double every note; other hosts give the plug-in's output only (from memory).
- **Trusting the plug-in's pairing (ADR 0057 16.2 as is).** Leaves the duplicate-off hole for identified plug-ins too, and leaves downstream pairing oldest-first.
- **Reusing ADR 0057's kit ledger.** Its anonymous offs close anonymous entries only; the formats' wildcard rule needs an anonymous off to close an identified note.
- **Using the host's carry for out-of-range offsets.** Gives meaning to offsets neither format defines.
- **Calling a hosted plug-in for events between blocks.** Advances its time with no audio time passing.
- **Muting an absent or failed stage.** Silence with no hint while a session loads; pass-through is the slot's existing rule.
- **A per-stage destination field now.** An interim surface the routing record would replace.
- **One instance per rack member.** Independent random states and N times the cost, for a structure the rack stage will replace.

## Choices made without a rule to follow (for the review)

Each is decided above; each is listed so a judge can test it.

1. First output bus or port only, others dropped (decision 3).
2. Out-of-range output offsets clamped, not carried (decision 3).
3. Output replaces input, pedals included (4.2).
4. Hosted stages wait for the next block instead of a between-blocks call (4.6).
5. The stage ledger's wildcard matching, and its own table instead of the kit ledger (5.2, 5.7).
6. Restart and state load are barriers (decision 6).
7. The VST3 `setProcessing` cycle as the stage reset, for MIDI stages only (decision 6).
8. Absent, missing and failed stages pass through rather than mute (decision 7); failed until Stop (7.4).
9. Reported latency taken at its word for a note generator (10.1).
10. Hosted stages refused on racks (10.2).
11. Routing deferred, with Capture and same-track placement as the interim answer (decision 11).
12. The scan probe's `None` hides a plug-in from the MIDI menu instead of listing it unverified (2.4, 2.6).
