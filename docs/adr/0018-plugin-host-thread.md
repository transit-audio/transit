# ADR 0018: A plug-in host thread owns hosted instances; the UI only sends requests

- **Status:** accepted 2026-10-24 (shipped 2026-10-23, #36 #56 #66)
- **Date:** 2026-10-23
- **Reopen when:** a reference plug-in misbehaves because its main thread is not the process main thread on Windows; macOS needs the same guarantee (that needs editors out of process, or a run-loop design); or out-of-process hosting (G-13) is taken up, which replaces the stuck-thread handling below.

## Context

Hosted plug-ins (CLAP, VST3, AU) were created, restored, opened and destroyed on the UI thread. The Player already announces a new instance a frame before making it ("Loading…", `playback/src/player/handles.rs`), but the make itself (module entry, VST3 `createInstance` and `initialize`, CLAP `init` and `activate`, `setState`) is one SDK call that a large sampler can keep for seconds, and the UI is frozen meanwhile. Editor creation (`IPlugView::attached`, `clap_plugin_gui.create`), state reads for Save, and destruction of retired instances also ran there. A plug-in that never returns from `initialize` froze the app for good. The scan is already off-thread (`plugin_scan.rs`, child processes) and stays so.

What each SDK requires of the thread that hosts it:

- **VST3:** the edit controller, its views and the component's `initialize`, `setState`, `setActive` and `terminate` run on the host's "UI thread", which must be one thread per instance and must dispatch window messages for the views. Windows has no process main thread: any thread with a message loop qualifies. On macOS, views are `NSView`s and AppKit requires the process main thread.
- **CLAP:** `[main-thread]` calls go to the thread the host designates as main; `request_callback` must be answered there. GUI embedding on Windows needs that thread to pump messages; on macOS the Cocoa API requires the process main thread.
- **AU:** macOS only; the view and most property calls are main-thread.
- **Module entry and exit** (`InitDll`/`ExitDll`, `bundleEntry`/`bundleExit`) must pair on one thread; Qt-based modules tie their application object to it.

## Decision

1. **One plug-in host thread per process** (`transit-plugin-host`, layer 1 beside the format hosts) owns hosted instances for their whole life: creation, state restore, the editor (open, idle, close), state reads, `restartComponent`/`request_callback` servicing, and destruction. It is the instances' main thread in every SDK's sense; VST3 modules are entered and exited on it. It pumps the OS message queue (Windows: an OLE single-threaded apartment, `MsgWaitForMultipleObjectsEx`, `PeekMessage`/`DispatchMessage`; elsewhere a park with a timeout) between requests, and every 15 ms runs the formats' service calls and each editor's `idle`. The pump is a safe API in `transit-rt` (ADR 0013).
2. **The UI sends requests and polls results; it never waits for a plug-in for more than a frame.** A request is a job on the host thread's queue; the result comes back through a shared slot the UI polls once per frame. The slot shows "Loading…" from the frame the request is announced until the instance is bound. Editor open, close and parameter echo are fire-and-forget; the editor reports open, closed and its edits through shared state the UI reads. Parameter edits and automation keep the existing queues to the audio thread.
3. **Handoff to the audio thread is unchanged.** The host thread returns a finished, prepared `NewInstance`; the control (UI) thread compiles it into a `PreparedPlan` and publishes it through the existing lock-free queue (`playback/src/publication.rs`), adopted at a block boundary. The audio thread does not allocate, lock or wait for anything new: the instance is wrapped in a `Hosted` forwarder (one extra virtual call per method, no allocation; tested with the counting allocator).
4. **Destruction goes back to the host thread.** Dropping the `Hosted` wrapper (on the control thread, when a plan retires it) sends the inner instance to its host thread, which destroys it there. Editor and state handles live on the host thread; the UI holds proxies.
5. **Timeout and the stuck state.** Every request and tick is bounded by 10 s of running time; one window-message dispatch gets 120 s, because a plug-in's modal file dialog or message box runs inside it for as long as the user leaves it open. The session request that needs a new instance waits for it (the active plan keeps playing), so other edits in that request wait too, at most the timeout. When a call runs past its budget, the host thread is declared **wedged**:
   - The creation that ran past the timeout is stuck: the slot reads "Not responding", the status line says so, and the session compiles without that instance (empty, as for a plug-in that fails to load). If the call later returns, that late instance is destroyed on its own thread; re-inserting the plug-in retries. *(Superseded by the issue #82 status update below: a creation has the 120 s budget, a late instance is adopted, and the slot offers Retry.)*
   - A fresh host thread takes over new creations; creations that had not started move to it.
   - While the thread is wedged, the instances on it keep processing audio, but their editors and state reads answer "not responding" at once, and a save keeps their stored states. The status line says their live state is not being saved.
   - **When the call returns, the thread is responsive again** (review B1): its instances' state reads, editors and destruction work as before, and the next save carries their live states. It stays a non-current thread; new creations stay on the fresh one.
   - A thread that never returns is never joined; its instances are leaked rather than destroyed elsewhere.
6. **What still waits.** Reading plug-in states for Save, Save As, autosave and a device reopen waits for the host thread (a modal dialog for at most 500 ms per save; see the status update), bounded by the timeout per wedge (a thread wedged at that moment answers at once with no state, so that plug-in's stored state is kept; once it returns, saves read it again). Shutdown sends one request per live host thread and waits at most 5 s in total; a host thread busy in a plug-in does not hold the exit.
7. **Platforms.** Windows and Linux run the host thread. On Windows the editor's `HWND` is created and its messages are dispatched on the host thread (achieved, not a fallback). **macOS keeps today's behavior** (requests run inline on the UI thread): AppKit requires editors on the process main thread, and VST3 and CLAP require the editor and the instance on the same thread. On Windows the editor window is now created on the host thread with **no owner window**: a cross-thread owner would attach the two threads' input queues and let a hung plug-in hang the UI, so the editor gets its own taskbar button and no longer floats above the main window.
8. **Crashes are out of scope.** A plug-in that crashes (access violation) still takes the process down; containing that is out-of-process hosting (G-13, issue #9).

## Consequences

- Loading a heavy instrument, opening its editor, and removing it leave the UI responsive; a plug-in hung in `initialize` costs one thread, not the session.
- One host thread serializes plug-ins: a slow load delays other plug-ins' editor messages and requests for its duration (not the UI or audio).
- Code that creates instances itself (offline bounce, freeze, stems, tests) still runs on its own thread; it is not routed through the host thread (see the status update below).
- **Status update 2026-10-23 (issue #56).** The review's follow-ups are done, except macOS (section 7):
  - A save no longer waits up to the timeout for a plug-in whose thread is held by a modal dialog. A plug-in that is answering is still waited for, however slowly (up to the request timeout, as before): a slow state read is work, not a hang, and leaving it out would keep a stale state in every save (review B1 of #56). A thread that is wedged, or inside one window message for longer than the request timeout, answers at once. A thread inside a window message longer than 100 ms (`MODAL_AFTER`: a dialog) is waited for at most what is left of one 500 ms deadline per save (`DEFAULT_SAVE_DEADLINE`, `Handles::set_save_deadline`), shared by all its plug-ins; except a plug-in the session holds no state for yet (inserted this session, never captured), which is waited for as if the thread were free, so it is never saved without a state. A plug-in left out keeps its stored state, and the status line names it ("State of X not refreshed: plug-in busy") after a save, a bounce or a device reopen.
  - An instance the compile asks for that staging did not predict (a slot whose layout changed) no longer blocks the UI (`make_now` is gone). The compile submits it to the host thread and leaves the slot vacant, reading "Loading…"; when it is ready, the compiler is asked to make that vacant slot again (`PlanCompiler::retry_vacant`) and the same document is requested again, as a latency refresh is, so the next plan takes it. The active plan keeps playing and the slot is silent meanwhile. Where the host runs inline (macOS) it is made in the compile, as before.
  - The host thread drops its job queue before its message queue (the COM apartment) ends, so a destroy job sent at exit is leaked, never run after it. The stuck check names the busy section it found overdue, so a call that returns while it is being marked never leaves an idle thread wedged or starts a takeover thread for it.
  - VST3 modules are entered outside the loaded-module lock (K38, closed): a hung module entry holds back loads of its own binary only. Both registries build a type's description outside their lock.
  - A command that needs the parameter table of a type never made (`mix.insert_param`) reads it on the host thread and waits at most 500 ms; past that the command is refused as still loading and the read carries on, so a retry finds it. Adding a plug-in that needs its description (`mix.insert` or `mix.instrument` with parameter values, or a type the scan does not list) reads it on the host thread too, but waits up to the request timeout, as the command did when it instantiated the plug-in itself.
- **Status update 2026-10-24 (issue #82, escape E48).** On a heavily loaded machine NI Battery 4 and Kontakt 7 were made 300 ms and 70 ms after the 10 s creation wait, and both were discarded: the wait that decides what a slot displays was also an abandonment deadline. Now:
  - **A late instance is adopted, never discarded.** A creation (`Host::submit`) runs on its own budget, `Config::creation_timeout` (120 s, the dispatch budget), not the 10 s request timeout. `Status::Stuck` is no longer final: a job that returns after it reads `Ready` on a later poll.
  - **The 10 s only decides what the slot shows** (`DEFAULT_SLOW_AFTER` in `playback/src/player/handles.rs`). The session request waits for a new instance at most that long; then it compiles with the slot vacant, the slot reads "Loading… (slow) N s", and when the instance is made it joins the next plan through the vacant-slot path (`PlanCompiler::retry_vacant` and the republish), with its stored state restored as at any creation. The log says "slow to load, still waiting" (warning) and later "loaded after N s" (info).
  - **Only the wedge reads "Not responding".** A creation past the creation budget wedges its thread as in section 5; the slot reads "Not responding" and keeps waiting for it, so a creation that still returns is adopted.
  - **Queued creations do not wait behind a slow one.** Once a creation has run past the request timeout, the creations queued behind it move to a fresh host thread, which becomes current; the slow thread is not marked wedged and keeps its instances.
  - **Retry.** A "Not responding" slot (device card and mixer insert row) has a retry button (a circular arrow painted with the theme tokens) beside the text and a "Retry" context-menu entry; the status line names the plug-in and offers "Retry all" when more than one slot is not responding. They run `plugin.retry` {track, slot} and `plugin.retry_all`, which are not document changes (no undo step): the creation starts again on the host's current (responsive) thread from the session's spec, so the state the session stores (#56) is restored. The abandoned creation, if it ever returns, is destroyed on its own thread.
- **Offline renders stay where they are.** Bounce, stems and freeze build a `RangeRender` synchronously in the command (`engine/src/io/bounce.rs`, `io/paths.rs`, `cmd/freeze.rs`) on the calling thread, which then makes, processes and destroys every instance; no editor is opened for them, so the one-thread-per-instance rule holds. Routing their creation through the host thread with a blocking wait would not free the calling thread (it waits as long), and it would tie the render to the live host thread: a plug-in's modal dialog there (up to the 120 s dispatch budget) or a wedged thread would make the render give up on its instances and write audio without them, where today it renders correctly. Making it asynchronous needs a "preparing" phase, polled per frame, in the bounce, stems and freeze jobs; that is left for when one of those jobs needs it.
- New `unsafe` (the message pump) is in `transit-rt`, which needs the ADR 0009 quoted-unsafe review before merge.

## Amendment 2026-10-25 (issue #104, escape E56): shutdown on every way out

A GPU power-state change lost the graphics device; egui-wgpu panicked on the UI thread, the panic unwound out of the event loop without the quit order, and the C runtime's exit hung in an instrument's DLL unload, which waited for a worker thread the exit had already killed. Section 6 assumed shutdown runs only at a normal quit. It now runs on every way out of the UI loop:

- **One quit order** (`StudioApp::shut_down`): autosave, close the input, drop the player and its instances, then shut plug-in hosting down (this ADR's 5 s host-thread wait, then the VST3 module exits on the main thread). The quit, a lost graphics device (wgpu's device-lost callback, checked at the start of each frame) and a panic on the UI thread (the app is dropped while the panic unwinds; `main` catches it around `eframe::run_native`) all run it once.
- **Bounded.** It runs under a watchdog (`soundcraft_engine::emergency::run_bounded`, 15 s); past that the process is terminated. A watchdog that fires during the autosave (a plug-in state capture that hangs) cuts that autosave short. That is accepted: the autosaver writes the session within a second of every change, so the previous autosave and the last save stand and at most the newest plug-in state is lost, where waiting longer would bring back the unbounded hang. The closing message says changes were kept in the autosave only when one was written. The message box stays up for at most 5 s (none on macOS, where it needs the main thread this path holds; the log line is always written).
- **CLAP is not covered** (K85): CLAP binaries are never deinitialized at exit and are not counted as not exited.
- **How the process ends.** `shutdown_plugin_hosts` reports whether the shutdown was clean: the host thread ended in time and no VST3 binary is left without its module exit (`soundcraft_vst3_host::modules_not_exited`). Only then does the process exit normally. Otherwise it is terminated without exit handlers or DLL unload code (`transit_rt::terminate_process`), so plug-in static destructors never run against threads the exit has killed. A lost device or a panic ends the process after the shutdown (exit codes 70 clean, 71 terminated, 72 watchdog) with a message to the user; the device is not re-created (K69).

## Amendment 2026-10-29 (issue #205): a stuck call is named, nothing is serviced inside a call, and the user can give up

Guitar Rig 7 stopped returning while its editor browsed presets: the host thread was inside the plug-in (a window message for its editor), Windows ghosted the editor, audio went on, the autosave kept the stored state, and the watchdog's log line named neither the plug-in nor the call. The only way out the user had was End Task on the ghost, which ends transit because the window belongs to it. What the single host thread now guarantees, and what it does not:

- **A stuck call is named.** Every busy section of a host thread carries the plug-in and the call it runs (`transit_plugin_host::Busy`): a creation names its plug-in from the session's id (`Ctx::name_job`), a request for an instance names that instance and the call (opening its editor, reading its state, a preset save or load, destroying it), a window-message dispatch names the plug-ins whose editors are open, and a tick names each editor idle in turn. The watchdog logs the plug-in and the call when a section first runs past its budget and every 60 s while it stays stuck, until the user gives up on it (one last "given up" line); `Host::stuck` lists the stuck calls, and Copy diagnostics has a Plug-in host section with one line per stuck call (`Plug-in host: Guitar Rig 7 stuck in a window message (its editor or a dialog it opened) for 240 s`).
- **No servicing inside a call into plug-in code.** The host thread enters a host-call scope (`transit_dsp::host_call`) around every creation, request and window-message dispatch, inline jobs included. VST3 `restartComponent` servicing, CLAP `request_restart`, `request_callback` and parameter-rescan servicing, both formats' editor `idle` and the host thread's tick leave their requests for the next idle while a call is on the thread's stack, and count the deferral (in the report). The scope is per thread, not per instance: two instances of one plug-in often share its library's locks. Today the tick runs only between sections and the formats' host callbacks only record flags, so no nested servicing happens now; the scope closes the path a plug-in call that pumps the message loop would open if anything ever services from a window message.
- **Give up.** While a host thread is stuck, the main window shows a message naming the plug-in and the call: audio keeps playing; a save keeps that plug-in's stored state (its changes since its last state read are not saved); End Task on its window ends transit. It offers Save now, **Give up on <plug-in>** (the label counts the other plug-ins on its thread, which Give up quarantines too) and Later (the message comes back at the next relog, 60 s later, or for another stuck call). Give up (`Host::give_up`) does, on every platform: the stuck thread is quarantined the way a hung render worker is (K89): it is never sent a job again, so its plug-ins are never called, freed or reused by transit again, even if the call returns (requests for them fail at once, dropping them leaks them, and a creation that returns on it is not delivered); it no longer counts as not responding; new plug-ins already load on the fresh thread that took over when it wedged. Their instances stay in the plan and keep processing on the audio thread, so their audio keeps playing, and saves keep their stored state until transit restarts and creates them again. On Windows it also asks the stuck thread's top-level windows to hide (`transit_rt::editor_window::hide_thread_windows`: `EnumThreadWindows` and `ShowWindowAsync`, which never wait for the owning thread). It does not and cannot: stop, kill or join the thread; destroy its windows (`DestroyWindow` refuses a window of another thread; `ShowWindow` and `SetParent` would wait for the hung thread); or remove the ghost Windows draws in place of a window whose thread does not retrieve messages. The hide takes effect when the thread next retrieves messages (a plug-in's own modal loop that still pumps, or the call returning). If the call does return, the thread parks: it hides its windows, keeps every plug-in object it held (leaked), never runs a job again and only retrieves window messages until the process exits, so its hidden windows never ghost. Linux hosts no editor windows yet and macOS runs inline (section 7), so there the window part does nothing.
- **Not done here.** The mixer insert row, device card and arrange header do not mark a live plug-in whose host thread is stuck or given up as unresponsive yet (the creation's "Not responding" stays as it was); that marker is shared with #190's hung render worker and is a follow-up. A process-wide `DisableProcessWindowsGhosting` would remove the ghost's End Task path but also the main window's; not adopted without a decision.

## Alternatives rejected

- **Keep creation on the UI thread and only defer by a frame** (the current mitigation): the call still blocks for its full duration.
- **A host thread per format:** no format requires it, it doubles the threads that need a message loop, and the module-thread rule is easier with one.
- **Editors as children of an egui viewport on the UI thread:** keeps the UI thread exposed to every plug-in's view code and needs a cross-thread parent, which attaches input queues.
- **Out-of-process hosting:** the real fix for crashes, much larger; left to G-13.
