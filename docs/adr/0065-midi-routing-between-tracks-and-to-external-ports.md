# ADR 0065: MIDI routing between tracks and to external ports

- **Status:** proposed 2026-11-27 (the record ADR 0064 decision 11 names as its next record; builds on ADR 0057, ADR 0059 and ADR 0064, all accepted; revised after judging round 1 the same day, Changed during review; four product choices decided 2026-11-27 by delegation, each marked where it is written and listed under For the maintainer to confirm or overturn).
- **Date:** 2026-11-27
- **Implementation:** not started. Slice cards in the Slices section; a contributor can take any slice whose needs have landed.
- **Reopen when:** a destination needs more than one routed source (fan-in, decision 1.4); a tap before the chain or after a given stage is wanted (decision 1.2); a plug-in that writes several note outputs meant for several destinations is supported (ADR 0064 decision 3 reads one); ADR 0036's rack stage lands (racks as sources and destinations, decision 1.5); the MIDI effect chain runs on an external output (ADR 0057, Where this goes), which would let an External Instrument track or a track with an external output be a source; ADR 0043's clock sending is built and a route is asked to carry clock; the alignment stage (decision 4) or a route recovery barrier (decision 3.4) is measured happening in ordinary use; a route's same-block ordering is measured costing more render time than a block can afford; or Ableton Live and Logic Pro are found, in their documentation, to agree on a behavior this record chose differently.

## Context

**The request.** Issue #671's reporting user has a note-writing plug-in (a generative chord performer with no sound of its own) on one track and wants its notes to drive synths on other tracks, and eventually external MIDI gear. ADR 0064 delivers a hosted MIDI effect's notes only to its own track's instrument (decision 11) and names this record as the next one. Its decision 11 sets the constraints this record keeps: the chain's output after its last stage is a per-block stream a second consumer can read without changing what the source instrument receives, and it is not fully identified (bypassed hosted stages pass their input's identities, built-in generators write anonymous notes), so a route must qualify identities by source; ownership stays per hop, a destination owning what it accepted by its own tables; a source barrier must reach every destination; admission at a destination is bounded; the tap is before the source instrument's admission. The record is written for whole classes of note source (hosted stages, built-in devices, clips and live input passing an empty chain) and is not designed around any reported plug-in.

**What the code does today** (verified against code on the branch carrying ADR 0064, head 4ca4f772; line numbers are that tree's).

- **A track's MIDI input** is `Track::midi_input: MidiInput { port: MidiPort, channel: Option<u8> }`, `MidiPort` one of `All` (the default), `None` or `Device { backend, name, ordinal, id }` (`crates/model/src/midi_input.rs:6` to `26`; `crates/model/src/track.rs:243`), set by `midi.input`, which refuses kinds other than MIDI and instrument tracks (`crates/engine/src/cmd/midi_input.rs:49` to `88`). The only chooser is the mixer strip's input row (`crates/ui-studio/src/mixer/channel.rs:262` to `295`, `crates/ui-studio/src/midi_input.rs:127` to `182`). The #760 "MIDI handoff" carries open MIDI inputs across an audio reopen (`crates/playback/src/player/device/midi_handoff_api.rs`); it does not choose inputs.
- **Monitoring.** Record Enable and Input Monitoring are runtime state, "never saved, and false whenever a session is opened ..., so opening a session never activates an input path" (`crates/model/src/mixer.rs:691` to `697`); undo and redo never change them (`keep_runtime_state`, `crates/engine/src/lib.rs:730` to `745`). For **MIDI**, playback opens a live hardware route to an instrument or MIDI track while it is active and armed **or** monitored, whether the transport plays, records or is stopped (`crates/playback/src/player/native.rs:582`); Audio > Monitor Armed Tracks does not enter that rule. For **audio**, a track hears its input with Input Monitoring on, or while armed when Monitor Armed Tracks is on and the transport records or the engine is monitor-only (`hears_input`, `crates/mix/src/strip.rs:86`; the preference's help, `crates/engine/src/cmd/options.rs:89`). The Input Monitoring button is enabled in the mixer and the arranger only for audio tracks and racks (`crates/ui-studio/src/mixer/channel.rs:409`, `crates/ui-studio/src/arrange/tracks.rs:150`); the `mix.input_monitor` command itself has no kind check (`crates/engine/src/cmd/mix.rs:52` to `61`). So today an instrument track's keyboard is heard while the track is armed, during playback as well as recording, and the track's clips play at the same time.
- **The mix's note table, per instrument,** matches by source: `Source { port: u16, channel: u8, generation: u64 }`, with reserved ports `Source::UI` and `Source::CLIP` (`crates/mix/src/events.rs:101` to `112`), and "Matching includes the whole source, then the sender id when there is one, else the key" (`NoteEntry::matches`, `:456` to `459`). It holds 224 notes and 32 pedals (`:376` to `381`), assigns every note a voice id of its own (`:27` to `28`), coalesces a same-source same-key re-strike (`:15` to `16`), releases everything one source generation holds with `release_sender` (`:1040` onward), and is the single exit to the chain or the instrument (`send`, `:811` to `821`). `release_sender` delivers its releases through `send`, so with an active chain they enter the chain's first stage. Clip events reach the table directly in the block, merged in time order with queued live events, "at a tie, chase and clips precede live events" (`crates/mix/src/midi.rs:199` to `209`).
- **The chain lives in the instrument's event state.** In a strip: `fx.begin`, retries, clip scheduling interleaved with earlier live events, `deliver`, `fx.flush`, then the instrument's `process` (`crates/mix/src/strip.rs:164` to `194`). The event state exists only for an instrument cell (`crates/mix/src/compile.rs:961` to `963`); an empty instrument slot, a MIDI track and an External Instrument have no cell (`crates/mix/src/instance.rs:67` to `78`), so no chain runs and no live route binds there (`native.rs:599`). A hosted instrument on a track with an external MIDI output still renders and gets note-offs only (`strip.rs:173` to `186`).
- **Render order and loops.** The route graph has edges Output, Send, Input and Key (`crates/model/src/route_graph.rs:39` to `49`). Commands refuse an edit that closes a loop (L22: `refuse_loop`, `crates/engine/src/cmd/track.rs:908` to `915`; backstop `Engine::validate_edit`, `crates/engine/src/lib.rs:911` to `918`). A loaded loop is cut by `RouteScratch::solve` (`route_graph.rs:442` to `534`): per round, in each strongly connected component, the edges into the bus that is the input of the component's first track (lowest track index, `:427` to `434`), else the Key edges into that first track; Key cuts are reported as dropped (`:529`). Phase-1 strips render in layers by depth (`crates/mix/src/compile.rs:322` to `351`): serially, one `run_strips` per layer (`crates/mix/src/active.rs:600` to `632`), or through the render workers' task graph with an edge from every key source in an earlier layer (`crates/mix/src/graph.rs:269`), where a missed source skips its dependents.
- **Delay compensation is audio only** (`head_latency`, `strip.rs:523` to `527`; `route_into`, `crates/mix/src/routing.rs:75` to `200`). ADR 0057 decision 7 (slice P4) adds `L_midi`, keeping a requested figure for planning and a provisioned figure for rendering.
- **Mute does not stop a strip.** `strip.muted` comes from mute, mute automation, a VCA and solo (`strip.rs:323` to `362`, solo at `:326`) and sets the fader to -144 dB (`:362`); the instrument is processed regardless (`:194`). External clip delivery suppresses non-release messages of a muted or solo-excluded track and lets releases pass (`crates/playback/src/player/audio/external.rs:190` onward).
- **Freeze** turns a frozen track into an audio track with no instrument in the plan (`crates/model/src/session.rs:558` to `582`). The freeze render keeps a frozen track's sidechain key feeders running (`key_feeders`, `crates/mix/src/offline.rs:303` to `370`). Freezing an External Instrument track is refused (known issue K64; `refuse_offline_print`).
- **External MIDI output** (ADR 0022): `Track::midi_output: Internal | External { port, channel, offset_ms }`. External clip events come from a traversal of the clips (`crates/mix/src/external_midi.rs:52` to `70`), stamped on the audio thread with the presentation time of their frame at the current speed (`crates/playback/src/player/audio/external.rs`), into a playback ring of 4,096 slots whose push can refuse even a release when the ring is full (`Producer::push`, `crates/playback/src/player/midi_out.rs:115` to `128`). The output thread keeps each track's held notes and the sustain pedal (CC 64) only (`:1015` onward), sends at Stop and panic a note-off per held key, CC 64 off and CC 123 (`:1153` to `1170`), and ends a destination's held playback notes at a loop wrap or locate (`:925` to `944`). The echo path rejects stale events by a route generation (`:130` onward). No MIDI clock is sent; ADR 0043's clock is not built.
- **MIDI output across an audio reopen.** On this branch the replacement output thread reopens the ports (`crates/playback/src/player/native/handoff.rs:95` to `147`); unlanded work carries them across instead (decision 7.7).
- **Recording** captures on the audio thread every live packet the mix buffered for an armed track while recording or counting in, at the output frame it was given (`crates/playback/src/player/audio.rs:996` to `1014`): hardware input before the chain, refused or not.
- **Cross-track references** are stored by `TrackId`; a key naming a missing track is inert. A session with an unknown field loads in an older build with the field dropped; an unknown enum variant fails the load (`Session::from_json`, `session.rs:781` to `792`).

**What other hosts document.** Ableton documents a destination track taking "MIDI From" another track and choosing the plug-in as the source ([Accessing the MIDI output of a VST plug-in](https://help.ableton.com/hc/en-us/articles/209070189-Accessing-the-MIDI-output-of-a-VST-plug-in); the page blocks automated reading and is cited for that claim only). Both reference workstations document that a track receiving internally routed MIDI is heard through its monitoring: Ableton's routing chapter describes a track's monitoring of its input ([Routing and I/O](https://www.ableton.com/en/manual/routing-and-i-o/)), and Logic's guide to internal MIDI routing tells the user to turn on Input Monitoring to hear the receiving track or Record Enable to record it ([Route MIDI internally](https://support.apple.com/en-ng/guide/logicpro/lgcp1efa7c4d/mac)). Those pages are cited for those monitoring claims only. No other decision rests on another host's behavior.

## Changed during review (judging round 1, 2026-11-27)

- Routed input follows the destination's monitoring instead of always sounding; a routed destination's Input Monitoring is saved with the route, and export renders monitored routes only (decision 5; P1 and P2).
- A route barrier is defined at the receiving chain: at a destination with an active MIDI effect it is a full chain barrier, propagated downstream (3.3).
- Every new boundary has bounded ownership and an automatic recovery barrier, detected by a monotonic epoch and sequence comparison (3.4); external buffers report refusal and retain releases (7.3).
- A route latency change is a route barrier; requested and provisioned figures are kept apart (4.3).
- The loop cut is extended to MIDI edges with a fixed priority (2.1).
- Source mute stops its routed output; destination mute works on external destinations (decision 6; P3).
- Deleting a source leaves its destinations disconnected (6.6; P4).
- Sinks: an empty instrument slot gets a silent sink; an external destination gets a route outlet beside any instrument (2.5).
- Recording is input recording at musical position; freeze is scoped to internal destinations; the output thread revokes scheduled route starts and tracks every pedal kind (5.5, 6.3, 7.4).

## Decision

### 1. The model

1. **What is routed: the chain's output after its last stage.** The **tap** of a track is the stream its MIDI effect host offers the instrument after the last stage, before the host's delivery filter and the instrument's admission (ADR 0057 P3b; ADR 0064 11.4): with stages, what the last stage's output buffer accepted; with no stage, the stream the mix's note table sends (the track's clips, live input, chase and seek releases). The tap does not depend on what the source instrument accepts or refuses, and reading it changes nothing the source instrument receives.
2. **No tap before the chain or per stage.** Out of scope: a destination that wants the source's raw input can take the same hardware input; a per-stage tap would put a destination inside every stage's edit and barrier rules.
3. **The choice lives on the destination.** A **route** goes from one source track to one destination track; the destination's MIDI input is either a hardware choice (today's `midi_input`) or one source track. That is the workflow Ableton documents (Context), and it keeps one rule for a track's input: one input, one channel filter, one monitoring state.
4. **One source per destination, any number of destinations per source.** Fan-in is out of scope. A source never admits on a destination's behalf: each destination reads the source's fixed tap (2.3) and admits by its own tables (decision 3), so fan-out multiplies no storage at the source; each destination's admission work is its own.
5. **Which tracks.**
   - **A source** is an instrument track that is not a rack, whose `midi_output` is `Internal`, whose instrument slot is not an External Instrument and which is not frozen; its instrument slot may be empty (2.5). Not sources: MIDI tracks (no chain, ADR 0036), tracks with an external output or an External Instrument (the chain does not run on an external output; ADR 0057, Where this goes), racks (the rack's chain runs once per member until ADR 0036's rack stage), and every other kind.
   - **A destination** is an instrument track that is not a rack (any instrument slot: hosted, built-in, empty or an External Instrument) or a MIDI track whose `midi_output` is `External`. A destination whose `midi_output` is `External` is an **external destination** (decision 7); every other one is an **internal destination**, which plays routed notes through its own chain and instrument.
   - A track is never its own source. A track may be both a source and a destination (a chain of routes); it then follows both sets of rules, and the freeze prohibition of a source (6.3).
6. **Session field.** `Track::midi_from: Option<MidiFrom>`, `MidiFrom { track: TrackId, monitor: bool }`, `#[serde(default, skip_serializing_if = "Option::is_none")]`, `monitor` defaulting to false. While it is `Some`, the track's hardware choice in `midi_input.port` is kept and not used (playback opens no hardware route for the track); `monitor` is the destination's Input Monitoring (decision 5.2). A separate field, not a `MidiPort` variant, because an older build fails to load an unknown enum variant and loads an unknown field (Context), which the `needs` marker warns about (decision 8).
7. **Commands.** `midi.input` gains `from`: a track id sets the route (keeping `monitor` from the track's current Input Monitoring); `null` clears it and the track takes its kept hardware choice again; a `port` given in the same call clears the route and sets that port instead (one undo step either way). Refused, with the reason, before any change: a source or destination outside 1.5 ("<track> cannot send MIDI to other tracks: <reason>", the reason one of "it is a MIDI track", "it sends to an external port", "it holds an External Instrument", "it is a rack", "it is frozen"; "<track> cannot take MIDI from another track: <reason>"); the destination itself; a route that would close a loop with any edge of the route graph (`refuse_loop`'s wording, "that route would create a routing loop: Bass → Keys → Bass").
8. **The channel filter.** `midi_input.channel` gates the routed **starts and other non-release events** (a generator writing bass on channel 2 can drive a bass track filtered to channel 2); routed note-offs and pedal-ups always reach the destination's table, which consumes those that match nothing. So changing the filter needs no ownership transition: notes admitted before the change still get their releases.

### 2. Timing: same block, after the source

1. **A route is an edge of the route graph, and the loop cut is extended.** `EdgeKind::Midi` goes from the source track to the destination track; depth gains the MIDI edges, so a destination renders in a later layer than its source. An edit that closes a loop through any mix of edge kinds is refused (L22, 1.7). For a loaded loop, `solve`'s rounds become: in each component of more than one node, cut (a) the edges into the bus that is the input of the component's first track, else (b) the Key edges into the first track, else (c) the MIDI edges into the first track, where "first" is the lowest track index in `Session::tracks` (not the lowest `TrackId`), as today. Every track in a loop receives from inside it through a bus input, a key or a MIDI route, so each round cuts at least one edge and the rounds end. Exact cuts: a pure MIDI loop Keys → Bass → Keys with Keys at index 2 and Bass at index 5 cuts the route into Keys (Bass → Keys); a MIDI and key loop (a route Keys → Bass, a key from Bass into an insert on Keys) cuts the key, so the route survives (a disabled key detects on its own input and still sounds; a disabled route silences its destination); a loop through a bus keeps today's cut of the bus input. A cut MIDI edge is reported as dropped like a cut key, the route is inert, and the load note names it: "MIDI from Bass to Keys is disabled: it made a loop (Keys → Bass → Keys)." Key-only and bus loops cut exactly as today.
2. **Same-block delivery with exact offsets.** A destination renders after its source in the same block and receives the source's tap for that block at its offsets. Rejected: one block later (a delay that depends on the block size, so play would not equal export at another buffer). The render paths follow ADR 0015 decision 4: the serial path runs layer after layer; a plan with a route renders through the task graph as a keyed plan does (`strip_graph` gains the MIDI edges), where ready tasks are published and no worker waits on a prerequisite; long chains of routes reduce parallelism and can miss a deadline, which decision 3.4 recovers from. The offline renderer is the same renderer.
3. **The tap.** Each source's event state keeps a fixed tap of 512 events (ADR 0057's per-block chain bound), a monotonic **tap epoch** (u64), and a **sequence** (u64, the count of events the tap has been offered since the event state was made, kept or not); per block it records the sequence at the block's start and the number of events it kept. It is written as the host offers events to the instrument, and read-only to destinations once the source's layer has finished (the key views' borrow). Events the host runs between blocks (ADR 0057 P2's call in which no time passes) are kept in the same buffer and reach destinations at offset 0 of the next block, ahead of its events. The tap epoch increases at every host barrier of the source and at the end of any block in which the tap could not keep an event it was offered (above ADR 0057's bound; counted, `tap_overflow`).
4. **Track order and cycles.** Decided by 2.1: never a run-time order between a destination and its source.
5. **Sinks and outlets.**
   - **Silent sink.** A source or internal destination whose instrument slot is empty gets a plan-only instrument cell holding a built-in sink plug-in that accepts every event, renders silence and reports no latency. With it the event state, the note table, the chain and the live binding exist exactly as for any instrument cell. It is made only where the track has no instrument cell; it never replaces one. Its id is reserved for the plan, never stored in a session or listed in a menu.
   - **Route outlet.** An external destination gets a route outlet: a note table of the same type, with no chain, whose output is written to the strip's external buffer (decision 7) instead of a plug-in. It is made beside the track's instrument cell when there is one (a hosted instrument on a track sending to a port keeps rendering and keeps getting note-offs only, exactly as today) and alone when there is none (a bare MIDI track, an External Instrument track).

### 3. Note ownership across a route

1. **Routed notes enter the destination's table as a source of their own.** A new reserved port, `Source::ROUTE`, with `generation` the destination's **route generation**: a per-destination u64 counter, starting at 1 when the destination is made in the plan and increased by one at every route barrier there (3.3); it never wraps in practice (2⁶⁴ barriers) and is never reused, so no packing is needed and an unchanged-plan adoption keeps it (it travels with the event state). Matching is the table's: the whole source, then the note id when there is one, else the key (Context), so a routed note never matches the destination's clip, live or audition notes, and a release from before a route barrier never matches a note after it. Same-key anonymous routed notes keep the table's existing re-strike coalescing (a second note-on of an open key re-strikes it). Routed events are given to the table in the block, merged in time order with the destination's other events; at one offset: the chase, clips, routed events, then live events, each stream keeping its own order, pedal and note ties included.
2. **Bounded admission and refusal.** Routed starts use the table's ordinary admission: a note-on needs a free note entry (224), a pedal press a free pedal entry (32); releases are reserved (ADR 0059 below the table). Routed events reach the table directly in the block, as clip events do, so the queue's non-release quota does not apply; past the table, the destination's chain input admits by ADR 0057 P3b. A refused start is counted per destination by cause (`route_refused_notes`, `route_refused_pedals`, `route_refused_downstream`, in `EventStatus` and the diagnostics report), its release is consumed, and nothing else changes. The destination's input label shows the total since the last Stop ("From Keys · 12 refused"), and its tip names the causes: "Bass refused 12 notes from Keys: 10 because 224 notes were already held, 2 because its MIDI effects' input was full."
3. **The route barrier.** Every way a route stops delivering is a **route barrier** at the destination, applied at offset 0 of the block in which the destination observes it, before that block's routed events:
   - **At an internal destination with at least one active (unbypassed) MIDI effect stage:** a chain barrier of the destination, exactly ADR 0057's edit barrier and ADR 0064 decision 6 (every note the host delivered ended from its `out` table, every pedal the instrument holds released and none pressed again, every stage reset, a new epoch), followed by `release_sender` of the route's generation in the table, whose releases reach the host after its epoch change and are swallowed there as old-epoch entries, so nothing is sent twice; then the route generation increases. **This also ends the destination's own notes** (clips, audition) at that moment, because a transforming stage can latch, delay or replace its input and no table can tell which of its outputs came from the route.
   - **At an internal destination with no active stage:** `release_sender` of the route's generation only (its releases go straight to the instrument, nothing can transform them), then the generation increases. The destination's own notes are untouched.
   - **At an external destination:** `release_sender` in the route outlet, then the generation increases, and the output-thread revocation of 7.4.
   - **Downstream.** A route barrier at a destination with an active stage is a host barrier of that destination, so it raises its tap epoch, and every track routed from it applies a route barrier in turn; with no active stage, the destination's released notes leave through its tap as ordinary note-offs and pedal-ups, which its own destinations match exactly. Deleting A in A → B → C therefore reaches C either way.
4. **What raises a route barrier.** At the destination's next rendered block, it compares what it last consumed (the source's cell identity, the tap epoch, and the sequence at the end of the block it read) with what the source's tap now shows, and applies a route barrier when any of these holds; the comparison is of monotonic state, so a destination that missed blocks or a one-block flag still sees it:
   - the route is set, changed or cleared, or its source is deleted, replaced by another cell or absent from the plan;
   - the tap epoch differs: a host barrier of the source (a chain edit or bypass, Stop, the end of a play range, the All MIDI Notes Off action, P3b's safety reset, ADR 0064's barriers: an instance arriving or leaving, a lifecycle generation change, a silent state, a failing block; the source instrument's failure containment, which runs its host's panic), or a tap overflow (2.3);
   - the sequence at the start of the block it reads differs from what it consumed: the destination missed a block of the source with events in it (a render deadline, a skipped strip), so a release may have been lost;
   - the route's delivery gate closes: the source is muted (6.1), inactive or frozen, or the destination's monitoring of the route turns off (5.2);
   - the provisioned route latency changes (4.3);
   - the route was cut as part of a loaded loop (2.1).
   A route that is gated off delivers nothing until the gate opens; when it opens, delivery starts with the tap's next events (a note already sounding at the source is not delivered, and its later release matches nothing and is consumed). With this, every note a destination accepted from a route is ended by its own release, by Stop, or by a route barrier at most one rendered block of the destination after the release was lost, while the host keeps executing; no manual action is needed.
5. **What does not end routed notes.** A destination's own chain edit ends them as it ends every note of its chain (ADR 0057 2.13). Solo on either track, a parameter change, a change of the channel filter (1.8) and an unchanged-plan adoption end nothing.

### 4. Latency compensation across a route (slice MR4)

1. **The figures.** For every track, `L_out = L_in + L_midi`, where `L_in` is its source's `L_out` when it takes a route, else 0. Two figures are kept, as ADR 0057 decision 7 keeps them: the **requested** recursive figure (from each stage's reported latency), which planning and storage sizing use; and the **provisioned** recursive figure (from each stage's provisioned latency, set when the plan that compensates it is adopted), which rendering, the alignment stage, runtime compensation, key alignment and external stamps use. A routed event at the destination's render frame `f` belongs to timeline frame `f − L_in` (provisioned). The source instrument's audio latency is never part of a route.
2. **An internal destination.** Its compensation latency becomes `L_in + L_midi + head + inserts`, `L_in` entering wherever P4 enters `L_midi` (planning, storage sizing, key alignment, the runtime observer, freeze, the offline render) and never the note readers' alignment. Its own events (clips, the chase, edit and seek releases, audition) pass an **alignment stage** that delays them by exactly `L_in` render frames before its chain; routed events do not pass it. The stage is host code at the head of the destination's MIDI host, present only while the provisioned `L_in > 0`, with a fixed schedule of 1,024 events: a note-on or a pedal press is admitted only with room for its release, which is reserved; another event while the schedule holds fewer than 768; a refusal is a refusal of the chain's input (ADR 0057 P3b), which the table already handles. Pending events are delayed across loop wraps and locates alike, as a delay line; a host barrier of the destination cancels pending starts with their reserved releases (the host has ended every note it delivered). Rejected: reporting `L_in` without aligning (own clips early by `L_in`); not compensating (routed notes late by `L_in`); reading the destination's clips `L_in` earlier on the timeline (wrong across a loop wrap).
3. **A change of the provisioned route latency is a route barrier.** At the adoption that changes a destination's provisioned `L_in`, at offset 0: the alignment stage's pending starts are cancelled with their reserved releases, the route barrier of 3.3 runs (which, with or without stages, ends every note and pedal the destination delivered from its own events and its route), then the new delay applies to later events, and at 0 the stage is removed. Nothing is reordered: no release can wait behind a delay its start no longer has. Example: with `L_in` 100, an own note-on at frame 0 waits until 100; at frame 10 a plan with `L_in` 0 is adopted; the note-on is cancelled with its release at 10, and the note-off the clip writes at 20 matches nothing and is consumed. The control shows the new value at once; the sound follows at adoption (ADR 0057 decision 7). Cost, stated: a route latency change cuts the destination's notes, as a chain edit does.
4. **External destinations** align by their stamps, with no stage (7.5).
5. **Before P4** every `L_midi` is 0, so every `L_in` is 0 and MR1 to MR3 need none of this. A hosted stage's reported latency may describe its audio rather than its notes (ADR 0064 10.1); the destination inherits that error, and the help says so.

### 5. Monitoring, recording and the destination's own chain

1. **Routed input follows the destination's monitoring, exactly as its hardware MIDI input does (Decided 2026-11-27 by delegation).** Both reference workstations document hearing a track that receives internally routed MIDI through its monitoring, and recording it through Record Enable (Context). transit's rule for hardware MIDI input today is that an instrument or MIDI track hears it while it is active and armed or Input Monitoring is on, playing, recording or stopped, and Monitor Armed Tracks does not apply to MIDI (Context). For a routed destination:
   - **Heard:** while the destination is active and Record Enable or Input Monitoring is on, whether the transport plays, records or is stopped. Monitor Armed Tracks does not apply, as for hardware MIDI. With both off, the route delivers nothing (its gate is closed, 3.4); the user stops listening by turning monitoring off, without removing the route.
   - **Recorded:** while the destination is armed and the transport records or counts in (5.5).
   - **Played back afterwards:** the destination's clips, its takes included, play as usual; its routed input is heard on top only while it is still armed or Input Monitoring is on. So after recording a route into a take and disarming, ordinary playback plays the take alone; the take and the live route both sound only if the user leaves Input Monitoring on, or keeps the track armed, which the help states.
2. **A routed destination's Input Monitoring is saved with the route; Record Enable is not (Decided 2026-11-27 by delegation).** `MidiFrom::monitor` holds it, and the track's runtime `input_monitor` mirrors it while the route is set (written from it on load and when the route is set; `mix.input_monitor` on a routed destination writes both). It is saved because a route is not an input path from the outside world: opening a session with a monitored route plays session content and activates no device input, which is the reason Input Monitoring is not saved for hardware inputs (Context). Like Input Monitoring today, changing it is not an undo step, and undo and redo keep its current value (`keep_runtime_state` extended to `MidiFrom::monitor`). Record Enable stays runtime state and is never saved.
3. **Export and freeze: the persistent state decides (Decided 2026-11-27 by delegation).** An offline render (export, bounce, freeze, Capture) renders a route exactly when its destination's saved Input Monitoring is on, and ignores Record Enable: monitoring that exists only because a track is armed is transient and is not rendered. That is the play-equals-export rule for routes: playback with the same routes monitored and no track armed gives the same events at the same frames as an export, to the extent the source's plug-ins are reproducible (ADR 0064 10.3); a route heard only because its destination is armed is live input and is not in an export, as any live input.
4. **Before its chain.** Routed events enter the destination's note table and pass its own MIDI effect chain, then its instrument: a route is the destination's input. A destination that wants the notes raw has an empty chain.
5. **Recording a route is input recording.** While the destination is armed and the transport records (or counts in), every routed event that passes its channel filter is captured for its take before the destination's table admits it, as hardware capture records what the mix buffered: a note the destination refused is recorded too. It is placed at its **musical position**, the timeline frame `f − L_in` (4.1), at the output frame the capture uses for that render frame. Takes, punch, loop recording, pickups and the pre-count zone follow the existing MIDI recording rules (ADR 0052 decision 8); the take stores ticks, so a recorded clip's fidelity limits apply (positions to the tick, same-key overlaps as the clip renderer plays them); note ids are not kept. **Timing after the input changes.** The take replays at its musical position. While the destination's audio is delay-compensated to Main (delay compensation on, and no Low Latency bypass on its path), that is also where the route was heard: live, a routed note at render frame `f = S + L_in` was compensated by the destination's `L_in` and reached Main at `S + A`; replayed with the route cleared, the take's note at `S` reaches Main at `S + A` with `L_in` gone from the destination's compensation. Where compensation was off or Low Latency bypassed a path, the live performance was already heard displaced by those rules, and the take keeps the musical position, not the displaced timing.
6. **Input recording keeps the offered performance, not a guaranteed copy of the sound.** For a source with free-running or random behavior, a recorded route keeps the notes that were offered live, which Capture MIDI Effect Output (ADR 0057 decision 9; ADR 0064 10.3) cannot, since it renders a new performance offline. Replaying the take through the destination's own stateful or random MIDI effects can sound different from what was heard, as for any recorded input.

### 6. Mute, solo, freeze, bypass, deletion

1. **Source mute stops its routed output; solo never stops a route (Decided 2026-11-27 by delegation).** A source whose own mute is on (its Mute button, its mute automation, or its VCA's mute) delivers nothing to any destination: turning mute on is a route barrier at every destination (3.4), and nothing is delivered while it stays on. Reason: a generator track often has a silent instrument (2.5), so muting it would otherwise do nothing anywhere. Solo exclusion is not mute for this rule: a source silenced only because another track is soloed keeps feeding its destinations, so soloing a destination keeps its sources running (they are part of what is soloed) and a soloed destination keeps hearing its route. An internal destination's mute and solo act on its audio as today; its route keeps delivering (its instrument still runs). An external destination that is muted or solo-excluded gets no routed non-release events, as its clips get none (Context), and its routed releases still pass (7.3).
2. **Inactive.** An inactive source is not rendered: its routes take a route barrier and carry nothing until it is active again. An inactive destination is not rendered; its table is voided as today.
3. **Freeze.** A track that is the source of a route cannot be frozen ("Keys sends MIDI to Bass; remove that route or freeze Bass instead"), whether or not it is also a destination; no route can be made from a frozen track. An internal destination can be frozen: the freeze render keeps its monitored route's sources running, transitively through routes and keys (`key_feeders` gains the MIDI edges), their audio cut, so the frozen audio holds the routed notes (an unmonitored route is not rendered, 5.3). While frozen the destination takes nothing from its route (it has no instrument in the plan); unfreezing resumes it. Parity: the frozen audio equals playback for the same effective processing (the same monitored routes, the source's plug-ins reproducible from their stored state, ADR 0064 10.3), with today's exclusions (live input is not rendered; the offline render ignores Low Latency's bypasses). External destinations are not frozen: freezing an External Instrument track is refused today (K64), and a MIDI track is not frozen. A session loaded with a route from a frozen track keeps the route, inert, with a load note.
4. **Bypass.** Bypassing a source stage is a source barrier, so a route barrier at every destination (3.4). Bypassing a destination stage is the destination's chain edit (3.5).
5. **Failure.** A source instrument contained for non-finite output or a reported processing error takes no events until Stop (ADR 0059 decision 2), so its chain takes nothing and its routes carry nothing until Stop (the containment is a source barrier). This is distinct from the source instrument refusing events, which never changes the tap (1.1). A failed hosted stage on the source is silent until Stop (ADR 0064 7.4). A destination's failure is its own containment.
6. **Deleting a source leaves its destinations disconnected (Decided 2026-11-27 by delegation).** Deleting a track leaves `midi_from` naming it on every destination; such a destination is **disconnected**: it takes no routed input (route barrier) and no hardware input, its input label reads "No input" with the tip "The track it took MIDI from was deleted", and its chooser marks the kept hardware choice "(previous)" so one choice restores it. Undo of the deletion brings the track back and the route works again. A session loaded with `midi_from` naming no track is disconnected the same way, with a load note: "Bass took MIDI from a track that is not in this session. Its input is disconnected until you choose one." Deleting a destination needs nothing.

### 7. External MIDI ports (slice MR5)

1. **Through a destination track whose output is external.** A route reaches a port by naming as destination a track whose `midi_output` is `External`: a bare MIDI track, an External Instrument track, or an instrument track sending to a port. One destination model (ADR 0022 decision 1), one output thread, its "device missing" state; no second path to a port. Such a destination's chain does not run (ADR 0036), so routed events go to the port as they are.
2. **The path.** The route outlet (2.5) owns the routed notes (decision 3) and writes each event it is given, as MIDI 1.0 bytes on the channel the destination's `MidiOutChannel` chooses (`AsRecorded` keeps the routed event's channel, a channel forces it, as for clips), into a per-strip external buffer of 512 events, 256 of them reserved for releases (the outlet's 224 notes and 32 pedals); the audio thread pushes that buffer into the playback ring after the block.
3. **Durable releases through both buffers.** The external buffer reports refusal to the outlet truthfully: a start is refused when no unreserved room is left (counted as a downstream refusal, 3.2, its release consumed), a release is never refused within the reserve. The ring push can refuse an event, a release included (`Producer::push`, Context): an event the ring refuses stays in the external buffer, ahead of later events, and is pushed again at the start of the next block (its stamp then past, so it is sent at once and counted late); a start that cannot be pushed in the block it was written is dropped with its own later release instead of being sent late (the outlet records it as refused). So a routed release is never lost between the outlet and the output thread while the host keeps executing.
4. **Revocation and note safety at the output thread.** Routed events carry an origin of their own, `Route`, with the destination's route generation, held per track beside the playback and echo origins. A route barrier at an external destination pushes a revocation marker for that track and generation (from the reserved slots) ahead of the outlet's releases; the output thread then drops every pending scheduled `Route` event of that track with an older generation, starts included, sends the releases, and rejects any later-arriving older-generation `Route` event except a release of a note it holds, as the echo path rejects stale events (Context). A loop wrap or locate on the destination's timeline does not end `Route` notes (they belong to their source and route, 3.4); Stop, the panic, a destination change, device loss and exit end them with every held note. MR5 extends the output thread's held state from CC 64 alone to all four pedal kinds (CC 64, 66, 67 and 69) for every origin, so Stop, the panic, a destination change and a revocation send the pedal-up of every pedal it holds, before its CC 123.
5. **Stamps.** A routed event at render frame `f` is stamped with the host time the player's existing frame-to-time conversion gives for render frame `f − L_in` (provisioned), at the current playback speed, plus the track's usual offset (the mix's compensation A on a bare MIDI-out track, none on an External Instrument track; ADR 0020 decision 2), so it leaves when its timeline frame does and an External Instrument's measured round trip compensates its return unchanged. A deadline already past when the output thread schedules it is sent at once and counted late by its existing rule. Whether that happens depends on how far the audio is rendered ahead of presentation, the output thread's scheduling, the destination's offset and the stamp fallback while no clock map is valid; with a large `L_in` an External Instrument destination is late by the excess, a causal limit (an event cannot leave before it exists), stated in the help.
6. **Shared channels.** MIDI 1.0 carries no source identity: when a destination's clips and its route play the same key, or move the same pedal, on one channel of one port, the hardware cannot tell them apart, and a note-off or pedal-up from either ends the other's voice or pedal. The output thread does not suppress it (suppressing would leave a voice the hardware cannot end). Stated limit; the help says to keep a route and the track's own clips on different channels when both play.
7. **Clock.** MIDI clock is not part of a route: a port's clock is ADR 0043's (not built), independent of tracks.
8. **Output ownership across an audio reopen.** Work that keeps output ports open across an audio reopen is in flight and not landed. MR5 does not wait for it: it depends only on the playback ring and the output thread's per-track state, adds nothing to port ownership, and its fake-backend tests run against whichever implementation is on `main`; whichever lands second rebases onto the other.

3. **On the destination.** The input label reads "From Keys" (" · Ch n" when filtered); the arranger header gains a chip "From Keys", opening the same chooser, drawn only while a route is set. ## Out of scope

- Taps before the chain or after a given stage (1.2); several sources into one destination (1.4).
- Racks as sources or destinations, until ADR 0036's rack stage.
- MIDI tracks, tracks with an external output and External Instrument tracks as sources.
- A plug-in's second and later note outputs (ADR 0064 decision 3).
- MIDI clock, transport, MTC and system exclusive over a route (7.7; ADR 0043, ADR 0022).
- Freezing an external destination (K64).
- Sample-exact recording of a route (recorded clips store ticks).
- Automating a route, or changing it by MIDI Learn.

## Consequences

- A note-writing plug-in, a built-in MIDI device or a track's clips on one track can drive any number of synths on other tracks, and through a MIDI track or an External Instrument, external gear.
- A destination is heard through its monitoring, like any MIDI input; a route with Input Monitoring on is saved, exported and frozen, one heard only because its track is armed is not.
- A routed destination renders after its source in each block, ordered like a keyed strip, at the same cost.
- Every routed note is owned by its destination, under a route generation; every way a route stops is a route barrier, detected even across missed blocks. At a destination with active MIDI effects a route barrier also ends the destination's own notes.
- A latent MIDI source delays its destinations' compensation and their own clips are aligned to it; a change of that latency cuts the destination's notes; an External Instrument destination can be late by the excess over the render-ahead time.
- Recording an armed destination keeps the routed input as it was offered; disarmed and unmonitored, the take plays alone.
- Muting a source stops its routes; solo never does. A source cannot be frozen; an internal destination can.
- Deleting a source leaves its destinations disconnected until the user chooses an input.
- On a shared hardware channel a route and the track's clips can end each other's notes.

## Alternatives rejected

- **The choice on the source (an output chooser).** The destination's input chooser would show a hardware input it does not play; Ableton documents the destination choosing (Context).
- **A `MidiPort::Track` variant.** An older build fails to load a session with an unknown variant.
- **Delivering a block later.** A delay that depends on the block size.
- **A route that sounds whatever the destination's monitoring (the first draft).** Departs from what both reference workstations document for routed MIDI (Context), and leaves no way to stop listening short of removing the route.
- **Rendering a route heard only because its destination is armed.** Arming is transient recording state; an export would depend on which tracks happened to be armed.
- **Keeping Input Monitoring runtime-only for routed destinations.** A monitored route would then never be in an export of a reopened session; a route activates no device input, which is why hardware monitoring is not saved.
- **A route barrier that releases only the route's notes through a destination's MIDI effects.** A transforming stage can latch, delay or replace them; only a chain barrier ends what it holds.
- **A routing table of its own at the destination.** The note table already qualifies by source, releases a source generation, holds pedals per source and is reached by Stop, failure and inactivation.
- **Packing a route serial and a source epoch into the generation.** Two unbounded counters do not pack into 64 bits; a per-destination counter bumped at every barrier is collision-free.
- **Dropping an overflowing release and waiting for Stop.** Leaves a note sounding until the user acts; the epoch and sequence comparison recovers within one block.
- **Keeping pending aligned events at their frames across a latency change (the first draft).** A release can then precede its pending start.
- **Muting a source leaves its routes running (the first draft).** A generator track with a silent instrument could not be muted anywhere; solo exclusion keeps sources running instead.
- **Restoring the kept hardware input when a source is deleted (the first draft).** An armed or monitored destination would start listening to a keyboard without being asked.
- **Routed notes after the destination's chain.** The destination's chain would not process its input.
- **A send-to-port route from the source.** A second path to a port beside ADR 0022's track destination.
- **A silent sink in place of an external destination's instrument.** It would stop a hosted instrument that renders today.
- **No latency alignment, or reporting `L_in` without aligning.** Late routed notes, or early own clips (4.2).

## Choices made without a rule to follow (for the review)

1. One source per destination; fan-in out of scope (1.4).
2. The tap with an empty chain is the mix table's output, so a track's clips and live input can be routed (1.1).
3. Eligible sources and destinations; a silent sink only where no instrument cell exists, a route outlet beside any instrument on an external destination (1.5, 2.5).
4. The channel filter gates starts and passes releases (1.8).
5. Same-block delivery through the route graph's layering and the task graph (2.2); the loop cut's priority bus input, key, MIDI (2.1).
6. Routed events at one offset after clips and before live events (3.1).
7. A route barrier at a destination with an active stage is a full chain barrier that ends its own notes too (3.3).
8. Recovery by epoch and sequence comparison, including a barrier after any missed source block with events (3.4).
9. The refusal counts by cause, shown until Stop (3.2).
10. The alignment stage, its capacity and its delay-line behavior; a latency change as a route barrier (4.2, 4.3).
11. A routed destination's Input Monitoring saved in `MidiFrom::monitor`, not an undo step (5.2).
12. Recording captures offered routed input at its musical position (5.5).
13. Freezing a source refused; a frozen internal destination renders its monitored route's sources (6.3).
14. External ports only through a destination track; the external buffer's reserve, retention of ring-refused releases and dropping of ring-refused starts; the `Route` origin, its revocation, all four pedal kinds; stamps at `f − L_in` (decision 7).
15. Routing's mix slices after HM3 and behind any ready hosting slice (Slices).

## For the maintainer to confirm or overturn

Decided 2026-11-27 by delegation, each in one sentence:

1. A track that takes MIDI from another track is heard only while it is armed or its Input Monitoring is on, exactly like a keyboard plugged into it, so turning monitoring off stops listening without removing the route, and a recorded take plays alone once the track is disarmed and not monitored.
2. A route whose destination has Input Monitoring on is saved with that setting and is in exports and freezes, while a route heard only because its track is armed is treated as live input and is not exported.
3. Muting a source track stops everything it sends to other tracks, while soloing never stops a route, and a muted or solo-excluded track that sends to a hardware port sends no new notes.
4. Deleting a source track leaves the tracks it fed with no input until you choose one, rather than switching them back to a keyboard, and undo brings the route back.
