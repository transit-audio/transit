# ADR 0065: MIDI routing between tracks and to external ports

- **Status:** proposed 2026-11-27 (the record ADR 0064 decision 11 names as its next record; builds on ADR 0057, ADR 0059 and ADR 0064, all accepted).
- **Date:** 2026-11-27
- **Implementation:** not started. Slice cards in the Slices section; a contributor can take any slice whose needs have landed.
- **Reopen when:** a destination needs more than one routed source (fan-in, decision 1.4); a tap before the chain or after a given stage is wanted (decision 1.2); a plug-in that writes several note outputs meant for several destinations is supported (ADR 0064 decision 3 reads one); ADR 0036's rack stage lands (racks as sources and destinations, decision 1.5); the MIDI effect chain runs on an external output (ADR 0057, Where this goes), which would let an External Instrument track or a track with an external output be a source; ADR 0043's clock sending is built and a route is asked to carry clock; the alignment stage (decision 4) is measured refusing events in ordinary use; a route's same-block ordering is measured costing more render time than a block can afford, which would ask for a one-block route with its delay compensated; or Ableton Live and Logic Pro are found, in their documentation, to agree on a behavior this record chose differently.

## Context

**The request.** Issue #671's reporting user has a note-writing plug-in (a generative chord performer with no sound of its own) on one track and wants its notes to drive synths on other tracks, and eventually external MIDI gear. ADR 0064 delivers a hosted MIDI effect's notes only to its own track's instrument (decision 11) and names this record as the next one. Its decision 11 sets the constraints this record must keep: the chain's output after its last stage is a per-block stream a second consumer can read without changing what the source instrument receives, and it is not fully identified (bypassed hosted stages pass their input's identities, built-in generators write anonymous notes), so a route must qualify identities by source; ownership stays per hop, a destination owning what it accepted by its own tables; a source barrier must reach every destination; admission at a destination is bounded; the tap is before the source instrument's admission. The record is written for whole classes of note source (hosted stages, built-in devices, clips and live input passing an empty chain) and is not designed around any reported plug-in.

**What the code does today** (verified against code on the branch carrying ADR 0064, head 4ca4f772; line numbers are that tree's).

- **A track's MIDI input** is `Track::midi_input: MidiInput { port: MidiPort, channel: Option<u8> }`, with `MidiPort` one of `All` (the default), `None` or `Device { backend, name, ordinal, id }` (`crates/model/src/midi_input.rs:6` to `26`; `crates/model/src/track.rs:243`), set by `midi.input`, which refuses kinds other than MIDI and instrument tracks (`crates/engine/src/cmd/midi_input.rs:49` to `88`). Playback opens a live route for a track only while it is armed or monitored and active (`crates/playback/src/player/native.rs:578` to `623`, the condition at `:582`); each port and track route registers its own ingress source slot (`:722` to `744`); the ingress worker applies the channel filter (`crates/playback/src/player/ingress.rs:1060`). The only chooser is the mixer strip's input row (`crates/ui-studio/src/mixer/channel.rs:262` to `295`, `crates/ui-studio/src/midi_input.rs:127` to `182`), listing "All MIDI inputs", "No MIDI input", the ports and a Channel submenu. The #760 "MIDI handoff" carries open MIDI inputs to a replacement player across an audio reopen (`crates/playback/src/player/device/midi_handoff_api.rs`); it does not choose inputs.
- **The mix's note table, per instrument,** matches by source: `Source { port: u16, channel: u8, generation: u64 }`, with reserved ports `Source::UI` and `Source::CLIP` (`crates/mix/src/events.rs:101` to `112`), and "Matching includes the whole source, then the sender id when there is one, else the key" (`NoteEntry::matches`, `:456` to `459`). It holds 224 notes and 32 pedals (`MAX_OPEN`, `MAX_PEDALS`, `:376` to `381`), assigns every note a voice id of its own so "two sources' notes on one key stay apart" (module documentation, `:27` to `28`), releases everything one source generation holds with `release_sender` (`:1040` onward), and is the single exit to the chain or the instrument (`send`, `:811` to `821`). Clip events reach it directly in the block (`clip_on`, `clip_off`, `clip_ctrl`, `:1144` to `1253`), merged in time order with queued live events, "at a tie, chase and clips precede live events" (`crates/mix/src/midi.rs:199` to `209`).
- **The chain lives in the instrument's event state.** In a strip the order is `fx.begin`, retries, clip scheduling interleaved with earlier live events, `deliver`, `fx.flush`, then the instrument's `process` (`crates/mix/src/strip.rs:164` to `194`). The event state exists only for an instrument cell (`crates/mix/src/compile.rs:961` to `963`), and an instrument track without an instrument, a MIDI track and an External Instrument have no cell (`crates/mix/src/instance.rs:67` to `78`), so no chain runs there and no live route binds there (`native.rs:599`). The add command accepts MIDI effects only on instrument tracks and racks (`crates/engine/src/cmd/midi_effect.rs:65` to `66`).
- **Render order and loops.** The session's route graph has edges Output, Send, Input and Key (`crates/model/src/route_graph.rs:39` to `49`), no MIDI edge. Commands refuse an edit that closes a loop (L22: `refuse_loop`, `crates/engine/src/cmd/track.rs:908` to `915`, through `would_create_cycle_all`, `route_graph.rs:725`; backstop `Engine::validate_edit`, `crates/engine/src/lib.rs:911` to `918`); a loaded loop is cut deterministically (F05, `route_graph.rs:19` to `22`, `solve` `:442` to `534`) and logged on open (`crates/engine/src/lib.rs:266` to `271`). Phase-1 strips render in layers by depth (`render_rows`, `crates/mix/src/compile.rs:322` to `351`): serially, one `run_strips` per layer with the key views filled before each (`crates/mix/src/active.rs:600` to `632`), or, for a keyed plan, through the render workers' task graph with an edge from every key source in an earlier layer (`crates/mix/src/graph.rs:1` to `14`, `strip_graph` `:269`); a missed source skips its dependents. A plan without keys publishes its strips with no ordering (`crates/mix/src/strip_pool.rs:798` to `905`).
- **Delay compensation is audio only.** A strip's latency is its head (frozen latency, the instrument's, an External Instrument's measured round trip) plus its inserts (`head_latency`, `strip.rs:523` to `527`); compensation reads each strip's output from a delay line at its arrival (`route_into`, `crates/mix/src/routing.rs:75` to `200`). Nothing delays or advances MIDI for compensation. ADR 0057 decision 7 (slice P4) adds the chain's MIDI latency `L_midi` to a track's compensation and never to the note readers' alignment.
- **Mute does not stop a strip.** `strip.muted` is set from mute, automation, a VCA and solo (`strip.rs:323` to `362`, the solo rule at `:326`), and only sets the fader gain to -144 dB (`:362`); the instrument is processed with no mute check (`:194`). An inactive track is not rendered and its instrument takes no events (`crates/mix/src/events/engine.rs:60` to `77`).
- **Freeze** replaces a frozen track in the plan by an audio track with no instrument (`Session::with_frozen_audio`, `crates/model/src/session.rs:558` to `582`), so its chain does not run. The freeze render keeps the tracks that feed the frozen track a sidechain key running, their audio cut (`key_feeders`, `crates/mix/src/offline.rs:303` to `370`).
- **External MIDI output** (ADR 0022) is `Track::midi_output: Internal | External { port, channel, offset_ms }` (`crates/model/src/midi_output.rs:42` to `58`). Clip events for an external destination are read by a separate traversal of the clips (`external_midi_events`, `crates/mix/src/external_midi.rs:52` to `70`), never through the chain; the instrument of such a track gets note-offs only (`strip.rs:173` to `186`). The audio thread stamps events with the presentation time of their render frame, adding the mix's compensation A for a bare MIDI-out track and not for an External Instrument (`Block::host_for`, `crates/playback/src/player/audio/external.rs:112` to `114`), into a playback ring of 4,096 slots with 256 reserved for releases (`crates/playback/src/player/midi_out.rs:27` to `29`); a dedicated output thread owns every port, keeps each track's held notes and pedals, and at Stop and panic sends a note-off for every held key, pedal-ups, then CC 64 off and CC 123 on every channel a port used (`:1153` to `1170`); at a loop wrap or locate it ends the destination's held playback notes (`:925` to `944`). No MIDI clock is sent anywhere in the output path; ADR 0043 specifies clock sending and it is not built.
- **MIDI output across an audio reopen.** On this branch the old output thread is dropped and the replacement reopens the ports (`crates/playback/src/player/native/handoff.rs:95` to `147`). Unlanded work on a branch carries open output ports across the reopen instead. This record does not design around it (decision 7.6).
- **Recording** captures on the audio thread every live packet the mix buffered for an armed track while recording or counting in, at the output frame it was given (`crates/playback/src/player/audio.rs:996` to `1014`): hardware input before the chain. Nothing else can be recorded: clip MIDI and the chain's output never reach the capture.
- **Cross-track references** are stored by `TrackId` (`crates/model/src/ids.rs`); a sidechain key naming a missing track is inert, and nothing clears a key when its source is deleted (`key_node`, `route_graph.rs:307` to `321`; the label shows "?", `crates/ui-studio/src/devices.rs:800` to `807`). A session with a field an older build does not know loads in that build with the field dropped; an unknown enum variant fails the load as "another build" (`Session::from_json`, `session.rs:781` to `792`).

**What other hosts document.** Ableton documents a destination track taking "MIDI From" another track and choosing the plug-in as the source ([Accessing the MIDI output of a VST plug-in](https://help.ableton.com/hc/en-us/articles/209070189-Accessing-the-MIDI-output-of-a-VST-plug-in)); the page blocks automated reading and is cited for that claim only. No Logic Pro documentation was consulted for this record. No decision below rests on another host's behavior except that cited claim, which decision 1.3 follows.

## Decision

### 1. The model

1. **What is routed: the chain's output after its last stage.** The **tap** of a track is the stream its MIDI effect host offers the instrument after the last stage, before the host's delivery filter and the instrument's admission (ADR 0057 P3b; ADR 0064 11.4): with stages, what the last stage's output buffer accepted; with no stage, the stream the mix's note table sends, which then equals the track's own notes (clips, live input, the chase, the releases of a seek). The tap does not depend on what the source instrument accepts or refuses, and reading it changes nothing the source instrument receives.
2. **No tap before the chain or per stage.** Out of scope: a destination that wants the source's raw input can take the same hardware input itself; a per-stage tap would put a destination inside the chain's edit and barrier rules for every stage. Reopen when wanted.
3. **From where to where.** A **route** goes from one source track to one destination track. The **choice lives on the destination**: its MIDI input is either a hardware choice (today's `midi_input`) or one source track. That is the workflow Ableton documents (a destination takes "MIDI From" another track, Context), and it keeps one rule for a track's input: one input, one channel filter. Storing it on the source would make the source's chooser a list of destinations and leave the destination's input chooser showing a hardware choice that is not what it plays.
4. **Counts: one source per destination, any number of destinations per source (Decided by the author without a rule; for the review).** A destination takes one source; a source feeds every destination that names it, so fan-out is bounded only by the session's tracks. Fan-in (two sources into one destination) is out of scope: the note table could keep two routes apart by source, but the chooser would stop being one input, and nothing reported needs it. A source never admits on a destination's behalf: every destination reads the source's fixed tap (decision 2.3) and admits by its own tables (decision 3), so fan-out multiplies nothing at the source.
5. **Which tracks.**
   - **A source** is an instrument track that is not a rack, whose `midi_output` is `Internal`, whose instrument slot is not an External Instrument and which is not frozen. Its instrument slot may be empty: the plan then gives it a **silent sink** (decision 2.5), so its chain runs and its live input binds. Not sources: MIDI tracks (they hold no chain, ADR 0036), tracks with an external output or an External Instrument (the chain does not run on an external output, ADR 0036 and ADR 0022; ADR 0057 lists it under Where this goes), racks (the rack's chain runs once per member until ADR 0036's rack stage, so there is no single rack output; ADR 0064 10.2), audio, aux, master, VCA and folder tracks.
   - **A destination** is an instrument track that is not a rack (with a hosted or built-in instrument, an empty instrument slot, or an External Instrument), or a MIDI track whose `midi_output` is `External`. A destination whose `midi_output` is `External` (a bare MIDI track, an External Instrument track, an instrument track sending to a port) sends routed notes to its port (decision 7); every other destination plays them through its own chain and instrument (decision 5).
   - A track is never its own source.
6. **Session field.** `Track::midi_from: Option<TrackId>`, `#[serde(default, skip_serializing_if = "Option::is_none")]`. While it is `Some`, the track's hardware choice in `midi_input.port` is kept and not used (playback opens no hardware route for the track), and `midi_input.channel` filters the routed events as it filters hardware input (a generator that writes bass on channel 2 can drive a bass track filtered to channel 2). Choosing a hardware input clears `midi_from` and restores the kept port choice. A separate field rather than a `MidiPort` variant, because an older build fails to load a session with an unknown enum variant and loads one with an unknown field (Context), which the `needs` marker then warns about (decision 8).
7. **Commands.** `midi.input` gains `from` (a track id, or `null` to return to the hardware choice), in the same undo step as its other fields. Refused, with the reason, before any change: a source or destination outside 1.5 ("<track> cannot send MIDI to other tracks: <reason>", the reason one of "it is a MIDI track", "it sends to an external port", "it holds an External Instrument", "it is a rack", "it is frozen"; "<track> cannot take MIDI from another track: <reason>"); the destination itself; a route that would close a loop with any edge of the route graph ("that route would create a routing loop: Bass → Keys → Bass", `refuse_loop`'s wording).

### 2. Timing: same block, after the source

1. **A route is an edge of the route graph.** `EdgeKind::Midi` goes from the source track to the destination track. So every rule the graph has applies: an edit that closes a loop is refused (L22, decision 1.7), whatever edge kinds the loop mixes (a MIDI route from A to B and a sidechain key from B into A's compressor is a loop); a loaded session's loops are cut by F05's deterministic rule, a cut route is inert, and the open names the loop as for any cut edge. Depth gains the MIDI edges, so a destination renders in a later layer than its source.
2. **Same-block delivery with exact offsets (Decided by the author without a rule; for the review).** A destination renders after its source in the same block and receives the source's tap for that block at the tap's own offsets. Rejected: delivering a block later, which delays every routed note by one block, makes that delay depend on the block size (so play would not equal export at another buffer), and would need its own compensation. The render paths follow the sidechain precedent of ADR 0015 decision 4: the serial path runs one layer after another; a plan with a route renders through the task graph exactly as a keyed plan does, with an edge from each route source in an earlier layer (`strip_graph` gains the MIDI edges; a plan with routes and no keys uses the task graph as a keyed plan does); a destination whose source missed its deadline in a block is skipped with it, as a keyed strip is. Cost, stated: a route serializes its destination behind its source, as a key does. The offline render (bounce, export, freeze, Capture) uses the same renderer, so play equals export.
3. **The tap buffer.** Each source's event state keeps a fixed tap of 512 events (ADR 0057's per-block chain bound), a barrier flag and the host's epoch, written as the host offers events to the instrument and read-only to destinations once the source's layer has finished (the borrow the key views already use). Events the host runs between blocks (ADR 0057 slice P2's call in which no time passes; today's `frames = 1` call) are kept in the same buffer and reach destinations at offset 0 of the next block, ahead of that block's events, as they reach the source instrument. An event the tap cannot hold (above ADR 0057's bound) is dropped and counted (`tap_overflow`); a release among them is not lost to the destination's ownership, because every note the destination accepted is still ended by the next barrier (decision 3.3).
4. **Track order and cycles.** Decided by 2.1: never a run-time order between a destination and its source; a cycle exists only in a loaded file and is cut there.
5. **The silent sink.** A source with an empty instrument slot, and every destination whose `midi_output` is `External` (decision 7), gets a plan-only instrument cell holding a built-in sink plug-in: it accepts every event, renders silence, reports no latency, and, for an external destination, writes what it is given into the strip's external buffer (decision 7.2). Its id is reserved for the plan and is never stored in a session or listed in a menu. With it, the event state, the note table, the chain (a source's) and the live binding exist exactly as for any instrument cell, so nothing else needs a second path.

### 3. Note ownership across a route

1. **Routed notes enter the destination's own note table as a source of their own.** A new reserved port, `Source::ROUTE`, with `generation = route serial × 2³² + source epoch`, where the route serial increases every time the destination's `midi_from` is set (a plan-time counter, not saved) and the source epoch is the source host's epoch carried by the tap (ADR 0057 P3b; ADR 0064 decision 6). The table matches a routed release by the whole source, then by its note id when it has one, else by its key (Context), so a routed note never matches the destination's clip, live or audition notes, and a release from before a source barrier never matches a note after it. Routed events are given to the table in the block, merged in time order with the destination's other events; at one offset: the chase, clips, routed events, then live events.
2. **Bounded admission and refusal.** Routed starts use the table's ordinary admission: a note-on needs a free entry of the 224, a pedal-down one of the 32, and releases are reserved (Context; ADR 0059 decision 1 below the table). A refused start is counted per destination (`route_refused`, in `EventStatus` and the diagnostics report), its release is consumed by the table, and nothing else changes. What the user is told: the destination's input label shows the count since the last Stop ("From Keys · 12 refused"), with the tip "Bass refused 12 notes from Keys because too many notes were held at once." Through the destination's own chain the events then meet ADR 0057 P3b's admission like any input.
3. **Every way a routed note ends.** At offset 0 of the block in which any of these takes effect, before that block's routed events, the destination releases everything the route's current generation holds (`release_sender`: a note-off for every routed note, a pedal-up for every pedal the route holds, through the table's existing release paths, which never refuse an owned release under ADR 0059):
   - the route is changed or removed, or its source is deleted (decision 6.6);
   - the source's tap carries a barrier: every host barrier of the source (a chain edit or bypass, Stop, the end of a play range, the All MIDI Notes Off action, P3b's safety reset, and ADR 0064's barriers: an instance arriving or leaving, a lifecycle generation change, a silent state, a failing block);
   - the source instrument's failure containment, which runs the source host's panic (ADR 0059 decision 2) and so a barrier;
   - the source becomes inactive (it is no longer rendered), is frozen (decision 6.3) or leaves the plan;
   - the route is cut as part of a loaded loop (2.1).
   Stop and the All MIDI Notes Off action also reach the destination directly (its own `release_all`), so their order does not matter: an owned release is delivered once.
4. **Identity is qualified, ambiguity is the source's.** Downstream of an active hosted stage the tap is identified by host ids (ADR 0064 5.4), so each routed release ends exactly its note. With an empty chain the tap carries the source mix table's voice ids, so it is identified too. Anonymous notes (from built-in generators, or a bypassed stage passing anonymous input) are matched by key within the route's own source, oldest first, so they can only shorten another note of the same route and key, never one of the destination's own or another route's. Nothing is left sounding past the next barrier of either track, with an instrument that accepts its releases (ADR 0059 owns refusal).
5. **What does not end routed notes.** A destination's own chain edit ends them as it ends every note of its chain (ADR 0057 2.13), and their later releases are swallowed by its epoch. Mute and solo on either track, a parameter change and an unchanged-plan adoption end nothing.

### 4. Latency compensation across a route (slice MR4)

1. **The figures.** For every track, `L_out = L_in + L_midi`, where `L_midi` is its chain's provisioned MIDI latency (ADR 0057 decision 7) and `L_in` is its source's `L_out` when it takes a route, else 0. A routed event at the destination's render frame `f` belongs to timeline frame `f − L_in`.
2. **An internal destination (Decided by the author without a rule; for the review).** Its compensation latency becomes `L_in + L_midi + head + inserts`, `L_in` entering wherever P4 enters `L_midi` (planning, storage sizing, key alignment, the runtime observer, freeze, the offline render), and never the note readers' alignment, exactly as `L_midi`. Its own events (clips, the chase, edit and seek releases, audition) pass an **alignment stage** that delays them by exactly `L_in` render frames before its chain, so the whole track is on one timeline; routed events do not pass it. The stage is host code at the head of the destination's MIDI host, present only while `L_in > 0`, with a fixed schedule of 1,024 events: a note-on is admitted only with room for its note-off, which is reserved; another event while the schedule holds fewer than 768; a refusal is a refusal of the chain's input (ADR 0057 P3b), which the mix's table already handles (its release then sends nothing). Everything in it is delayed across loop wraps and locates alike, as a delay line would; a host barrier of the destination cancels its pending note-ons with their releases (the host has ended every note it delivered). Rejected: reporting `L_in` without aligning (the destination's own clips would sound early by `L_in`); not compensating (routed notes late by `L_in`, a Humanize source no longer centered); reading the destination's clips `L_in` earlier on the timeline (wrong across a loop wrap, where the late frames before the loop end would be replaced by frames before the loop start).
3. **One adoption.** `L_in` is snapshot with every `L_midi` at a plan build and provisioned at the same adoption (P4's deferred activation), so the source's new latency, the destination's alignment and its compensation change in the same block. Events already in the alignment stage keep their frames.
4. **External destinations** align by their stamps, with no stage (decision 7.3).
5. **Before P4** every `L_midi` is 0, so every `L_in` is 0 and MR1 to MR3 need none of this. A hosted stage's reported latency may describe its audio rather than its notes (ADR 0064 10.1); the destination inherits that error, and the help says so.

### 5. The destination's own input and chain

1. **A route is session content.** It sounds whenever its source plays, whatever the destination's arm or monitor state, and an offline render includes it, so play equals export. Hardware input is gated by arm and monitor because it is live performance; a route carries clips and the chain's output, which are part of the session (Decided by the author without a rule; for the review). The source's own live input, while the source is armed, passes the source's chain and reaches the destination live, and is not in an export, as any live input.
2. **Hardware input.** A destination with a route has no hardware input (1.3). UI audition still plays it.
3. **Its own clips** play as before, aligned by decision 4.
4. **Before its chain (Decided by the author without a rule; for the review).** Routed events enter the destination's note table and pass its own MIDI effect chain, then its instrument: a route is the destination's input, and its chain processes its input. A destination that wants the notes raw has an empty chain.
5. **Recording a route.** While the destination is armed and the transport records (or counts in), every routed event the destination is given, after its channel filter and before its table's admission (as hardware capture records what the mix buffered), is captured for its take at the output frame of `f − L_in` (decision 4.1), so the take replays at the frames it was heard. Takes, punch, loop recording, pickups and the pre-count zone follow the existing MIDI recording rules (ADR 0052 decision 8); the take stores ticks, so the fidelity limits of a recorded clip apply (positions to the tick, same-key overlaps as the clip renderer plays them). Note ids are not kept (clips hold none).
6. **Recording a route is how the heard performance is kept, and it is not Capture.** For a plug-in with free-running or random behavior, a recorded route keeps the performance that was heard, live; Capture MIDI Effect Output (ADR 0057 decision 9; ADR 0064 10.3) renders the range again offline and keeps a new performance. Recording needs real time and the transport running; Capture is offline and needs neither. After recording, the take and the route both play, so the notes double; nothing is changed for the user: the help says to return the destination's input to its hardware choice to hear the take alone (one undo step).

### 6. Mute, solo, freeze, bypass, deletion

1. **Mute and solo never stop a route (Decided by the author without a rule; for the review).** Mute acts on a strip's audio (Context); the source's chain and tap run as before, so a muted source still drives its destinations and a destination's mute silences only itself. Soloing a destination mutes its source's audio, not its notes, so no solo-safe rule is needed. Reason: soloing a synth to hear it alone must not silence the notes that drive it.
2. **Inactive.** An inactive source is not rendered: its routes end their notes (3.3) and carry nothing until it is active again. An inactive destination is not rendered; its table is voided as today.
3. **Freeze (Decided by the author without a rule; for the review).** A track that is the source of a route cannot be frozen ("Keys sends MIDI to Bass; remove that route or freeze Bass instead"), because a frozen track has no chain in the plan, so freezing it would silence its destinations; no route can be made from a frozen track (1.7). A destination can be frozen: the freeze render keeps its route's sources running, transitively, as it keeps key feeders (`key_feeders` gains the MIDI edges), their audio cut, so the frozen audio holds the routed notes; while frozen the destination takes nothing from its route (it has no instrument in the plan), the route stays in the session, and unfreezing resumes it. As for keys, editing a source after a destination is frozen does not change the frozen audio. A session loaded with a route from a frozen track (an older build or a hand edit) keeps the route, inert, with a load note.
4. **Bypass.** Bypassing a source stage is a source barrier (3.3); the stream that follows passes the bypassed stage's input. Bypassing a destination stage is the destination's chain edit (3.5).
5. **Failure.** A source instrument contained for non-finite output or a reported processing error takes no events until Stop (ADR 0059 decision 2), so its chain takes nothing and its routes carry nothing until Stop: a stated limit, since the chain lives in the instrument's event state (ADR 0036). A failed hosted stage on the source is silent until Stop (ADR 0064 7.4), and stages after it, if any, keep writing. A destination's failure is its own containment.
6. **Deletion.** Deleting a track clears `midi_from` on every destination that names it, in the same undo step, and each such destination returns to its kept hardware choice (audible only when armed or monitored). Deleting a destination needs nothing (the route is its field). A session loaded with `midi_from` naming no track keeps the field, the destination silent from the route, with a load note: "Bass takes MIDI from a track that is not in this session. Choose another input."

### 7. External MIDI ports (slice MR5)

1. **Through a destination track whose output is external.** A route reaches a port by naming as destination a track whose `midi_output` is `External`: a bare MIDI track, an External Instrument track, or an instrument track sending to a port. One destination model (ADR 0022 decision 1: "a destination is a field of the track"), one output thread, its note safety and its "device missing" state; no second path to a port. Such a destination's chain does not run (ADR 0036), so routed events go to the port as they are.
2. **The path.** The destination's sink cell (2.5) holds the note table that owns the routed notes (3.1 to 3.4) and writes every event it is given, as MIDI 1.0 bytes on the channel the destination's `MidiOutChannel` chooses (`AsRecorded` keeps the routed event's channel, a channel forces it, as for clips), into a per-strip external buffer of 512 events; the audio thread pushes the buffer into the playback ring after the block, as it pushes the track's clip events. Releases use the ring's reserved slots. The routed events carry an origin of their own at the output thread, held per track beside the playback and echo origins, which a loop wrap or locate release does not end (routed notes are ended by their source and route, 3.3, not by the destination's timeline); Stop, the panic, a destination change, device loss and exit end them with every held note, as today.
3. **Stamps and latency.** A routed event at render frame `f` is stamped at the presentation time of `f − L_in` plus the track's usual offset: `P(R(f)) − L_in / r + A / r` on a bare MIDI-out track, and `P(R(f)) − L_in / r` on an External Instrument track (Context; ADR 0020 decision 2), so it leaves when its timeline frame does and an External Instrument's measured round trip C compensates its return unchanged. A stamp already past when pushed is sent at once and counted late, by the output thread's existing rule: on a bare track only when `L_in > A` (which needs a source whose audio does not reach Main, since A includes the source's compensation, which includes its `L_out`); on an External Instrument track when `L_in` exceeds the time the audio is rendered ahead of presentation. Stated limit; the help says that a latent MIDI source makes an External Instrument destination late by the excess.
4. **Notes on route change and source barriers.** The sink's table gives the note-offs and pedal-ups of 3.3 through the ring at the block they take effect; a destination change at the output thread still sends CC 64 off and CC 123 on the channels the port used (ADR 0022), routed notes included.
5. **Clock.** MIDI clock is not part of a route and not part of this record: a port's clock is ADR 0043's (not built), independent of tracks. Routed clock or transport messages do not exist (the chain carries none).
6. **Dependency on output ownership across an audio reopen.** Work that keeps output ports open across an audio reopen is in flight and not landed. MR5 depends only on the playback ring and the output thread's per-track held state as they are on `main` when MR5 starts, and adds nothing to port ownership; whichever lands second rebases onto the other, and MR5's tests use the fake output backend only.

### 8. Session format

- `Track::midi_from` (1.6), written only when set. `Session::needs()` lists `midi_routes` when any track has it, so an older build that knows markers warns that parts may sound different; such a build drops the field and plays the destination from its kept hardware choice. Alpha: no migration.
- Missing source track, an ineligible source or destination (1.5, including a frozen source), and a route cut from a loop each load with the field unchanged, the route inert, a load note naming both tracks, and the session saved byte-identical.
- Missing port on an external destination: ADR 0022's "device missing" state, unchanged.
- `Session::KNOWN_NEEDS` gains `midi_routes`.

### 9. The user interface (slice MRU)

1. **The chooser.** The destination's MIDI input chooser (the mixer strip's input row, `InputView::popup`) gains, after the ports and before Channel, a "Tracks" section listing every other track in session order, each with its name and color: an eligible source is enabled; one that would close a loop is disabled with the tip "Would create a routing loop: Bass → Keys → Bass"; an ineligible one (1.5) is disabled with its reason as the tip. A track that cannot be a destination shows no Tracks section. Choosing a track sends `midi.input { from }`; choosing a port or "All MIDI inputs" or "No MIDI input" clears it. Channel stays and filters the route.
2. **On the destination.** The input label reads "From Keys" (with " · Ch n" when filtered); the arranger header gains a chip "From Keys", opening the same chooser, drawn only while a route is set (as the output chip is drawn only for an external output).
3. **On the source.** The arranger header gains a chip "→ Bass" (or "→ 3 tracks"), with the destinations listed in its tip, drawn only while the track feeds a route; clicking it selects the first destination. The Devices pane shows the same marker at the end of the MIDI FX group, before the instrument card; its placement and size are for the panel design hand-off (ADR 0057 K2a's `deviceChain` tokens), and until the hand-off places it, the marker uses the tokens' smallest strip and every test reads them.
4. **States**, on the destination's label and chip, amber with a tip: "Keys is inactive: no notes arrive"; "Keys is not in this session"; "Keys cannot send MIDI: <reason>" (a loaded ineligible route); "Route cut on open: it made a loop (Bass → Keys → Bass)"; "From Keys · n refused" (3.2); a frozen destination: "Frozen: the route plays again when you unfreeze". On an external destination the Out button keeps its port states.
5. **Help.** One entry: what is routed (the chain's output, before the source instrument), one source per destination, same-block timing, that mute and solo never stop a route, that routed notes pass the destination's chain, recording a route and how it differs from Capture, the doubling after recording, freeze rules, external ports and the External Instrument latency limit, and that a hosted plug-in's reported latency may not describe its notes.
6. **No interim surface.** Nothing of this appears until slice MRV. Before it, `midi.input`'s `from` is accepted only through the control channel (a preview gate, as ADR 0064 decision 12), so tests and the maintainer's hands-on check can use it. External destinations list sources only from MR5's visibility (Slices).

## Out of scope

- Taps before the chain or after a given stage (1.2); several sources into one destination (1.4).
- Racks as sources or destinations, until ADR 0036's rack stage.
- MIDI tracks, tracks with an external output and External Instrument tracks as sources (the chain on an external output is ADR 0057's Where this goes).
- A plug-in's second and later note outputs (ADR 0064 decision 3).
- MIDI clock, transport, MTC and system exclusive over a route (7.5; ADR 0043, ADR 0022).
- Sample-exact recording of a route (recorded clips store ticks; ADR 0057's Where this goes owns sample-exact clips).
- Automating a route, or changing it by MIDI Learn.

## Consequences

- A note-writing plug-in, a built-in MIDI device or a track's clips on one track can drive any number of synths on other tracks, and through a MIDI track or an External Instrument, external gear.
- A routed destination renders after its source in each block: plans with routes are ordered like plans with sidechain keys, at the same cost.
- Every routed note is owned by its destination's own table, qualified by route and source epoch, so a source's edit, Stop, failure, removal or deactivation ends exactly the notes it routed, and two sources of notes on one destination never end each other's notes.
- A latent MIDI source delays its destinations' compensation, and the destinations' own clips are aligned to it; an External Instrument destination can be late by the excess over the render-ahead time.
- Recording an armed destination keeps a generator's heard performance; the take and the route then both play until the input is changed.
- A source cannot be frozen; a destination can, and its freeze renders its sources.
- Mute and solo never stop a route.

## Alternatives rejected

- **The choice on the source (an output chooser).** The destination's input chooser would show a hardware input it does not play; Ableton documents the destination choosing (Context).
- **A `MidiPort::Track` variant.** An older build fails to load a session with an unknown variant; a separate field loads, and `needs` warns.
- **Delivering a block later.** A delay that depends on the block size and needs its own compensation.
- **Ordering destinations at run time, or refusing loops only at load.** The route graph already refuses at edit and cuts deterministically at load.
- **A routing table of its own at the destination.** The note table already qualifies by source, releases a source generation, holds pedals per source and is reached by Stop, failure and inactivation; a second table would duplicate it.
- **Muting a source stops its routes.** Soloing a destination would silence the notes that drive it.
- **Gating a route by the destination's arm or monitor.** An export would hold routed notes only if the destination happened to be armed.
- **Routed notes after the destination's chain.** The destination's chain would not process its own input.
- **A send-to-port route from the source.** A second path to a port, with its own safety and stamping, beside ADR 0022's track destination.
- **Freezing a source by keeping its chain running.** The frozen plan has no instrument cell for the chain to live in; refusing is explicit.
- **No latency alignment, or reporting `L_in` without aligning.** Late routed notes, or early own clips (4.2).

2. The tap with an empty chain is the mix table's output, so a track's clips and live input can be routed (1.1).
3. Eligible sources and destinations, including empty instrument slots through a plan-only silent sink (1.5, 2.5).
4. `midi_input.channel` filters routed events (1.6).

6. Routed events at one offset after clips and before live events (3.1).
7. The refusal count shown on the destination's label until Stop (3.2).
8. The alignment stage for an internal destination's own events, its capacity and its delay-line behavior across wraps (4.2).
9. A route sounds regardless of the destination's arm and monitor state (5.1).
10. Routed notes enter before the destination's chain (5.4).
11. Recording captures routed events before the destination's admission, at `f − L_in` (5.5), and nothing is changed to stop the doubling afterwards (5.6).
12. Mute and solo never stop a route (6.1).
