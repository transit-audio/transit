# ADR 0051: Note names: one namer, a Middle C preference, files in their own convention

- **Status:** proposed 2026-11-09 (the maintainer agreed to the plan: "i agree with your preferences")
- **Date:** 2026-11-09
- **Implementation:** not started. Order of work in decision 9; scope is v0.7.0, ahead of the Sampler's Start note field, which must not ship on the old naming.
- **Reopen when:** a user asks for a third Middle C choice (C5, which Logic also offers); a file format we add has no stated octave convention and its reference implementations disagree; or the control channel needs a second note convention for a script that cannot change.

## Context

transit names the same key two ways. `transit_midi::note_name` calls MIDI 60 "C3" (its doc calls this the Pro Tools convention; Logic's default and Ableton Live's display agree), and the piano roll, the MIDI Monitor, the built-in editor's note parameters and the Macro Oscillator use it. The Tuner (`note_label`) and the Random Sequencer's Octave parameter call 60 "C4" (scientific pitch). A private copy of the C3 namer sits in `midi_learn.rs`, and the Resonator's Tonic carries 61 baked C3 strings. A player who reads a key in the piano roll and in the Tuner sees two names for it, and the Random Sequencer's default, "Octave 3", plays a root that every other panel calls C2. The Sampler's Start note field (ADR 0041) is about to add another surface, and it should not be built on a split.

A guitar tuner and MusicXML say C4 = 60; Logic and Live show C3 = 60. Neither is wrong. A DAW needs one name for one key everywhere in its own windows, a switch for a person who thinks in the other convention, and file formats that keep the convention they were written in.

**Convention.** Logic has a preference, "Display Middle C as" (C3, C4 or C5), with C3 as the default. Ableton Live shows C3 = 60 with no preference. The two agree on the default, so C3 is the default here, and transit offers the switch for C3 and C4 (C5 is in the reopen list).

## Decision

1. **One namer and one parser, in `crates/midi`.** `names.rs` holds `note_name(pitch, MiddleC) -> String` and `parse_note(text, MiddleC, bare_octave) -> Option<u8>`, with `enum MiddleC { C3, C4 }` (the name given to MIDI 60) passed as an argument by every caller. There is no global, `static` or thread-local convention in the crate; the UI holds the preference and passes it. A helper `octave(pitch, MiddleC) -> i32` returns the octave number for the one parameter that shows an octave alone (decision 4). The private copy in `midi_learn.rs`, the Tuner's `note_label` and the Random Sequencer's `OCTAVE_NAMES` are deleted.
   - *Names.* Sharps only (`C#`, as every table today): the letter, an optional `#`, then the octave, negative as `-1`. Under C3, 0 is `C-2` and 127 is `G8`; under C4, 0 is `C-1` and 127 is `G9`.
   - *Grammar the parser accepts.* After surrounding whitespace is trimmed: a letter `A` to `G`, either case, always the first character; an optional accidental, `#`, U+266F, `b` (lowercase only) or U+266D, so a `b` after the letter is the flat (`bb3` and `Bb3` are B flat 3, `b3` is B3, `BB3` is an error); an optional octave, ASCII digits with at most one leading `-` and no `+` (leading zeros are accepted: `C03` is `C3`); nothing else, and no spaces inside. The octave belongs to the letter and the accidental moves the pitch after it: `Cb3` is 59 and `B#2` is 60, the same key as `C3` under C3 (the namer never writes `Cb` or `B#`). Spellings that land outside 0 to 127 return `None` (`B#8` is 132 and `Cb-2` is -1 under C3). No field parses a note range; a later field that does must not use `-` as its separator.
   - *Bare letters and bare integers.* `bare_octave: Option<i32>`: with `None` a letter with no octave is not a note; with `Some(n)` it means that octave. Typed note fields in the UI (the Start note field and any later one) pass `None` (a typed "c" shows an error in place) and, where the field takes numbers, accept a bare integer 0 to 127 as a MIDI number (unsigned digits only: `-1` alone is refused), then apply the field's own range (the Start note field's is 0 to 64). The control channel's `midi.chord_add` keeps its documented "bare names use octave 3" through its own call (decision 5).
2. **A preference.** Options > Middle C: `C3` (default) or `C4`, a radio pair, saved per machine in `ui.json` beside the other Options settings (`UiState` in `ui_state.rs`, a new `middle_c` key; a missing key reads C3; the `ui_state.rs` test that every key is accounted for gains it). It is not in the session file and not in undo. It governs display and typing in the UI: a typed `c1` in a note field means the key the UI shows as C1 under the current setting. A new `options.middle_c` command, `{value?: "C3" | "C4"}` (without `value` it answers the setting), sets it, because every user action is a registered command (`docs/architecture.md`). It follows the machine-preference pattern of `options.low_latency`: the engine registers it and refuses it without the app's adapter; the app handles it, saves `ui.json`, passes the setting to the engine's message convention (decision 5), and `ui.inspect` reports `middle_c`. It is not undoable, not in the session, and never changes how any command parses. `docs/control-protocol.md` gains its row.
3. **Every display site goes through the namer with the preference.** The survey below is the list: the piano roll, the MIDI Monitor, MIDI Learn's mappings table, the built-in editor's note parameters, the Macro Oscillator, the Tuner, the Sampler's Start note field and pad labels (when they exist), and the tooltip and help text in the survey (made convention-neutral, decision 7).
   - **The Tuner follows the preference** (the maintainer's decision): one key has one name everywhere. The DSP crate does not depend on `transit-midi`, so `Reading::name` and `Reading::text` and `note_label` are removed from it; it keeps the note number and cents, and the panel names the note through the namer. The Reference knob keeps its id `reference_hz` and its `ParamInfo` name `Reference` (the automation lane, MIDI Learn and the plug-in listing say "Reference"). On the panel its label reads `Reference A3` under C3 and `Reference A4` under C4, the name of MIDI 69 through the namer, and its value text stays the frequency (`440.0 Hz`). No other consumer reads the dsp-side name: its only callers are `tuner_panel.rs` and `tuner_tests.rs`, and the control channel reports no tuner note (a later inspect field reports the MIDI number). The help entries (`tuner.note`, `tuner.frequency`) and the user guide stop saying "A4" and "C4 is middle C"; a catalog line is static text, so they say "the A above middle C" and "middle C" with the octave number left to the display.
   - **The cost, said plainly.** At the C3 default a guitar's low E (MIDI 40) reads E1 in the Tuner where a hardware tuner and a guitar book say E2, and A 440 reads A3 where a tuner says A4. A player who tunes to the note name switches the preference to C4, one click. The gain is that the Tuner and the piano roll give one pitch one name inside one window. This was weighed in the alternatives.
4. **Parameter labels baked into DSP.** The DSP crate cannot read a UI preference. The Resonator's `tonic` and the Random Sequencer's `octave` stay `Unit::Choice` parameters; what changes is who writes their labels.
   - *What does not change.* The parameter ids (`tonic`, `octave`); the stored value, which is the choice index (Resonator `tonic` 0 to 60, default 24; Random Sequencer `octave` 0 to 8, default 4); the mapping from index to sound (tonic index `i` is MIDI `12 + i`; octave index `i` puts the root at MIDI `12 * i + root`); the factory presets (`assets/presets/random_sequencer/*.json` hold `"octave"` 3.0, 4.0 and 5.0; the Resonator's presets store no `tonic` and take the default 24); and saved sessions, automation lanes and MIDI mappings, which all store the number. A session or preset written before the change reads the same after and sounds the same.
   - *What changes.* The label text only. `ParamInfo` gains `note_labels: Option<NoteLabels>` (`NoteLabels { first_note: u8, step: u8, octave_only: bool }`, default `None`), and `choices` stays populated with the fixed C3 = 60 strings (the Resonator's 61 names as today; the Random Sequencer's nine octave numbers become `-2` to `6`), so `ParamInfo::format` and every consumer that does not know the marker still get a name, correct at the default. On screen the UI names entry `i` through one helper in `ui-studio`, `param_text(p, value, MiddleC)`: with `note_labels` set it returns `note_name(first_note + step * i, MiddleC)`, or the bare `octave(..)` number when `octave_only` (the Random Sequencer's marker is `first_note: 0, step: 12, octave_only: true`; the Resonator's `first_note: 12, step: 1`); otherwise it returns `p.format(value)`. Every UI call of `ParamInfo::format` and every UI read of `choices` goes through it or through the marker: the built-in editor (`builtin_editor.rs` combo and `format_param`), `panel.rs`, `panel_matrix.rs`, `midi_fx_panel.rs` (the combo and the octave button text), `device_editor` (`value_text`, and `parse`, which parses through the marker before it matches `choices`, so a typed `C1` under C4 is never matched against a C3 string), the macro strip and device page knob (`widgets/param_knob.rs`), the automation lane value text (`automation/lane.rs`) and the Macro Oscillator's dropdown. The control channel's `engine.plugins` lists the fixed C3 strings and the `note_labels` marker whatever the setting: under C4 it disagrees with the screen by design, because commands are fixed C3 (decision 5). `engine.midi_effects` lists no choices and is unchanged. Range checks are unchanged: `mix.instrument_param`, insert values and MIDI Learn clamp to `min` and `max`, not to `choices`.
   - *The defect fixed.* The Random Sequencer disagrees with the rest of the application at the default: its Octave choice shows "3" at index 4, whose root is MIDI 48, which the piano roll calls C2. The sound is right; the label is wrong. After the change index 4 reads "2" under C3 and "3" under C4; the nine entries read `-2` to `6` under C3 and `-1` to `7` under C4. This is a visible relabel with no stored change, and the help line and release notes say so.
   - *The Resonator's Tonic* shows the same 61 keys it always did, MIDI 12 to 72: `C-1` to `C4` under C3 (the baked table, so nothing visible changes at the default) and `C0` to `C5` under C4.
   - Hosted third-party plug-ins (CLAP, VST3, AU) name notes themselves and are out of scope: the preference does not reach their editors or parameter texts.
   - If the marker cannot meet "stored value unchanged", the work stops and returns to this ADR. Storing a note in place of the index would change the meaning of every saved value, and the alpha rule would then apply (no migration, said loudly). It is not needed for this design and is not chosen.
5. **Commands do not follow the preference.** The control channel is a scripting interface: a script means the same thing on every machine. Wherever a command accepts a note name it parses in one fixed, documented convention, C3 = 60 (what `midi.chord_add` documents today), through `parse_note(text, MiddleC::C3, Some(3))`, never through the preference, and it always accepts MIDI numbers. The trace of every command that takes a name:

| Command | Parameter | Takes a name before | After | Convention |
|---|---|---|---|---|
| `midi.chord_add` | `root` | yes: `G3`, `Bb2`, `F#3`, `C-2`; a bare `G` is `G3` (private `note_number` in `cmd/midi_chord.rs`) | yes, through `parse_note` | C3 = 60 and a bare letter is octave 3, before and after; through the shared grammar it now also accepts surrounding whitespace and U+266F/U+266D, and refuses an octave written with `+` (`C+3`, which the old integer parse accepted as 60); every other string reads as before |
| `mix.sampler_load` | `params.root_note`, `key_low`, `key_high` | no: each value must be a JSON number; the test `instrument_params_reach_the_sampler` asserts that `"root_note": "C3"` is an error | no, numbers only | not applicable |
| `mix.instrument_param` | `value` (for `root_note`, `key_low`, `key_high`) | no: `value` must be a number | no | not applicable |
| `event.midi_note`, `event.step_input` (`pitch`, `pitches`), `event.retrospective_record` notes, `midi.note_add`, `midi.note_edit`, `midi.notes_move` | pitches | no: numbers, 0 to 127 | no | not applicable |
| `midi.notes_constrain` | `root` | no: a pitch class 0 to 11 | no | not applicable |
| `event.add_key_change` | `key` | free text ("C major"), stored as given | no change | no octave, so not a note name in this sense |

   A numeric string (`"60"`) is not a number to `midi.chord_add` today and stays an error. The help line in `cmd/midi.rs` and the command catalog keep saying C3 = 60 and add "regardless of the Middle C setting"; the sentence at `docs/assistant-access.md` 92, "Names use transit's display convention: **C3 = MIDI 60**", becomes "Names use a fixed convention, **C3 = MIDI 60**, whatever the Middle C setting". The Sampler start-note command of decision 9 is numbers only. A later command that takes names states this convention in its help and uses the same call.

   **Text a command writes for a person.** A refusal or status notice that names a note (ADR 0041's 2026-11-09 amendment: refusals (a) to (d) of `mix.sampler_pad_set` and the start-note notice) names it in the machine's Middle C setting, as that amendment requires. The engine holds a message convention, a `MiddleC` field on `Engine` (default C3), that the app sets from `ui.json` at startup and on every `options.middle_c`; it is not in the session and not in undo, and only `note_name` calls that build message text read it, passing it explicitly. Parsing never reads it, and every result field carries MIDI numbers (`mix.sampler_state` and the rest). So commands do not follow the preference in what they accept or return, and human-readable message text does follow it: a script run on two machines may see different message text, never different behavior, and a script must not parse message text.
6. **File formats parse and write in their own convention, never through the display path.** MusicXML export stays scientific pitch, C4 = 60 (`score.rs` `spell`, octave = `pitch / 12 - 1`); it never calls the namer and its output is byte-identical under both preferences. SFZ import (#271; nothing parses it yet) reads note names as C4 = 60, the SFZ convention (`pitch_keycenter=c4` is 60); the required evidence on #271 is a test that `pitch_keycenter=c4` is 60 under either preference. Any later importer or exporter states its convention in its own parser, with a test; a format parser calls `parse_note(text, MiddleC::C4, ..)` with a literal, never with the setting. Standard MIDI files and DAWproject carry numbers.
7. **What persists as text, and what happens when the preference flips.**
   - *Sessions, clips, patches, presets and mappings store numbers.* Confirmed in the serialized types: `Note.pitch` is a `u8`; `MidiSource.number` is a `u8`; the Sampler's `root_note`, `key_low` and `key_high` are parameter numbers in `Instrument.params`; a choice parameter stores its index; presets store parameter numbers. No saved file holds a note name, so a flip changes nothing saved. `ui.json` holds the preference, the MIDI Monitor's filter text and the other window state; none of it is session data.
   - *The MIDI Monitor stores its lines as text, formatted at capture.* `Row.text` is built once by `describe`, `Row.search` (the lower-cased text the filter matches) is built from it, and `Copy` and `Copy report` join the stored strings. A flip today would leave every retained row (up to `MAX_ROWS`) in the old convention while new rows show the new one, and Copy would mix both in one block. Decision: when the preference changes, the Monitor re-derives `text` and `search` for every retained row whose status is note-on, note-off or polyphonic aftertouch, from the raw bytes the row already holds (`raw`), so the screen and Copy always match the current setting; no other row changes. The LED tooltip (`led_tip`) calls `describe` when drawn and follows. The filter text a user typed ("C3") is a text match against the displayed names and is saved as typed; after a flip it matches the new names, as any displayed text would. A row held by MIDI Learn (`Learn::Caught`) is re-derived with the rest.
   - *MIDI Mappings rows.* `midi_learn::rows` builds `source` from the number on every draw, so it follows. The Monitor report is the only copied diagnostic text that names notes, and it goes through the same rows.
   - *Fixed text.* Help catalog and user guide lines are static text and cannot follow the setting, so each one that spells a pitch is rewritten convention-neutral: a MIDI number, Hz, "middle C" or "the A above middle C", never an octave-numbered name. The lines: `docs/help/tuner.toml` (`tuner.note`, `tuner.frequency`), `random-sequencer.toml` (`octave`: the default puts a C root at MIDI 48, an octave below middle C), `resonator.toml` (`tonic`: "MIDI 69 at 440 Hz"), `cross-modulator.toml` (`Osc Frequency`: "65 Hz (MIDI 36) to 2.09 kHz (MIDI 96)"); the `docs/user-guide.md` lines on the Macro Oscillator's tuning ("A4 = 440 Hz"), its modulation key ("middle C, C3"), the Resonator ("A4, MIDI 69") and the Tuner ("the pitch of A4"); the Measure tooltip in `external_instrument.rs` ("MIDI note 60"). Source comments that say "C3 = 130.81 Hz" (`texture_synth.rs` 14 and 84) are tuning facts about a module in scientific pitch and say "MIDI 48" instead. None of these catalog files carries a generated docs section, so `cargo xtask help --check` is unaffected beyond the entry text.
   - *Tests that pin names* change with the implementation: `tuner_tests.rs` (`note_names_count_octaves_from_c4_at_60` and the `A4` lines), `hero_tests.rs`, `scale_tests.rs`, `midi_monitor/tests.rs` and `resonator_panel_tests.rs`. `assistant_access.rs` (command parsing) stays green unchanged.
8. **Evidence for the implementation job.**
   - A name and parse round trip over 0 to 127 in both conventions, with the landmarks (0, 60, 69, 127) pinned for each.
   - A parser table: every grammar case above, accepted and rejected, including range overflow, `Bb` against `BB`, `Cb`, `B#`, `-2`, inner whitespace, a numeric string and an empty string; `C+3` and `-1` refused; `C03`, `bb3`, `B#2` accepted.
   - One rig test per Display row of the survey, plus the automation lane value text and the macro strip knob for the Resonator's `tonic`, and one engine refusal that names a note (its text follows the setting; its result numbers do not): flip the preference and the site shows the other name in the next frame, with every other string in the frame unchanged.
   - A command's parsing identical under both preferences (`midi.chord_add` with `C3` is 60 under either).
   - MusicXML output of one fixed clip byte-identical under both preferences.
   - The Tuner's test replaced by one per preference (A 440 reads `A3` under C3 and `A4` under C4, and the Reference caption follows).
   - The two DSP parameters: a preset and an automation lane written before the change give the same stored values and the same rendered audio after it (a golden render at `tonic` 24 and `octave` 4 is bit-identical); only the labels differ, as stated.
   - The MIDI Monitor: a row captured under C3 is re-derived on a flip, Copy matches the screen, and a non-note row is untouched.
   - Negative controls: the parser fed C3 text with the C4 argument returns the other pitch; a command routed through the preference by mistake fails the "identical under both" test; a hard-coded name in a display site fails its flip test.
9. **Order of work.** This ADR (judged to settled); the unification job (decisions 1 to 4 and 7); the Sampler start-note command (numbers only, independent); the Pads bar Start note field, built on the shared parser; SFZ import later (#271). **Cross-reference:** ADR 0041's amendment of 2026-11-09 (default pad trigger notes start at 36), accepted 2026-11-09, says the Start note field displays and accepts names through this namer and that its range label depends on the preference: the default base 36 reads `C1` under C3 and `C2` under C4, and 16 pads span `C1` to `D#2` under C3 and `C2` to `D#3` under C4. The field takes `parse_note` with `bare_octave: None` and unsigned numbers, and refuses in place anything outside the amendment's range, 0 to 64.

Every place that turns a pitch into a name or a name into a pitch. Pitch-class-only tables carry no octave and are unaffected: chord names in `event_more.rs`, `scale.rs`, the Random Sequencer's `ROOT_NAMES`, `event.add_key_change`'s free text and `midi.notes_constrain`'s root.

## Alternatives considered

- **A fixed C3 and no preference.** Rejected: the Tuner, MusicXML and most instrument and guitar references say C4 = 60, so a user who works that way would translate in every window, forever. Logic, the closest convention, ships the switch. C3 stays as the default.
- **A fixed C4 (scientific pitch).** Rejected: Live and Logic show C3 = 60 by default, and workflow follows what they agree on; it would rename every piano roll key and every Monitor line for a Live or Logic user.
- **The convention in a global or thread-local in `crates/midi`.** Rejected: hidden state makes a parser's answer depend on who set it last and on which thread; a command or a file format parser could pick it up by accident, which is the bug decisions 5 and 6 exist to prevent; and a test would have to set and reset it. An explicit argument costs one parameter and makes each call site state its convention.
- **The Tuner fixed on C4.** Rejected by the maintainer's decision, with both costs stated. For: it matches a hardware tuner and a guitar book (low E reads E2 where the C3 default reads E1, and A 440 reads A4 where C3 reads A3), and the Tuner is where a musician compares transit with a device. Against: one pitch would carry two names inside one window (the Tuner says A4 while the piano roll shows the same key as A3), which is the defect this record exists to remove. The preference gives the tuner-book reading in one click.
- **Commands that follow the preference.** Rejected: a script's meaning would change with a menu setting on a machine its author never sees; `midi.chord_add` with `C3` would be 60 on one machine and 48 on another. The control channel stays fixed and documented.
- **Storing the Resonator tonic and the Random Sequencer octave as notes.** Rejected: it would change the meaning of every stored value, preset and automation lane, and the alpha rule would apply, for a labeling change. The labels come from a marker instead.
- **Leaving the MIDI Monitor's stored text alone on a flip.** Rejected: Copy would mix two conventions in one block, and the filter would match names no longer on screen.
- **Formatting Monitor rows at draw time and keeping no text.** Rejected for now: the text filter matches every retained row each frame, and formatting each would cost more than one re-derive on a flip. Revisit if the retained row count grows.

## Consequences

- One key has one name in every transit window, and the other naming is one menu click away.
- The Random Sequencer's Octave label changes at the default (from "3" to "2" under C3); its sound and everything stored are unchanged.
- At the C3 default the Tuner reads one octave lower than a hardware tuner; the Reference caption names the A it means.
- The MIDI Monitor re-derives retained rows when the preference flips; `Row` keeps its raw bytes for this.
- `ParamInfo` gains a field, and the plug-in listing keeps the fixed C3 strings and adds the `note_labels` marker.
- Engine messages that name notes follow the machine's setting; command parsing and results do not.
- A new `options.middle_c` command and a `ui.json` key are added; neither enters the session or the undo history.
- File-format code is forced to name its convention at the call, and the tests for #271 and MusicXML pin it.
