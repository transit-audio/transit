# ADR 0054: Parametric EQ

- **Status:** proposed 2026-11-11
- **Date:** 2026-11-11
- **Implementation:** not started. Slices in the Slices section. Issue #233 (this device, milestone v0.7.1); #437 and #277 (portable math).
- **Reopen when:** the portable math record (#437, #277) lands and changes a helper this device names; the zero-latency magnitude bounds of decision 2.5 are missed in the slice 1 measurement; a user needs a band frequency outside 20 Hz to 20 kHz, more than 24 bands, or a Q on the cuts; the linear-phase low-end resolution of decision 6.4 is reported as a problem; dynamic bands are designed (their own record); the CPU targets of decision 13 are missed; or the reference workstations' equalizers are found to agree on a behavior this record chose differently.

## Context

Issue #233 asks for a transparent parametric equalizer that competes on workflow and visualization: no "color", a display-first editor with the analyzer behind the curve and band nodes dragged directly, up to 24 bands added and removed dynamically, per-band stereo placement, three phase modes, gain match, and dynamic bands in a later release. The maintainer calls it a must-have for v0.7.1. Effects get a decision record first; this device is transit's own design, not a port ([ADR 0042](0042-stock-effects-airwindows-ports.md) covers ports).

**The panel is designed.** The design hand-off for #233 fixes the window (1120 by 560 points, minimum width 880), the toolbar (analyzer Pre, Post, Both, Off; Freeze; an analyzer settings menu with resolution, decay, peak hold and smoothing; phase Zero latency, Natural, Linear with the reported latency; Gain match with its applied gain; Range ±6, ±12, ±18, ±30 dB), the display well (log frequency 20 Hz to 20 kHz, the analyzer's own scale −90 to 0 dB), the OUT column (a stereo channel meter and an Output knob of ±24 dB), the band list (one chip per band, "+ Band", "6 of 24 bands") and the band strip (Type, Slope, Frequency, Gain, Q, Placement, On, Solo, remove, and a reserved dynamic block). It names nine band types: Bell, Low shelf, High shelf, Low cut, High cut, Notch, Band pass, Tilt shelf, Flat tilt. It shows Slope only for the cuts, Gain not for the cuts, Notch and Band pass, and Q not for the cuts. The hand-off is not on `main` yet; it lands with the panel slice. This record makes the engine deliver exactly what the panel shows and does not redesign the panel. Where the panel needs a fact only the engine can give (ranges, refusal words, the curve, the analyzer data, the latency), this record defines it.

**Decided by the maintainer (2026-11-11, #233; fixed here):**

1. The name is Parametric EQ. Transparent: no saturation, no modeled hardware.
2. Accurate drawing. The EQ curve is the engine's computed magnitude response, one value per physical pixel column joined by straight segments, never an approximated shape; a selected band's own curve is that band's response alone. The analyzer draws the measured spectrum: one point per frequency bin at the bin's center joined by straight segments, the maximum where several bins share a pixel column, no smoothing across frequency unless the user turns it on (1/12, 1/6, 1/3 octave; default Off, shown with a tag). Coarse low-end resolution is fixed in the engine, never in the drawing.
3. Q changes with Ctrl+wheel over a node and with Alt-drag; a plain wheel never changes a control.
4. Per-band placement (stereo, left, right, mid, side) is shown by a letter badge and by solid and dashed channel curves, not by color; color names the band (content palette, fills only).
5. Up to 24 bands.
6. No second bypass: the title bar's power button is the device's bypass. A bypassed device shows no moving meter or analyzer; a static dimmed curve may stay.
7. Project-wide rules apply: no analog dials; VU is a ballistics mode of the meter; follow what the reference workstations agree on unless transit can clearly do better (both put the analyzer behind the curve with direct node dragging; transit adds pre and post blending); alpha, so no migration shims; renders are to be bit-identical across operating systems through portable math (#437, #277), so this device lists exactly which transcendental functions it needs and routes them through that seam.

**How built-in effects and the existing EQs work today** (read on `main` at 6531fba9):

- A built-in is a `Plugin` (`crates/dsp/src/lib.rs`) with a static `PluginInfo` (`id`, `name`, `short_name` of at most 8 characters, `category`, `params`, `pages`) registered in `crates/dsp/src/plugins/mod.rs`. Parameters are static `ParamInfo` tables built with `lin`, `log`, `toggle` and `choice` (`crates/dsp/src/params.rs`); `Params::set` clamps into range and turns NaN into the default. `ParamInfo` has no "not automatable" flag: every parameter can be automated, MIDI-learned and mapped by a rack macro. `Unit` has `None`, `Db`, `Hz`, `Ms`, `Percent`, `Ratio`, `Semitones`, `Cents`, `Seconds`, `Toggle` and `Choice`.
- **How many parameters a built-in may have.** The mix keeps the values last pushed to each plug-in in `Applied` (`crates/mix/src/lib.rs`): up to `APPLIED_INLINE` = 136 values inline in the slot, longer maps in storage the plan compiler prepares off the audio thread (`plan::needs_storage`, `Attach::Applied`). The test `every_builtin_parameter_map_is_tracked_inline` (`crates/mix/src/tests.rs`) requires every built-in to fit inline; the longest today is the Texture Synth's 131. No other limit applies to a parameter count: automation lanes name a parameter by insert slot and id (`AutoParam::Plugin { slot, param: String }`, `crates/model/src/automation.rs`), MIDI mappings and rack macros name it by id (`crates/model/src/midi_map.rs`, `crates/model/src/rack.rs`), built-in presets are JSON maps of id to value (`crates/ui-studio/src/presets.rs`), and a session stores `Insert::params` as a `BTreeMap<String, f32>` (`crates/model/src/mixer.rs`). Factory macro pages hold 8 slots each (`PAGE_SLOTS`, ADR 0047); each slot may name an enable toggle that dims it.
- The mix gives a built-in its parameter values at the block start (`apply_params`, `crates/mix/src/automation.rs`): one `set_param` per changed value, on the audio thread.
- **EQ 7-Band and EQ 1-Band** (`crates/dsp/src/plugins/eq.rs`) run RBJ cookbook biquads (`crates/dsp/src/biquad.rs`): coefficients computed in f64 and rounded to f32, frequency clamped to 1 Hz to 0.49·fs, Q to 0.025 to 100, gain to ±48 dB, run as transposed direct form II in f32 with the states flushed of denormals (`util::flush`) and reset to zero after a non-finite output. Every parameter has a 20 ms one-pole `Smoother` in its own value (frequency smoothed linearly in Hz), and while any smoother settles the sections are redesigned every 32 samples. `eq7_response` and `eq1_response` compute the magnitude response in dB from the same design functions (`Coeffs::magnitude_db`, f64); only tests call them today. Cuts are 6 to 24 dB per octave from first-order and Butterworth sections (`butterworth_qs`).
- **The closed-form evidence the issue cites** is the Filter insert's test (`crates/dsp/src/plugins/filter/tests.rs`, `every_mode_and_slope_matches_the_analytic_transfer_function`): the impulse response's DFT within 0.05 dB of an independently written digital transfer function where it is above −60 dB, else within 1e-4 linear. It is a tolerance test, not a bit-exact one.
- **State-variable sections** live in `transit-instrument-core` (`crates/instrument-core/src/svf.rs`): the trapezoidal-integrator SVF in f32 with `g = tan(π·fc/fs)`, cutoff clamped at `max_cutoff` = 0.49·fs, low, band (`k·v1`), high and notch outputs, states flushed. Its `math` module (`crates/instrument-core/src/math.rs`) routes `sin`, `cos`, `tan`, `exp`, `exp2`, `ln`, `log2` and `powf` (f32) and `tan`, `sqrt` and `floor` (f64) to the platform with `std` and to `libm` without; it is the seam a portable implementation will replace.
- **Spectrum.** `crates/dsp/src/spectrum.rs` has `magnitude_db(samples, fft_size)`: a Hann window, `rustfft`, a full-scale sine at a bin center reading about 0 dB, floored at −144 dB. It plans an FFT and allocates on every call. Only tests call it.
- **Sample taps.** An insert whose plug-in returns true from `Plugin::wants_sample_tap` (the Tuner) gets a `SampleTap` (`crates/mix/src/sample_tap.rs`): a preallocated ring of 16,384 frames of the channels' signed sum, written by the render only while the UI has enabled it, with relaxed stores and a release store of the write counter; a reader takes a span ending `READ_MARGIN` (2048) frames behind the newest write. The strip pushes it after `run_insert` (`crates/mix/src/strip.rs`). Nothing allocates or locks on the audio thread.
- **Scope taps.** Every insert instance has a `ScopeTap` (`crates/mix/src/scope.rs`): a ring of the per-frame peak of the insert's output (the largest channel) and a few per-block words, read by the UI through `ScopeHub` by track and insert uid. It holds no per-channel peaks. The title bars' output meters read it.
- **Latency.** `Plugin::latency` reports samples for delay compensation. The strip sums it every block (`strip.rs`). `low_latency::observe_raw` (`crates/mix/src/low_latency.rs`), run every render block, compares each slot's `latency()` with the last value and bumps `raw_latency_revision` on a change; the player then requests the same document again (`crates/playback/src/player/runtime.rs`), and the new plan's compensation includes the new latency. So a plug-in may change its latency while playing; the engine realigns after one recompile. Low Latency mode (ADR 0015 amendment) may bypass a latent insert on a live path. Offline processing compensates `latency()` (`crates/dsp/src/offline.rs`).
- **Bypass.** A bypassed insert is skipped by the strip (`continue` before `run_insert`), so it neither processes nor pushes its taps. **Reset** (`Plugin::reset`) runs on stop on the audio thread (`render_pool::reset_render_state`); `snap_initial_params` runs on the control thread for a fresh instance only.
- **Device window.** `crates/ui-studio/src/device_window.rs`: content-sized and fixed, the design width narrowed toward the panel's minimum on a smaller screen, recomputed every frame (so a note row that appears re-fits the window), no resize handle.
- **Loudness.** `crate::meter::k_weighting` (`crates/dsp/src/meter.rs`, used by `loudness.rs`) builds the ITU-R BS.1770 K-weighting biquads.
- **ADR 0040** retires the inherited EQ 7-Band and EQ 1-Band in stage 2 "when each replacement lands", with #233 as their replacement: the slot is emptied, its lanes and mappings dropped, a load report written, and no conversion.
- **ADR 0053** (accepted, not implemented) adds `transit_dsp::builtin_check_param` for refusals when set, and accumulate-and-swap meter cells in the `ScopeTap` (`Plugin::band_meters`, `BandMeters { bands, io }`) whose `io` part carries per-channel input and output peaks.

**Conventions.** Read in the current manual of one reference workstation, for its eight-band equalizer: up to eight bands per channel, each with an on/off switch; low and high cuts at 12 or 48 dB per octave, low and high shelves, peak and notch; Stereo, L/R and M/S modes, in which both curves are shown and only the active one is editable; an Audition mode in which holding a filter's dot plays only that filter's effect; a spectrum analyzer of the output behind the curves; optional two-times oversampling for "smoother filter behavior at high frequencies"; a Scale control for every band with gain. That manual says nothing about phase modes, latency or band colors. The other reference workstation's equalizer documentation did not load for this draft; nothing about it is verified here beyond the maintainer's statement that both reference workstations put the analyzer behind the curve with direct node dragging. Nothing about specialist parametric equalizers (fixed band slots with a used flag, automatic gain compensation computed from the curve, a "natural" phase mode) was verified from their documentation; where this record makes the same choice it stands on its own reasons, not on theirs.

## Decision

### 1. One device, its identity and its home

- **Registry id `parametric_eq`**, name "Parametric EQ", short name "ParamEQ", `Category::Eq`, an effect insert (`is_instrument: false`), `audiosuite: true` (offline processing already compensates latency). No other product's name appears in an id, a parameter, a preset, the help or the panel.
- **The DSP lives in a new Tier B crate, `transit-parametric-eq`** (`crates/parametric-eq`): the band designs, the section realization, the band chain, the placement stages, the smoothing and ramps, the correction and linear-phase kernel builders, a small FFT, the partitioned convolution, the gain-match computation and the response functions the panel draws from. `default = ["std"]`, `#![cfg_attr(not(feature = "std"), no_std)]`, `alloc`, allocation only in constructors and `prepare`; it enters the bare-metal compile job, `xtask`'s `LAYERS` (layer 1) and `STANDALONE` in its first slice (ADR 0037), with a `testing` feature that `transit-dsp`'s `testing` feature forwards. It owns a `math` module naming exactly the functions of decision 11.
- **The `Plugin` wrapper lives in `transit-dsp`** (`crates/dsp/src/plugins/parametric_eq.rs`): parameter table, pages, `update`, `process`, the meter and tap hooks. `transit-dsp` depends on the crate with `std` named explicitly.

### 2. Band types and their filters

**2.1 The analog prototypes.** Every band type is defined by an analog prototype in the variable `s/ω0` (`ω0 = 2π·f`, `f` the band's used frequency), with `A = 10^(G/40)` for a gain `G` in dB (RBJ's convention, so `A²` is the peak or shelf gain):

| Type | Prototype `H(s)`, `s` normalized by `ω0` | Panel fields used |
|---|---|---|
| Bell | `(s² + (A/Q)·s + 1) / (s² + s/(A·Q) + 1)` | Frequency, Gain, Q |
| Low shelf | `A·(s² + (√A/Q)·s + A) / (A·s² + (√A/Q)·s + 1)` | Frequency, Gain, Q |
| High shelf | `A·(A·s² + (√A/Q)·s + 1) / (s² + (√A/Q)·s + A)` | Frequency, Gain, Q |
| Low cut | Butterworth high pass of order `N = slope/6`: `N/2` second-order sections `s²/(s² + s/Qᵢ + 1)` and, for odd `N`, one first-order `s/(s + 1)` | Frequency, Slope |
| High cut | the same as a Butterworth low pass: `1/(s² + s/Qᵢ + 1)` and `1/(s + 1)` | Frequency, Slope |
| Notch | `(s² + 1) / (s² + s/Q + 1)` | Frequency, Q |
| Band pass | `(s/Q) / (s² + s/Q + 1)`, unity at `f` | Frequency, Q |
| Tilt shelf | the high shelf of gain `G` times the constant `10^(−G/40)`: −G/2 dB far below `f`, +G/2 dB far above, 0 dB at `f` | Frequency, Gain, Q |
| Flat tilt | a constant slope through 0 dB at `f`: `G` dB across the ten octaves 20 Hz to 20 kHz, so `G/9.966` dB per octave, built from first-order pairs (2.4) | Frequency, Gain |

The Butterworth Qs are `Qᵢ = 1 / (2·cos(π·(2i − 1)/(2N)))` for `i = 1 … ⌊N/2⌋`, computed once as constants for the eight slopes (6, 12, 18, 24, 36, 48, 72, 96 dB per octave; at most eight second-order sections per band). A cut is −3 dB at `f` and has no Q (the panel shows none). The bell's Q is RBJ's: the frequencies where the bell reaches half its gain in dB are `f·(√(1 + 1/(4Q²)) ± 1/(2Q))`, which is what the panel's Q bracket spans. Shelves at Q = 1/√2 have no overshoot; higher Q overshoots, as the prototype does, and the curve shows it.

The prototypes are what "transparent" means for this device: each band does what its analog prototype does, with no added nonlinearity, no modeled hardware and no level change beyond its response. Decision 2.5 makes that measurable.

**2.2 The zero-latency design: magnitude-matched sections.** A plain bilinear (RBJ) biquad maps the whole analog frequency axis into 0 to Nyquist, so every response is squeezed toward Nyquist ("cramping"): a bell or shelf's response at Nyquist is forced to its value at infinite analog frequency. The issue asks for highs that behave like the analog prototype. The choice is a closed-form magnitude match at the native rate:

- **Poles by the exact mapping `z = e^(s·T)`** of the prototype's poles. For a complex pair at frequency `ω_p` (radians per sample) and damping `ζ < 1`: `r = e^(−ζ·ω_p)`, `θ = ω_p·√(1 − ζ²)`; for real poles (`ζ ≥ 1`) the two real roots map separately. Real poles never alias, whatever their frequency; a complex pair is valid while `θ < π`.
- **Which form of a section is designed.** A bell or shelf whose poles would lie above its zeros in frequency (a cut bell, a boosting high shelf, a cutting low shelf) is designed as the reciprocal of its mirror (the bell of gain −G, the shelf of −G) and inverted, so the mapped poles are always the lower-frequency pair and stay below Nyquist for every frequency in range.
- **Zeros fitted to the prototype's magnitude.** With `φ1(ω) = sin²(ω/2)`, `φ0 = 1 − φ1`, `φ2 = 4·φ0·φ1`, the squared magnitude of a second-order polynomial is `B0·φ0 + B1·φ1 + B2·φ2` with `B0 = (b0 + b1 + b2)²`, `B1 = (b0 − b1 + b2)²`, `B2 = −4·b0·b2` (likewise `A0, A1, A2` for the denominator). Given the poles, `B0`, `B1`, `B2` solve three linear equations so that `|H(e^(jω))|²` equals the prototype's `|H(jω·fs)|²` (the prototype in hertz, unwarped) at `ω = 0`, at `ω = π` and at the section's match frequency `ω_m = ω0` (clamped to 0.49·2π). The zeros are taken minimum-phase (the larger root as `b0`).
- **Exceptions by type.** High-pass sections keep their double zero at DC (`b = g·(1, −2, 1)`) and fit only `g` at Nyquist. The notch keeps its zeros on the unit circle at `ω0` (infinite depth at `f`) and fits its gain at DC. First-order sections map the pole the same way and fit `b0`, `b1` at DC and Nyquist.
- **Feasibility.** The fit needs `W² + B2 ≥ 0` with `W = (√B0 + √B1)/2`. A parameter sweep in the drafting of this record (every type over 30 frequencies from 20 Hz to 20 kHz, gains of ±6, ±18 and ±30 dB, Q from 0.1 to 40, at 44.1, 48, 96 and 192 kHz) found no infeasible point with the forms above. The core clamps `W² + B2` at 0 if it is ever negative (a continuous fallback, no jump), and slice 1 repeats the sweep in the crate with a finer grid and records any clamped point.

Measured in the same drafting sweep, maximum magnitude deviation from the analog prototype from 20 Hz to min(20 kHz, 0.45·fs), where the prototype is above −40 dB (the slice 1 tests restate and pin these bounds; decision 2.5):

| | 44.1 kHz | 48 kHz | 96 kHz |
|---|---|---|---|
| Bell, ±3 to ±12 dB, Q 0.5 to 4, `f` ≤ 16 kHz: matched / bilinear | 1.36 / 7.79 dB | 1.09 / 6.22 dB | 0.36 / 1.41 dB |
| Shelves, ±3 to ±12 dB, Q 0.707, `f` ≤ 16 kHz: matched / bilinear | 0.44 / 3.53 dB | 0.39 / 3.04 dB | 0.03 / 0.59 dB |
| Bell, full ranges (±30 dB, Q 0.1 to 40, `f` to 20 kHz): matched / bilinear | 4.30 / 16.40 dB | 3.32 / 12.66 dB | 0.54 / 2.36 dB |
| Band pass, Q 0.5 to 4, `f` ≤ 16 kHz: matched / bilinear | 2.49 / 14.23 dB | 1.96 / 10.44 dB | 0.61 / 1.80 dB |
| High cut sections, Q 0.5 to 5.1, `f` to 20 kHz: matched / bilinear | 2.52 / 25.95 dB | 1.28 / 18.17 dB | 0.11 / 2.76 dB |
| Low cut sections, Q 0.5 to 5.1, `f` to 20 kHz: matched / bilinear | 9.15 / 27.11 dB | 6.85 / 18.17 dB | 1.07 / 2.76 dB |

The largest residuals sit at the top of the range at 44.1 and 48 kHz: broad, deep bells and the high-Q sections of steep low cuts near 20 kHz, where a second-order digital section cannot follow a response that extends past Nyquist. With `f` at most a fifth of the rate the low cut sections stay within 0.73 dB at 44.1 kHz. The matched sections are minimum phase, but their phase near Nyquist is not the prototype's (up to about 100 degrees for a 15 kHz high cut at 44.1 kHz in the same sweep); that is what Natural phase fixes (decision 6.2).

**Compared honestly:**

- *Plain bilinear biquads* (the existing EQs): exact at DC and at the band frequency after prewarping, cheap, but the cramping above is large at 44.1 and 48 kHz. Rejected as the zero-latency design; they remain the existing EQs' design.
- *Oversampling* (the reference workstation offers two times): with bilinear sections inside a two-times oversampled loop at 48 kHz the cramping is that of the 96 kHz bilinear column above: worse than matched sections at 48 kHz for the typical bell (1.41 against 1.09 dB), better at the extremes (2.36 against 3.32 dB). It costs about twice the section work plus the resampling filters, and those filters are either linear phase (latency, so it is not a zero-latency mode) or minimum phase (their own phase and passband ripple near Nyquist, so it is not transparent). Rejected.
- *Matched sections* (chosen): closed form, native rate, no latency, about the cost of a biquad at control rate; the residual is bounded, and Natural phase removes it entirely for 64 samples of latency.

**2.3 Realization: 64-bit trapezoidal state-variable sections with output mixing.** Any stable digital biquad is exactly a trapezoidal SVF with mixed outputs. With the digital section `(b, a)` written in `σ = (1 − z⁻¹)/(1 + z⁻¹)`:

- denominator `c2·σ² + c1·σ + c0` with `c0 = (1 − r)² + 4r·sin²(θ/2)`, `c2 = (1 + r)² − 4r·sin²(θ/2)`, `c1 = 2·(1 − r²)` (for real poles the same quantities from the two roots), computed in these forms because `1 + a1 + a2` cancels catastrophically at low frequencies;
- numerator `n2·σ² + n1·σ + n0` with `n0 = √B0`, `n2 = √B1`, `n1 = 2·√(W² + B2)`, taken straight from the fit, never from `b0, b1, b2`;
- `g = √(c0/c2)`, `k = c1/√(c0·c2)`, and output `y = m0·v_low + m1·v_band + m2·v_high` with `m0 = n0/c0`, `m1 = n1·g/c0`, `m2 = n2/c2`, where `v_low`, `v_band` (before multiplication by `k`) and `v_high` are the SVF's unit outputs in the notation of `svf.rs`.

The map needs only `sqrt`, which IEEE 754 rounds exactly. First-order sections use a trapezoidal one-pole with the same mixing. The sections hold their states and coefficients in f64 and the whole chain (sections, placement stages, correction filter and convolution) runs in f64 from input to output (one conversion each way). The SVF keeps its states meaningful when coefficients change, which direct forms do not, and its coefficient sensitivity at low frequencies is low; f64 removes the remaining concern at 20 Hz and 192 kHz, where the pole radius is within 1e-3 of 1. The cost is a few more cycles per section than f32, accepted (decision 13). The `Biquad` of `biquad.rs` is not used.

**2.4 Flat tilt.** Fifteen first-order shelving pairs at `f_k = 10·2^k` Hz for `k = −1 … 13` (5 Hz to 81.92 kHz), each `(1 + s/z_k)/(1 + s/p_k)` with `p_k/z_k = 10^(t/20)` and `z_k = f_k·10^(−t/40)` for a slope of `t = G/9.966` dB per octave (swapped for a negative slope), the whole scaled so the response is 0 dB at `f`. The analog cascade lies within 0.07 dB of the straight line from 20 Hz to 20 kHz at ±3 dB per octave (measured in drafting; slice 1 pins it). Pairs above Nyquist are real poles and map validly; the digital response near Nyquist is the matched one, and Natural phase corrects the rest. The pairs are packed two per section (eight sections, the last first-order).

**2.5 What "transparent" means, measurably.**

- **Bit-exact pass-through.** With no used band, or with every used band on at a type and setting whose target is identity (a bell, shelf or tilt at exactly 0 dB, after smoothing has reached it), Output at 0 dB and Gain match off, the output equals the input bit for bit in Zero latency mode, and equals the input delayed by exactly the reported latency in the other modes (decision 6.5). An identity band is skipped, not computed, as the existing EQs skip a 0 dB peak.
- **Magnitude.** In Zero latency mode, the deviation from the analog prototype composite from 20 Hz to min(20 kHz, 0.45·fs), where the prototype is above −40 dB, stays within the table's matched bounds for the stated settings (each plus 0.05 dB for the finer grid of slice 1). In Natural mode it stays within 0.1 dB and 0.5 degree of the prototype (magnitude and phase, after removing the reported delay) for every setting in range, where the prototype is above −40 dB. In Linear mode the magnitude stays within 0.1 dB of the prototype wherever the linear-phase resolution allows (decision 6.4 says where).
- **No nonlinearity.** The chain is linear: scaling the input by a power of two scales the output by the same power of two bit for bit, away from the denormal flush threshold and from overflow (no saturation, no level-dependent processing).

**2.6 Order and form of the chain.** Within a stage (decision 4), used and active bands run in band-number order; a band runs its sections in a fixed order (second-order sections by ascending Q, then the first-order one). The order changes nothing in the response; it fixes the arithmetic so renders repeat.

### 3. Changing parameters without clicks

**3.1 Smoothing rule: parameters, per sample; coefficients at control rate.** Each used band smooths its frequency and Q in the log2 domain and its gain in dB, each a one-pole of 20 ms on the plug-in's own sample clock with the snap of `transit-dsp`'s `Smoother` (to the target within 1e-6 relative). A band whose smoothers moved recomputes its sections every 16 samples of that clock (the Filter's `CONTROL` rule, ADR 0038 and ADR 0053 decision 2.5), plus once in `prepare` and `reset`. A band at rest costs no design work. Output is smoothed as a linear gain over 20 ms.

Cost: one design of one band is a few dozen floating-point operations plus one `exp2`, one `cos` and one `sin` per second-order section; 24 bands all moving at 96 kHz is 144,000 band designs a second, a small fraction of the section ticks themselves. Smoothing coefficients directly (interpolating `b` and `a`) was not chosen: an interpolated coefficient set is not the design of any parameter value and can leave the stable region between two stable endpoints.

**3.2 Discrete changes are crossfaded.** Type, Slope and Placement are not continuous. A change of one of them, and On and Used toggling, ramp the band's wet amount `w` (output `x + w·(band(x) − x)`, linear over 10 ms on the sample clock): a change ramps the old configuration out to `w = 0`, switches with cleared states, and ramps the new one in, so the band is briefly absent and never steps. A band at `w = 0` that is off or unused is skipped and its states cleared.

**3.3 Criterion.** As ADR 0053's: a 100 Hz sine at −6 dBFS at 48 kHz, the device with band 1 a bell at 400 Hz, +6 dB, Q 1; after 500 ms of settling one parameter steps at a block start; the output high-passed at 12 kHz (fourth-order Butterworth in the test) holds no sample above −60 dB relative to the larger of the output's steady peaks before and after, in the 50 ms after the step (Evidence lists the steps and their negative controls).

### 4. Placement: a left/right stage, then a mid/side stage

- **Stages.** Stage 1 runs every Stereo, Left and Right band in the left/right domain: a Stereo band on both channels, a Left band on channel 0, a Right band on channel 1. Stage 2 runs every Mid and Side band in the mid/side domain. Stereo bands commute with everything (the same filter on both channels), so placing them in stage 1 changes no response. Left/right and mid/side bands do not commute with each other; the fixed order (stage 1, then stage 2) is part of the device's definition.
- **Encode and decode.** Stage 2 exists only while at least one Mid or Side band is used (or ramping). Then, in f64: `M = L + R`, `S = L − R` before it and `L = (M + S)·0.5`, `R = (M − S)·0.5` after it. Each step is exact in f64 whenever the two input samples are within a factor of 2^29 of each other or either is zero (their f32 sum and difference then fit in 53 bits, and the halving is exact), so encode then decode with nothing between returns both channels bit for bit. With no Mid or Side band in use the encode and decode are skipped, so a session with only Stereo, Left and Right bands runs exactly the left/right arithmetic.
- **An untouched side.** With Mid bands only, the side signal passes stage 2 untouched in f64; the output's side component, computed in f64 from the f32 outputs, equals the input's to within the final rounding of the two outputs (one unit in the last place of each). It is not bit-identical at the f32 output, because the decode rounds `M' ± S` to f32; the record does not claim more.
- **Cost.** Two additions and two multiplications per frame each way, only while stage 2 exists.
- **Mono** (proposed): Stereo and Mid bands process the one channel; Left, Right and Side bands are inactive (no left, right or side exists), and the panel shows their nodes as disabled. **More than two channels** (proposed): Stereo bands process every channel; Left, Right, Mid and Side bands apply to channels 0 and 1 only.

### 5. Parameters: 24 fixed band slots with a used flag

Truly dynamic parameters are rejected: `PluginInfo::params` is a static table, every part of the system that names a parameter (lanes, mappings, macros, presets, pages, the protocol) names it by a stable id, and a parameter that comes and goes would orphan all of them. With fixed slots every id is always valid.

**5.2 Adding, removing and numbering bands.**

- **A band's number is its slot** and never changes while it lives: the chip, the node, the strip, every readout and every lane name ("Band 3 Gain") use it. Removing band 3 of 6 leaves 1, 2, 4, 5, 6 and "5 of 24 bands"; nothing is renumbered, because renumbering would move every lane, mapping and macro of the higher bands to another band's sound.
- **Add** (+ Band, a double-click or a drag on the empty display) takes the lowest-numbered unused slot that has no automation lane, MIDI mapping or rack macro on any of its parameters, else the lowest unused slot (proposed), and writes `used = on`, type, frequency, gain, Q, the default slope and placement, and the color in one `mix.insert_params` call: one undo step.
- **Remove** writes `used = off` and every other parameter of the slot back to its default in one `mix.insert_params` call: one undo step. Lanes, MIDI mappings and rack macros on that slot are left as they are, as for any parameter (the user removes them); while the slot is unused they drive values nobody hears. Undo restores the band and its values together.
- **At 24 used bands** the panel's + Band chip is gone (hand-off); nothing in the engine needs to refuse a 25th band, because there is no 25th slot.
- **Automation of `used`** is allowed like any parameter (clamped when used: a value at or above 0.5 is used) and ramps (3.2).

**5.3 Checked when set, clamped when used** (ADR 0041's rule). A value typed or sent through `mix.insert_param`, `mix.insert_params` or `mix.insert` outside its range is refused for this device, with the document unchanged and these words, which the panel shows verbatim in its note row: "Frequency must be between 20 Hz and 20 kHz.", "Gain must be between −30 dB and +30 dB.", "Q must be between 0.10 and 40.", "Output must be between −24 dB and +24 dB." The check goes through `transit_dsp::builtin_check_param` of ADR 0053 decision 2.4, which whichever device lands first builds. Automation lanes, rack macros and session files are never refused: `Params::set` clamps them, as for every built-in. Choices and toggles cannot be out of range once rounded.

**5.4 Mixer and editor paths.** Every writer goes through the commands above: the device panel, the generic editor and macro strip (`builtin_editor.rs`), MIDI Learn (a refusal goes to its status line, as for any refused write), preset recall (`presets.rs` through `mix.insert_params`). Each panel gesture is one undo step (hand-off section 5).

### 6. Phase modes

**6.1 Zero latency (minimum phase).** The matched sections of decision 2, no latency. Its magnitude is close to the prototype (decision 2.5); its phase is the sections' own minimum phase, equal to the prototype's well below Nyquist and different near it.

**6.2 Natural: the analog prototype's response, magnitude and phase, with a fixed short latency.** Natural targets the prototype composite `H_a(jω)` exactly: its magnitude and its (minimum) phase, the way the analog filter would behave, unwarped, up to min(20 kHz, 0.45·fs). It is realized as the zero-latency sections followed by a short linear correction filter whose target is `C(ω) = H_a(jω)/H_d(e^(jω))·e^(−jωD)`: near 1 at low frequencies (the matched poles agree with the prototype there) and a smooth correction near Nyquist, so its impulse response is short. The kernel is `2D + 1` taps, computed by frequency sampling of `C` on a 512-point grid (inverse FFT), centered and windowed with a 4-term Blackman-Harris window; `D` is 64 samples at 44.1 and 48 kHz, 128 at 88.2 and 96 kHz and 256 at 176.4 and 192 kHz (about 1.33 to 1.45 ms; the higher rates keep the same time span, and slice 6 measures them against the bound). Reported latency: `D`. Drafting measurements with `D = 64` at 44.1 kHz (a +12 dB Q 1 bell at 15 kHz, a 15 kHz second-order high cut, a −12 dB high shelf at 16 kHz, a pair of overlapping bells): at most 0.029 dB and 0.10 degree from the prototype; with `D = 32`, 0.125 dB and 0.37 degree. The correction runs as a direct-form FIR per channel (129 multiply-adds per sample at 48 kHz). The magnitude errors of Zero latency vanish and the phase becomes the analog filter's. Because the IIR sections stay in the path, a parameter drag moves the sound at the sections' smoothing rate in Natural mode too; only the small correction lags (6.4).

**6.3 Linear: zero phase plus a fixed delay.** An FIR whose magnitude is the prototype composite `|H_a|` and whose phase is a pure delay `L`. `L` = 4096 samples at 44.1 and 48 kHz (92.9 and 85.3 ms; the hand-off's example readout is `85.3 ms · 4096 smp`), 8192 at 88.2 and 96 kHz, 16384 at 176.4 and 192 kHz. The convolution is uniformly partitioned FFT convolution with partition `P` = 256 samples at 44.1 and 48 kHz (512 and 1024 at the higher rates; FFT size 2P), and the kernel is symmetric about tap `L − P`, `2(L − P) + 1` taps long (7681 at 48 kHz, 31 partitions), so the input buffering of one partition plus the kernel's center make exactly `L`. Kernel design: the target magnitude on a 16,384-point grid at 48 kHz (scaled with the rate), zero phase, inverse FFT, truncated to the kernel and windowed with a 4-term Blackman-Harris window, then the partition spectra. Pre-ringing is inherent: a linear-phase filter rings before a transient as much as after it, most for narrow, deep bands at low frequencies; it is the documented trade of this mode. With bands in both placement domains, the composite is a 2×2 matrix of zero-phase responses (left to left, right to left, left to right, right to right), run as four kernels sharing one delay; with one domain only, two kernels (left and right, or mid and side between the encode and decode).

**6.4 Rebuilding kernels on the audio thread, on a fixed schedule.** Correction and linear-phase kernels depend only on parameter values. When a band's targets differ from those a kernel was built from, a rebuild starts from the targets at that moment and advances by a fixed number of work units per partition frame (`P` samples) of the sample clock: evaluating the target on a share of the grid, one FFT, windowing, partition spectra. A linear-phase rebuild completes in at most 16 frames (4096 samples, 85 ms at 48 kHz); a correction rebuild in at most 4 frames of 128 samples. When it completes, the output crossfades from the old kernel's convolution to the new one's over one frame (both run during the fade; two sets of partition spectra are preallocated). The rebuild never allocates, locks or waits, and because it advances by samples rather than wall-clock time, a render (live or offline) gives the same output for the same input and the same parameter history. A drag in Linear mode therefore moves the sound in steps of up to 85 ms plus a 5 ms crossfade: Linear is for settled or slow changes, and the help says so. A thread per instance was rejected: the moment its result lands would depend on scheduling, so renders would not repeat. `snap_initial_params` (control thread, fresh instance) builds the kernels at once, so the first sample of a fresh instance is correct. `reset` (stop, on the audio thread) keeps the current kernels and restarts any rebuild in flight from its first unit.

**Linear-phase resolution.** The kernel's length sets the narrowest feature it can draw: about `fs/(2(L − P))` per bin (3.1 Hz at 48 kHz) spread by the window's main lobe. A Q 40 bell at 20 Hz (0.5 Hz wide) or a steep cut near 20 Hz comes out wider and shallower than the prototype. The curve shows the realized kernel (decision 8), so the user sees exactly this; nothing is approximated in the drawing. A longer kernel (more latency) is a reopen condition, not a setting.

**6.5 Latency and mode changes.**

- `Plugin::latency()` returns 0, `D` or `L` for the active mode. The panel's readout prints what the engine reports (`85.3 ms · 4096 smp`, milliseconds to one decimal and samples).
- In Natural and Linear mode, while the composite target is identity (decision 2.5), the device uses a plain delay line of the same length (bit-exact), crossfading to and from the kernel path over one frame.
- **A mode change while playing** (a click, or automation of `phase`, which `ParamInfo` cannot forbid): the device fades its output out over 5 ms, switches path and latency, lets the new path fill, and fades in over 5 ms. The engine's existing mechanism realigns the track: `observe_raw` sees the new `latency()` in the next block and the player recompiles with the new compensation. Until that plan is adopted the track plays with the old compensation. The change is therefore audible as a short gap, as any latency change is; it is not seamless. Offline renders compensate the latency in force at their start.
- Low Latency mode may bypass the device in Natural or Linear mode on a live path (ADR 0015), like any latent insert; the panel then draws the bypassed state (decision 10).
- `tail_samples` keeps the default (0): built-ins are never suspended.

**6.6 Which modes ship when.** Zero latency in the first slices; Linear and Natural after the analyzer (Slices). Until a mode's slice lands, the panel shows its segment unavailable (Open).

### 7. Gain match

- **Computed from the curve, not measured from the audio.** The applied gain is `G_match = −10·log10(P)` dB, with `P` the weighted mean power of the composite magnitude response: `P = Σᵢ wᵢ·|H(fᵢ)|² / Σᵢ wᵢ` over 241 frequencies at 1/24 octave from 20 Hz to 20 kHz, with weights `wᵢ = |K(fᵢ)|² / fᵢ` (a pink spectrum through the BS.1770 K-weighting of `meter::k_weighting`, evaluated once per sample rate in `prepare` into a table the core receives). `|H|` is the prototype composite, the same in every phase mode, so changing the mode never changes the match. With bands placed, `P` is the mean of the two channel curves' powers of decision 8 (left and right, or mid and side), and one gain applies to every channel, so the image does not move. `G_match` is clamped to ±30 dB.
- **When it is computed.** On every `set_param` that changes a band's targets, from the targets: each band keeps a table of its own 241 squared magnitudes, recomputed only when that band changes, and the composite sums them. No transcendental call outside `log2` and `exp2` (decision 11). The applied gain is smoothed over 50 ms and multiplies with Output.
- **Why it cannot pump.** It depends only on parameters. It changes when a band changes (that is what gain match means) and never with the program material. It is also exactly repeatable offline, which a loudness measurement over time would not be.
- **Shown and saved.** `gain_match` is a parameter; the applied value is not saved: it is a pure function of the parameters, recomputed identically on load. The panel prints it (`match −2.4 dB` and Output's sub-label `auto −2.4`) by calling the same function on the stored values.

### 8. The published response curve

- **The panel computes the curve with the engine's own design code.** The core crate exposes pure functions over the band set, the sample rate and the phase mode: `response_db(bands, rate, mode, channel, freqs, out)` for the composite and `band_response_db(band, rate, mode, freqs, out)` for one band alone. The panel calls them on the UI thread with the stored parameter values, one frequency per physical pixel column, and joins the values with straight segments. Nothing crosses the audio thread, and the curve is exactly what the engine converges to once smoothing settles (during a drag the sound follows within 20 ms).
- **What each mode's curve is.** Zero latency: `|H_d(e^(jω))|` of the matched sections, evaluated in f64. Natural: the sections times the correction kernel's exact DTFT. Linear: the realized kernel's exact DTFT at each column frequency, not the target, so the resolution limit of 6.4 is visible. The DTFT is summed directly in f64 (no interpolation); if a long kernel's curve does not fit in one UI frame, the panel computes it on a UI worker and keeps the previous drawing until it is done, never an approximation.
- **Channel curves.** `channel` selects one composite: with no placed band, the single composite; with left or right bands, the left curve (Stereo and Left bands) and the right curve (Stereo and Right bands); with mid or side bands, the mid curve (Stereo and Mid bands) and the side curve (Stereo and Side bands). Each is that channel's own path through its stages. With bands in both domains a channel's input-to-output response is a 2×2 matrix, not one curve; the panel then draws the pair of the selected band's domain (Open, hand-off question 6).
- **Bypassed:** the same functions give the static dimmed drawing.

### 9. The analyzer

- **Taps.** A new `Plugin::wants_analyzer_taps` (default false; true for this device) makes the compiler give the instance two `SampleTap`s, pre (pushed by the strip before `run_insert`) and post (after it), registered in the `ScopeHub` beside the existing sample tap. Each holds the channels' mean per frame (the sum scaled by `1/channels`, exact for 1, 2 and 4 channels), so a centered full-scale sine reads 0 dBFS and opposite-phase channels cancel, as any mono fold does. Their ring holds the largest analysis window at the plan's rate plus the largest latency plus `READ_MARGIN`, rounded up to a power of two (65,536 frames at 48 kHz, 256 KB per tap), allocated by the compiler. The panel reads the pre ring `latency()` frames further back, so Pre and Post show the same audio in Natural and Linear mode.
- **Cost when the window is closed: none.** The taps write only while the panel has enabled them (the existing `enabled` flag); the push returns at once otherwise. A bypassed insert writes nothing (the strip skips it), so nothing moves.
- **FFT and window.** On the UI thread, on the newest frames each UI frame, with a 4-term Blackman-Harris window (sidelobes below −92 dB, so the −90 dB scale is not filled by leakage) and the coherent gain corrected so a full-scale sine at a bin center reads 0 dB; floored at −144 dB. `rustfft` with a planned, reused buffer (the existing `spectrum::magnitude_db` allocates per call and is not used here). The analyzer is display only, never rendered, so it is outside the portable-math requirement.
- **Low-end resolution: two windows.** A short FFT covers the whole range and a long FFT covers the low end: below `f_x = 12·fs/N_short` (141 Hz at 48 kHz with 4096 points, where the short FFT reaches 12 points per octave) the long FFT's bins are drawn, at and above it the short FFT's. Each bin is one point at its own center, joined with straight segments into one polyline; nothing is interpolated. Resolution in the analyzer menu: **Fast** (4096 only), **Normal** (4096 and 16,384; default), **Fine** (8192 and 32,768), sizes at 44.1 and 48 kHz, doubled at 88.2 and 96 kHz, and at 176.4 and 192 kHz doubled again but capped at 65,536. A single larger FFT was rejected as the only choice: its window is long for the highs too (341 ms at 16,384 points), so the top end responds late.
- **Drawing** (decided by the maintainer): one point per bin at its center, the maximum where several bins share a pixel column, straight segments, the area closed under the same polyline. Smoothing Off by default; 1/12, 1/6 or 1/3 octave averages each bin's power over the bins within half that fraction either side of its center, before the column maximum, and the well shows its tag.
- **Time behavior only.** Decay: Off, Fast (falls 40 dB per second), Medium (20; default), Slow (6); rises at once. Peak hold: Off (default), 2 s, Infinite (until clicked). Freeze keeps the last trace. These run on the panel's frame time; tests drive it with explicit steps.
- **Panel state.** Analyzer mode (default Both), Freeze, Resolution, Decay, Peak hold, Smoothing and Range are per-instance panel state, not parameters and not saved (proposed; Open).

### 10. Meters and bypass

- **OUT column.** The output peak per channel. This device implements ADR 0053's `Plugin::band_meters`, filling `io` (output left and right in `io[1]`, input in `io[0]`) and leaving `bands` at zero; the accumulate-and-swap cells and `ScopeHub::band_meters` of ADR 0053 decision 6.2 are built by whichever of the two devices lands first. Mono: one value in both wells; more than two channels: ADR 0053 decision 6.3's even and odd fold. Ballistics are the panel's (`Ballistics::PEAK_FALLOFF`, clip cells, the hand-off's peak fall-off).
- **Title bar meter.** Unchanged: the insert's `ScopeTap` ring, as for every device.
- **Bypassed** (decided by the maintainer): no meter, no analyzer, nothing animates; the curve, nodes and axis labels may stay as a static dimmed drawing (decision 8). It needs no engine work: the strip skips a bypassed insert and pushes nothing. The panel treats Low Latency mode's bypass the same way.

### 11. Determinism and the transcendental functions

Every transcendental call in a rendered path goes through the new crate's `math` module, and only these, all in f64:

- **When a band is designed** (control rate, only for moving bands): `exp2` (the log2-domain frequency and Q back to linear; the pole radius `e^(−ζω)` as `exp2(−ζω·LOG2_E)`, `LOG2_E` an f64 literal; `cosh` for real poles from two `exp2`), `cos` (the pole angle), `sin` (`sin²(ω/2)` at the match frequency and in the cancellation-free forms of 2.3). `sqrt` is IEEE-exact and needs no seam.
- **When a parameter is set:** `log2` (smoother targets into the log2 domain), `exp2` (dB to linear for Output and the applied match gain as `exp2(dB/LOG2_TO_DB)`), and `log2` for the gain-match power to dB.
- **In `prepare`:** `exp2` for the smoothers' one-pole coefficients (`time_coef`'s formula through `exp2`), `cos` for the Blackman-Harris windows, `cos` and `sin` for the FFT's twiddle table and the correction filter's bin phasors.
- **Per sample:** none. The section ticks, the encode and decode, the FIR and the convolution are arithmetic only.

**The FFT is the crate's own** (radix-2, real input, power-of-two sizes from 256 to 32,768), with its twiddles from the seam and a fixed arithmetic order. `rustfft` is not used in a rendered path: its twiddles come from the platform, outside the seam, and its planner picks SSE, AVX or NEON code at run time (its documentation), so its rounding can differ between machines. The analyzer keeps `rustfft` (display only).

The dsp-wide `db_to_gain` and `gain_to_db` (platform `powf` and `log10`) are not used in the render, so this device adds nothing to #277's list. When the portable helpers exist, the `math` module forwards to them and nothing else changes; until then no cross-platform golden is pinned over a render that calls them (decision 19).

### 12. Block size, sample rate, channels, reset, silence and hostile input

- **Block size.** Everything runs on the plug-in's own sample clock: per sample for the sections, every 16 samples for designs, every `P` samples for the convolution frames and the rebuild schedule (with an internal FIFO). The output is bit-identical whatever the host block size, for the same input and the same parameter values at the same absolute frames (the Filter's rule). Parameter values reach built-ins at block starts, so automation is as block-quantized as for every built-in.
- **Sample rates.** Designs, `D`, `L`, `P` and the analyzer sizes come from the prepared rate (44.1 to 192 kHz in the tests); a rate change goes through `prepare`.
- **Channels.** The strip's channel count, up to `MAX_CHANNELS` (decision 4 for mono and wider layouts). `prepare` allocates per-channel states, FIFOs, kernels for the largest case (four kernels) and both kernel sets, then calls `reset`.
- **Reset:** section states, FIR and convolution histories, FIFOs and ramps to zero; smoothers snapped to their targets; designs recomputed; kernels kept (6.4); the sample clock to 0.
- **Silence and denormals.** f64 states are flushed to zero below 1e-30 in magnitude (no flush-to-zero mode is set on the audio thread); a silent input gives an exactly silent output once the states have decayed, and from a reset at once.
- **Hostile input.** Non-finite input samples are read as 0 at the device's input, so no state ever holds NaN or infinity and `contain_failure` never takes the device out for its input. Out-of-range parameter values are clamped by `Params::set`.

### 13. CPU cost and the small-target view

- **Targets** (recorded measurements in `plugin_bench`, not CI gates, as the bench is wall-clock): Zero latency, 24 bells, stereo, 96 kHz, block 256: at most 3 % of one core of the implementer's machine; the worst case, 24 Flat tilt or 96 dB/oct cut bands (192 sections a channel), at most 15 %; Natural adds the correction filter (at most 1 % more at 96 kHz); Linear, steady, at most 5 % at 96 kHz, and a rebuild fits its schedule without missing a block at 64 samples. A moving band's design cost is counted in the steady figures with all 24 bands smoothing.
- **Unused bands cost nothing** (skipped); a band at rest costs its section ticks only.
- **Small targets** (ADR 0037, the adaptable-core principle): the crate is Tier B, so a small target can run it. A small target keeps Zero latency and every band type; it may drop Natural and Linear (their memory: about 1 MB of f64 kernel spectra at 48 kHz for four kernels in two sets, doubling with each doubling of the rate, plus FIFOs) and the analyzer (UI only); the device then clamps `phase` to Zero latency when used. Its band count stays 24 in the table; a CPU budget table per target may cap how many are processed (that table's own decision).

### 14. Solo (audition)

- **What is heard:** the device's input (delayed by the reported latency, so the audition is aligned with the normal output), through a filter derived from the soloed band, at unity gain, instead of the device's output: a Bell, Notch or Band pass band plays through a second-order band pass at its frequency and Q (Notch: what the notch removes); a Low shelf or Low cut through a second-order low pass at its frequency (Q 1/√2), so a low cut auditions what it removes; a High shelf or High cut through the matching high pass; a Tilt shelf or Flat tilt through the band's own response alone (proposed; Open). Zero-latency matched sections, designed by decision 2.
- **One band at a time,** latched by a click and momentary while S is held for 300 ms or longer (the panel's rule). Switching in and out crossfades over 10 ms.
- **Never saved, never automated, never in a render.** Solo is not a parameter. The `ScopeTap` gains one `AtomicU32` audition word (a band number, or none), set by the panel through a new `ScopeHub::set_audition(track, uid, band)` and cleared by `ScopeTap::set_enabled(false)` when the panel closes. The strip reads it before `run_insert`, only while the tap is enabled, and passes it to a new `Plugin::set_audition(band: Option<u8>)` (default: ignored). An offline render has no enabled tap, so it never contains an audition; undo, presets and the session never see it.

### 15. Window

The hand-off's 1120 by 560 points with a minimum width of 880 follows the device window rule as is (`device_window.rs`: content-sized, fixed, the design width narrowed toward the minimum, recomputed every frame); the note row adds 24 points while a refusal shows, and the per-frame refit grows the window. 584 points at 150 percent is 876 pixels, within a 1080-pixel screen with its taskbar. No exception to the rule is needed.

### 16. Session format, presets and the existing EQs

- An insert of this device is an ordinary `Insert { plugin: "parametric_eq", params }`. No new session field, no `format_version` change, no `needs` entry, no migration shim (alpha). An older build reading such a session plays the slot without the device and keeps the stored parameters (ADR 0053 decision 13's reading, confirmed by a test in slice 2).
- A parameter id once shipped never changes meaning; while alpha a change is a clean break said in the release notes.
- **Presets** are the built-in format (`{"plugin", "version": 1, "params"}`); recalling one sets every parameter, the unlisted ones to their defaults (so unlisted slots are unused). No factory preset in the first slices (Open).
- **EQ 7-Band and EQ 1-Band** are not converted: there is no conversion of their sessions to this device, in line with ADR 0040's no-shim rule. They stay available while this device's slices land. When they go is ADR 0040 stage 2's rule ("when each replacement lands"), and which landing counts is listed under Open.

### 17. Control channel and help

- **No new command.** The device is driven by the existing `mix.insert`, `mix.insert_param` and `mix.insert_params` with the ids of decision 5, and read by `session.inspect`. Refusals carry the words of 5.3. A read-only query of the computed curve is a later option (Open).
- **Help:** `docs/help/parametric-eq.toml` with rows for the device, adding and removing bands, Type, Slope, Placement, Solo, the three phase modes (with Linear's latency, pre-ringing and stepped drags), Gain match (computed from the curve), the analyzer and its settings, and the bypassed state. The user guide gets a Parametric EQ section and the README Features line, in the slices that change public behavior.

### 18. Dynamic bands (a later release)

Nothing is reserved in the parameter table now: parameter ids are additive (a session without a new id gets its default), so a later `b{n}_dyn_*` set breaks nothing, and reserving dead parameters now would put them in every lane menu and preset. What the first slices must keep open, and do: each band's gain is already a smoothed per-sample value designed at control rate (decision 3), which a detector can drive the same way; the Zero latency and Natural modes keep the band sections in the signal path (a dynamic gain flows through them unchanged). What would change: about five parameters per band (on, threshold, range, attack, release; their own record decides), `APPLIED_INLINE` again or the prepared-storage path, a detector per dynamic band (with or without a sidechain), per-band gain-change meters (ADR 0053's cells), and a decision for Linear mode, where a moving gain would mean rebuilding kernels continuously.

### 19. Evidence an implementation must carry

All tests are deterministic, use no wall clock and no audio device, and drive time by counting samples. Each negative control says what fails without the rule.

- **Every band type against its closed form** (slice 1). The impulse response of each type and slope, at 44.1, 48, 96 and 192 kHz, over a grid of frequencies, gains and Qs, evaluated by a direct DFT in f64, matches the digital transfer function of the designed coefficients within 0.05 dB above −60 dB, else 1e-4 linear (the Filter test's bounds; proves the realization of 2.3 is exact). Negative control: an SVF map with `m1` computed from `b0 − b2` instead of the fit fails at 20 Hz and 192 kHz.
- **The matching claim** (slice 1). The deviation of the designed magnitude from the analog prototype, over the same grid from 20 Hz to min(20 kHz, 0.45·fs), stays within decision 2.5's bounds, and the same test run on RBJ bilinear sections (the comparison) exceeds them; the measured maxima are recorded in the result note. Negative control: the bilinear sections fail the zero-latency bound at 44.1 kHz.
- **Feasibility** (slice 1). The sweep of 2.2 on a finer grid; any clamped point is recorded.
- **Flat tilt** (slice 1). Within 0.07 dB of the line from 20 Hz to 20 kHz in the analog cascade at ±3 dB per octave.
- **Natural** (slice 6). Within 0.1 dB and 0.5 degree of the prototype composite after removing `D`, for single bands and sets of up to 24 at every rate. Negative control: `D = 16` fails at 44.1 kHz.
- **Linear** (slice 5). The kernel is symmetric about tap `L − P` to the bit (it is built symmetric); the impulse response of the device peaks at sample `L` for a flat target; the reported latency equals the measured delay of a click at every rate; the magnitude within 0.1 dB of the target for bells, shelves and band passes of Q at most 4 at 1 kHz and above at 48 kHz (proposed; the slice records the measured region where the bound holds, and below it the resolution-limited deviation is recorded, not bounded). Negative control: reporting `L − P` fails the delay check.
- **Bit-exact pass-through** (slices 1 and 2). No used band, or every band an identity: output equals input bit for bit (Zero latency) or the input delayed by exactly the latency (Natural, Linear). Negative control: computing identity bands instead of skipping them breaks bit-exactness.
- **Mid/side exactness** (slice 1). Encode then decode with no band between returns every input pair bit for bit, over random pairs within a factor of 2^29, pairs with a zero, and full-scale extremes. Negative control: the f32 encode and decode fails. With Mid bands only, the output's side component equals the input's within one unit in the last place of each output. With no Mid or Side band, the output is bit-identical to a build with the stage removed.
- **Click-free automation** (slices 1, 2 and 5). Decision 3.3's measure, with a negative control for each (that parameter's smoothing or ramp set to 0): frequency 400 Hz to 4 kHz and back, Gain −30 to +30 dB, Q 0.1 to 40, Type Bell to High cut, Slope 6 to 96 dB per octave, Placement Stereo to Side, On and Used toggled, Output −24 to +24 dB, Gain match toggled with a band at +12 dB; a linear-phase rebuild completing (negative control: switching kernels without the crossfade). A phase-mode change is excluded (decision 6.5); its fade-out and fade-in are checked by their own test.
- **Block-size independence** (slices 1, 2 and 5). The same input at block sizes 1, 7, 64 and 512 gives bit-identical output and end state (`Plugin::fingerprint`), with band frequencies, gains and Qs set to new values after a reset at other values (so smoothers move and designs recompute), and in Linear mode with a rebuild in flight. Negative control: a build that redesigns at block starts instead of on the sample clock differs at block size 7.
- **No allocation on the audio thread** (slice 2, extended in 5 and 6). A counting allocator over `process`, `set_param` of every parameter, `reset`, `set_audition` and `band_meters`, in every mode and through a rebuild; zero allocations. Bare-metal compile of the crate (slice 1).
- **Hostile input** (slice 1). NaN and infinity give finite output and unchanged state; a run of 1e-30 values leaves no subnormal state; silence in gives zero out after reset at once.
- **Gain match** (slice 1 for the function, slice 7 for the device). A flat curve gives 0 dB; a composite of +6 dB at every grid frequency gives −6 dB within f64 rounding; a +6 dB low shelf at 200 Hz gives the value of the f64 weighted sum computed in the test; two runs with different program material give identical applied gains (it cannot pump). Negative control: a level-follower variant differs between the two runs.
- **The published curve** (slice 3). The panel's curve at each column equals the core's response function at that column's frequency (the same function), and in each mode equals the device's measured response (impulse DFT) within the closed-form bounds. Negative control: a curve drawn from the analog prototype in Zero latency mode differs at 15 kHz at 44.1 kHz.
- **The analyzer against known sines** (slice 4). A sine at a bin center at −6 dBFS reads −6 dB within 0.01 dB; between bins the reading drops by at most the window's scalloping loss (0.83 dB for 4-term Blackman-Harris); a 40 Hz sine is read from the long FFT, its peak within one long bin of 40 Hz; two sines falling in one pixel column draw the larger. Negative control: averaging the bins of a column instead of taking their maximum fails the narrow-peak case. The taps write nothing while disabled and nothing for a bypassed insert.
- **Session round trip** (slice 7). A 12-band session (every type, every placement) saved and loaded in each phase mode gives identical parameters and an output identical sample for sample to the original instance's render (in process).
- **Refusals** (slice 2). Each out-of-range value through `mix.insert_param` is refused with its words and the document unchanged; an automation lane past the range is clamped. Negative control: without the check the value is stored clamped.
- **Older builds** (slice 2). A session with an unknown built-in id round-trips with its parameters unchanged.
- **Pinned results.** Only IEEE-exact values: the parameter table and pages, the Butterworth Q constants (as literals), the SVF map from given `B` and `A` values (arithmetic and `sqrt`), the mid/side round trip, the bit-exact pass-through, the meter publication. Every render that passes through a design, a kernel or the gain match (they call `exp2`, `log2`, `sin` and `cos`) is proven in process, never by a pinned hash, until the portable math record lands.

## Consequences

- transit gets a transparent equalizer whose zero-latency highs are close to the analog prototype at 44.1 and 48 kHz without oversampling, and exact to it in Natural mode for 1.3 ms of latency.
- The curve the user sees is computed by the code that runs, so it cannot drift from the sound.
- Linear mode costs 85 ms of latency, pre-ringing and stepped drags; Natural is the mode for analog behavior at almost no latency.
- 219 parameters make this the longest built-in table; the fixed slots keep every lane, mapping and macro valid for the device's life, at the cost of long lane menus (grouped by band in the menus is a UI matter) and unused slots stored in every session.
- A new rendered FFT enters the workspace, small and ours, so the linear and natural paths can become bit-identical across operating systems with the portable math record.
- A device-to-panel control word (audition) and a pre-insert tap enter the strip; other devices can use them later.

## Alternatives rejected

- **Truly dynamic parameters** (bands created and destroyed as parameters): every reference to a parameter is by id and would be orphaned or remapped on removal; static `PluginInfo` tables cannot express it.
- **Renumbering bands on removal:** moves lanes, mappings and macros to another band's sound.
- **Plain bilinear biquads for Zero latency:** cramping of several dB at 44.1 and 48 kHz (decision 2.2).
- **Oversampling:** no better than matched sections at the base rate, at about twice the cost, and either latent or not transparent (decision 2.2).
- **Direct-form sections** (the existing `Biquad`): coefficient changes under a running state disturb a direct form more than an SVF, and f32 direct forms lose precision at low frequencies.
- **Interpolating coefficients instead of smoothing parameters:** intermediate sets are not designs and can leave the stable region.
- **Natural phase as a fixed phase curve or a mix of modes:** "natural" is defined here as the analog prototype's response, which is measurable; anything else would be a taste.
- **Kernel rebuilds on a worker thread:** renders would depend on scheduling.
- **`rustfft` in the rendered path:** platform twiddles and run-time code selection, outside the seam.
- **A measured gain match** (loudness before and after): follows the program, pumps, and differs between runs.
- **Publishing curve arrays from the audio thread:** more traffic and a copy of what the UI can compute with the same code.
- **One large FFT for the analyzer:** slow highs; two windows give fast highs and a real low end.
- **Solo as a parameter:** it would be saved, automated, undoable and could reach a render.
- **Converting EQ 7-Band and EQ 1-Band sessions:** a shim, against the alpha rule and ADR 0040.

## Open for the maintainer

Each with a recommendation. Points the maintainer already decided are in Context and are not repeated.

1. **When EQ 7-Band and EQ 1-Band go.** ADR 0040 retires them "when the replacement lands" with no conversion; this record keeps them while its slices land. *Recommend* the minimum cut (slices 1 to 4) as "lands": stage 2 then removes them in the release that ships slice 4, by ADR 0040's rule, with no conversion.
2. **Default phase mode.** The hand-off draws Natural as the default; Natural adds 1.3 ms and a recompile on insert, and ships after Linear. *Recommend* Zero latency as the parameter default (inserting never changes a track's latency), with Natural one click away.
3. **Phase segments and Gain match before their slices.** *Recommend* showing them unavailable with a "later release" tooltip rather than hiding them, so the panel matches the design from the start.
4. **Band color as a parameter** (decision 5.1). The alternative is a new per-insert field, which presets would not carry without a format change. *Recommend* the parameter.
5. **Which slot a new band takes** (5.2). *Recommend* the lowest unused slot with no lane, mapping or macro on it, else the lowest unused.
6. **Frequency range.** *Recommend* 20 Hz to 20 kHz, matching the display; widening later is additive.
7. **Mono and wider layouts** (decision 4). *Recommend* as written: on mono, Stereo and Mid bands act, Left, Right and Side are inactive; on wider layouts placement applies to the front pair.
8. **Flat tilt's Q field.** The engine does not use it. *Recommend* the panel shows it unavailable (`—`), a one-line design follow-up.
9. **Audition of tilt bands** (decision 14). *Recommend* the band's own response alone.
10. **Analyzer settings and Range as unsaved panel state** (hand-off question 2 for Range). *Recommend* unsaved, per instance, defaults on every open; remembering them per device in the UI state is a later option.
11. **Analyzer channel fold.** *Recommend* the mean of the channels (decision 9).
12. **Factory presets.** *Recommend* none in the minimum cut; a few generic ones (a low cut, a gentle air shelf) with slice 7.
13. **A curve query command** (`mix.insert_response {track, slot, freqs}`) for scripts and agents. *Recommend* later, outside the minimum cut.
14. **Placement curves with both domains** (hand-off question 6). *Recommend* the hand-off's: draw the selected band's domain pair (decision 8) and name the other domain's bands in the curve tags' tooltip.
15. **`APPLIED_INLINE` to 224** (decision 5.1). *Recommend* as written.
