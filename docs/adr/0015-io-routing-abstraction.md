## Context

The project owner asked for that layer to be abstracted to support large custom routing and mixing configurations. Today transit opens output channels 1 and 2 only, and "Out 3-4" goes nowhere. Verified against `soundcraft` branch `transit`, head 6b81c4b (code paths relative to `crates/`):

- **The stream width follows the main bus, not the device.** `Player::prepare`/open asks for `main_channels(&session)` channels (`playback/src/player/device.rs:198`; `LegacyPlayer::open`, `playback/src/lib.rs:774`). `main_channels` is the main format's channel count clamped to 2..=16 (`mix/src/lib.rs:108`). `open_device` accepts only configurations with `2 <= channels <= want_ch` (`lib.rs:1343`, `1359`); when none matches it falls back to `default_output_config()` (`lib.rs:1376`). On ASIO, cpal lists every width 1..=outs per rate, so a stereo session on the Model 12 matches the 2-channel configuration and opens 2 channels; the default-config fallback bites on WASAPI, where only the mix format is listed (cpal `host/wasapi/device.rs:360-465`, `host/asio/device.rs:97-129`). Either way the other outputs never open. The callback writes main channel k to device channel k and zeroes the rest (`player/audio.rs:603-646`, clamps at 633, 636, 640); a main wider than the device is folded to stereo (`audio.rs:625`, `fold_gains` at `lib.rs:1219`).
- **Hardware routes are input-only, and by string.** `Route` is `None | Main | Bus(BusId) | Hardware(String)` (`model/src/mixer.rs:413`). The mix renders `Route::Hardware` only for monitoring an audio track's input, parsing digits out of a label like "In 1-2" (`mix/src/lib.rs:1824-1828`). `route_into` drops any output that is not `Main` or `Bus` (`lib.rs:1774-1781`); sends to anything but a bus are skipped (`lib.rs:1697`, `1735`). `track.mixer.output = Route::Hardware("Out 3-4")` is accepted from a file and silent. Today's `track.route` command turns an unknown output string into a new bus and maps "out 1-2" to Main (`engine/src/cmd/track.rs:818-838`; UI `ui-studio/src/mixer.rs:410`).
- **`OutputPath` exists; `InputPath` does not.** `OutputPath { name, first_channel, format }` (`model/src/mixer.rs:404`) lives in `Session::outputs` (`model/src/session.rs:317`, no `serde(default)`), seeded with "Out 1-2" (`session.rs:358`). Commands add, edit and remove paths (`engine/src/cmd/setup_more.rs:270-289`). Nothing reads it except `outputs.first().format` as the main format (`mixer.rs:583`, `cmd/surround.rs:105-120`) and the label for `Route::Main` in the UI (`ui-egui/src/mix_window.rs:136`). A 5.1 session stores its format only there.
- **Settings are per machine, but thin.** `AudioConfig { system, output, input, sample_rate, buffer_size }` (`playback/src/devices.rs:27`) lives in `UiState.audio` (`ui-studio/src/lib.rs:54`), saved to `ui.json` in the folder `TRANSIT_CONFIG_DIR` overrides (`apps/transit/src/config.rs`). `DeviceInfo.max_channels` (`devices.rs:44`) is shown but not used to open anything.
- **Input reaches the mix as a flat ring, and recording parses the same label.** The capture stream already opens the configuration with the most channels, uncapped (`playback/src/record.rs:292-306`, `Reverse(c.channels())`); the plan bridge copies it into `input_storage` (`playback/src/plan_bridge.rs:122-165`) and the mix sees `LiveInput.input` (`mix/src/lib.rs:1795`). Monitoring picks `(first + k) % n_in` (`lib.rs:1827-1836`) and recording does the same label parse and wrap (`engine/src/io.rs:1485-1489`, `plan_takes`), so a missing channel wraps silently in both.
- **The route graph, PDC and L22 know three edge kinds.** `EdgeKind` is `Output | Send { slot, pre_fader } | Input` (`model/src/route_graph.rs:36`); hardware and none are not edges (`route_graph.rs:11-12`). Edit-time refusal is `would_create_cycle_all` (`route_graph.rs:667`, from `engine/src/cmd/track.rs:866`); load-time loops are cut by `RouteScratch::solve`, only at the `Input` edge into a component's first track (`route_graph.rs:386-399`), and `dropped` reports only track-to-bus edges (`462-467`); `reserve` sizes edges as sends + 2 per track (`203-206`). PDC is two passes: `pdc_visit` (`mix/src/lib.rs:1643`) records each strip's output latency and each bus's arrival (`main_arrival`, `1659`); `route_into` delays each edge by the summing point's arrival minus the strip's own (`1683-1722`); `path_need_with` (`2594`) sizes the delay lines. Engine latency is `main_arrival + lmax_m` (`1525`) plus master-insert latency (`1498-1507`); delay is clamped at `MAX_LATENCY` (`507`). All of this sees only `Main` and `Bus`.
- **Render order has no track-to-track dependency.** Every non-aux strip runs its whole insert chain in one parallel phase before any routing (`mix/src/lib.rs:1451-1480`, `run_strips` `2486-2501`; plan renderer the same, `mix/src/active.rs:392-405`). `process_strip` gets `&busses` read-only and one `&mut Strip`; the delay lines `tap`/`tap_pre` are written later in `route_into`. `Layering.depth` (`route_graph.rs:100`) orders routing and the aux phase only. "Pre" means after inserts, before the fader (`lib.rs:2013-2018`); `strip.pre` is filled only when a pre-fader send exists (`1975-1981`).
- **Sidechain is not hosted.** VST3 aux buses are inactive (`vst3-host/src/lib.rs:39`); `Plugin::process(&mut self, io: &mut [Vec<f32>], frames)` is one in-place buffer (`dsp/src/lib.rs:223`); the CLAP host binds only the main pair, with bus layout fixed at `activate` (`clap-host/src/plugin.rs:114-130`). The compressor has a sidechain high-pass (`dsp/src/plugins/dynamics.rs:58`) but no key input.
- **Routing changes already travel one safe path.** A control-side compiler builds a `PreparedPlan` (`mix/src/plan.rs:233`) from a `Session` (`mix/src/compile.rs:263`) for a `RenderTarget { device, sample_rate, max_block }` (`plan.rs:55-60`, no channel count). `PlanEnvelope`s go through the bounded publication queue (`playback/src/publication.rs`, `plan_bridge.rs:252-279`); the audio thread adopts at most one per callback at a drained boundary (`active.rs:214`, `Audio::service`, `plan_bridge.rs:524-531`). `DeviceGeneration` means a new device or rate is a new engine (`plan.rs:46-48`). Callback allocation is gated (`mix/tests/plan_alloc_probe.rs`).
- **Offline render is the legacy renderer.** `LegacyPlayer` (`playback/src/lib.rs:641`) is `doc(hidden)` and used only by playback tests; the app's `Player` drives the plan renderer (`MixEngine::render_active`, `active.rs:350`). But `MixEngine::render` (`mix/src/lib.rs:1426`) is the only offline path: `RangeRender::render` (`3480-3485`), `engine/src/io.rs:503-612`, `engine/src/cmd/{mix,instrument,sampler,surround}.rs`, `engine/tests/bounce.rs`, and it is the oracle of `mix/tests/plan_parity.rs`.
- **Discrepancies with the problem statement.** (1) `MAX_CHANNELS` is 16 in the mix (`mix/src/lib.rs:105`) and in `MeterBank`/`Buffers.fold` (`plan_bridge.rs:27`, `125`), 64 in `dsp` and both hosts (`dsp/src/util.rs:14`, `vst3-host/src/gate.rs:12`); 16 binds a path or bus. (2) The output restriction is the `<= want_ch` filter, not a literal "channels 1-2" pick. (3) The path model is per session, not per machine. (4) The `Route::Hardware` label is treated as a channel number, so an input rename silently changes which channel is heard.

Test hardware: TASCAM Model 12 (about 10 outputs and 12 inputs to the host; channel counts may vary with USB mode) and a Focusrite Scarlett 2i2 (2 and 2). Backends: WASAPI and ASIO on Windows, CoreAudio, ALSA, through CPAL in `crates/playback` (pin `derekmwright/cpal`).

## Decision

### 1. Device channel map, with named paths per machine
1. **Open every channel the device offers, up to a cap of 32 outputs and 32 inputs.** The cap is a separate constant, `MAX_DEVICE_CHANNELS = 32`; the 16-channel path/bus width (`MAX_CHANNELS`) is not widened. Meters (`MeterBank.peaks`) and `Buffers.fold` are sized from the `IoMap` (or the 32 cap), not 16. The cap is new only for inputs, which already open at their maximum count uncapped; wider devices open the first 32 and say so in Audio Devices. The output stream is opened at the device's channel count, the `<= want_ch` filter is removed, and selection prefers the highest channel count at the chosen rate and format. **Stated limit:** WASAPI shared mode lists only the system mix-format channel count, so on Windows multichannel means ASIO; Audio Devices says how many channels the current system offers.
2. **A path is a name, a width and a channel set.** `IoPath { name, direction, channels: Vec<u16>, format: ChannelFormat }`, width 1 to `MAX_CHANNELS` (16), `channels` an explicit list so a path may be non-contiguous. `OutputPath` becomes the output half; `InputPath` is added. Defaults when a device opens: "Out 1-2" stereo plus one stereo path per remaining pair, "In 1" mono per input plus stereo pairs. The generated names equal today's labels exactly ("In 1", "In 1-2", "Out 3-4") so existing sessions keep their meaning.
3. **Paths are per machine, and reach the engine as an `IoMap`.** `IoMap { device identity, opened input/output channel counts, named path table, Main's target path }` is loaded by the app from `ui.json` (beside `AudioConfig`; keyed on audio system plus device name, with the channel count stored inside it, so one device in two USB modes is one entry) and handed to the engine with a `setup.io` command. `PlanCompiler::compile`, `Buffers::prepare` and `Player::prepare` take the `IoMap`; `RenderTarget` gains the opened output and input channel counts. Headless and automation (MCP, engine tests) build a default `IoMap` from the device, Main on its first two channels. The path commands (`create_output`, `rename_output`, `delete_output`) edit the `IoMap` the engine holds and the host persists, so they stay scriptable and undoable. **`Session::outputs` stays, in the file, with its current shape, through slices (a) and (b):** it remains the source of `main_format()` and the seed for a first default table, so a 5.1 session never silently becomes stereo (a build that dropped the field would load old files with no error, `mixer.rs:585`). Retiring it needs a versioned migration (`FORMAT_VERSION`, `session.rs:342`; `Session::from_json` has no migration hook today) and its own ADR.
4. **Assignments are per session, by path name.** `Route::Hardware(String)` stays the on-disk variant and means "the I/O path with this name" for inputs and outputs. Names are unique across buses and paths (bus and path share one namespace for `track.route`); `parse_route` resolves path table first, then bus, and creates a bus only on explicit request. On a load collision the bus wins and the route is flagged. Monitoring and recording resolve inputs through one function (`engine/src/io.rs:1485` joins `mix/src/lib.rs:1827`); a missing input path refuses to record with a message and never records a wrong channel.
5. **Resolution when a name is missing on this machine.** An output route to a missing path renders to a **flagged silent sink**: muted, shown in the UI and on load, the session not rewritten. A cue or click mix never lands on the PA. Only the Main path itself falls back to device channels 1-2. A missing input falls back to the first input path of the same width, else silence with a flag. The session keeps the original name, so the right machine restores the routing. Fold or fan-out of widths follows `build_matrix` (`mix/src/lib.rs:3207`). **Bounce is machine-independent:** it renders sinks logically, tracks routed to a named path are excluded from the main bounce, and stems are slice (e).

### 2. Routing matrix
Every track, bus and send may target `Main`, any `Bus`, or any output path; today's default (`Main`) is unchanged. A track's output goes to one target, its sends to as many as it has slots, so main plus cue mixes plus stems are a track output plus sends. The mix keeps one accumulation buffer per device channel (preallocated at the cap) and every path sums into its channel set. Paths overlapping on a device channel sum, with a warning on each ("Out 3-4 shares channel 3 with Headphones"). Metering and clipping apply per device channel after the sum, with the existing clamps (`audio.rs:633, 636, 640`). The device-frame layout travels with `Buffers` (as `fold` does), so render-ahead blocks keep their old layout across a path edit. There is no full matrix-mixer UI (see Alternatives).

### 3. Main as one path among paths
The main mix remains the primary output and still sets the main format (`Session::main_format`, `mixer.rs:583`). Which path Main plays on is stored per machine in the `IoMap` (default "Out 1-2"), which also answers what `Route::Main` shows in the UI (`mix_window.rs:136`).

### 4. Sidechain key inputs are edges in the route graph
An insert gets an optional key: `Insert.key: Option<KeySource>` with `#[serde(default, skip_serializing_if = "Option::is_none")]` like its sibling fields (`mixer.rs:428-443`), so old sessions load. `KeySource { from: KeyFrom, tap: Pre | Post }`, `KeyFrom { Track(TrackId), Bus(BusId) }` (`Route` cannot name a track). *As built:* there is no `KeyFrom::Send`; sends are not key sources, and a key from a track reads that track's pre- or post-fader tap directly. The key belongs to the slot and moves with it on reorder, copy and presets. `EdgeKind` gains `Key { slot, pre_fader }`.

**Execution rule (dependency layering).** A strip whose insert has a key from another strip renders in a later layer than its key source: `Layering` extends from routing edges to key edges, and phase 1 runs as one `run_strips` call per layer. `process_strip` gains a read-only key view (the source strip's tap or pre buffer, written when its layer finishes), a borrow change that is safe because layers are disjoint. Kick-to-bass must work. A bus key reaches only a strip rendered after the bus fills (an aux). A key cycle is refused by L22 like any loop. If layering proves too costly in slice (c), the fallback is a one-block-delayed key with the delay counted in PDC; "aux-only keys" is rejected as a product limit.

**Loops and sizing.** The load-time cut in `RouteScratch::solve` assumed every loop holds an `Input` edge; a two-track mutual key holds none. The cut rule, `dropped` and `reserve` (count insert slots) change, with a test loading a two-track mutual key from a file; edit-time refusal gains `RouteChange::Key`.

**Delivery and alignment.** The mix writes the key tap into a preallocated per-strip key buffer and passes it through `Plugin::process_with_key(&mut self, io, key: &[Vec<f32>], frames)`, default ignoring the key. Alignment point: the keyed slot's input (inserts before it may be latent, `process_strip` accumulates latency per insert, `lib.rs:1928-1947`). A late key (key latency above the keyed signal's) delays the keyed strip's input through a per-strip pre-slot delay line sized at compile and counted in `strip.latency` and PDC; an early key delays only the key. A Pre tap counts as a consumer for `strip.pre`, `tap_pre` and `path_need_with`. Channel mapping uses `build_matrix` (mono kick into a stereo aux bus).

**Hosts.** The VST3 host activates the aux bus and the CLAP host the sidechain port at instance creation whenever the plug-in declares one, and feeds silence (silence flag) when unrouted, so key edits are ordinary plan changes and never touch a live instance. `run_insert`'s suspend logic (`lib.rs:2081-2113`) considers the key as well as the main input, so a silent main with a loud key does not sleep a ducker. Built-in compressor and gate read the key in place of their own input when set. Implementation is slice (c).

### 5. Hardware inserts
A hardware insert is a send to an output path plus a return from an input path: a sibling `Option<HardwareInsert { send, ret }>` on `Insert` (`Insert` is a struct, `mixer.rs:425`), by path name. **Duplex only:** it needs input and output on one clock, which is ASIO on Windows (`player/device.rs:200-232`); on other backends the drift invalidates a fixed measured latency, so the insert is unavailable and flagged. The return for block N arrives in a later callback: the slot is a send, a FIFO of the measured round-trip length, and a read from the input ring, and `latency()` equals that length (the measured value covers the blocks of delay). A ping measurement writes an impulse on the send path, finds it on the return and stores `{ send, return, device identity, rate, buffer, frames }` per machine. No measurement means zero latency and a flag. A missing path bypasses the insert dry, flagged. Offline render is dry bypass with a flag. Implementation is slice (d).

*As built (slice d):* the implementation uses no in-slot FIFO, because the capture ring already delivers the return one round trip late. The loop check is edit-time plus open-time disabling (an offending insert becomes `Disabled` and runs dry), not a graph edge.

*The converters' look-ahead (amended 2026-11-15, #709; not built; Amendment 2026-11-15 below).* A measurement stores, beside the session rate of its key, the device rate it was taken at, and the round trip without the look-ahead the rate converters added at that device rate ([ADR 0017](0017-clock-contract-annex.md), the rate converters; nothing to remove when the device ran at the session rate). The insert's `latency()` is the stored round trip plus the look-ahead for the device rate now running, computed from the session rate and the device rate in whole plan frames and 0 at equal rates. (Amended 2026-11-16: this was "so one measurement stays right at any device rate"; it is the intended converter-only adjustment of the unbuilt #709 rule, its term is not yet defined, and it cannot assure that the hardware's own delay is the same at another rate.) (Amended 2026-11-16, #724: the converters' added round trip is not a function of the two rates; it depends on the converters' relative phase, the captured input history kept at alignment and the callback endpoints met afterward; the device buffer influences those but does not determine the result alone (ADR 0017, Amendment 2026-11-16). So the look-ahead "computed from the session rate and the device rate" is not yet defined, and #709 waits on a decision. The Amendment 2026-11-16 on the #709 converter term, below, accepted and not built, decides it for paired devices and gives a new rule for figures stored without a device rate.) The device rate is not part of the key. A round trip stored before this rule carries no device rate: it is taken as measured with the device at the session rate, the look-ahead for the device rate now running is added to it, and when that rate is not the session rate the insert shows an amber hint, "measure again at this rate"; it is never adjusted without that hint.

### 6. PDC and L22 across all edge kinds
Main and ordinary output paths are padded to one shared device latency **L = max(Main arrival + M, maximum other sink arrival)**, where M is the running master-chain latency (`crates/mix/src/tail.rs::fold_latency`). Main's pre-master alignment target is L - M; direct output paths do not pass through the master. For Main arrival 0, M = 100 and direct-output arrival 300 frames, L is 300, not 400. A path fed only by a zero-latency track is delayed to L, so stems and cues align with Main sample for sample. Hardware sends themselves flush unaligned: their measured round trip already covers the send/return delay (section 5, as built). `routing.rs::path_need` (formerly `path_need_with`) computes a conservative capacity bound, which can exceed rendered L; it is not the latency readout. The existing `MAX_LATENCY` clamp is unchanged. One stated exception: a path declared "live" (a performer's headphone cue) may opt out of sink padding, off by default; this declaration is not implemented on this base and is a prerequisite specified in amendment rule 4. Sidechain edges align at the keyed slot input (section 4); hardware insert latency counts through `latency()`. `route_graph`, `pdc_visit`, `route_into`, `path_need_with` and `RouteScratch` change together per slice. New `plan_parity` cases for sinks and keys compare against hand-computed golden outputs, not the legacy renderer. Outputs to paths are not loopable edges (sinks have no readers); only key edges add cycles. The offline renderer follows chain latency changes per block; see the amendment in ADR 0038 (#251).

**Low Latency mode (2026-11-04 amendment).** During live playback, temporarily bypass the selected high-latency audio inserts on armed/monitored tracks, their downstream buses and the master. Recompute L from that effective bypassed plan; all other paths keep full compensation to the resulting L. This is separate from a live cue's opt-out: the mode removes insert latency, and a cue declared live still skips its sink padding. Neither switch changes the other's rule. Offline rendering ignores the mode.

### 7. Realtime and publication

Low Latency mode adds a control-thread compile input: the set of insert uids to bypass for rendering (amendment below). It travels with `PreparedPlan`, published and adopted like any bypass plan; the audio thread never computes the set or edits session flags.

Path tables, key sources and the channel map reach the audio thread inside `PreparedPlan` through the bounded queue and the single adoption per callback. Accumulation buffers, key buffers, pre-slot delay lines and sink scratch are allocated by the compiler from the `RenderTarget` and `IoMap` and move with the existing cell moves; `RouteScratch::reserve` grows. **Only a device or opened-channel-count change is a reopen** (`DeviceGeneration` bump). Path and route edits are structural plan changes adopted at a drained boundary, never a stream stop, and must not swap a still-audible output buffer (`Audio::service`). `plan_alloc_probe` gains each new route kind. No `unsafe` is added (ADR 0013).

## Implementation plan: slices, crates, gates

Each slice ships alone and gets a refutation review (ADR 0009). Slices 0 through (e) leave stereo behavior unchanged; (f)'s mode override changes live rendering only when enabled. Rule 4 names two separately reviewed prerequisites: the cue declaration and a repair of master hardware processing. Existing off-mode goldens remain unchanged outside those explicitly added or repaired paths.

**(0) Offline render onto the plan renderer.** Move `RangeRender`, `render_range`, `render_bus` and `engine/src/io.rs` export/bounce onto `PlanCompiler::compile`, `adopt_plan`, `render_active` with an offline target; convert the `plan_parity` oracle tests to golden outputs; then delete `LegacyPlayer` and `MixEngine::render`. New sinks, key edges and hardware inserts are built only on the plan renderer. Gate: `plan_parity` goldens and `engine/tests/bounce.rs` pass bit-identical.

**(a) Open all device outputs; Audio Devices shows them; paths editable.**
Files: `playback` (`lib.rs` `open_device`, `devices.rs` identity, `player/audio.rs`, `player/device.rs` `Player::prepare`, `plan_bridge.rs` `Buffers`, `MeterBank`, `fold`), `mix` (`plan.rs` `RenderTarget`, `compile.rs`), `model` (`IoPath`), `engine` (`setup.io`, `cmd/setup_more.rs`, `cmd/track.rs` `parse_route`, `io.rs` shared input resolution), `ui-studio` (`audio_devices.rs`), `apps/transit` (`config.rs`).
Gate: a fake device opens 10 and 2 channels, cap holds at 32; the `IoMap` round-trips through `ui.json`; a session with "Out 3-4" on the 2-channel fake shows the silent flagged sink with unchanged session text; a golden 5.1 session round-trip (load, save, compare) keeps `main_format()`; stereo audio bit-identical; bus/path collision and missing input path refuse as stated. Note-level real-hardware gate on the Model 12: same ASIO buffer size, round trip and overrun count with 2 channels open versus 10 out / 12 in (cpal's ASIO streams share one buffer set, `player/device.rs:239-244`), and the Scarlett 2i2 unchanged.

**(b) Route tracks, buses and sends to any output path, with consistent PDC.**
Files: `mix` (`route_into`, `process_strip`, send filters at `lib.rs:1735` and `pdc_visit` `1663-1666`, `path_need_with` `2615-2625`, accumulation buffers, `compile.rs`, `plan.rs`), `model` (`route_graph.rs` sinks, `RouteGraph::load` send filter `263-268`), `engine` (`cmd/track.rs`, `cmd/mix.rs:463` send creation targets paths), `ui-studio` (`mixer.rs`), `playback` (`plan_bridge.rs`). Sends now target output paths, so cue mixes work.
Gate: two different tracks with different plug-in latencies routed to two different sinks (Main and a path) land sample-aligned after removing L; overlapping paths sum; a missing path is a silent flagged sink; `plan_alloc_probe` shows zero callback allocations across path edits; golden `plan_parity` cases.

**(c) Sidechain key routes and host wiring.**
Files: `model` (`Insert.key`, `KeyFrom`, `EdgeKind::Key`, `RouteChange::Key`, `route_graph.rs` cut and `reserve`), `mix` (dependency layers, key buffers, pre-slot delay, PDC), `dsp` (`process_with_key`, compressor and gate), `vst3-host`, `clap-host`, `engine`, `ui-studio`.
Gate: key loop refused at edit and cut at load, including a two-track mutual key; kick-to-bass key in the parallel renderer and again with `serial` forced, identical output; late and early keys aligned within one sample with a latent earlier insert; a Pre tap; fixture VST3 and CLAP plug-ins receive the key; a compressor ducked by a kick matches a hand-computed curve; no key leaves the plug-in on its own input unchanged; a silent main with a loud key does not suspend the insert.

**(d) Hardware inserts with latency measurement.**
Files: `model`, `mix` (send/return slot, `latency()`), `playback` (loopback ping, duplex only), `ui-studio`, `apps/transit`.
Gate: a fake-duplex loopback with a known delay measures it to the frame and PDC aligns a parallel dry track; a long-run stability test in the fake; unmeasured flags and counts zero; missing return bypasses dry; offline is dry bypass; Model 12 out 3-4 to in 3-4 loopback recorded as a note.

**(e) Stems.** Bounce over output paths on the plan renderer (needs slice 0). Gate: a stem render per path sums to the main bounce for non-overlapping paths.

**(f) Low Latency mode.** Proposed; implement the eight rules in the 2026-11-04 amendment after rule 4's prerequisites. Touches `crates/mix`, `crates/playback`, `crates/engine` and `crates/ui-studio`; the cue prerequisite also touches `crates/model`. Required gate:

- **Selection and persistence:** deterministic fixture engine tests show a latent master insert delays a live impulse by its reported frames with the mode off and removes that delay with it on. Compare the complete serialized session content with the mode off and on, through save/load and another machine's preferences; allow only explicitly requested ordinary session edits, never a mode-induced change to any field. ## Consequences

- A session built on the TASCAM opens on the Scarlett with path-targeted outputs silent and flagged; nothing is lost, nothing is rewritten, and no cue reaches the PA.
- `route_graph.rs`, `pdc_visit`, `route_into`, `path_need_with` and the compiler change together per slice. Slice 0 removes the second renderer first so each change is made once.
- `Plugin` gains a defaulted method, touching `dsp`, `vst3-host`, `clap-host`; upstream offers need care, as with ADR 0012's note API.
- The settings schema grows (`ui.json` `IoMap` tables, measured latencies); old files load with defaults. The session file is unchanged through (a) and (b), so older builds still read it.
- Stereo-only users pay nothing: one stereo path, identical output. The 32-channel cap is a documented limit raised by one constant and the scratch budget. On Windows, multichannel requires ASIO.

## Alternatives considered

- **Ableton Live's Reduced Latency When Monitoring.** It exempts monitored tracks from compensation but retains the latency of devices on their own route, including the master ([documented behavior](https://help.ableton.com/hc/en-us/articles/209072249-Reduced-Latency-When-Monitoring-FAQ)). That leaves exactly the master-chain delay reported in #321. Transit takes Logic Pro's live-path insert-bypass shape instead ([plug-in latency controls](https://support.apple.com/guide/logicpro/work-with-plug-in-latencies-lgcpe11997ba/mac)).
- **Switch Delay Compensation off outright.** Available in Ableton Live and already in transit as `options.delay_compensation`; it sacrifices alignment throughout playback and still cannot remove an insert's own processing delay. Keep it independent; Low Latency does not flip it.

- **Keep two-channel main plus per-track direct outs.** Smallest change. Rejected: a parallel mechanism beside buses and sends, no cue mix summed from several tracks, no home for sidechain or hardware inserts.
- **A full matrix-mixer UI like RME TotalMix.** Rejected for now: asks users to re-solve routing a session already states, duplicates a mixer, and sums at the device without PDC awareness. Revisit if direct-monitor routing for devices without a hardware mixer becomes a goal.
- **Per-session device channel numbers, no named paths.** Rejected: breaks on any other interface and cannot show a human name. Names resolve per machine; numbers do not.
- **Paths stored in the session (today's `Session::outputs`).** Rejected for paths: the session would carry device facts. It stays only as the main-format source (section 1.3).
- **Cap at the main width, or at 16.** Rejected: 16 is the width of a path, not of a device.
- **Sidechain as a special per-plug-in parameter, or aux-only keys.** Rejected: the first hides a dependency from loop refusal and PDC; the second makes kick-to-bass impossible, the common case.

## Amendment 2026-11-15: a stored round trip excludes the rate converters' look-ahead (#709)

Accepted 2026-11-15 after three judging rounds (proposed the same day). Not built; issue #709. ## Amendment 2026-11-16: the #709 converter term on paired devices (#709)

Accepted 2026-11-16 after three judging rounds (proposed the same day). Not built; issue #709, for v0.7.4. When built it replaces section 5's look-ahead paragraph and the 2026-11-15 amendment's rule for figures stored without a device rate. [ADR 0020](0020-external-instrument-device.md) decision 4 takes the same rule for External Instrument latency. The correction of fact this rests on is the 2026-11-16 amendment above and [ADR 0017](0017-clock-contract-annex.md)'s: since #724 the converters' added round trip depends on the converters' relative phase, the captured input history kept at alignment and the callback endpoints met afterward, so no term computed from the two rates matches it until the code makes it deterministic.

**Decision.**

1. **Scope.** The term applies on a paired device with the transport at speed 1. Paired means the backend condition, not only that a live input is open (`Player::duplex`): the active input belongs to this output callback's clock and cycle, the ring was built with `capture_precedes_render(endpoint)` true (the `ALIGNED_BACKLOG_BLOCKS_PAIRED` case; native ASIO and JACK today, not WASAPI's separate capture and render callbacks), and capture and output frame counts are related by an explicit same-cycle anchor. Hardware inserts are duplex only already (section 5). An External Instrument qualifies when its return comes from such an input; its MIDI need not share the audio callback, because its notes are stamped at presentation time.
2. **The term.** With S the session rate and D the device rate, at a converted rate the term is T = ceil(32·max(1, S/D) − S/D) plan frames: 34 at 48 kHz on 44.1 kHz, 32 at 44.1 on 48, 32 at 48 on 96, 62 at 96 on 48, 32 at 48 on 88.2, 32 at 44.1 on 88.2, 32 at 48 on 176.4 and 32 at 48 on 192. At equal rates at a whole-frame phase it is 0 (the converters pass samples through).
3. **How it is made exact.** The input is aligned from the output converter's coordinates instead of from where its first read stops. A block's frame j, rendered in the callback whose last output frame n sits at render position x, reads the input at device position n + (j − x − T)/q, q = S/D. Every round trip through the converters then gains exactly T plan frames, at every phase and buffer and at every supported attachment after initialization (rule 9 and the build list).
4. **Why T is enough.** The block's last frame satisfies j − x < r_o, r_o = 16·max(1, q) the output converter's reach (`Phase::reach` returns the end of the last output frame's span). Its input position is then before n + (r_o − T)/q, and its taps lie less than r_i = 16·max(1, 1/q) input frames past it. They stop at or before the newest captured frame n when T ≥ r_o + q·(r_i − 1) = 32·max(1, q) − q. T is that bound rounded up to a whole plan frame, for every converter phase, a fraction inherited from another speed included. At 96 on 48 the bound is exactly 62; 61 is not enough for every phase. Today's test admits 61 to 62 there and does not establish 61 for every phase, so the deterministic term adds that frame on purpose. This argument proves the input is available up to the right edge of each read; it does not prove that the history the left edge needs was kept (rule 9).
5. **Stored figures and lookup.** A measurement stores enough to recover both the original measured total and the normalized figure (measured total minus T): the device rate, that the term was in force, and both values. The running T is applied only when the measurement has term provenance and the running alignment is valid (paired, speed 1, initialized). Otherwise the original measured total is used, with the existing rescaling by the session rate, and a hint shows whenever the provenance or the alignment differs. A measurement without term provenance never receives T merely because playback is now paired. A missing measurement stays zero and flagged.
6. **Older figures.** A figure stored without the device rate and term provenance is unknown at every running rate, equal rates included. It is used as stored, with no term added or removed, and the amber hint "measure again at this rate" shows until it is measured again. (This replaces the 2026-11-15 rule that took such figures as measured at equal rates: a figure measured at a converted rate before the rule holds that rate's converter delay, and figures from before #724 can also hold about one device callback.)
7. **Manual latency** (ADR 0020 `manual_ms`): no automatic term and no measurement-provenance hint. While rule 10's alignment is not valid, it shows "timing changed: stop at 1x, then check the manual latency", and the value is left unchanged. It is the user's complete compensation for the current path. It is not adjusted when the device rate or the alignment changes; the user sets it again.
8. **Stated limit.** "One measurement stays right at any device rate" holds only while the hardware's own delay, in time, is the same at both rates. Drivers and interfaces can change their buffering and converter delay with the rate. A fake device cannot establish that; only a measurement at the running rate does. So every measurement other than a manual value shows "measure again at this rate" when it is used at a device rate other than the one it was measured at, term provenance included: normalizing the converters does not validate the hardware's delay. (The External Instrument lookup already tells an exact match, `Measured`, from another rate or buffer, `Stale`.)
9. **History and start-up.** At alignment the ring keeps the available input from the computed first tap onward. When the history a read needs is not there (an empty or short ring, or samples a clear or an earlier commit already discarded), the input reads counted silence while the prescribed coordinates advance; it never holds or shifts the alignment to wait for samples it no longer has, and it resumes when a read's whole span is available. Start-up is bounded while paired capture continues and the history it needs is kept. Let F be the first frame kept from uninterrupted capture, y0 the prescribed first input position, q = S/D and h = `halo(1/q)` (0 at equal rates with a whole-frame phase). The input reads at most ceil(max(0, q·(F + h − y0))) plan frames of silence: each plan frame moves the input position by 1/q input frames, and a read's taps lie within h input frames of its position. The time before capture resumes is not bounded. Tests assert this bound before exact-delay comparisons begin.
10. **Speed changes.** Leaving speed 1 invalidates the deterministic alignment, and returning to speed 1 alone does not restore it: `Transport::apply_speed` changes the timeline's rate but neither the converter phase nor the input alignment, and a converter restart resets the output alone. The alignment is restored only after a converter restart at speed 1 followed by a new alignment from coordinates. Until then the original measured total is used, with the hint "timing changed: stop at 1x, then measure again"; a manual value is left unchanged and shows the manual hint of rule 7. This avoids another audible restart just for returning to speed 1.

**What the slice must build.**

- Output and capture coordinates (the output converter's phase and the device frame of the callback's last output frame) passed through `plan_bridge::render` into the input's alignment. Today that call is only `input.pop_into(&mut self.mix.input, frames, target.sample_rate)`.
- A fractional input start position, including fractions inherited from the output phase's finer denominator (units of 1/(device rate·1000) frame per speed step).
- Start-up and realignment as rule 9 states, for every `align_on_next_read` and clear, with an empty, short or prefilled ring; speed changes as rule 10 states.
- The hardware probe emits its click in render coordinates on its send channels, through the output converter with its history, instead of adding it to device frames after conversion (`probe.add_click(frame, at)` in `fill_inner` today).
- Provenance in both stored records (`HardwareLatency`, `ExternalLatency`): the device rate, whether the term was in force, and both the original measured total and the normalized figure.
- A latency lookup that knows the running device rate and pairing, for hardware inserts (`latency()`) and External Instruments (decision 4's lookup).

**Out of scope, with the behavior.**

- *Separate input and output streams* (capture and render on their own callbacks, or an input on another device): no deterministic term. The original measured total is used, and the panel shows "measure again at this rate" whenever the running device rate, the provenance or the alignment differs from the measurement's. The ring's slack does not make the alignment exact there, and the ring does not compensate independent clock drift.
- *A fractional phase left by a speed change at equal nominal rates, and input backlog accumulated at another speed:* covered by rule 10. The output then reads through the filter with look-ahead (`Phase::whole` takes only whole positions), the backlog stays (`Transport::apply_speed` does not realign the input), no term is claimed, and the original measured total is used with the hint until a converter restart at speed 1 and a new alignment.

**Rejected alternatives.**

- *The high tested figure from the rates (a term per pair, no player change):* not exact. Measured against the probe, the error between a figure and the term is up to two plan frames at 48 on 192, and between two converted rates it is not bounded by one frame. It also normalizes against probe readings that carry the click's hold.
- *Storing the device buffer and computing per buffer:* `ExternalLatency` already stores the buffer and `HardwareLatency` does not. Either way the buffer does not determine the phase or the history kept at alignment, so it cannot give the delay.
- *Tracking the actual phase-dependent delay and normalizing each measurement against it:* exact alignment would then need fractional delay compensation or an equivalent fractional adjustment of the return, and `HwSlot::round_trip` returns whole frames. It is not simpler, and the delay would still vary by attachment.

**Acceptance (the slice's tests).**

- An independent reference, computed offline from a deterministic signal, explicit rational device and session coordinates and a known device-frame delay, without fitting a lag. For a hardware insert it applies the output filter, the device delay and the input filter independently of the alignment code. For an External Instrument it generates the fake synth's device-rate response from the injected MIDI presentation stamps and applies the input filter; there is no output audio filter on that send. The plan's compensated return must match the reference at the prescribed positions, and must fail with the compensation deliberately one frame early and one frame late.
- All eight pairs above, 96 on 48 and 48 on 192 included, and equal rates.
- Attachment with an empty ring and with a prefilled ring, at several different attachment phases; callbacks of fixed and changing size; clears and device reopens. The two limits ADR 0017 states (48 on 192 with 64-frame callbacks; 48 on 96 with a prefilled ring) become cases that give T.
- A loop delay whose length times S/D is a whole number of plan frames, where the comparison is exact; any other loop delay leaves a sub-frame hardware delay, which no converter term removes.
- A measurement at one device rate applied at another gives the same comparison result as a measurement at the running rate, for fixtures with the same physical delay at both rates and a detector bias verified equal at both. The converter term does not remove a rate-dependent bias of onset detection: Measure's onset is the first crossing of a fraction of the filtered attack's peak, which a different filter can move.
- A figure without provenance shows the hint at every rate and is not adjusted. A manual value gets no automatic term and no measurement-provenance hint; while the alignment is not valid it shows "timing changed: stop at 1x, then check the manual latency" and is left unchanged.
- Separate streams excluded explicitly: a test shows no term is added and the hint shows when the running rate differs from the measured one.
- Provenance in both directions: a normalized figure used where the alignment is not valid falls back to the original total with the hint, and a figure without term provenance never gains T on a paired device. A figure at the same rate with the alignment not in force shows the hint.
- Speed 1 → another speed → 1: the hint shows and the original total is used until a restart at speed 1 and a new alignment. A fractional phase at equal rates claims no term.
- Insufficient retained history: counted silence while the coordinates advance, then exact delay.
- A missing measurement stays zero and flagged; records serialized before the change load with the provenance defaults of rule 6.
- A latency change and its alignment are adopted together, with no block that uses one without the other.
- Callbacks split into several blocks by the plan's largest block, loop wraps inside callbacks and count-in ends.
- A capture loss (dropped device frames) invalidates the anchor. The input re-anchors from the next valid same-cycle capture and output pair, keeps the history it can and initializes under rule 9; until then the original measured total is used with the hint. The alignment and the normalized compensation are restored together. A count of accepted frames alone never bridges a loss.

**Cost.** Changes in `crates/playback` (the alignment, the bridge, the probe) and in `crates/model` and `crates/mix` (provenance and lookup). Latency at a converted rate becomes T at every buffer and attachment, not a probe reading that varies with phase. The change from today is T minus the delay the code gives now, which can be a fraction of a frame either way. A null test of a send and return through the converters then has no converter timing residue. The converters' passband and alias error, and a hardware delay that is not a whole number of plan frames, still prevent a bit-exact null at a converted rate.

## Amendment (#431, accepted 2026-11-20; revision accepted 2026-11-20): the server's sources as one input device

Proposed 2026-11-19, accepted 2026-11-20 after one judging round with changes (responses below); not built. **Revised the same day; the revision was accepted after one judging round with changes** (see "Revision 2026-11-20" and "Judging round 2 (#431): responses" at the end): the maintainer cut the scope from a curated source list to one preference, "Show virtual devices", in the Input list. Rules 1 to 5, 10, 12 and 13 and slice C are rewritten. The source list is kept, whole, under Deferred, and slice D is withdrawn. Rules 6 to 9, 11 and 14 keep their numbers, so the briefs for slices A and B still point at the right rules. The heading's title is historical: in the revised scope, one input device at a time may be any group the server offers.

Issue #431, with #759 (input paths) and #689 (a stored round trip after the input changes). The amendment lets the native JACK system ([ADR 0021](0021-native-linux-audio-over-the-jack-client-api.md)) offer non-physical port groups as input devices, moves the input half of section 1.3's table to the input device, and states transit's rule for graph links. ADR 0021 is not changed: quantum and rate changes keep its reset and reopen (rule 7). Sentences of this record that the amendment supersedes:

- Section 1.3, "keyed on audio system plus device name": for the input half, the key becomes the identity of the capture endpoint actually opened (rule 8).
- Section 1.5, "A missing input falls back to the first input path of the same width, else silence with a flag": on every backend, an input path whose name clashes with an output path monitors silence and refuses to record (rule 10). Section 1.4's "never records a wrong channel" is kept, and this case enforces it.

Every other rule of sections 1 to 7 stands. Paths below are relative to `crates/` at `transit` 4020713a; the revision was checked at a04e4fde, which changes nothing under `crates/`. Each statement about today's code cites the line read; anything not read is marked *open question* or *hypothesis*.

### Context

A tester's desktop runs PipeWire with dozens of nodes: hardware captures, virtual sinks with monitor ports, virtual sources and application streams. Native JACK (through PipeWire's JACK library) lists three hardware capture devices there, opens one at a time and links transit's two input ports to it. Anything else, an application's output or a sink's monitor, has to be linked to `transit:in_1` by hand in an external graph tool. That works (a take recorded with audio), but nobody finds it, and the I/O table reshapes input paths whenever another input of a different width opens (#759). What the code does today:

- **Only physical ports are devices.** Enumeration asks the server for audio ports with `JackPortIsPhysical` added to the direction flag (`audio-jack/src/ffi.rs:286-293`, both directions at `374-378`) and groups them by the client part of their names (`audio-jack/src/devices.rs:116-132`). Only ports the server marks physical appear in today's device enumeration; which virtual sources, application outputs and monitors PipeWire marks physical remains to be measured (Q1). The backend already expects a port group of `monitor_*` capture ports and labels it (`playback/src/backend/native.rs:283-286`, `playback/src/system_audio.rs:796-805`); the tester's list showed no monitors.
- **One client links its inputs to one group.** The first open creates the client and registers `in_1..in_N` for every capture port of the chosen group (`audio-jack/src/session.rs:171-185`, `482-514`). At start it links the group's i-th capture port to `in_i` (`session.rs:502-509`, `556-563`), unless `TRANSIT_JACK_AUTOCONNECT=0` (`session.rs:44-46`, `81-83`). A link that fails is logged and the port is left unlinked (`session.rs:558-561`). The chosen input names any group with capture ports, else the output's own, else the first (`session.rs:319-336`). Capture and render run in one process callback, capture first (`session.rs:338-342`), so the input is paired with the output in the sense of the 2026-11-16 #709 amendment, rule 1.
- **Ports are fixed while the client runs.** An open after a start is refused (`session.rs:492-494`), and the port arrays are handed to the callback state once, at activation (`ffi.rs:403-408`). A different number of input ports is a new client, as section 7 already says ("only a device or opened-channel-count change is a reopen"). Input and output share that one client (`session.rs:314-317`), so any input reopen is a reopen of both.
- **Links made outside transit live only as long as the client.** transit binds no disconnect call: the function table has `jack_connect` and no `jack_disconnect` (`audio-jack/src/sys.rs:66-119`, `99-100`). But the last direction's stop deactivates the client (`session.rs:571-597`), and dropping the last stream closes it (`session.rs:599-611`, `814-830`); jack.h, as quoted in the binding, says deactivation disconnects every port of the client (`ffi.rs:507-514`). A reopen must close the old client first, because the slot refuses a second open on a started session (`session.rs:201-216`, `492-494`). So every reopen (a quantum or rate change, the server's return, Reconnect, Apply) drops every link other clients made to transit's ports, and the new ports get only transit's own links. Reading a port's links is bound for tests only (`ffi.rs:461-494`, `sys.rs:104-108`).
- **A quantum change ends a take.** The buffer size callback stores the quantum (`audio-jack/src/engine.rs:216-221`); the watcher turns a rate or quantum other than the open ones into `ResetRequested` once per new pair (`session.rs:633-637`) and logs "reopening" (`session.rs:716-720`). The Player's error callback marks the output gone and stops playing (`playback/src/player/device.rs:1302-1316`); the app stops the transport, keeps the take and reopens (`ui-studio/src/host/reconnect.rs:29-38`). This is ADR 0021's 2026-10-25 amendment ("Buffer size and rate changes are a reopen"). #591 item 3 asks for the chunked path without a reopen; this amendment does not take it (rule 7, Deferred).
- **No port-registration, rename, connection or latency callback is bound.** The table binds the process, buffer size, sample rate, xrun and shutdown callbacks (`sys.rs:85-94`, installed at `ffi.rs:412-440`); nothing tells the backend that a port appeared, went away or was renamed. `JackStream::latency` returns `None` ("Port latencies are slice 3", `session.rs:797-800`), and `jack_port_get_latency_range` is not in the table.
- **The I/O table belongs to the output.** The open builds the default table for (system, output name) with the duplex input's channel count (`playback/src/player/device/open.rs:480-485`, `512`). The app swaps in the saved table with the same key (`ui-studio/src/io_settings.rs:16-23`) and later sets a separate input's count on it (`io_settings.rs:54-58`). On a channel-count change, `reconcile` drops paths that no longer fit and adds default inputs when the previous input count was zero (`model/src/io_map.rs:536-547`, `559-566`); repairing a missing Main also adds defaults (`io_map.rs:548-558`). Otherwise an input-width increase does not restore them. So going from a 2-channel input to a 1-channel input deletes "In 2" and "In 1-2", and going back adds nothing (#759 case 2), and a table that older builds saved with inputs but no input paths is never repaired (#759 case 1). Hardware insert and External Instrument measurements live in the same table (`io_map.rs:181-184`) and do not record which input they returned through (`io_map.rs:77-86`, `94-116`), so a round trip measured through one JACK input group is applied through another (#689).
- **Which device the input is.** The recorder's `device_name` is the name of the endpoint object passed to the capture open (`playback/src/record.rs:247`, `491`), which is not always the capture endpoint actually opened. On ASIO and native WASAPI the object passed is the output's own endpoint (the trait default returns `render.clone()`, `audio-backend/src/lib.rs:647-649`). Native WASAPI then opens the capture endpoint paired with that render endpoint, resolved afresh at each open (`audio-wasapi/src/lib.rs:244-258`, the resolution at `256`), so the recorder's name is the output's while the stream comes from another endpoint. JACK resolves the chosen group into the endpoint it passes (`session.rs:324-336`); cpal opens its input as its own device (`playback/src/backend/cpal.rs:346-350`).
- **Track inputs resolve by name, with a numeric fallback.** `input_channel` resolves a name through the table, else keeps the label meaning ("In 3" is channel 3), and an unrecognized name falls back to channel 0 (`io_map.rs:229-242`); `live_input_channel` wraps a device path to the live channel count and keeps "System Audio" silent when it does not run (`io_map.rs:254-266`). The System Audio pair is Windows only (`playback/src/system_audio.rs:192-200`); on Linux "System Audio" is only the Input list's label for a monitor source (`ui-studio/src/audio_devices_system.rs:71-78`).
- **A chosen input that is missing falls back today.** When the chosen group is not on the server, the duplex input logs a warning and opens the output's own group if it has capture ports, else the first group with capture ports (`session.rs:319-336`). The recorder then carries the name of the group that actually opened (`record.rs:491`). The Input dropdown shows a saved choice that is not offered as "Not available (falls back to the default)" (`ui-studio/src/audio_devices/window.rs:25-31`). Switching the audio system clears the chosen output and input (`window.rs:323-326`). Nothing reopens the input when a group appears or comes back: no registration callback is bound (above), and the JACK backend does not implement the trait's device-change hook, whose default reports that it cannot (`audio-backend/src/lib.rs:704`, not overridden in `audio-jack/src/session.rs:295-380`).
- **What PipeWire's JACK library reports.** These facts were read from the library's public source, MIT (`pipewire-jack/src/pipewire-jack.c` at upstream commit 0e30a57, line numbers from that commit):
  - A port is reported `JackPortIsPhysical` only when its PipeWire property `port.physical` is set (3964-3970). A virtual sink, a virtual source or an application stream is physical only if its node sets that property.
  - A sink's monitor ports are shown by default (`jack.show-monitor`, 3980, default at 4521), under the sink's own client name (`jack.merge-monitor`, 4523, and 3737-3740).
  - A client's name is the node's description, else its nick, else its name. The application's name is put in front ("<app>/<name>") when it differs (3866-3885). The media title is never used.
  - Several streams from one PipeWire client share one client name (3890-3893), and a port whose full name is already taken gets "-<object serial>" appended (3745-3748).
  - Every JACK client gets `node.lock-quantum=true` by default, as read from the same source (line not recorded here). That default proves neither an immutable quantum nor an immutable rate (rule 12).

  Inferred: an application playing one stream keeps its client and port names across restarts. An application playing several streams from one process presents them as one group whose later ports carry a serial that changes, so that group's channel count and order can change between opens. A virtual sink or virtual source with a fixed name keeps its names. Stable names alone do not guarantee a stable port order; rule 5's guard checks the order at every open. Which of the tester's nodes set `port.physical` is still to be read on the machine (rule 12).

Convention: Ableton and Logic both take every input from the one chosen input device and let the user name and pair its channels (Ableton's Input Config, Logic's I/O Labels). Neither offers other applications' streams as inputs. On a JACK or PipeWire server those streams are ports like any other, which is why #431 asks for them. The revised rule keeps the convention exactly: one chosen input device, its channels named as paths. It only lets that device be a virtual one. Mixing several sources stays in the server, where virtual sinks already do it.

### Decision

1. **Show virtual devices (revised 2026-11-20).** On the native JACK system, Audio Devices > Input gets one checkbox, **Show virtual devices**, off by default. It is saved per machine as `AudioConfig.jack_show_virtual: bool` (serde default false) beside `input` (`playback/src/devices.rs:167-203`).
   - *Off.* Today's list: port groups of the ports the server marks physical (`ffi.rs:286-293`), grouped by client (`devices.rs:116-132`).
   - *On.* The list also offers every eligible *virtual device*: the audio output ports of one client that the server does not mark physical, grouped by the same rule. That includes a virtual sink's monitor ports, a virtual source and an application's output, as far as the server presents them as output ports.
   - *Eligibility (one rule, revised in judging round 2).* A virtual device is eligible when all of these hold:
     - its ports are audio output ports the server does not mark physical (MIDI is excluded by type, as today, `ffi.rs:293`);
     - its client has no physical audio output ports (no mixing: physical and non-physical ports are never put in one device, and such a client is listed as today, a stated limit);
     - its client is not a client transit currently owns. That means every session client and every probe client, by the actual name the server assigned it (`JackClient::name`, `api.rs:62-63`), not by the requested `CLIENT_NAME` or `PROBE_NAME` (`audio-jack/src/lib.rs:73-75`) alone, since the server may make either unique.

     The same rule decides what the list offers and how a saved name resolves (rule 2).
   - *The server's flag only.* Classification is the server's physical flag and nothing else. Nothing is grouped or labeled by a kind guessed from port names, except the existing monitor label (rule 13, *Feedback*).
   - *The output side.* It lists physical playback ports only, as today.
   - *No choice made.* With no chosen input (`AudioConfig.input` empty), the input keeps resolving among physical groups only, the output's own and then the first (`session.rs:332-335`). So turning the preference on never changes an input the user did not choose.
   - *The note.* One line under the checkbox: "An application playing several streams appears as one device whose ports can change between opens; paths over changed ports stay off until you use the current ports."

2. **A virtual device opens like a port group (revised 2026-11-20).** A virtual device is chosen, opened, linked and saved exactly like a hardware port group:
   - One input device at a time.
   - transit registers one input port per port of the group and links the group's i-th port to `in_i` through the existing loop (`session.rs:482-514`, `502-509`, `556-563`).
   - The choice is saved by name in `AudioConfig.input` (`playback/src/devices.rs:176`).
   - The open resolves a saved name among all eligible groups (rule 1's eligibility), physical and virtual, whatever the preference: the preference filters only what the list offers. A saved name that is not eligible, for example the name of a client transit now owns, is treated as absent (rule 4).
   - Its input identity (rule 8) is the group name.

   There is no list of sources and no per-entry state.

3. **The chosen input is always shown (revised 2026-11-20).** On the JACK system the dropdown shows the chosen input under its own name whenever it is present, with the preference on or off. When it is absent, it shows "<name> (not present: no input opens)" (rule 4) instead of today's "Not available (falls back to the default)" (`window.rs:25-31`). Turning the preference off never hides or clears the active choice.

4. **A chosen input that is absent opens no input (revised 2026-11-20).**
   - *At open.* On the JACK system, a chosen input that is not on the server opens no input, for virtual and hardware groups alike. The open's existing soft input failure (`open.rs:547`) carries "The chosen input "<name>" is not present; no input opened. Use Reconnect when it is back." No other group is substituted. This replaces the fallback in `duplex_capture_endpoint` (`session.rs:326-331`) when a choice is made; with no choice, the default resolution of rule 1 is unchanged.
   - *While running.* When a chosen group's ports go away, transit's input ports are left unlinked and deliver silence, and transit is not told (Context). That ports which go away leave no link is *inferred* from the server removing a port; it is not read here.
   - *When it comes back.* Nothing reopens or relinks the input. The user presses Reconnect or Apply. No callback is added for this.
   - *What changes for hardware users (settled in judging round 2: the rule applies to hardware and virtual inputs).* A first run is unchanged, because with no saved choice the input still resolves among physical groups (rule 1). Only an explicit choice that is absent behaves differently. Today it records from the output's own group or the first group (`session.rs:332-335`), a source the user did not choose. A capture group that was renamed, for example by a PipeWire profile change, or a name saved on another machine, now needs the input chosen again, even while the output is still present. That intentionally removes today's convenient but possibly wrong-source fallback. The output keeps running: the input failure is the existing soft one (`open.rs:547`). A system switch clears the choice (`window.rs:323-326`), so a name from another audio system does not reach this rule.

5. **Channel order and stability (revised 2026-11-20).** A virtual device's channels are its ports in the order the server lists them (`ffi.rs:298-308`; grouping keeps that order, `devices.rs:116-132`), named by the ports' short names (`devices.rs:36-39`), as for hardware.
   - *Dependable.* A virtual sink's monitor or a virtual source keeps its names (Context). That makes it the dependable choice, but stable names alone do not guarantee a stable port order; the guard below checks it.
   - *Not stable.* An application playing several streams is offered, but its channel count and order can change between opens (Context), and the note of rule 1 says so.
   - *Width changes.* Slice A's rules cover a width change: paths that do not fit become unavailable and keep their definitions, widening re-enables them (rule 9), and a clashing name never records another channel (rule 10).
   - *The port-mapping guard (judging round 2; slice C).* The ordered port names are stored with each virtual input table (an `InputMap` field, serde default empty, written only for virtual devices; slice A's record is otherwise unchanged).
     - The first creation of the table sets this baseline, and a reopen never replaces it silently.
     - At open, a path containing an index whose port name changed or disappeared becomes unavailable as a whole, without numeric fallback. It monitors silence and refuses recording with the path named, as rule 10's unresolved state does. Its definition and the saved mapping are kept.
     - It stays so until the original mapping returns or the user accepts the current mapping while stopped. **Use the current ports** is one action on the I/O paths page, shown only when a mismatch exists; it replaces the baseline with the ports now open.
     - Port names are addresses, so the guard detects changed or missing addresses. It cannot detect a different stream that reuses the same port name.
     - Rule 6 likewise drops a restored outside link whose port changed.

6. **transit does not explicitly disconnect outside links, and preserves eligible links across its own reopen.** This holds for every port group, physical or virtual. transit makes only its own links (the group's i-th capture port to `in_i`, `out_i` to the group's i-th playback port) and binds no disconnect call. Closing the client drops every link of its ports (Context), so a reopen restores the others:
   - *The snapshot.* The snapshot belongs to one explicit reopen operation and is transferred outside the dying backend session. It is consumed once by that operation's replacement client. Quitting, switching servers or abandoning the operation discards it. It is not saved.
   - *Taking it.* The snapshot is taken on a control thread before the first deactivation, never in a JACK callback or the Player's error callback, with `jack_port_get_all_connections` (bound today for tests only, `ffi.rs:461-494`). Snapshot and client lifetime operations are serialized. A transit endpoint is stored as direction plus local port index and mapped to the replacement client's actual assigned name. A remote endpoint is stored by exact full name, and its direction and type are validated before connecting.
   - *Restoring.* Existing links, including `EEXIST`, count as restored. A port disappearing between enumeration and connection is a failed restore, logged once and not retried. A link to `in_k` or `out_k` beyond the new port count is dropped and logged. Links equal to configured transit links are classified as transit links, even if another client originally made them.
   - *Meaning.* Outside links are restored only where the transit port keeps its endpoint and channel meaning. An endpoint change, or a group whose k-th port has another name after the reopen (a virtual device's ports can change, rule 5), changes that meaning for the affected ports and drops their saved links with a visible diagnostic. It does not attach an old patch to a different source. (Revised 2026-11-20: this was "a source-list edit or endpoint change".)
   - *Limits.* After a server shutdown the client is gone before anything can be read (`session.rs:614-625`), so nothing is restored then. The snapshot is best effort: graph edits racing with the snapshot or the deactivation cannot be made atomic by this scheme.
   - *What a user sees.* Today a quantum change stops the transport, keeps the take up to that point and reopens the device, and every hand-made link to transit's ports is gone. After slice B the same happens, and the links come back.

7. **Timing changes keep ADR 0021's reset and reopen.** Quantum and rate changes retain ADR 0021's existing reset/reopen behavior: stop transport, preserve the take and reopen (Context). Uninterrupted quantum changes are deferred to a separate timing-contract amendment (Deferred) and are not a prerequisite for virtual devices. A virtual device may run on another driver, so Audio Devices warns, under **Show virtual devices** and in the hover of each virtual device in the Input list (revised 2026-11-20; this was the source list page): "Choosing a virtual device can change the server's buffer size or rate; transit then stops, keeps the take and reopens."

8. **The input half of the table belongs to the input device.** The saved tables are kept per side. Output paths, Main, `hardware_latency` and `external_latency` stay in `UiState.io_maps`, keyed by (audio system, output device) as today (`ui-studio/src/ui_state.rs:24-25`). Input paths move to a new `UiState.input_maps: Vec<InputMap>` (ui.json key `input_maps`, serde default, bounded at 64 like `io_maps`, `io_settings.rs:10-11`), keyed by (audio system, input identity).
   - *Input identity.* Input-map and measurement identity comes from the capture endpoint actually opened, reported by the backend; display names are separate. A backend's stable endpoint identifier is used where available, otherwise the backend's exact name, with its stated rename and duplicate-name limitation. ASIO uses its driver's identity, JACK the group name, a hardware or a virtual device (revised 2026-11-20; the reserved source list identity went with the source list), native WASAPI the resolved capture endpoint identifier (`audio-wasapi/src/lib.rs:256`), not the render endpoint's name, and cpal its input device's name. The capture open reports this identity (a new field beside `Achieved`; the recorder's `device_name`, `record.rs:491`, stays the display name).
   - *No substitution.* An unavailable or ambiguously identified input does not select another device's saved map. A failed input open does not erase its saved paths.
   - *The record.* `InputMap { system, device, inputs, defaults_for, paths }`: `device` is the input identity, `inputs` the open input's channel count, and `defaults_for` the width the default input paths were last made for (rule 9). A missing `input_maps` record and an explicitly empty one differ: the first may take an old table's input half (rule 11), the second is the user's empty table and is never refilled automatically.
   - *Composition.* The engine keeps one `IoMap` (`engine/src/lib.rs:333-351`): the output record's outputs, Main and measurements, plus the input record's count and paths. `IoMap` gains `input_device: String` (serde default empty) naming the input record. Saving splits it again (rule 11 for records older builds wrote).
   - *Clashes.* Names stay unique across both directions (section 1.4, `io_map.rs:369-381`). When a record's input path has the name of an output path of the record it joins, the input path is unresolved on every backend (rule 10). It stays in its record and is listed on the I/O paths page with "same name as an output path: rename one".
   - *Silent device.* `--null-audio` saves neither half (`io_settings.rs:44-45`, `63-66`).

9. **Default input paths follow the width.** This applies to every port group, physical or virtual, and to every other system.
   - *Wider.* When the open input has more channels than `defaults_for`, the defaults for the new width are added ("In 1" per channel and stereo pairs, `io_map.rs:288-307`). Generated defaults never overwrite an existing definition: a name already present, a user path or a renamed default is left as it is.
   - *Narrower.* A narrower open makes out-of-range paths unavailable but retains their definitions; widening re-enables them.
   - *When it changes.* `defaults_for` becomes the open width only after a successful input open, not after an input failure.
   - *Removed defaults.* A default the user removed stays removed while the width does not grow past `defaults_for`. A record without `defaults_for` counts as 0 (#759 case 1, rule 11).

10. **Names and resolution (revised 2026-11-20; the source list's naming and resolution rules moved to Deferred).**
    - *Clashes, on every backend.* An input path whose name clashes with an output path (rule 8) is unresolved. It monitors silence and refuses recording with the path named in the error. It never falls through to a numeric channel (`io_map.rs:240-241` today) or wraps to another channel (`io_map.rs:265` today). A hardware insert using it gets the existing flagged dry bypass, an External Instrument gets an unavailable return, and calibration refuses it. This supersedes section 1.5's fallback for this case (opening paragraph) and keeps section 1.4's "never records a wrong channel".
    - *Default names.* Every port group, physical or virtual, keeps the defaults "In 1" and "In 1-2" (section 1.2), made by rule 9. Defaults are never regenerated automatically. **Add default paths** (rule 14) is the explicit, idempotent exception: it fills missing defaults without duplicating renamed paths or altering existing definitions. Names use the existing case-insensitive comparison (`io_map.rs:328-330`) and the reserved "System Audio" (`io_map.rs:13-15`, `373-375`); a collision with a bus follows section 1.4 (the bus wins and the route is flagged).
    - *Other unresolved names.* On a port group, physical or virtual, other unresolved names keep today's label meaning (`io_map.rs:236-242`). A session's "In 1" on a virtual device reads its first port.

11. **Tables saved by older builds.** Old input paths are preserved on disk, not imported. An older build wrote one table per (system, output device) holding both halves, in the serialized `IoMap` form (`io_map.rs:169-194`; `IoPath.live` is absent from files written before it existed, `io_map.rs:30-32`).
    - *Never erased.* A new build reads and writes only the output half of a record an older build saved. The struct already carries every field of that form (`io_map.rs:173-184`, `serde(default)` and no unknown-field refusal at `171-172`), so a new build that saves the record writes its `inputs` and input `paths` back exactly as it read them, and applies no input-side reconcile to them. No new field is needed, and nothing in a new build reads them except the next bullet. A record that a new build creates has `inputs: 0` and no input paths.
    - *Automatic use only where ownership is established.* When no `input_maps` record exists for the open input identity, and an old record's key is that actual input identity, its input half is the starting input record. This happens, for example, on ASIO, where driver, output and input are one, or for a JACK group that was earlier the output and is now the input. Paths that do not fit are unavailable (rule 9), and the defaults for the open width are added once, because there is no `defaults_for` (#759 case 1: a table that says 2 inputs but holds no input paths gets "In 1", "In 2" and "In 1-2"). Otherwise the input record starts from the defaults for the open input.
    - *No inference.* The ownership of a separate capture device is never inferred from an output key. A native WASAPI record is keyed by the render endpoint's name (`open.rs:462`, `512`) and does not establish which paired capture endpoint its input paths belonged to, so it is not used for the input.
    - *Measurements.* An old measurement is applied only when its actual return identity is established, that is, when the old record's key is the open input identity as above; equality of two display names is insufficient. Otherwise it is retained and shows "measure again".
    - *Downgrade.* An older build reading a preserved record sees its own input half. Reading a record a new build created, it sees 0 inputs and makes its own default input paths (`io_map.rs:559-566`).
    - *Import.* An explicit action that copies an old input half into the selected input device is deferred until someone needs it (Deferred).

    The release notes carry, under "Before you upgrade": "⚠️ **Input paths now belong to the actual input device.** Output paths are kept. Input paths you made by hand for an input that was a different device from the output are not shown for that input; they stay in the settings file, unused. On Windows, a WASAPI input paired with an output gets its own paths, starting from the defaults. A hardware insert or External Instrument measurement whose return input cannot be established says Measure again. Going back to an older build may show default inputs."

12. **Experiment on a real PipeWire machine (revised 2026-11-20 and in judging round 2; bounded; gates slice C and the release).** Fakes cannot show which nodes a desktop marks physical, or what the server does when transit links a node on another driver. On the tester's machine, transit runs on Native JACK.
    1. Read the forced quantum and rate settings with `pw-metadata -n settings 0` at the start, and check at the end that they did not change. Record `pw-jack jack_lsp -c -p` (port flags and links).
    2. Turn **Show virtual devices** on. Pick a virtual sink's monitor, then a virtual source, and for each record a short take to confirm audio arrives.
    3. For each pick, identify the drivers actually exercised (`pw-top -b -n 3` before and after: each node's driver, quantum and rate). Record the buffer size transit requested and the one it achieved (Audio Devices' requested-versus-running line, ADR 0021's 2026-10-25 amendment), so that transit's own request is not mistaken for an effect of linking. If no node on a different driver is exercised, mark that case untested.
    4. For each device, compare `pw-link -l` right after opening and again after a minute of recording. A final snapshot alone cannot tell a failed first connection from a later removal.

    About 15 minutes.
    - *H1, an observation question.* Under the tested configuration, does selecting and linking a group on another driver change the achieved quantum or rate? The library's `node.lock-quantum=true` default (Context) settles neither. No quantum change is a valid observation.
    - *H2.* The session manager does not remove links it did not make.
    - *Take preservation.* Selecting a device before recording does not test it; an asynchronous timing reset is covered by the existing deterministic reset gates (rule 7).
    - *If the achieved quantum or rate changes,* keep reset/reopen and take preservation, document the observed trigger, and make no uninterrupted-recording claim.
    - *If H2 is false,* transit does not fight the session manager by reconnecting. Slice C and the release remain blocked until a tested coexistence configuration is documented or a revised link-ownership design is accepted.

    One run supports the tested configuration, not every PipeWire desktop.

13. **Interactions.**
    - *Hardware inserts and External Instruments (#689).* `HardwareLatency` and `ExternalLatency` gain `input_device: String` (serde default empty): the input identity the return came through (rule 8). A measurement through a virtual device is valid only while that group's port names, in order, are the ones it was measured through. Slice C stores them with the measurement, and a mismatch shows "measure again" (revised 2026-11-20; this was the source list's mapping). A figure whose identity or ports do not match is not applied; the insert shows "measure again" and counts zero, as an unmeasured insert does (section 5). The JACK loopback calibration is bound the same way (judging round 2). Today it is keyed by the input group that opened (`playback/src/player/device/open.rs:474-479`) and looked up for the open request (`open.rs:503-510`, the JACK branch at `505-507`). For a virtual device it also records the ordered port names it was measured through. A missing or mismatching mapping means "measure again", and no stale correction is applied. Old figures follow rule 11. Section 5's duplex rule is met: every port group arrives on the one client and callback (`session.rs:338-342`).
    - *The recorder's clock.* A virtual device adds no clock domain on transit's side. It reaches transit's capture callback in the same process cycle as the render, so the input stays paired (2026-11-16 #709 amendment, rule 1), and the retained-history refusal ("recording start fell outside retained input history", `playback/src/record/start.rs:410`, `496-501`) is not changed by this amendment. This record makes no claim about how the server delivers a node that runs on another driver; rule 12 does not test that timing property.
    - *Latency.* A shared callback establishes delivery coordinates, not equal physical capture latency. Ordinary inputs receive no automatic compensation for another application's processing, buffering or cross-driver resampling. Monitoring includes that delay; PDC and Low Latency mode cannot remove unreported upstream delay. The latency readout does not claim to include it. Port latencies are not read today (`session.rs:797-800`); reading `jack_port_get_latency_range` is ADR 0021 slice 3, not this amendment.
    - *Feedback (revised 2026-11-20).* Choosing the monitor of the output transit plays to, with monitoring on, makes a loop. Today:
      - The Input list labels a Linux monitor source "System Audio (monitor of <output>)" from its name alone, through `monitor_label(&d.name, &[])` (`ui-studio/src/audio_devices_system.rs:71-78`).

    - *Sessions and offline render.* The preference and the input maps remain machine preferences. Sessions carry path names only; moving a session never copies or guesses device names.     - *System Audio.* The Windows pair is unchanged (`system_audio.rs:192-200`). On Linux, a sink's monitor may be offered as a virtual device (rule 1) and is labeled as above.
    - *The 32-channel cap.* A virtual device is a port group and follows the same cap. The JACK backend asks for every port of a group with no 32 cap (`session.rs:171-185`, `346-349`), while the table caps at 32 (`io_map.rs:269-274`); what a wider group does downstream was not read. Slice A resolves it before landing: the existing 32-channel limit is enforced safely, or the behavior beyond 32 is explicit and bounded.

    - *Other systems.* There is no virtual-devices preference outside JACK, but rules 8 to 11 apply everywhere. #### The source list as accepted on 2026-11-20 (deferred; not built)

In this block, "rule 1" to "rule 5" and "rule 10" mean the items below, and "slices C and D" mean the two slices at its end. Rules 6 to 9, 11 and 14 are the amendment's own. Two parts would have to be revisited when it is picked up. Rule 6's restore by port index already covers changed meaning, so a reorder is a case of it. The port registration and rename callbacks of rule 4 are not bound by the revised scope. The accepted text's real-machine experiment (live linking, list edits, H3) was superseded by the revised rule 12 and is not retained. Its H3 outcome belongs here: if an application's port names change across restarts, retain exact-name matching and require stopped replacement; do not guess another port identity.

1. **The source list is an input endpoint of the JACK system.** Beside the port groups, Audio Devices > Input on the native JACK system offers one more entry, **Source list**, with its channel count ("Source list · 5 ch"). Choosing it makes the input the user's list of sources (rule 2); choosing a port group keeps today's behavior. The output stays a port group. The name is reserved: a port group whose client name is exactly "Source list" is not offered as an input device under that name (its ports can still be added to the list). The working name "All sources" is not used, because the endpoint carries the sources the user chose, not every source. Other systems list no such entry. The entry is not offered until the page that edits the list exists (slices C and D).

2. **A source, and the list.** A *source* is an audio port of another client that data can be read from: `jack_get_ports` with the audio type and `JackPortIsOutput`, without `JackPortIsPhysical` (today's call minus the flag, `ffi.rs:286-293`). The ports of every client transit owns (its session client, under the name the server gave it, and its probe client) are excluded. That covers hardware captures, sink monitors, virtual sources and application outputs, as far as the server presents them as output ports; MIDI ports are excluded by the type, as today. The list is per machine, saved as `AudioConfig.jack_sources: Vec<String>` (serde default empty) beside `input` (`playback/src/devices.rs:167-203`), because the open reads only `AudioConfig` (`open.rs:458-470`). Each entry is one source's full port name, and its position is its channel number (entry 1 is device channel 1).

   Full port names are exact addresses, not guaranteed identities across application restarts. No suffix stripping, fuzzy matching or automatic substitution is allowed. A changed name leaves the entry unresolved until the user replaces it while stopped (**Replace source**, rule 5). Replacement keeps the entry's channel position and path names but invalidates measurements that use that entry. Reuse of the same full name is treated as the same configured address; transit cannot establish application identity from it.

   The list is validated when the configuration loads and at every command that changes it: at most `MAX_DEVICE_CHANNELS` (32, `io_map.rs:10`) entries, exact names unique, each a valid non-empty port name, the audio-output direction when the port is present, and no port of a transit-owned client. An invalid saved list produces a diagnostic in Audio Devices and opens no input from it; it is never silently truncated or renumbered. An entry may name a port that does not exist now. Every port of the server as a channel is rejected (Alternatives).

3. **Opening the list.** The endpoint is a `JackDevice` whose capture ports are the list in order (`audio-jack/src/devices.rs:14-25` already holds full port names), so `capture_format` gives the list length (`session.rs:346-349`), and the open registers `in_1..in_N`, one per entry, with the names ADR 0021 keeps stable. At start transit links entry k to `in_k` through the existing loop (`session.rs:502-509`, `556-563`). Nothing is renumbered when a source is missing. An absent configured source contributes silence. Another client may nevertheless connect audio to that transit input; such outside links are shown separately, so "source not present" does not claim that the input is silent. An empty list opens no input: the open's existing refusal of 0 channels (`session.rs:197-199`) becomes the existing soft input failure (`open.rs:547`) with the text "The source list is empty: add a source". `TRANSIT_JACK_AUTOCONNECT=0` turns off these links as it turns off the port group links.

4. **Reappearing sources.** The backend tracks each entry's presence. Initial activation and an absent-to-present transition each permit one automatic connection attempt from the source to its `in_k`. An unrelated registration event does not restore a link removed while its source remained present. Auto-connect off suppresses both the initial and the reappearance connections.
   - *How the backend learns.* A port registration callback (`jack_set_port_registration_callback`) and a port rename callback (`jack_set_port_rename_callback`) are installed with the others, before activation (`ffi.rs:412-440`). Like every non-process callback (ADR 0021 decision 4), each only sets one atomic flag. The watcher (`session.rs:662-727`, every 20 ms) clears the flag, then lists the sources once with `jack_get_ports` and compares them with the last listing. A notification that arrives during the listing sets the flag again, so events are coalesced and none is lost. The first listing runs after the callbacks are installed and the client is active, so a port that appears in between is seen.
   - *Renames.* A rename is handled as the old name going absent and the new name appearing. An entry follows its exact name only (rule 2), so a renamed source leaves its entry unresolved.
   - *Failures.* A connection that fails is logged once per transition with the entry, the port and the server's code, and the page shows "could not link"; it is retried only at the next absent-to-present transition.
   - *What stays manual.* A source that goes away needs no action: the server removes its links. The flags also refresh the presence the page shows.
   - *Cost.* Two new functions in the table, two new `extern "C"` trampolines under `catch_unwind` in `callback.rs` with quoted SAFETY notes (ADR 0013, ADR 0021 decision 2), and fake-server events; no real-time work. Installing before activation and doing only atomic notification is the conservative choice whatever the header guarantees. The binding quotes the applicable header's actual guarantee for each call (Q5). If PipeWire's library does not deliver the notifications, the fallback is control-side reconciliation: a listing on a slower watcher period, at the cost of one server listing per period.

5. **Changing the list.** Adding, removing, replacing or reordering entries changes the ports or their meaning. A source-list edit is one coordinated reopen of the shared JACK input/output client (`session.rs:314-317`). All entry points (the page, the control channel and headless commands) reject edits during playback, recording, count-in, a pending record start or an active measurement, with "Stop the transport to change the source list". Edits are applied while stopped, and an edit that is applied reopens once.
   - *Reorder.* Reordering permutes every path's channel indices while preserving channel order within the path, width, format and name.
   - *Remove.* Removing a source makes every path containing it unavailable as a whole; it does not collapse a stereo or surround path onto its surviving channels. The unavailable definition is kept for repair and shown on the page, and session references are unchanged.
   - *Replace.* **Replace source** puts another port at the entry's position (rule 2); paths over that channel stay available.
   - *Add.* Adding appends an entry and its defaults (rule 10).
   - *Measurements.* A replacement, a removal or a changed return-channel mapping invalidates the affected hardware insert, External Instrument and loopback calibration measurements. Retaining a path name alone does not validate a measurement.
   - *One operation.* The configuration, the path changes and the reopen form one operation. A failed open leaves a visible unavailable configuration and never substitutes another source.

10. **Names and resolution on the source list.**
    - *Default names.* When an entry is added, defaults are made for it. Take the entry's client part C (before the first `:`) and short name S. S gets a tag: L when S, lowercased, ends in `fl`, `_l` or `left`; R when it ends in `fr`, `_r` or `right`; otherwise the tag is S itself. The mono path is "C tag" (for example "Music L"). When the new entry and the entry before it have the same C and the tags L then R, the stereo path "C L/R" over the two channels is added as well.
    - *Collisions.* Names use the existing case-insensitive comparison (`io_map.rs:328-330`). A name taken by any path of the composed table, by the reserved "System Audio" (`io_map.rs:13-15`, `373-375`) or by a bus of the open session (section 1.4's shared namespace) gets " (2)", " (3)" and so on, the lowest free number. A user rename is kept.
    - *Regeneration.* Defaults are never regenerated automatically. **Add default paths** (rule 14) is the one explicit, idempotent exception: it fills missing defaults without duplicating renamed paths or altering existing definitions.
    - *Port groups.* The port group defaults keep "In 1" and "In 1-2" (section 1.2).
    - *Resolution.* On the source list endpoint, inputs resolve only through valid input paths. Missing, conflicting or unavailable paths monitor silence and refuse recording with the path named in the error; they never fall through to a numeric channel (`io_map.rs:240-241` today) or wrap to another channel (`io_map.rs:265` today). Hardware inserts use the existing flagged dry bypass, External Instruments have an unavailable return, and calibration refuses an unavailable return. The same unresolved state applies on every backend to an input path that clashes with an output path (rule 8). This supersedes section 1.5's fallback for these cases (opening paragraph) and keeps section 1.4's "never records a wrong channel". On port groups, other unresolved names keep today's label meaning.

### Alternatives considered

- **The source list** (the accepted design before the revision; Deferred). It is more machinery than picking one virtual source, and mixing sources is done in the server with virtual sinks.
- **Every port of the server as a channel (#431's first proposal, "JACK (all ports)").** The tester's graph has more ports than the 32-channel cap, and the set changes as applications start and stop. A channel number would then point to another port after each change, and a saved path could read the wrong source without a word.
- **Keep external patching and document it.** It works today, but nobody finds it, and every reopen, a quantum change included, drops the patch (Context). Rule 6 fixes the second half for everyone who keeps patching by hand; a quantum change still reopens (rule 7).
- **Always list virtual devices, with no preference.** The tester's graph has dozens of nodes; a default list of every application stream buries the interfaces most users want. Off by default keeps today's list.
- **Label devices by a kind guessed from their names** (sink monitor, application, virtual source). PipeWire's names are descriptions and application names (Context), not kinds. The server's physical flag is the one classification it gives, plus the existing monitor label.
- **A graph window inside transit.** It duplicates the system's graph tools, is a large UI to build and keep, and puts routing outside the I/O paths, where Ableton and Logic keep it in the device preferences.
- **The native PipeWire API.** ADR 0021 already rejects it for now (JACK 2 users left out, a much larger `unsafe` surface). Virtual devices need nothing the JACK API lacks.

### Consequences

- On a JACK or PipeWire server, a virtual sink's monitor or a virtual source can be the input, without a graph tool, after one checkbox. Choosing one can still change the server's timing, and then the take ends (kept) and the device reopens (rule 7).
- An application with several streams can be chosen, but its ports may change between opens. Paths over changed ports go unavailable until the original ports return or the user uses the current ports.
- A chosen input that is absent now opens no input instead of recording from another device, for hardware as well as virtual devices. A renamed capture group or a name saved on another machine needs the input chosen again; the output keeps running.
- Hand-made links now come back after transit's own reopens (slice B), except after a server shutdown.
- Input paths stop being reshaped by the output's table. A narrower input no longer deletes paths.
- Hand-made input paths for an input that was a different device from the output are not shown for that input after upgrading. They stay on disk, unused. Native WASAPI inputs start from defaults and follow the paired capture endpoint (rule 11, "Before you upgrade").
- An input path whose name clashes with an output path is silent and refuses to record instead of falling back to a channel number.
- No new callback in the `unsafe` binding: slice B promotes an existing test-only call, and slice C changes the flags of an existing one.

### Reopen when

- Someone needs several separate sources at once inside transit: pick up the deferred source list.
- Rule 12 finds H2 false (the server or session manager removes transit's links), and a revised link-ownership design is needed.
- Applications with several streams are commonly needed with stable channels; that needs an identity finer than the group name.
- A timing-contract amendment for uninterrupted quantum changes (Deferred) is accepted; rule 7 is then revisited.
- Users need outputs to destinations or old input paths imported (Deferred).
- ADR 0021 moves Linux audio to the native PipeWire API.
