# ADR 0047: The device macro strip: eight controls per page, factory, remote and user pages

- **Status:** proposed 2026-11-07 (#355)
- **Date:** 2026-11-07
- **Implementation:** none yet; five slices below, each with main green.
- **Amends:** [ADR 0028](0028-midi-learn-mappings.md) (adds the `selected:` mapping targets of decision 6; its realtime contract, stores and takeover modes are unchanged).
- **Reopen when:** a controller or surface needs a bank wider than eight (sixteen encoders as one page); users ask for the current page to survive closing a session; a factory page needs a deliberate gap or a hidden factory page; the MIDI effects group stops listing every parameter inline (see 2); VST3 or AU gains a remote-pages mechanism; or selecting a device from its editor window (not only from the Devices view) is asked for (see 6).

## Context

The maintainer decided on 2026-11-06 (#355) that every device in the rack gets a compact macro strip: eight controls per page with paging, so the controls that matter turn without opening the device. Eight is one row of knobs, one controller bank and the shape of the CLAP remote-controls extension. Convention (#355): Ableton Live shows a hosted plug-in in the chain with a configurable panel of chosen parameters, Logic Pro has Smart Controls, and both agree a compact view belongs in the rack; Bitwig's eight-knob remote-control pages are the shape chosen here because they match controllers and the CLAP extension, and Bitwig's controllers follow the selected ("cursor") device's current page.

What the code has today (at `ca595100`), where #355 assumed otherwise:

- **Device cards carry no knobs.** The Devices view (`crates/ui-studio/src/devices.rs`) draws each device as a 168 by 116 card: title with power and remove, load and hang states, the editor button, the sidechain key. The kit's S knob (`widgets/knob.rs`) is 38 across in a cell at least 56 wide and 69 high (dial, label row, value row), so a row of eight needs at least 448 points of width: the card's geometry changes, not just its height.
- **Parameters are tables of stable string ids.** Built-ins declare `ParamInfo` tables (`crates/dsp`; the Macro Oscillator's `macro_osc_params.rs`), referenced from `PluginInfo::params`. Hosted parameters reach the same `ParamInfo` shape through the host registries, ids being the format's numeric id as decimal text (CLAP `clap_id`, VST3 `ParamID`, AU parameter id); hidden, read-only and meter parameters are dropped from those tables. Automation lanes, MIDI Learn targets and rack macro mappings all store these ids.
- **The session has no schema version to bump for this.** `Session::FORMAT_VERSION` is 1 and, by [ADR 0023](0023-session-compatibility-markers.md), only a change an older reader cannot load safely bumps it. A feature an older reader would load but drop on save goes in the `needs` list. Fields are additive with serde defaults.
- **The CLAP host does not read remote controls.** `crates/clap-host` asks for params, audio and note ports, latency, tail, state, GUI and log. `clap-sys` 0.5.0 (pinned) already binds `clap.remote-controls/2` (and the `.draft/2` compat id): a page has a section name, a page id, a page name, eight param ids (`CLAP_INVALID_ID` for an empty slot) and `is_for_preset`; the host side has `changed` and `suggest_page`. The brief's "is-for-modulation flag" does not exist; the flag says the page belongs to the current preset.
- **The rack's eight macros are stored bindings, not a view.** [ADR 0034](0034-racks-layering-instruments-through-track-groups.md)'s slice 1 amendment (#197) gives each macro its own mappings to member parameters (range and curve), its own MIDI Learn source and its own automation lane (`slot: 253, param: "macro1".."macro8"`). #355 cited #243 for them, which is the Macro Oscillator's shaper; the reference was corrected to ADR 0034 and #197.
- **There is no control-surface layer and no bank-of-eight mapping.** Controllers reach transit only through MIDI Learn (ADR 0028): one source to one target, a session store addressing tracks by id and a per-machine profile addressing strips by position. Surface drivers are open issues (#126, #240), not code. There is also no notion of a selected device: the Devices view follows the focused track.
- **The Macro Oscillator's page 1 in #355 includes shaper controls.** Cutoff, Attack and Release are `cutoff`, `amp_attack` and `amp_release`, which act only while `shaper` is on (off by default). Its panel dims a disabled but open Shaper to 40 percent and keeps it editable.

## Decision

### 1. The page model

1. **A page is a name and eight slots.** A slot holds a parameter id of its own device or is empty. A device's pages form one ordered list in three tiers, always in this order: **factory pages** (a built-in's declared pages, or a CLAP plug-in's remote-controls pages, see 2 and 5), then **user pages** (from the session, see 3 and 4). A device with no parameters (a hardware insert, an External Instrument, Invert) has no pages and no strip row.
2. **The current page is UI state per device instance**, held in the studio's memory keyed by `Insert.uid` (the per-instance identity that already survives moves and is never saved). It starts at the first page, is not saved, does not dirty the session and makes no undo step. Why not session state: a page flip is a view position, like a scroll offset, and controllers flip pages constantly; storing it would turn every flip into an edit (dirty flag, undo history, file churn) and make two people opening the same file disagree about nothing that sounds. When the list shrinks (a page removed, a plug-in's pages changed), the current page is kept by identity (a CLAP page id, a user page's index among user pages) and otherwise clamps to the last page.
3. **The strip adds no parameter.** A slot is the same parameter id the panel, the automation lane and MIDI Learn address. A strip knob writes through the same commands as the device's panel knob (`mix.insert_param`, `mix.instrument_param`, after `touch_param`), merged per knob so a drag is one undo step, and records automation in Write, Latch and Touch exactly as the panel does. Nothing on the audio thread changes.

### 2. Factory pages for built-ins

1. **Declared as data beside the parameter table.** `transit_dsp` gains `PageInfo { name: &'static str, slots: &'static [PageSlot] }` and `PageSlot { param: &'static str, enable: Option<&'static str> }`, and `PluginInfo` gains `pages: &'static [PageInfo]`. A device declares a `PAGES` constant next to its `PARAMS` (for the Macro Oscillator, in `macro_osc_params.rs`). Factory slots are packed from the left with no gaps; slots after the last are empty.
2. **`enable` dims, it does not lock.** A slot whose `enable` names a toggle parameter that is off draws dimmed to 40 percent and stays editable, exactly as the device's panel draws that control (the Macro Oscillator's disabled Shaper). This keeps #355's page honest: Cutoff, Attack and Release read as inactive while the Shaper is off instead of silently doing nothing.
3. **The Macro Oscillator's page 1, "Main":** `model`, `harmonics`, `timbre`, `morph`, `level`, `cutoff` (enable `shaper`), `amp_attack` (enable `shaper`), `amp_release` (enable `shaper`), as #355 lists them. A second factory page ("Shaper") comes with the device's own next job (#356 changes the filter's parameters), not in this ADR: adding a page is a data change under the validation test and needs no amendment.
4. **Built-ins without declared pages get one derived page** until their panel migrates (#355: "other devices get theirs as their panels migrate"): their first eight parameters in table order, named "Main". Fewer than eight parameters fill from the left and leave the rest empty. The validation test keeps an allow-list of built-ins still on the derived page that may only shrink (the ratchet pattern of the file-size gate); a device leaves it when its panel migration declares `PAGES`.
5. **Validation test** over every built-in in the instrument and effect registry: each declared page has at most eight slots, every `param` and `enable` id exists in that device's table, `enable` names a `Unit::Toggle` parameter, page names are unique within the device and nonempty, and no id appears twice within one page (an id may appear on two pages). The same test asserts the derived page rule for devices on the allow-list.
6. **MIDI effects are outside the strip in these slices.** The MIDI effects group card (`midi_fx_panel.rs`, ADR 0036) already lists every parameter of every MIDI effect inline; a strip would draw them twice. `MidiEffectSlot` gets no pages now; the reopen condition covers the day that group moves to cards.

### 3. User pages and the Configure gesture

1. **Any device with parameters can have user pages, built-in or hosted, by the same mechanism.** For VST3 and AU plug-ins, and CLAP plug-ins without remote controls, user pages are the only pages. A hosted plug-in with no pages shows eight empty slots and the Configure affordance: transit does not fill a hosted strip from the first eight parameters, because hosted parameter order is the vendor's (often bypass, MIDI CC proxies or hundreds of entries) and a guessed page would be noise.
2. **Configure is a state of the strip**, entered from the strip's Configure control and left by the same control or Escape. Entering it opens the device's editor (the hosted plug-in's window or the built-in's panel). If the current page is a factory page, entering Configure first appends a user copy of it (same slots, name "User n") after the last user page and makes it current; factory pages themselves are never edited.
3. **A touch joins the current page.** While Configure is on, the next parameter the device reports as edited (a changed value, not an echo: the detection of ADR 0028 decision 14) is added to the current user page's first empty slot, and Configure stays on for the next touch. A parameter the host registries do not list is refused with ADR 0028 decision 15's status line. A parameter already on the current page changes nothing.
4. **The ninth touch starts a new page.** When the current page has no empty slot, the touch creates a new user page right after it, places the parameter in its first slot, makes it current and says so in the status line ("Page full: started User 3"). At most 16 user pages per device; a touch that would make a seventeenth is refused with a status line.
5. **Editing.** In Configure, a slot can be dragged to another slot of the same page (the two swap, so other slots never shift), removed (the slot becomes empty) and a user page renamed (trimmed, at most 32 characters, an empty name reads as "User n"), moved among the user pages or deleted. Each edit is one undo step through one command, `mix.device_pages {track?, slot, pages}`, which replaces the device's whole user page list (`slot` addresses the device as `mix.insert_param` and `mix.instrument_param` do). A query, `mix.device_pages_list {track?, slot}`, returns the resolved pages of all tiers with each slot's id, name and state (`ok`, `empty`, `missing`, `pending`), so tests and the control surface read one truth.
6. **A default per plug-in id, per machine.** "Save pages as default for this device" writes the device's user pages to `<settings>/presets/<plug-in id made file-safe>/strip.pages` (the folder of ADR 0025 decision 3 and the built-in presets, the engine's `presets::folder_name`, accessed through its checked roots). The file is JSON (`{"plugin": "...", "version": 1, "pages": [...]}` in the shape of 4) and its extension is not `.json`, `.vstpreset` or `.clappreset`, so neither preset lister shows it. A new instance of that plug-in starts with a copy of the default's user pages in its insert, so the session stays self-contained; "Clear default" deletes the file. Neither action dirties the session or makes an undo step (per-machine settings, as presets are).

### 4. The save format

1. **User pages live on the insert**, as `Insert::pages: Vec<UserPage>` with `#[serde(default, skip_serializing_if = "Vec::is_empty")]`, so they move, copy and undo with the device (`mix.insert_move`, `mix.insert_copy`) and an instrument slot carries its own. `UserPage { name: String, slots: [Option<String>; 8] }` in `crates/model` (data only; the model stays free of `transit_dsp`).
2. **Serialized shape**, always eight slot entries on write, `null` for empty:

   ```json
   "pages": [
     { "name": "User 1", "slots": ["1032", "1033", null, null, null, null, null, null] }
   ]
   ```

   On read, a missing `name` reads as "User n", fewer than eight slots pad with empty, entries past the eighth are dropped, a non-string slot reads as empty, a name is trimmed and cut to 32 characters, and pages past the sixteenth are dropped with one load note naming the device. The file is untrusted; none of this panics.
3. **No `format_version` bump and no migration step.** A session without the field has no user pages and shows the factory tier, which is what an old session means. Following ADR 0023, a session in which any insert has user pages lists `device_pages` under `needs` (added to `Session::needs()` and `KNOWN_NEEDS` together), so a build that knows the marker but not the feature warns before a save that would drop the pages. Factory and CLAP pages are never saved: they come from the device at load.
4. **A slot whose id no longer exists shows as missing and never reorders.** After a plug-in update (or a built-in id retired under ADR 0040's rules) the slot keeps its stored id, draws the kit's disabled knob labeled "Missing" with the id as its value in mono, and does nothing when turned or mapped. It is never removed or compacted automatically: if the id returns (a downgrade, a reinstalled version) the slot works again. Removing it is a Configure edit. While a hosted plug-in's table is not known yet (loading, not cached, not responding), its slots read `pending`, not missing.

### 5. CLAP remote controls

1. **The host offers `clap_host_remote_controls`** (both ids, `clap.remote-controls/2` and the compat `clap.remote-controls.draft/2`, in `host_get_extension`) and, on the plug-in host thread ([ADR 0018](0018-plugin-host-thread.md)) after the instance's parameter table is read, reads `count` and `get` for at most 64 pages and publishes them to the UI with the instance.
2. **Mapping.** Each CLAP page becomes one factory page in the plug-in's order: the page name as its name, prefixed by the section name and " / " when the section is not empty (so "Filter / Envelope"), the page id kept as its identity, slot n as the decimal text of `param_ids[n]` (the id form the host already uses everywhere). `CLAP_INVALID_ID` is an empty slot. An id the registry dropped (hidden, read-only) or does not list is drawn empty, not missing: the page is the plug-in's declaration, not the user's, and the user cannot fix it. `is_for_preset` pages are shown like any other; they are why a preset change triggers `changed`.
3. **`changed` is a flag serviced on the host thread**, as `params.rescan` already is (`crates/clap-host/src/ffi/host.rs`): the callback only sets an atomic; the next service re-reads every page and republishes. The current page is kept by page id, else clamps (1.2). User pages after them are untouched. **`suggest_page`** makes the suggested page id current for that instance when it exists (the UI state of 1.2), and is ignored otherwise.
4. **VST3 and AU use user pages only.** Neither format has a remote-pages mechanism: VST3's units (`IUnitInfo`) and AU's parameter clumps are groupings of parameters for display, with no fixed size, no order meant for a controller and no notion of a page; transit already reads them as `ParamInfo::group`. Splitting a group into pages of eight would invent pages the vendor never chose, which is the guess 3.1 rejects.

### 6. Controllers follow the page

1. **The selected device.** Within the focused track (the Devices view's existing rule, `focus_track`), the selected device is the card last clicked in the Devices view on that track, remembered per track for the run (UI state, not saved). With none clicked: the rack card on a rack, else the instrument on an instrument track, else the first insert. Clicking a card's title or strip selects it; the selected card is marked as the board specifies. Changing the focused track changes the selected device to that track's.
2. **A view-follows-page rule, not stored bindings.** ADR 0028 gains eight continuous targets `selected:control:1` to `selected:control:8` and two button targets `selected:page_prev` and `selected:page_next`, learnable in either store (normally the per-machine controller profile). Main resolves a `selected:control:n` move at apply time to slot n of the selected device's current page and applies it through the panel's commands (1.3); the snapshot, the worker and the cells of ADR 0028 decision 4 do not know what a target is, so nothing is rebuilt when the page or the selection changes. Main refreshes each such mapping's value cell once a frame from the resolved parameter, and a page or selection change counts as a new mapping start for scaled takeover (ADR 0028 takeover amendment, decision 2: the first message only records where the controller is), so turning a knob after a page flip never jumps the new parameter. Why a rule and not bindings: a stored binding per device per page would multiply mappings by every device in every session and go stale with each page edit, while the rule is one profile of ten entries that serves every device, the shape Bitwig's remote controls use; a surface driver (#126, #240) reads the same selected device and current page.
3. **An empty, missing or pending slot ignores the controller**: the move is dropped with no status line (a knob turned on an empty slot is not an error), and the slot shows no value to pick up.
4. **The rack's macros keep their bindings.** They are not re-pointed at the current page (#355's wording): a macro has its own mappings, curve, MIDI source and automation lane, and a lane on `macro1` must drive the same parameters whatever the UI shows. Instead, the rack card is a selectable device whose one fixed page, "Macros", is its eight macros (the `rack.macro` targets, labeled with the macros' names). With the rack card selected, `selected:control:n` drives macro n through `rack.macro`; a rack has no user pages. A macro's own learned source (`track:<rack>:macro:<n>`) keeps working beside this.

### 7. The strip in the design language

1. **Components** (ADR 0045 decision 1: added to `docs/design/language/README.md` in the landing that draws them, slice 2, not by this ADR): the **macro strip**, one row of eight S-size kit knobs with label and value, fixed at eight cells so positions never shift and a controller's knob n is always cell n; the **empty slot** cell (no dial, a faint placeholder); the **missing slot** (the kit's disabled knob, "Missing", the id in mono); the **page indicator** (previous and next, `n / m` in mono and the page name, the arrows disabled at the ends: pages do not wrap, so a controller's next button at the last page does nothing); and the **Configure state** of the strip.
2. **The modulation ring is the panel's ring.** A strip knob shows a ring exactly when the device's panel draws one for that parameter, from the same function (the Macro Oscillator's `ring_depth` over its matrix; the Sampler's matrix when it lands; nothing for hosted plug-ins), so strip and panel can never disagree.
3. **A Devices view board is a precondition for slice 2.** The card's new geometry (at least 448 points of strip, see Context), the selected-device mark and the Configure state are drawn from a board of the maintainer's design work, not improvised. The data slices (1, and the model parts of 3 and 4) do not wait for it.

### 8. Slices (main green at each)

1. **Model and data, no UI.** `PageInfo`, `PageSlot`, `PluginInfo::pages`, the Macro Oscillator's `PAGES`, the derived page and its allow-list; `UserPage` and `Insert::pages` with the read rules; the `device_pages` need; the resolver (the factory tier, then user pages, slot states) in the engine; `mix.device_pages` and `mix.device_pages_list`. Tests: the validation test (2.5); round trip with defaults (absent field reads empty, empty is not written, existing fixtures stay byte-identical); the `needs` marker present with user pages and absent without, and a file with the marker removed still loads the pages; read rules (short, long and malformed slots, a seventeenth page with its load note); a missing id resolves `missing` at its index and the other slots keep theirs; move and copy carry pages; one undo step per `mix.device_pages`. Control: the validation test fails when a page names an id not in the table.
2. **The strip in the Devices view, on the board.** Knobs, empty and missing cells, page indicator, `enable` dimming, rings, the selected device. Tests: a strip drag writes the same parameter id through the same command as the panel and is one undo step; a page flip leaves the session clean with no undo step; with `shaper` off the three shaper slots draw dimmed and still write; a missing slot is drawn and takes no input; a hosted plug-in with no pages shows eight empty cells and Configure; the ring matches the panel's for a routed destination; layout tests assert tokens; help entries in `docs/help/device-chain.toml`; the design README gains the components of 7.1.
3. **User pages and Configure.** Tests: touches fill the next free slot; the ninth starts a new page and the seventeenth is refused; a duplicate touch changes nothing; a refused hosted parameter shows ADR 0028's status line; a factory page is copied before editing; swap, remove, rename, move and delete are one undo step each; the default file writes, seeds a new instance and is listed by neither preset lister; a pending hosted table does not mark slots missing. Control: with the copy step removed, the factory-page test fails.
4. **CLAP remote controls.** The CLAP test fixture (`crates/clap-host/tests/fixture`) gains remote-control pages, an invalid slot, a hidden-parameter slot, a `changed` call and a `suggest_page` call. Tests: pages map in order with section prefixes and empty slots; `changed` republishes on the host thread and keeps the current page by id; `suggest_page` moves the current page; the callback does no work beyond the flag; a plug-in without the extension shows user pages only.
5. **Controllers follow the page.** Tests: a learned `selected:control:3` drives slot 3 of the selected device's current page and, after a page flip, the new slot 3 without a jump (scaled takeover); `selected:page_next` and `selected:page_prev` stop at the ends; an empty or missing slot drops the move; with the rack card selected the controls drive `rack.macro`; a macro's own learned source still works; the realtime snapshot is not rebuilt on a page or selection change (counted).

### 9. Gate (at each landing)

The workspace gates of the day (fmt, clippy, tests, layers, file-size), and: user pages round-trip with defaults and the `needs` marker appears exactly when they exist; factory pages validate for every built-in and the derived-page allow-list did not grow; a missing id shows as missing at its own slot and nothing reorders; the strip's knobs drive the same parameter ids as the panel with one undo step per gesture and the same automation recording; a page flip is never an edit; CLAP pages map, follow `changed` and honor `suggest_page` against the fixture; a controller bank follows the selected device's current page, ignores empty slots and never jumps after a flip; no audio-thread code changed (the slices touch the model, engine, host-thread and UI crates only). The review bar is [ADR 0009](0009-refutation-review-before-every-push.md)'s.

## Consequences

- Every device card grows a strip row and widens; the Devices view shows fewer cards at once, which the board has to answer (scrolling, a collapsed card).
- A device panel's own macro or hero knobs (the Macro Oscillator's L knobs) are not the strip: the panel keeps its layout and the strip is a second view of the same parameters. The rack card's macro knobs are the rack's own controls (ADR 0034), shown to controllers as its one page.
- Hosted plug-ins start with empty strips until configured or saved as a default; CLAP plug-ins that ship remote controls arrive configured.
- Sessions with user pages warn on builds that know the `needs` marker but not `device_pages`, and lose the pages if saved there; older pages never break loading.
- A controller profile with the ten `selected:` mappings works in every session; mapping a knob to `selected:control:n` and also directly to a parameter is two mappings of one source, which ADR 0028 decision 2 already resolves (the later replaces the earlier).
- MIDI effects have no strip and are not reachable through `selected:` until their group moves to cards.

## Alternatives considered

- **A free-form macro mapping with amounts and curves per device.** Rejected: one control driving several parameters by amounts is the modulation matrix's job (and the rack macros' for layered devices). The strip is a window onto parameters, one slot one parameter, so what a knob shows is what the parameter is.
- **Four or sixteen controls per page.** Four halves what a controller bank and the CLAP extension carry and doubles paging; sixteen does not fit one row of S knobs on a card, is two banks on most controllers and breaks the one-to-one match with CLAP pages. Eight is the maintainer's decision and the extension's constant (`CLAP_REMOTE_CONTROLS_COUNT`).
- **A strip only for hosted plug-ins.** Rejected: built-ins are the devices transit controls best, and controllers following the page need every device to have pages; one mechanism for both is less code than two.
- **Storing the current page in the session.** Rejected in 1.2: every page flip would be an edit with an undo step and a dirty flag, for state that changes nothing audible.
- **Bumping `format_version` for the pages.** Rejected by ADR 0023's rule: an older build can load the file safely; refusing every newer file for an optional view would break "newer files load on the previous build". The `needs` marker is the tool.
- **Re-pointing the rack macros at the current page (#355's wording).** Rejected in 6.4: it would make a macro lane drive whatever the UI shows, so playback would depend on selection.
- **Filling hosted strips from the first eight parameters, or from VST3 units and AU clumps.** Rejected in 3.1 and 5.4: a guessed page from a vendor's arbitrary order is noise, and groups are not pages.
