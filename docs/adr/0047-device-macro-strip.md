# ADR 0047: The device macro strip: eight controls per page, factory, remote and user pages

- **Status:** accepted 2026-11-07 (#355); settled after four judging rounds
- **Date:** 2026-11-07
- **Implementation:** five slices below, each with main green. Slice 1 landed: the page data in `transit_dsp` (`PageInfo`, `PageSlot`, `PluginInfo::pages`, the Macro Oscillator's `PAGES`, the derived-page allow-list), `UserPage` on `Insert` and `MidiEffectSlot` with the read rules and the `device_pages` need (`crates/model/src/device_pages.rs`), the resolver and the current-page identity rules (`crates/engine/src/device_pages.rs`), and `mix.device_pages` and `mix.device_pages_list`.
- **Amends:** [ADR 0028](0028-midi-learn-mappings.md) (adds the `selected:` mapping targets, their takeover generation and the `plugin:midi<n>:` target form for MIDI effects, decision 6; its stores, worker contract and takeover modes are otherwise unchanged). On acceptance, ADR 0028's file and README row gain "amended by ADR 0047".
- **Reopen when:** a controller or surface needs a bank wider than eight (sixteen encoders as one page); users ask for the current page to survive closing a session; a factory page needs a deliberate gap or a hidden factory page; VST3 or AU gains a remote-pages mechanism; selecting a device from its editor window (not only from the Devices view) is asked for (see 6); users ask for large hosted plug-ins to fill their strips themselves, or for small ones not to (see 3.1); a rack's page needs Touch and Latch writing (ADR 0034's open slice); or the current page should follow the plug-in's preset (CLAP `is_for_preset` pages changing on every preset load is the likely trigger).

## Context

The maintainer decided on 2026-11-06 (#355) that every device in the rack gets a compact macro strip: eight controls per page with paging, so the controls that matter turn without opening the device. Eight is one row of knobs, one controller bank and the shape of the CLAP remote-controls extension. Convention (#355): Ableton Live shows a hosted plug-in in the chain with a configurable panel of chosen parameters, Logic Pro has Smart Controls, and both agree a compact view belongs in the rack; Bitwig's eight-knob remote-control pages are the shape chosen here because they match controllers and the CLAP extension.

What the code has today (at `ca595100`), where #355 assumed otherwise:

- **Device cards carry no knobs, except the rack card.** The Devices view (`crates/ui-studio/src/devices.rs`) draws each device as a 168 by 116 card: title with power and remove, load and hang states, the editor button, the sidechain key. The rack card (`rack_panel.rs`) is the exception: 660 wide, with a row of eight macro knobs (`widgets::param_knob` cells). The kit's S knob (`widgets/knob.rs`) is 38 across in a cell at least 56 wide and 69 high (dial, label row, value row), so a row of eight needs at least 448 points plus padding: ordinary cards change geometry, as the rack card already did.
- **Parameters are tables of stable string ids.** Built-ins declare `ParamInfo` tables (`crates/dsp`; the Macro Oscillator's `macro_osc_params.rs`), referenced from `PluginInfo::params`. Hosted parameters reach the same `ParamInfo` shape through the host registries, ids being the format's numeric id as decimal text (CLAP `clap_id`, VST3 `ParamID`, AU parameter id); hidden, read-only and meter parameters are dropped from those tables. Hosted `PluginInfo`s are leaked once per plug-in type (`crates/clap-host/src/registry.rs`). Automation lanes, MIDI Learn targets and rack macro mappings all store these ids.
- **The session has no schema version to bump for this.** `Session::FORMAT_VERSION` is 1 and, by [ADR 0023](0023-session-compatibility-markers.md), only a change an older reader cannot load safely bumps it. A feature an older reader would load but drop on save goes in the `needs` list. Fields are additive with serde defaults.
- **The CLAP host does not read remote controls.** `crates/clap-host` asks for params, audio and note ports, latency, tail, state, GUI and log. `clap-sys` 0.5.0 (pinned) already binds `clap.remote-controls/2` (and the `.draft/2` compat id): a page has a section name, a page id, a page name, eight param ids (`CLAP_INVALID_ID` for an empty slot) and `is_for_preset`; the host side has `changed` and `suggest_page`. There is no "is-for-modulation" flag; the flag says the page belongs to the current preset.
- **The rack's eight macros are stored bindings, not a view.** [ADR 0034](0034-racks-layering-instruments-through-track-groups.md)'s slice 1 amendment (#197) gives each macro its own mappings to member parameters (range and curve), its own MIDI Learn source and its own automation lane (`slot: 253, param: "macro1".."macro8"`). #355 cited #243 for them, which is the Macro Oscillator's shaper; the reference was corrected to ADR 0034 and #197.
- **There is no control-surface layer and no bank-of-eight mapping.** Controllers reach transit only through MIDI Learn (ADR 0028): one source to one target per store, a session store addressing tracks by id and a per-machine profile addressing strips by position, with pickup and scaling done in the ingress worker from a per-entry cell. Surface drivers are open issues (#126, #240), not code. There is no notion of a selected device: the Devices view follows the focused track.
- **MIDI effects live in one group card.** `midi_fx_panel.rs` (ADR 0036) lists every MIDI effect's parameters inline; they are written with `mix.midi_effect_param {track, index, param, value}` and automated on slots 240..247. ADR 0028 has no target form for them.
- **The Macro Oscillator's page 1 in #355 includes shaper controls.** Cutoff, Attack and Release are `cutoff`, `amp_attack` and `amp_release`, which act only while `shaper` is on (off by default). Its panel dims a disabled but open Shaper to 40 percent and keeps it editable.

## Decision

### 1. The page model

1. **A page is a name and eight slots.** A slot holds a parameter id of its own device or is empty. A device's pages form one ordered list in two tiers, always in this order: **factory pages** (a built-in's declared or derived pages, a CLAP plug-in's remote-controls pages, or a small hosted plug-in's derived pages, see 2, 3.1 and 5), then **user pages** (from the session, see 3 and 4). "Device" means an instrument, an insert, a MIDI effect or a rack card (6.4). A device with no parameters (a hardware insert, an External Instrument, Invert) has no pages and no strip row.
2. **The current page is UI state per device instance**, held in the studio's memory keyed by `Insert.uid` (for MIDI effects, `MidiEffectSlot.uid`; for a rack card, the rack's track id): the per-instance identity that survives moves and is never saved. It starts at the first page, is not saved, does not dirty the session and makes no undo step. Why not session state: a page flip is a view position, like a scroll offset, and controllers flip pages constantly; storing it would turn every flip into an edit (dirty flag, undo history, file churn) for state that changes nothing audible.
3. **Identity of the current page.** A factory page is identified by its index in the factory tier (for CLAP, by its page id); a user page by its index among user pages, and the UI follows its own edits: deleting or moving a user page before the current one shifts the stored index with it, deleting the current page makes the next one current (else the previous). After undo, redo, a plug-in's `changed` or any other change the UI did not make, a CLAP page is found again by page id and anything else clamps to the last page. With no pages at all (m = 0) the indicator reads `0 / 0` with the name "No pages" and the arrows disabled.
4. **The strip adds no parameter.** A slot is the same parameter id the panel, the automation lane and MIDI Learn address. A strip knob writes through the same commands as the device's own panel (`mix.insert_param` or `mix.instrument_param` after `touch_param`; `mix.midi_effect_param` for a MIDI effect; `rack.macro` for a rack page), merged per knob so a drag is one undo step, and records automation exactly as that panel does today (a rack page records as `rack.macro` does: ADR 0034 leaves Touch and Latch writing from a macro move for later).
5. **No audio-thread change, by test.** A `mix.device_pages` edit is a session change that reaches the plan compiler like any edit; it must keep the device instance (same uid, same live instance, no re-prepare or re-instantiate), tested with a control (8.1). The CLAP extension lookup the audio thread may call (`get_extension` is thread-safe in CLAP) returns static vtables with no allocation, tested with the counting allocator as ADR 0018 decision 3 does.

### 2. Factory pages for built-ins

1. **Declared as data beside the parameter table.** `transit_dsp` gains `PageInfo { name: &'static str, slots: &'static [PageSlot] }` and `PageSlot { param: &'static str, enable: Option<&'static str> }`, and `PluginInfo` gains `pages: &'static [PageInfo]`, empty for hosted types (hosted pages are per instance, see 5). A device declares a `PAGES` constant next to its `PARAMS` (for the Macro Oscillator, in `macro_osc_params.rs`). This covers the instrument and effect registry and the MIDI effect registry (`midi_fx::REGISTRY`). Factory slots are packed from the left with no gaps; slots after the last are empty.
2. **`enable` dims, it does not lock.** A slot whose `enable` names a toggle parameter that is off draws dimmed to 40 percent and stays editable, exactly as the device's panel draws that control (the Macro Oscillator's disabled Shaper), so Cutoff, Attack and Release read as inactive while the Shaper is off instead of silently doing nothing.
3. **The Macro Oscillator's page 1, "Main":** `model`, `harmonics`, `timbre`, `morph`, `level`, `cutoff` (enable `shaper`), `amp_attack` (enable `shaper`), `amp_release` (enable `shaper`), as #355 lists them. A second factory page ("Shaper") comes with the device's own next job (#356 changes the filter's parameters): adding a page is a data change under the validation test and needs no amendment.
4. **Built-ins without declared pages get one derived page**: their first eight parameters in table order, named "Main"; fewer than eight fill from the left and leave the rest empty. Unlike a large hosted table (3.1), transit orders its own tables by function, so the first eight are a sensible if uncurated page (the Macro Oscillator's would be `model` to `aux_mix`, then `level`). The validation test keeps an allow-list of built-ins still on the derived page that may only shrink (the ratchet pattern of the file-size gate); a device leaves it when its panel migration declares `PAGES`. **A new built-in declares `PAGES` at birth** (the stock effects of #305 included), as ADR 0045 decision 5 builds new panels from the kit from the start.
5. **Validation test** over every built-in in both registries: each declared page has at most eight slots, every `param` and `enable` id exists in that device's table, `enable` names a `Unit::Toggle` parameter, page names are unique within the device and nonempty, and no id appears twice within one page (an id may appear on two pages). The same test asserts the derived-page rule for devices on the allow-list and that the list did not grow.

### 3. Hosted plug-ins, user pages and the Configure gesture

1. **A hosted plug-in with no factory pages fills itself when its table is small**. If the registry table (after hidden, read-only and meter parameters are dropped) has at most 64 parameters, the factory tier is derived from it in table order, eight per page, at most eight pages, named "Main", "2", "3" ...; above 64, the factory tier is empty and the strip offers Configure. This follows the agreement of Ableton and Logic: Live configures plug-ins with up to 64 parameters automatically and opens larger ones empty for Configure (*Using Plug-Ins*), and Logic's Smart Controls map third-party plug-ins automatically by default ("Map screen controls automatically"). Large tables are where vendor order turns into noise (CC proxies, hundreds of entries), so the cutoff is Live's. VST3, AU and CLAP plug-ins without remote controls follow this rule; CLAP plug-ins with remote controls use them instead (5).
2. **Any device with parameters can have user pages, built-in, hosted or MIDI effect, by the same mechanism.**
3. **Configure is a state of the strip**, entered from the strip's Configure control and left by the same control or Escape. Entering and leaving are not edits: with no touch, nothing changes. Entering opens the device's editor (the hosted plug-in's window or the built-in's panel; a MIDI effect's rows are already in its group card).
4. **What counts as a touch.** For a hosted plug-in, the next parameter it reports as edited (a changed value, not an echo: ADR 0028 decision 14's detection), refused with decision 15's status line when the registries do not list it. For a built-in instrument or insert, the next `touch_param` call for that device from its panel. For a MIDI effect, the next `mix.midi_effect_param` write from its row in the group card. Configure stays on for the next touch.
5. **Where a touch lands.** A parameter already on the current user page changes nothing. Otherwise:
   - the current page is a user page with an empty slot: the parameter takes its first empty slot;
   - the current page is a user page that is full (the ninth touch): a new user page is inserted right after it with the parameter in its first slot, made current, and the status line says so ("Page full: started User 3");
   - the current page is a factory page: the first accepted touch appends a user copy of it (same slots) after the last user page, puts the parameter in the copy's first empty slot (or a new page after the copy when it is full) and makes the copy current. Factory pages themselves are never edited;
   - the device has no pages at all: the first touch creates "User 1" holding the parameter.

   Each of these is one `mix.device_pages` step. At most 16 user pages per device: a touch that would create a seventeenth (a new page or a factory copy) is refused with a status line, and the parameter's value change still happens.
6. **The page edit waits for the gesture to end.** A touch is detected at the first changed value of a drag that goes on, and any document change outside the drag's merge ends it (`Engine::execute` clears `merge_key` when the document changed), so executing the page edit at detection would split the drag into three undo steps. Instead the studio queues the touch, keyed by the device's uid (`Insert.uid` or `MidiEffectSlot.uid`) and the session it belongs to, never by a slot letter or `midi<n>`, and executes the queued touches, in touch order, as one `mix.device_pages` step when no gesture of that device is running: the pointer is released (a built-in knob or a MIDI effect row; for a Ctrl+wheel nudge, the frame after the last notch, the kit's merge rule), ADR 0028's 400 ms idle ends a controller gesture, or `HOSTED_HOLD_S` passes after a hosted editor's newest value. A touch dragged over any number of values therefore makes exactly two undo steps: the value change (the whole merged drag), then the page edit; undo removes the page edit first, then the value change. Touches of several parameters during one running gesture (a hosted XY pad) join the same page step. Leaving Configure while a touch is queued still executes it at the gesture's end; the device's address is resolved from its uid only when the touch executes, so a move or reorder before the gesture ends sends it to the same device, and a uid that no longer resolves then (the device removed or undone, the session closed or switched) drops the touch. While Configure is on, an undo or redo that removes the current page clamps the current page by 1.3 and Configure stays on. Why a queue and not joining the drag's merge (`hold_merge`): a joined step would make undoing a page edit also revert the sound, and the merge key differs per edit path (panel, hosted editor, controller), so the join would have to be threaded through each; the queue touches only the studio's Configure code and leaves every merge rule as it is.
7. **Editing.** In Configure, a slot can be dragged to another slot of the same page (the two swap, so other slots never shift), removed (the slot becomes empty), and a user page renamed (trimmed, at most 32 characters), moved among the user pages or deleted. **Names are stored at creation** ("User n" with the lowest n not in use on that device, "<factory name> copy" for a copy); a page whose stored name is empty reads as "User <position>" and that reading is never written back.
8. **Commands.** Each edit is one undo step through `mix.device_pages {track?, device, pages}`, which replaces the device's whole user page list. `device` uses ADR 0028 decision 10's addressing, an insert letter `a` to `j` or `instrument`, extended with `midi1` to `midi8` for MIDI effects (the order of the group card, matching automation slots 240..247) and `rack` for a rack card (which accepts no user pages). `midi<n>` is the effect's position in `Track::midi_effects` plus one (`mix.midi_effect_param`'s `index` plus one), the position at the moment the command runs (a `mix.device_pages` call resolves it then, so it always reaches the effect now at that position). The engine query `mix.device_pages_list {track?, device}` returns the resolved pages of both tiers and each slot's id, name and state (`ok`, `empty`, `missing`, `pending`). The current page and the selected device are studio state the engine cannot read: the studio reports them through `ui.inspect` (a `device_pages` object: the selected device per track and the current page per device, by the addressing above), so a test or a surface reads the tiers from the engine and the position from the studio, each from its one owner.
9. **A default per plug-in id, per machine.** "Save pages as default for this device" writes the device's user pages to `<settings>/presets/<plug-in id made file-safe>/strip.pages` (the folder of ADR 0025 decision 3 and the built-in presets, the engine's `presets::folder_name`, accessed through its checked roots). The file is JSON (`{"plugin": "...", "version": 1, "pages": [...]}` in the shape of 4) and its extension is not `.json`, `.vstpreset` or `.clappreset`, so neither preset lister shows it. A new instance of that plug-in starts with a copy of the default's user pages, read under the rules of 4.2 (so at most 16), so the session stays self-contained; "Clear default" deletes the file. Neither action dirties the session or makes an undo step (per-machine settings, as presets are).

### 4. The save format

1. **User pages live on the device's slot record**, as `pages: Vec<UserPage>` with `#[serde(default, skip_serializing_if = "Vec::is_empty")]` on `Insert` (instruments and inserts) and on `MidiEffectSlot`, so they move, copy and undo with the device. `UserPage { name: String, slots: [Option<String>; 8] }` in `crates/model` (data only; the model stays free of `transit_dsp`).
2. **Serialized shape**, always eight slot entries on write, `null` for empty:

   ```json
   "pages": [
     { "name": "User 1", "slots": ["1032", "1033", null, null, null, null, null, null] }
   ]
   ```

   Read rules (the file is untrusted and none of this panics): a missing or non-string `name` reads as empty (shown as "User <position>"); a name is trimmed and cut to 32 characters; fewer than eight slots pad with empty; entries past the eighth are dropped; a non-string slot, an empty string, or an id longer than 64 characters reads as empty; a duplicate id within one page keeps its first slot and reads later ones as empty (the rule of the validation test); pages past the sixteenth are dropped. Dropped pages produce one load note naming the track and device, added in a post-load pass in `Session::from_json` (as the unknown-`needs` note is), because the `Insert` deserializer cannot reach `load_notes`.
3. **No `format_version` bump and no migration step.** A session without the field has no user pages and shows the factory tier, which is what an old session means. Following ADR 0023, a session with user pages on any device lists `device_pages` under `needs` (added to `Session::needs()` and `KNOWN_NEEDS` together); `needs()` scans every track's instrument, every track's `mixer.inserts` and every track's MIDI effects. Why a marker when session MIDI mappings shipped without one: configured pages are user labor, and losing them silently on a save from an older build is the case ADR 0023 decision 2 names, even though nothing plays differently. An older build with the marker loads the session, warns once and drops `pages` on save; builds that predate the marker drop them silently, as ADR 0023 decision 5 admits. Factory and CLAP pages are never saved: they come from the device at load.
4. **Slot states.** A slot whose id is not in a known table is **missing**: it keeps its stored id, draws the kit's disabled knob labeled "Missing" with the id as its value in mono, and does nothing when turned or mapped. It is never removed or compacted automatically: if the id returns (a downgrade, a reinstalled version) the slot works again; removing it is a Configure edit. A slot whose device's table is not known yet (a hosted plug-in loading or not responding) is **pending**. A plug-in that is not installed or failed to load has no table that will arrive: its card already says so, and its slots are **missing**, so a slot never reads `pending` for a device that will not load.

### 5. CLAP remote controls

1. **The host offers `clap_host_remote_controls`** under both ids (`clap.remote-controls/2` and the compat `clap.remote-controls.draft/2`) in `host_get_extension`, as static vtables. On the instance's main thread (the plug-in host thread on Windows and Linux, the UI thread on macOS, [ADR 0018](0018-plugin-host-thread.md) decision 7), after the instance's parameter table is read, it reads `count` and `get` for at most 64 pages.
2. **Owned per instance.** The pages are an owned `Arc<[RemotePage]>` (`RemotePage { id: u32, name: String, slots: [Option<String>; 8] }`) held in the instance's shared state (`Shared` in `crates/clap-host/src/plugin.rs`) behind a `Mutex`, as `Shared` already holds `rescan`: the instance's main thread replaces the whole `Arc` under the lock after each read, and a reader clones the `Arc` under the lock and releases it. Only the UI-side handle of the instance (the one the editor and parameter-table queries use) and the instance's main thread touch it, never the `Hosted` forwarder in the audio plan (ADR 0018 decision 3), so the process path neither locks nor reads it, and a replaced `Arc` is dropped on the main thread or the UI thread, never the audio thread. The engine's resolver behind `mix.device_pages_list` takes them as the factory tier. `PluginInfo::pages` stays empty for hosted types: a `&'static` page cannot change at runtime without leaking.
3. **Mapping.** Each CLAP page becomes one factory page in the plug-in's order: the page name as its name, prefixed by the section name and " / " when the section is not empty ("Filter / Envelope"), the page id kept as its identity, slot n as the decimal text of `param_ids[n]` (the id form the host already uses everywhere). `CLAP_INVALID_ID` is an empty slot. An id the registry dropped (hidden, read-only) or does not list is drawn empty, not missing: the page is the plug-in's declaration, not the user's. `is_for_preset` pages are shown like any other; they are why a preset change triggers `changed`. **Which factory tier a CLAP plug-in shows:** 3.1's derived tier until a read returns at least one page (the table may be cached before the first read), the CLAP pages while the last read returned some, and the derived tier again when a read returns none. Each switch is a change the UI did not make: the current page is re-found or clamped by 1.3 and the takeover generations are checked by 6.3. A user page copied from a derived page stays as it is.
4. **Callbacks only store.** `changed` sets an atomic flag and `suggest_page` stores the page id in an atomic slot, both in the instance's shared state, as `params.rescan` already works (`crates/clap-host/src/ffi/host.rs`). The next service on the instance's main thread re-reads the pages after `changed`; the studio takes a suggested page id at its next frame and makes it current when it exists (the current page is studio UI state, which a callback cannot set). User pages are untouched by either.
5. **VST3 and AU have no remote pages.** VST3's units (`IUnitInfo`) and AU's parameter clumps are groupings for display, with no fixed size, no order meant for a controller and no notion of a page; transit already reads them as `ParamInfo::group`. These plug-ins get 3.1's derived pages (or none above 64 parameters) and user pages.

### 6. Controllers follow the page

1. **The selected device.** Within the focused track (the Devices view's existing rule, `focus_track`), the selected device is the device last clicked in the Devices view on that track (a card's title or strip, or a MIDI effect's row), remembered per track for the run (UI state, not saved). With none clicked: the rack card on a rack, else the instrument on an instrument track, else the first insert. Changing the focused track changes the selected device to that track's. This is where the conventions agree: Live's control surfaces follow the appointed ("blue hand") device, the one selected in Device View, remembered per track and banked in eights; Logic's Smart Controls follow the selected track; Bitwig's remote controls follow its cursor device.
2. **A view-follows-page rule, not stored bindings.** ADR 0028 gains eight continuous targets `selected:control:1` to `selected:control:8` and two button targets `selected:page_prev` and `selected:page_next`, learnable in either store (normally the per-machine controller profile). Main resolves a `selected:control:n` move at apply time to slot n of the selected device's current page and applies it through 1.4's commands; the snapshot and the worker do not know what a target is, so nothing is rebuilt on a page or selection change. Why a rule and not bindings: a stored binding per device per page would multiply mappings by every device in every session and go stale with each page edit, while the rule is one profile of ten entries that serves every device, the shape Bitwig's remote controls use; a surface driver (#126, #240) reads the same selected device and current page (3.8).
3. **Takeover generation.** Main keeps, per `selected:control:n` entry, the resolved pair (device identity, parameter id) it last wrote, and bumps that entry's generation whenever the pair changes, for any reason: a page flip, a selection change, a Configure swap, remove or fill of slot n on the current page, an undo or redo of a page edit, a CLAP `changed` that rewrites the current page, or a factory-tier switch (5.3). It checks the pair at each change it applies itself and once a frame for changes it did not make (a CLAP `changed`, a tier switch); in each frame that check, with any bump, runs before Main takes that frame's cell values, so an old-generation move published just before such a change is dropped rather than applied to the parameter that now resolves in the slot. On a bump it writes the newly resolved parameter's normalized value with the new generation (an empty, missing or pending slot writes the generation with no value). The worker treats a generation it has not seen as a mapping start (the first message only records where the controller is, ADR 0028's takeover amendment decision 2) and publishes its values tagged with the generation it scaled against; Main drops any value tagged with an older generation. So a move that lands between such a change and Main's next refresh can never be scaled against the old parameter and applied to the new one.

   **One word per cell.** Value and generation are read and written together, never as two atomics that can tear: each direction's cell for a `selected:` entry is one `AtomicU64` holding the f32 value's bits in the low 32 bits and a u32 generation in the high 32 (Main to worker: the control's value; worker to Main: the newest scaled value). Words are stored with Release and loaded with Acquire. ADR 0028 decision 8's publish count, which pickup uses, stays its own atomic beside the worker-to-Main word and is advanced (a Release store) after that word is stored; Main loads the count (Acquire), then the word (Acquire), and a word whose generation is old is dropped whatever the count says. Cells of other targets are unchanged.
4. **The rack's macros keep their bindings**. They are not re-pointed at the current page (#355's wording): a macro has its own mappings, curve, MIDI source and lane, and a lane on `macro1` must drive the same parameters whatever the UI shows. Instead, the rack card's existing row of eight macro knobs **is** the rack's strip: one fixed page, "Macros", indicator `1 / 1`, labeled with the macros' names, no second row and no user pages. With the rack card selected, `selected:control:n` drives macro n through `rack.macro`. A macro's own learned source (`track:<rack>:macro:<n>`) keeps working beside this.
5. **An empty, missing or pending slot ignores the controller**: the move is dropped with no status line (a knob turned on an empty slot is not an error).
6. **Learning.** Window > MIDI Mappings gains "Learn controller bank", which arms the ten `selected:` targets in turn (eight knobs, then previous and next, each skippable) into the controller profile. Right-clicking a strip knob offers ADR 0028 decision 14's items for the concrete parameter in that slot, as the panel knob does, never the slot. For a MIDI effect that needs a target form ADR 0028 lacks, so this ADR adds one to decision 10's grammar: `track:<id>:plugin:midi<n>:<param id>` (session) and `strip:<k>:plugin:midi<n>:<param id>` (profile), `midi<n>` as in 3.8 (position plus one). These mappings are positional, as insert-slot mappings are under decision 10: nothing rewrites session or profile mappings on a reorder (`mix.midi_effect_move` re-points only the automation lanes), so after a reorder `midi2` drives whichever effect is now second, while the effect's lane follows the effect. The `selected:` bank is unaffected (6.3's pair check bumps on a reorder). They are resolved like decision 10 and refused at `midi.learn` and `midi.map` when no effect sits at that position or the parameter does not exist; a move is applied through `mix.midi_effect_param`. A rack card's knob keeps its existing `track:<rack>:macro:<n>` learn.
7. **Precedence with direct mappings.** A source mapped to `selected:control:n` and to a concrete parameter is two mappings: within one store ADR 0028 decision 2 keeps the later; across stores decision 3 applies, the session mapping wins and the bank entry shows "overridden".

### 7. The strip in the design language

1. **Components** (ADR 0045 decision 1: added to `docs/design/language/README.md` in the landing that draws them, slice 2, not by this ADR): the **macro strip**, one row of eight S-size kit knobs with label and value, fixed at eight cells so positions never shift and a controller's knob n is always cell n; the **empty slot** cell (no dial, a faint placeholder); the **missing slot** (the kit's disabled knob, "Missing", the id in mono); the **page indicator** (previous and next, `n / m` in mono and the page name, the arrows disabled at the ends: pages do not wrap, so a controller's next button at the last page does nothing); and the **Configure state** of the strip. The rack card's macro row moves to these components when its card migrates; it already is the rack's strip (6.4).
2. **The modulation ring is the panel's ring.** A strip knob shows a ring exactly when the device's panel draws one for that parameter, from the same function (the Macro Oscillator's `ring_depth` over its matrix; the Sampler's matrix when it lands; nothing for hosted plug-ins), so strip and panel can never disagree.
3. **A Devices view board is a precondition for slice 2** and is requested now: ordinary cards with at least 448 points of strip plus padding (the 660-wide rack card is the precedent), the selected-device mark, the Configure state, the MIDI effects group's strips, and scrolling or collapse for a chain that no longer fits. The data slices (1, and the model parts of 3 and 4) do not wait for it.

### 8. Slices (main green at each)

1. **Model and data, no UI.** `PageInfo`, `PageSlot`, `PluginInfo::pages`, the Macro Oscillator's `PAGES`, the derived page and its allow-list; `UserPage` on `Insert` and `MidiEffectSlot` with the read rules; the `device_pages` need; the resolver (both tiers, slot states, 3.1's hosted derivation) in the engine; `mix.device_pages` and `mix.device_pages_list`. Tests: the validation test (2.5); round trip with defaults (absent field reads empty, empty is not written, existing fixtures stay byte-identical); the `needs` marker present with user pages on an instrument, on an insert and on a MIDI effect, absent without, and a file with the marker removed still loads the pages (the `PREVIOUS_RELEASE` constant pattern of `sampler_patch_tests.rs`); the read rules (short, long, empty-string, over-long and duplicate slots, a seventeenth page with its load note); a missing id resolves `missing` at its index and the other slots keep theirs; an uninstalled plug-in's slots read `missing`, a loading one's `pending`; hosted derivation at 64 parameters fills eight pages and at 65 none; move and copy carry pages; one undo step per `mix.device_pages`; a `mix.device_pages` edit keeps the device instance (same uid and instance, no re-prepare). Controls: the validation test fails when a page names an id not in the table; the same-instance test fails when the edit is routed through a path that rebuilds the slot.
2. **The strip in the Devices view, on the board.** Knobs, empty and missing cells, page indicator, `enable` dimming, rings, the selected device, MIDI effect strips. Tests: a strip drag writes the same parameter id through the same command as the panel, calls `touch_param`, and is one undo step; a page flip leaves the session clean with no undo step; with `shaper` off the three shaper slots draw dimmed and still write; a missing slot is drawn and takes no input; a hosted plug-in above 64 parameters shows eight empty cells and Configure, and at or below 64 its derived pages; the ring matches the panel's for a routed destination; layout tests assert tokens; help entries in `docs/help/device-chain.toml`; the design README gains the components of 7.1. Control: with the strip writing through a different command, or skipping `touch_param`, the "same id, same command, one undo step" test fails.
3. **User pages and Configure.** Tests: enter and Escape with no touch leave the session clean; the first touch on a factory page makes the copy and fills it in one step; the first touch on a device with no pages makes "User 1"; touches fill the next free slot; the ninth starts a new page; a seventeenth page (new or copy) is refused while the value change stands; a duplicate touch changes nothing; a refused hosted parameter shows ADR 0028's status line; a built-in's touch comes from `touch_param` and a MIDI effect's from its row; a touch dragged over many values (built-in, hosted with its hold, controller with its 400 ms idle) yields exactly two undo steps, the whole drag then the page edit, and undo removes the page edit first; touches during one running gesture join one page step; a touch queued when Configure is left still lands at the gesture's end; an undo that removes the current page clamps with Configure still on; swap, remove, rename, move and delete are one undo step each and the current page follows the UI's own delete; the default file writes, seeds a new instance under the read rules and is listed by neither preset lister. Controls: with the copy step removed, the factory-page test fails; with the page edit executed immediately at detection, the two-step test fails (three steps, the rest of the drag undone first).
4. **CLAP remote controls.** The CLAP test fixture (`crates/clap-host/tests/fixture`) gains remote-control pages with a section, an invalid slot, a hidden-parameter slot, a `changed` call and a `suggest_page` call. Controls: with the section prefix or the `CLAP_INVALID_ID` mapping removed, the mapping test fails; with `changed` serviced inline in the callback, the flag-only test fails.
5. **Controllers follow the page.** Tests: a learned `selected:control:3` drives slot 3 of the selected device's current page and, after a page flip, the new slot 3 without a jump (scaled takeover); a move that lands between the flip and Main's refresh is not applied to the new slot; a Configure swap of slot n on the current page between two moves leaves the second move as a mapping start, not applied to the swapped-in parameter; undo of a page edit, a CLAP `changed` and a tier switch each bump the generation; the packed word never pairs a new value with an old generation (a stress test of concurrent writes and reads); a right-click learn on a MIDI effect's strip knob maps `plugin:midi<n>:<param id>`, and after a reorder that mapping drives whichever effect is now at position n (positional, as insert slots); `selected:page_next` and `selected:page_prev` stop at the ends; an empty or missing slot drops the move; with the rack card selected the controls drive `rack.macro`, and a macro's own learned source still works; with a MIDI effect selected they drive `mix.midi_effect_param`; "Learn controller bank" arms the ten in turn; a session mapping of the same source shows the bank entry overridden; the realtime snapshot is not rebuilt on a page or selection change (counted). ### 9. Gate (at each landing)

The workspace gates of the day (fmt, clippy, tests, layers, file-size), and: user pages round-trip with defaults and the `needs` marker appears exactly when they exist; factory pages validate for every built-in and the derived-page allow-list did not grow; a missing id shows as missing at its own slot and nothing reorders; the strip's knobs drive the same parameter ids as the panel with one undo step per gesture and the same automation recording; a page flip is never an edit; CLAP pages map, follow `changed` and honor `suggest_page` against the fixture; a controller bank follows the selected device's current page, ignores empty slots and never jumps after a flip, including a move between the flip and the refresh; the audio thread gains nothing, shown by the counting-allocator test of the extension lookup and the same-instance test of `mix.device_pages`. Every named test has its control where 8 names one. The review bar is [ADR 0009](0009-refutation-review-before-every-push.md)'s.

## Consequences

- Every device card grows a strip row and widens; the Devices view shows fewer cards at once, which the board has to answer (scrolling, a collapsed card).
- A device panel's own macro or hero knobs (the Macro Oscillator's L knobs) are not the strip: the panel keeps its layout and the strip is a second view of the same parameters. The rack card's macro row is both the rack's own controls (ADR 0034) and its strip.
- Small hosted plug-ins arrive with pages in vendor order; large ones start empty until configured or saved as a default; CLAP plug-ins that ship remote controls arrive with the vendor's pages.
- MIDI effects get strips and the controller bank while their group card keeps listing every parameter, so their controls show twice.
- Sessions with user pages warn on builds that know the `needs` marker but not `device_pages`, and lose the pages if saved there; older pages never break loading.
- A controller profile with the ten `selected:` mappings works in every session.

## Alternatives considered

- **A free-form macro mapping with amounts and curves per device.** Rejected: one control driving several parameters by amounts is the modulation matrix's job (and the rack macros' for layered devices). The strip is a window onto parameters, one slot one parameter, so what a knob shows is what the parameter is.
- **Four or sixteen controls per page.** Four halves what a controller bank and the CLAP extension carry and doubles paging; sixteen does not fit one row of S knobs on a card, is two banks on most controllers and breaks the one-to-one match with CLAP pages. Eight is the maintainer's decision and the extension's constant (`CLAP_REMOTE_CONTROLS_COUNT`).
- **A strip only for hosted plug-ins.** Rejected: built-ins are the devices transit controls best, and controllers following the page need every device to have pages; one mechanism for both is less code than two.
- **Storing the current page in the session.** Rejected in 1.2: every page flip would be an edit with an undo step and a dirty flag, for state that changes nothing audible.
- **Bumping `format_version` for the pages.** Rejected by ADR 0023's rule: an older build can load the file safely; refusing every newer file for an optional view would break "newer files load on the previous build". The `needs` marker is the tool.
- **Re-pointing the rack macros at the current page (#355's wording).** Rejected in 6.4: it would make a macro lane drive whatever the UI shows, so playback would depend on selection.
- **Empty strips for every hosted plug-in without pages.** Rejected in 3.1 against the Ableton and Logic agreement: a six-parameter effect would arrive dead. Pages from VST3 units or AU clumps are rejected in 5.5: groups are not pages.
- **Copying a factory page when Configure is entered.** Rejected in 3.3 and 3.5: entering and leaving with no touch would be an edit and leave a stray page.
