# ADR 0050: Generated indexes: one file per entry, tables built by `cargo xtask indexes`

- **Status:** proposed 2026-11-08 (the maintainer: "Do it. Needs to be low friction for contributors."); revised after a judging round; the pull-request and required-check decisions settled 2026-11-08
- **Date:** 2026-11-08
- **Implementation:** branch `docs/generated-indexes`: `xtask/src/indexes.rs` (the generator, the validator and the one-shot converter), the entry files, the three README tables between markers, `.github/workflows/indexes.yml`, the gates list and `CONTRIBUTING.md`.
- **Reopen when:** an entry pull request is blocked in practice by something in the generated blocks (they are not committed by contributors, so this would mean the main workflow cannot push); GitHub changes how it renders a leading HTML comment in a markdown file; a known-issue entry needs a list-valued field; entries outgrow the one-paragraph body; or the site needs the data (then it reads the entry files, not a README).

## Context

Three indexes were hand-edited: `docs/known-issues/README.md` (a table), `docs/adr/README.md` (a table) and `docs/escapes/README.md` (a list). Every addition appends at the end of a shared file, so two branches always touch the same lines. On 2026-11-08 the known-issues table conflicted four times in one day (twice between the project's own stacked branches, twice on contributor pull requests #379 and #382), and two branches both claimed the next number, K111. GitHub runs no CI on a pull request that conflicts with its base, so a conflict blocks a contributor outright, and the number race needed a maintainer to settle it. Pull requests that touch only markdown or `docs/` are also skipped by `ci.yml` (`paths-ignore`), so a check that lives only there never sees an entry-only pull request.

## Decision

1. **One file per entry; the README block is a view that contributors never commit.** A known issue is `docs/known-issues/entries/<id>.md`. An escape stays where it is, `docs/escapes/<id>.md`, and an ADR stays `docs/adr/NNNN-<slug>.md`: those folders already hold one file per record and many documents link to them. A pull request that adds an entry changes that one file and nothing else, so two entry pull requests can never conflict.
2. **Where the index text lives, with nothing to render badly.**
   - A known-issue entry starts with a hidden comment block, which GitHub does not display: a line `<!-- transit-index`, one `key: value` line per field (the value is everything after the first `: `, verbatim, one line), and a line `-->`. Fields: `status`, `follow-up` (optional), and for the converted legacy entries `order`. The text under the block is the issue column: one paragraph, which may be wrapped (the table row joins its lines with single spaces).
   - An ADR or escape needs no block. The index text is read from what the record already carries: the `# ADR NNNN: <title>` heading and the first clause of the `- **Status:** ...` line (up to the first `;`, ` (` or sentence end) for an ADR; the `#` heading for an escape. The status is never stored a second time, so a status change is made on the record's own line and the index follows. Converted records whose old index title differs from the heading carry a block with a `title` that overrides it (46 of the 50 ADRs, because the old rows were hand-abbreviated; two escapes). A new record needs none.
   - There is no YAML front matter, so GitHub shows no error box or duplicated title above any record.
   - Relative links in an entry are written from its own folder and rebased to the README's folder when the row is written; the validator checks that every relative link in an entry resolves.
3. **The id is the file name, in one rule for both kinds.** A converted entry keeps its name (`K42`, `KC3`, `Note`, `E45`...), because issues, release notes and code comments cite them; the frozen list is `xtask/src/indexes_legacy.txt`. A new entry is `issue-<number>` when a GitHub issue exists, `issue-<number>-b` (then `-c`) for a second entry on the same issue, and otherwise a short lowercase kebab-case slug. Ids are unique across the known-issues and escapes folders (the validator enforces it, case-insensitively), so a defect that has both a known issue and an escape gives the second one the `-b`. A citation names the folder and the id: known issue `issue-380`, escape `issue-380-b`, or the legacy `K42` and `E45`. Nobody assigns a sequence. Two branches that pick the same slug conflict as an add/add on the second pull request; that is rare and the contributor renames the file. ADR numbers stay sequential and are claimed by whoever opens the ADR, as before.
4. **Order is a rule with one frozen exception.** Entries sort by natural id: digit runs compare as numbers, the rest byte for byte (`issue-99` before `issue-380`, `issue-380` before `issue-380-b`, `issue-*` before a slug starting with a later letter). The converted known issues keep their historical table order, which is not sorted (`Note` after K57, then K51; KC1 to KC7 before K73), through an `order` field that only those files carry; the validator refuses `order` on any other file, so copying `K42.md` as a template cannot move a new entry into the legacy block. Converted escapes come first by natural file name. ADRs are by number. Sorting by status was dropped: it would reshuffle 122 rows for no reader's benefit and the conversion has to reproduce the old table byte for byte.
5. **Who runs what.**
   - `cargo xtask indexes --validate` checks the entry files and writes nothing: the hidden `<!-- transit-index` block parses and has its fields, the file name follows the id rule and ids are unique across known issues and escapes, `order` appears only on the converted entries, the body is one paragraph with no table pipe, every relative link resolves. It is the check on pull requests: the `validate` job of `.github/workflows/indexes.yml` runs on **every** pull request, with no path filter, because a required check that a path filter skips stays pending forever and blocks the merge. Validation takes seconds and passes when no entry changed. It never compares the README blocks, so a pull request cannot fail because the base moved.
   - `cargo xtask indexes` validates, then rewrites the three blocks; it is idempotent (a second run changes nothing).
   - On every push to `main` that touches the entry folders or `xtask/`, the `regenerate` job runs `cargo xtask indexes`. If a README changed, it commits that as a docs-only commit with a fixed message and pushes it, then runs `--check`. It does nothing when nothing changed, so it cannot loop, and `ci.yml` ignores docs-only pushes. The README on `main` can lag one workflow run behind a merged entry; this is accepted.
   - The push uses a deploy key with write access, stored as the repository secret `INDEXES_DEPLOY_KEY` and named in the workflow, which the maintainer adds as a bypass actor on the `main` ruleset. `GITHUB_TOKEN` cannot bypass a required status check, so the job does not use it for the push.
   - **Fallback.** When the secret is absent or the push is rejected, the `regenerate` job fails with one line that names the fix (add the deploy key and its bypass, steps in [gates](../contributing/evidence/gates.md)). The landing chain brings the tables current on the next landing: it runs `cargo xtask indexes` before every push to `main` and commits the result on the candidate, and `cargo xtask indexes --check` stays in its gate list and in `cargo xtask ci`. So `--check` on `main` is allowed to lag by one landing. The failed `regenerate` run is a failed workflow run, not a failing gate on the code of `main`, and it goes away once the key is set.
   - The Windows job of `ci.yml` runs `--validate`, not `--check`, so a code pull request is never failed by a README that is one workflow run behind.
6. **Required check, and the order of the setup.** The pull request check is a required status check on `main` (the maintainer's decision, 2026-11-08). Its job is `validate` in `.github/workflows/indexes.yml`, named `indexes entries are valid`; GitHub lists it as `indexes / indexes entries are valid`, and the ruleset names that job. The `regenerate` job is not a required check; it runs after the merge. The maintainer sets, after the first landing of this record and in this order, the `main` ruleset, then the deploy key with its bypass, then the required check, and verifies the `regenerate` job on a test entry before turning the required check on. The numbered steps are in [gates](../contributing/evidence/gates.md#generated-indexes-adr-0050).
7. **Contributor path** (in `CONTRIBUTING.md`): add one file under the entries folder and open the pull request. No toolchain is needed, and the GitHub web editor works. CI validates the file; after the merge, `main` regenerates the table.
8. **The conversion** (`cargo xtask indexes --split-legacy`) split the old tables once. It is kept behind that flag with a test: frozen copies of the three old tables live under `xtask/tests/fixtures/indexes/`, and the test splits them into a temporary tree and regenerates, asserting each README, minus its two marker lines, equals the frozen table byte for byte (one row, K59, gains the closing pipe it lacked). The ADR table is compared outside its status column, which now derives from each record (39 of the 49 rows then showed a changed status, among them three that were stale: 0029, 0042 and 0043 still read proposed). That is the proof the conversion lost nothing. The link rebasing is part of it: the 13 entries whose links were written relative to the README's folder now resolve from `entries/`.

## Alternatives considered

- **Contributors commit the regenerated block.** Rejected: two entry pull requests both change the tail of the table, the second conflicts when the first merges, GitHub then runs no CI on it, and the contributor needs a Rust toolchain to fix it, which the web editor cannot provide. That is the failure this record exists to remove.
- **A merge driver or `.gitattributes` union merge for the tables.** Rejected: it lives in each clone's configuration, so it protects nobody on GitHub.
- **YAML front matter.** Rejected: GitHub renders a leading `---` block as a table, or as an error box when a value is not valid YAML, and many titles start with a backtick or contain `: `.
- **Deriving every index text from the headings, with no overrides.** Rejected for the converted records: the old rows were abbreviated by hand and the conversion has to preserve them; new records derive and carry no block.
- **A YAML parser, a database or a JSON file per kind.** Rejected: a new dependency in a gate crate, or one shared file again.
- **Moving escape and ADR files into `entries/` folders.** Rejected: it breaks every link to them for no gain.

## Consequences

- No shared table is edited or committed by a contributor; the generated blocks are marked as generated, and the main workflow owns them.
- The README on `main` can lag one workflow run after an entry merges.
- Known-issue ids stop being a counter. Citing `K42` still works; a new one is cited as `issue-380`.
- The 46 override blocks on converted ADRs repeat a short title that the record also carries; a title change must be made in both places, and `--check` guards the index against the files, not the files against each other. Status never repeats. New ADRs carry no block.
- Rows keep the historical order for the converted entries forever; search, not order, is how a reader finds one.
- The workflow's push to `main` needs the deploy key and its bypass; without them `regenerate` fails by design with a one-line message and the next landing brings the tables current.
