# ADR 0019: Loops live inside the clip; linked copies stay as Repeat

- **Status:** accepted 2026-10-23 (issue #59); amended 2026-11-09, proposed, MIDI cycles step in ticks (#422)
- **Date:** 2026-10-23
- **Reopen when:** a loop needs a phase the model cannot express (a loop that starts mid-cycle after a split of MIDI), a second loop level (nested loops) is asked for, or the Session view needs per-scene loop lengths that the arrangement length cannot carry.

## Context

`clip.loop` lays down back-to-back copies of a clip and tags them with a shared `loop_id`. Editing one copy does not edit the others, the set is many clips (selection, split, move and fades all see N clips), and a partial last repeat is a separately trimmed copy. Logic's loop handle and Ableton's clip loop brace are one clip whose content cycles: change the content and every cycle changes, the arrangement shows one region with cycle ticks, and the length is one number. The project owner chose this model for the loop handle (#59).

## Decision

1. **A clip is a source region, an optional loop range inside it, and an arrangement length that may exceed one cycle.** `Clip` gains `looping: Option<ClipLoop>` (`#[serde(default)]`; `ClipLoop { start, end }`, samples measured from the clip start, the unit `length` already uses; may be negative after a start trim). `None` means unlooped, so every existing session loads unchanged. Valid when the cycle is at least `MIN_CYCLE` (64 samples), so a loop cannot spin thousands of cycles per block; `sanitize` clears a loop that is not. `length` is the arrangement length and is no longer bounded by the source for a looped clip.
2. **Playback renders the loop modulo the range.** A position `rel` samples into the clip plays content position `rel` while `rel < end`, then `start + (rel - start) % (end - start)`. Only integer arithmetic runs per block (no allocation, no tempo-map lookup for audio), so the wrap is sample accurate and the audio thread stays allocation free (tested with a counting allocator).
3. **Audio.** The wrap happens before the source read, so `stretch` applies to the looped timeline as it does today (the loop range is in clip time, not file time). Fades and the gain envelope follow the arrangement bounds (one fade-in at the clip start, one fade-out at the end), not each cycle. A crossfade at the seam is an optional later refinement (a `seam_fade` length); v1 butts the cycles, which is sample accurate for loops cut on a zero crossing or a bar. Trim start shifts the range by the trimmed amount; trim end past the range adds cycles (no file limit while looped). Split on a looped audio clip keeps both halves looped with the right half's range shifted by the cycle phase at the cut.
4. **MIDI.** Notes and controllers stay in ticks inside the clip; the loop range is in samples like audio, so a cycle is a fixed time span and `retime` scales it with the clip on a tempo change (the cycle as a fixed time span is replaced by Amendment 2026-11-09: a cycle is a whole number of ticks). Cycle 0 plays notes starting before `end`; later cycles play notes with `start <= note start < end`. A note crossing the seam ends at the seam (the same clamp the clip end already applies to held notes) and sounds again at its own position in the next cycle. Controllers replay at their positions in every cycle; there is no reset at the seam, and chase on a seek sends the latest value any cycle produced before the position. Notes before the range start belong to the intro (cycle 0 only). A start trim of a looped MIDI clip goes through one helper (`edit::trim_start`, used by the trim drag, Trim to Selection, Trim Start to Insertion, range copy, retime and split): it moves the notes, controllers and the loop together by the cycle phase of the cut and keeps what the cut moved before the start at negative ticks, because later cycles play it; only the first pass skips it. Splitting a looped MIDI clip therefore keeps every note on both halves. Clarified 2026-10-24: the loop range is stored in samples, but playback, consolidate and the arranger all step cycles from the clip's tick-grid origin with the loop edges rounded to the nearest tick (`soundcraft_mix::loop_frame`), so an off-tick edge plays and draws on the grid; a range that would round under the minimum cycle keeps its sample edges.
5. **Automation follows the arrangement timeline**, not the loop: lanes are keyed to session time and keep that meaning inside a looped clip.
6. **`clip.loop` and `loop_id` stay as Repeat**: independent copies that share an id only so `clip.unloop` can find them. They are not converted automatically. `clip.set_loop` on a clip that has a `loop_id` set is allowed (the copies stay copies); a later `clip.flatten_loop` could replace a Repeat set by one looped clip. The handle's Alt-drag makes a Repeat.
7. **Commands (all one undo step):** `clip.set_loop {clip, start?, end?}` (default the whole clip: `0` to its length), `clip.clear_loop {clip}` (keeps one cycle's length), and `clip.loop_to {clip, to, independent?}`, the handle's command: on an unlooped clip it sets the loop over the whole clip and then the length to `to`; on a looped clip it sets the length; at or before the first cycle's end it clears the loop. `independent: true` (Alt) lays Repeat copies instead. **Any operation that renders a clip to a new file clears the loop on the result**, because the file already holds every cycle: AudioSuite processes, Warp and fit-to-selection stretches (which read the cycles the way playback does), Remove Pitch Shift, and rendering clip gain. MIDI consolidate writes the cycles out as plain notes and controllers (`mix::unroll_midi_loop`, the same cycle math as playback) and the result is unlooped. Lengths stop at neighboring clips, as a trim does.
8. **The header handle.** The upper right of the clip's header strip (clear of the 6-point trim edge and the move area) shows a loop cursor. Dragging right extends the arrangement length in whole cycles with a partial last cycle allowed, snapped to the grid (Shift: no snap); dragging left shortens, and dragging back to the first cycle clears the loop. Ghost cycles draw in the clip color at reduced alpha during the drag; the commit is one command.
9. **Arranger drawing.** A looped clip is one region. A divider tick marks each cycle boundary in the header strip; audio waveforms and MIDI notes draw per cycle from the content under it.
10. **Out of scope, enabled by this model:** a Session/launcher view plays a clip's loop without any arrangement length; a tracker view addresses cycles of one clip; both are separate decisions.

## Consequences

- One clip edit changes every cycle, which is the Logic/Ableton behavior users expect; the cost is that code which assumes `length <= source length` must check `looping` (trim, heal/merge, freeze/bounce, consolidate). `render_clip` is shared by playback and bounce, so both wrap the same way.
- Old sessions load unlooped; a session saved with a loop opens in an older build as an unlooped clip of the saved length (the unknown field is ignored), with audio running past the source end silent.
- The seam crossfade is a known gap. A MIDI cycle is a fixed span of samples, so a tempo change inside a looped clip lets later cycles drift off the bar grid (known issue; withdrawn for MIDI by Amendment 2026-11-09). A saved session opened and saved by an older build drops the loop (known issue). Notes at negative ticks can appear in editors after a start trim of a looped MIDI clip.

## Amendment 2026-11-09: a looped MIDI clip's cycles step in ticks

Amended 2026-11-09, proposed (issue #422). It replaces one clause of decision 4 and withdraws one sentence of the Consequences for MIDI; every other decision, and decision 4's 2026-10-24 clarification, stands.

**The defect.** At 48 kHz and 102.5 BPM a bar is 112,390.24 samples. A looped one-bar MIDI clip placed repeat k of a note at its first-pass sample plus k × 112,390 (the loop length, snapped to ticks, converted to whole samples once, then multiplied), so repeat k sounded about 0.24 × k samples before its tick. Repeat 8, the kick of bar 9, landed at 899,120, inside both the clip end and the arrangement loop end (899,122, the bar-9 tick converted once), so it played two samples before the wrap and the wrap played the first pass's kick again: two note-ons two samples apart on every pass. Where a bar rounds up instead, repeats drift late.

**The rule.**
1. A looped MIDI clip whose frame is on the tick grid (decision 4's clarification: origin and loop edges rounded to ticks, snapped cycle at least `MIN_CYCLE`) has a cycle of C ticks: the tick distance between its loop edges, read through the tempo map at the clip's position. Repeat k (k ≥ 1) of a content point at tick t (a note-on, a note-off, a controller) sounds at `tick_to_samples(t + k·C)`: one conversion per position, through the tempo map's one tick-to-sample function, which also places every note and produced the clip length and the arrangement loop end.
2. Apart from item 4, no path places a repeat from a cycle counted in samples, accumulated or multiplied: playback, offline render, external MIDI output and its chase, controller chase and pedal state, consolidate (`unroll_midi_loop`) and the arranger's ghost notes all take repeat positions from one type, `mix::midi::LoopFrame`, and the piano roll takes its loop edges from it in ticks.
3. Ranges stay half-open: p is inside `[a, b)` when `a <= p < b`, compared in samples after conversion. The conversion is monotonic and a tick spans at least one sample (every supported tempo at 16 kHz and up; this also makes recovering t from a point's first-pass sample exact), so against a boundary that is itself a tick conversion (the clip end and the arrangement loop end, when set on the grid) the sample comparison equals the tick comparison: an event due at the boundary tick is outside.
4. Unchanged exception: a loop whose snapped cycle would be under `MIN_CYCLE` keeps its sample edges and repeats every `end - start` samples.

**Decision 4, old and new.** It said: "the loop range is in samples like audio, so a cycle is a fixed time span and `retime` scales it with the clip on a tempo change." It now means: the loop range is stored in samples like audio and `retime` moves its edges with the clip on a tempo change (unchanged); a cycle is C ticks, not a fixed time span, and its repeats are placed by item 1. The Consequences sentence on later cycles drifting off the bar grid after a tempo change is withdrawn for MIDI. ADR 0023 decision 6 and known issue K40 carry the same sentence and need the same pointer.

**What a listener sees.**
- Constant tempo: every repeat sounds on its tick's sample however long the clip runs; the error no longer grows with k. At tempos where a bar is a whole number of samples nothing changes.
- A tempo change inside a looped clip: C is fixed in ticks, so later repeats stay on the bar grid and a repeat in a slower section lasts more samples. This is what Ableton Live and Logic do for MIDI: a MIDI clip's or region's loop is a musical length whose repeats stay on the bars when the tempo changes.
- A note-off is placed as its own content point, so an off at the seam lands on the next cycle's note-on, never a sample after it.

**Not changed.**
- Audio clips: decision 2 stands, a whole-sample cycle by integer modulo with no tempo-map lookup. Their drift against the grid is #427, a separate decision.
- Saved sessions: no field is added, removed or renamed, and the loop edges keep their meaning (sample offsets from the clip start); what changes is the cycle derived from them, C ticks instead of `end - start` samples. `needs` and `format_version` are unchanged; there is no migration. A loaded file plays differently only in where later MIDI repeats sound: at a constant tempo by at most the old accumulated rounding, and under a tempo change inside a looped MIDI clip, onto the grid. The tests replay the #422 session's stored values unchanged (loop end 899,122, clip loop end 112,390).
- Known gap: the arranger's seam dividers (`cycle_segments`), the cycle whose ghost notes it draws in each segment, and the loop drag's ghost cycles still step the snapped range in samples. At a constant tempo they sit within the old accumulated rounding of the heard seams; under a tempo change inside the clip they part from them. A follow-up brings them under item 2.

**Tests** (fix branch): in `crates/mix/src/loop_wrap_tests.rs`, `the_kick_at_the_loop_start_fires_once_per_pass_with_the_sessions_numbers`, `a_pass_plays_the_same_kicks_at_any_block_size`, `every_tempo_rate_and_length_plays_one_kick_per_beat_per_pass` (2 rates, 7 tempos, 16 lengths), `a_note_over_the_wrap_is_released_once_at_the_wrap`, `consolidating_the_looped_kick_writes_one_note_per_beat_on_its_tick`, `controllers_cycle_long_notes_and_the_chase_follow_the_tick_grid`, `a_four_bar_audio_loop_one_sample_over_the_grid_plays_end_to_end_to_the_wrap`; in `crates/playback/src/player/audio/tests/loop_wrap.rs`, `the_player_wraps_the_kick_loop_with_one_kick_per_beat_per_pass`; `the_latest_cycle_before_a_position_is_found_for_chase` in `crates/mix/src/clip_loop_tests.rs`. Required before landing and not yet written: a tempo change after the first cycle of a looped clip, asserting repeats at `tick_to_samples(t + k·C)` on both sides of it, which fixed-span stepping fails.

**Alternatives rejected.**
- Keep sample stepping with a correction term: a second conversion that must agree with `tick_to_samples` at every k, and the cycle stays a time span, so a tempo change still drifts.
- Snap the loop end so a cycle is a whole number of samples: a bar rarely is, so the loop leaves its bars; it rewrites stored values (under the alpha rule a loud break) for a defect that needs none; and tempo changes still drift.
- Store the loop range in ticks: a format change that adds no behavior here, since playback already snaps the edges to ticks and `retime` keeps them musical.
