# ADR 0019: Loops live inside the clip; linked copies stay as Repeat

- **Status:** accepted 2026-10-23 (issue #59); amended 2026-11-09, proposed, MIDI cycles step in ticks (#422)
- **Date:** 2026-10-23
- **Reopen when:** a loop needs a phase the model cannot express (a loop that starts mid-cycle after a split of MIDI), a second loop level (nested loops) is asked for, or the Session view needs per-scene loop lengths that the arrangement length cannot carry.

## Context

`clip.loop` lays down back-to-back copies of a clip and tags them with a shared `loop_id`. Editing one copy does not edit the others, the set is many clips (selection, split, move and fades all see N clips), and a partial last repeat is a separately trimmed copy. Logic's loop handle and Ableton's clip loop brace are one clip whose content cycles: change the content and every cycle changes, the arrangement shows one region with cycle ticks, and the length is one number. The project owner chose this model for the loop handle (#59).

## Decision

1. **A clip is a source region, an optional loop range inside it, and an arrangement length that may exceed one cycle.** `Clip` gains `looping: Option<ClipLoop>` (`#[serde(default)]`; `ClipLoop { start, end }`, samples measured from the clip start, the unit `length` already uses; may be negative after a start trim). `None` means unlooped, so every existing session loads unchanged. Valid when the cycle is at least `MIN_CYCLE` (64 samples), so a loop cannot spin thousands of cycles per block; `sanitize` clears a loop that is not. `length` is the arrangement length and is no longer bounded by the source for a looped clip.
2. **Playback renders the loop modulo the range.** A position `rel` samples into the clip plays content position `rel` while `rel < end`, then `start + (rel - start) % (end - start)`. Only integer arithmetic runs per block (no allocation, no tempo-map lookup for audio), so the wrap is sample accurate and the audio thread stays allocation free (tested with a counting allocator).
3. **Audio.** The wrap happens before the source read, so `stretch` applies to the looped timeline as it does today (the loop range is in clip time, not file time). Fades and the gain envelope follow the arrangement bounds (one fade-in at the clip start, one fade-out at the end), not each cycle. A crossfade at the seam is an optional later refinement (a `seam_fade` length); v1 butts the cycles, which is sample accurate for loops cut on a zero crossing or a bar. Trim start shifts the range by the trimmed amount; trim end past the range adds cycles (no file limit while looped). Split on a looped audio clip keeps both halves looped with the right half's range shifted by the cycle phase at the cut.
4. **MIDI.** Notes and controllers stay in ticks inside the clip; the loop range is in samples like audio, so a cycle is a fixed time span and `retime` scales it with the clip on a tempo change (the cycle as a fixed time span is replaced by Amendment 2026-11-09: a cycle is a whole number of ticks). Cycle 0 plays notes starting before `end`; later cycles play notes with `start <= note start < end`. A note crossing the seam ends at the seam (the same clamp the clip end already applies to held notes) and sounds again at its own position in the next cycle. Controllers replay at their positions in every cycle; there is no reset at the seam, and chase on a seek sends the latest value any cycle produced before the position. Notes before the range start belong to the intro (cycle 0 only). A start trim of a looped MIDI clip goes through one helper (`edit::trim_start`, used by the trim drag, Trim to Selection, Trim Start to Insertion, range copy, retime and split): it moves the notes, controllers and the loop together by the cycle phase of the cut and keeps what the cut moved before the start at negative ticks, because later cycles play it; only the first pass skips it. Splitting a looped MIDI clip therefore keeps every note on both halves. Clarified 2026-10-24: the loop range is stored in samples, but playback, consolidate and the arranger all step cycles from the clip's tick-grid origin with the loop edges rounded to the nearest tick (`transit_mix::loop_frame`), so an off-tick edge plays and draws on the grid; a range that would round under the minimum cycle keeps its sample edges.
5. **Automation follows the arrangement timeline**, not the loop: lanes are keyed to session time and keep that meaning inside a looped clip.
6. **`clip.loop` and `loop_id` stay as Repeat**: independent copies that share an id only so `clip.unloop` can find them. They are not converted automatically. `clip.set_loop` on a clip that has a `loop_id` set is allowed (the copies stay copies); a later `clip.flatten_loop` could replace a Repeat set by one looped clip. The handle's Alt-drag makes a Repeat.
7. **Commands (all one undo step):** `clip.set_loop {clip, start?, end?}` (default the whole clip: `0` to its length), `clip.clear_loop {clip}` (keeps one cycle's length), and `clip.loop_to {clip, to, independent?}`, the handle's command: on an unlooped clip it sets the loop over the whole clip and then the length to `to`; on a looped clip it sets the length; at or before the first cycle's end it clears the loop. `independent: true` (Alt) lays Repeat copies instead. **Any operation that renders a clip to a new file clears the loop on the result**, because the file already holds every cycle: AudioSuite processes, Warp and fit-to-selection stretches (which read the cycles the way playback does), Remove Pitch Shift, and rendering clip gain. MIDI consolidate writes the cycles out as plain notes and controllers (`mix::unroll_midi_loop`, the same cycle math as playback) and the result is unlooped. Lengths stop at neighboring clips, as a trim does.
8. **The header handle.** The upper right of the clip's header strip (clear of the 6-point trim edge and the move area) shows a loop cursor. Dragging right extends the arrangement length in whole cycles with a partial last cycle allowed, snapped to the grid (Shift: no snap); dragging left shortens, and dragging back to the first cycle clears the loop. Ghost cycles draw in the clip color at reduced alpha during the drag; the commit is one command.
9. **Arranger drawing.** A looped clip is one region. A divider tick marks each cycle boundary in the header strip; audio waveforms and MIDI notes draw per cycle from the content under it.
10. **Out of scope, enabled by this model:** a Session/launcher view plays a clip's loop without any arrangement length; a tracker view addresses cycles of one clip; both are separate decisions.

## Consequences

- One clip edit changes every cycle, which is the Logic/Ableton behavior users expect; the cost is that code which assumes `length <= source length` must check `looping` (trim, heal/merge, freeze/bounce, consolidate). `render_clip` is shared by playback and bounce, so both wrap the same way.
- Old sessions load unlooped; a session saved with a loop opens in an older build as an unlooped clip of the saved length (the unknown field is ignored), with audio running past the source end silent.
- The seam crossfade is a known gap. A MIDI cycle is a fixed span of samples, so a tempo change inside a looped clip lets later cycles drift off the bar grid (known issue; withdrawn for MIDI by Amendment 2026-11-09). A saved session opened and saved by an older build drops the loop (known issue). Notes at negative ticks can appear in editors after a start trim of a looped MIDI clip.

## Amendment 2026-11-09: a looped MIDI clip's cycles step in ticks

Amended 2026-11-09, proposed (issue #422). It replaces one clause of decision 4 and withdraws one sentence of the Consequences for MIDI; every other decision, and decision 4's 2026-10-24 clarification, stands.

**The defect.** At 48 kHz and 102.5 BPM a bar is 112,390.24 samples. A looped one-bar MIDI clip placed repeat k of a note at its first-pass sample plus k × 112,390 (the loop length snapped to ticks, converted to whole samples once, then multiplied), so repeat k sounded about 0.24 × k samples early. Repeat 8, the kick of bar 9, landed at 899,120, inside both the clip end and the arrangement loop end (899,122, the bar-9 tick converted once), so the wrap played the first pass's kick again two samples later, on every pass. Where a bar rounds up instead, repeats drift late.

**The rule.**
1. A looped MIDI clip whose frame is on the tick grid (decision 4's clarification: origin and loop edges rounded to ticks, snapped cycle at least `MIN_CYCLE`) has a cycle of C ticks: the tick distance between its loop edges, each converted at its absolute position (the clip start plus the stored offset) through the tempo map. Repeat k (k ≥ 1) of a content point whose first pass sounds at session tick t (a note-on, a note-off, a controller; t is read before the MIDI Track Offset, which then moves the sounding sample) sounds at `tick_to_samples(t + k·C)`: one conversion per position, through the tempo map's one tick-to-sample function, which also places every note and produced the clip length and the arrangement loop end when they were set on the grid.
2. Apart from the exception (item 5), no path that sounds or writes a repeat of a looped MIDI clip places it from a cycle counted in samples, accumulated or multiplied: playback, offline render, external MIDI output and its chase, controller chase and pedal state, consolidate (`unroll_midi_loop`) and the start-trim helper (`edit::trim_start` through `LoopFrame::trim_to`, item 4) all take positions from one type, `mix::midi::LoopFrame`, or from C ticks. Drawing is outside this rule for now: the arranger places each ghost note through `LoopFrame`, but picks the cycle a segment draws, its seam dividers and the loop drag's ghost cycles by stepping the range in samples (known gap below). The piano roll takes its loop edges from `LoopFrame` in ticks.
3. Ranges stay half-open: p is inside `[a, b)` when `a <= p < b`, compared in samples after conversion. The conversion is monotonic, and a tick spans at least one sample whenever the rate in Hz is at least 16 times the tempo in BPM: every supported tempo, 5 to 1,000 BPM, at 16 kHz and up, and up to 500 BPM at 8 kHz, 689 at 11.025 kHz and 750 at 12 kHz; this also makes recovering t from a point's first-pass sample exact, and makes a loop edge stored by item 4 convert back to its tick. So against a boundary that is itself a tick conversion (the clip end and the arrangement loop end, when set on the grid) the sample comparison equals the tick comparison: an event due at the boundary tick is outside. Above that bound, at the supported rates under 16 kHz only, a tick is shorter than a sample: recovering t can be one tick off, a repeat can sound one sample off its tick, and the comparison can disagree with the tick comparison by one tick at a boundary; a loop trimmed by item 4 can also store an end that rounds to 0 samples from the cut, and the trim then clears the loop, because a stored loop needs an end past 0, with item 4's result for a cleared loop. Accepted, not tested.
4. A start trim or split (a trim that is not zero) of a looped MIDI clip whose frame is on the grid (`edit::trim_start`, every caller) takes the cut's cycle phase in ticks, through `LoopFrame::trim_to`: the cut's tick from the grid origin, reduced into the loop range by whole cycles of C ticks once it is at or past the loop end. Notes and controllers move earlier by that many ticks (later, for a start moved earlier); the new loop edges, that cycle's edges in ticks, are converted once and stored as samples from the cut, so they convert back to the same ticks. Audio clips and a MIDI loop under the exception (item 5) keep the phase as the stored range's sample modulo (the trim itself, for a start moved earlier). A point whose sample is before the cut belongs to the left half only, also when the cut falls between ticks. Where a tick spans at least one sample (item 3), the two halves of a split together sound exactly what the unsplit clip sounded, at a constant tempo and across tempo changes, except where the cut's cycle, under a faster tempo than the clip's first cycle, is under `MIN_CYCLE` samples (a loop of at most 21 ticks at 48 kHz, 127 at 8 kHz, even at 1,000 BPM): the trim then clears the loop (as `shift_loop` clears a loop it leaves invalid), the right half no longer repeats, and the notes the cut moved to negative ticks stay in the now unlooped clip, where playback starts them at its first tick, all at once. Accepted, not tested.
5. Unchanged exception: a loop whose snapped cycle would be under `MIN_CYCLE` keeps its sample edges and repeats every `end - start` samples. Nothing else falls back: a snapped loop end at or before the clip's grid origin (a session trimmed or split by an earlier build, at the stored range's sample phase, can hold one; a trim by item 4 cannot leave one) is still a grid frame: nothing plays in its first pass, and its cycles play.

**Decision 4, old and new.** Its "a cycle is a fixed time span" now means: the loop range is stored in samples and `retime` moves its edges with the clip on a tempo change (unchanged; a time-locked clip keeps its edges in samples, so its C is re-read from them under the new map); a cycle is C ticks, placed by item 1; the cycle phase of a start trim (decision 4's `edit::trim_start`) of a MIDI clip on the grid is measured in ticks by item 4, not by the stored range's sample modulo. The Consequences sentence on later cycles drifting off the bar grid after a tempo change is withdrawn for MIDI. ADR 0023 decision 6 and known issue K40 carried the same sentence and are updated in the same change.

**What a listener sees.**
- Constant tempo: every repeat sounds on its tick's sample however long the clip runs. Where one cycle is a whole number of samples at a constant tempo (for example a one-bar loop at a tempo whose bar is), nothing changes.
- A tempo change inside a looped clip: C is fixed in ticks, so later repeats keep their musical positions (every C ticks) and a repeat in a slower section lasts more samples. This follows the convention Ableton Live and Logic share for MIDI: a MIDI clip's or region's loop length is musical (bars and beats), so its repeats follow tempo changes.
- A note-off is its own content point, so an off at the seam lands on the next cycle's note-on, never a sample after it.

**Not changed.**
- Audio clips: decision 2 stands, a whole-sample cycle by integer modulo with no tempo-map lookup. Their drift against the grid is #427, a separate decision.
- Saved sessions: no field, `needs` entry or `format_version` changes and there is no migration; the loop edges keep their meaning (sample offsets from the clip start), only the cycle derived from them changes. A loaded file plays differently only in where and whether later MIDI repeats sound: at a constant tempo they move by at most the old accumulated rounding, a repeat the old rounding put inside a clip end or loop end no longer sounds before it, and one it pushed to or past that end now sounds inside it; under a tempo change inside a looped MIDI clip they move onto the grid, so how many repeats fit before the clip end follows the tempo (the tempo-change test hears 32 kicks a pass where the old placement played 26).
- Known gap: the arranger's seam dividers (`cycle_segments`), the cycle whose ghost notes it draws in each segment, and the loop drag's ghost cycles still step the snapped range in samples, so they part from the heard seams under a tempo change inside the clip. Drawing only: nothing sounds or is written from these. Follow-up issue #N, filed at landing, brings them under item 2.

**Alternatives rejected.**
- A correction term on sample stepping: a second conversion that must agree with `tick_to_samples` at every k, and a tempo change still drifts.
- Snapping the loop end to a whole-sample cycle: the loop leaves its bars, stored values are rewritten for a defect that needs none, and tempo changes still drift.
- Storing the loop range in ticks: a format change that adds no behavior, since playback already snaps the edges to ticks and `retime` keeps them musical.
