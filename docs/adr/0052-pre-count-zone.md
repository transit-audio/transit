# ADR 0052: A pre-count zone before bar 1

- **Status:** accepted 2026-11-11 (proposed 2026-11-10; settled after three judging rounds; the maintainer decided the product choices on 2026-11-10); amendment 2026-11-16, accepted after three judging rounds: the latch at a converted device rate (#724); amendment 2026-11-26 proposed: audio in the zone and audio during the count-in (#442, decision 18)
- **Date:** 2026-11-10
- **Implementation:** all slices built: 1, 2, 2b, 3, 4, 5, 6a and 6b landed; 7 (recording into the zone) built; slices 8 to 11 (amendment 2026-11-26) not started. Slices in the Slices section and the amendment. Issues #441 (this decision), #440 (the stopgap it replaces), #327 (pickups, whose clip-start rule it changes), #442 (audio during the count-in), #330 (retrospective capture).
- **Reopen when:** a user asks to drag the session start by hand (Logic's project start marker); a tempo or meter change before bar 1 is asked for; a hardware sync output (ADR 0043) has to start a receiver inside the zone; or the derived session start costs a frame budget on a session with many clips.

## Context

A player records MIDI from the very start of a session with a count-in, plays into the downbeat while the click counts, and loses what they played: nothing exists before the session start. Today three places clamp a pickup to sample 0, and the take builder turned a note played wholly before it into a sliver on the first tick; `main` now leaves such a note out (#440's stopgap, decision 8):

- `MidiTake::timed` (`crates/playback/src/player/device.rs`) clamps each offset at `-point.position.sample.max(0)`.
- `Journal::events` (`crates/engine/src/midi_journal.rs`) clamps at `-h.position.max(0)`.
- `taken` (`crates/engine/src/midi_take.rs`, called by `build_wrapping`) computes `floor = -cut.start.max(0)`, `lead = earliest.max(floor).min(0)`, and maps every kept event to `e.offset.max(lead)`, so a note-on and note-off before the floor land on the same sample (before #440's stopgap `close` gave such a note the length `(b - a).max(1)`; on `main`, `ended_before_start` drops it).

The clip start today follows #327: `pickup` returns the earliest note-on before the latch, and the first stretch starts there. A punch takes no pickup. With Cycle on, pickups join the first lap only (ADR 0026, amendment of 2026-11-04).

**A MIDI clip's left edge destroys today; its right edge hides.** `trim_start` (`crates/engine/src/edit.rs`), the one start trim for the trim drag, Trim to Selection, Trim Start to Insertion, range copy, retime and the split of a looped clip (an unlooped split partitions in `split_clip`), re-anchors notes by the cut's ticks and, for a clip that is not looped, drops what the cut left before the new start (`sequence.notes.retain(|n| n.start >= shift)`, the same for controllers). A looped clip keeps those notes at negative ticks, because later cycles play them (ADR 0019 decision 4; on the tick grid the shift comes from `LoopFrame::trim_to`). `Clip::trim_end_to` (`crates/model/src/clip.rs`) only shortens `length`: notes past the end stay in the sequence and do not sound (`played_note` in `crates/mix/src/midi.rs` keeps a note only when it starts before the clip's grid end), so dragging the end back out restores them. Playback of a clip that is not looped clamps a note at a negative tick to tick 0 (`played_note`, `n.start.max(0)` when `keep_negative` is false), so it sounds at the clip's first tick, while a controller at a negative tick does not sound (`c.tick >= 0 || looping.is_some()`). `split_clip` partitions the notes of a clip that is not looped between the two halves.

**The time model is already signed.** `Samples` is `i64` (`crates/time/src/lib.rs`), `Range` is a signed half-open pair, and `MAX_POSITION` bounds positions at ±2^40. `TempoMap` (`crates/time/src/tempo.rs`) extends its first tempo and its first meter backward: `tick_to_samples` of a negative tick and `samples_to_ticks_f` of a negative sample both use the tick-0 tempo, `bar_start_tick` documents "bars before 1 extend the first meter backwards", and `bar_beat_at_tick` returns bar 0 for the bar before bar 1 (test `negative_positions`). `format_position` and `parse_position` (`crates/time/src/format.rs`) print and read negative Min:Secs and negative bars. `GridValue::line_at_or_before` (`crates/time/src/grid.rs`) uses `div_euclid`, so snapping is correct on either side of zero. `Clip::sanitize` (`crates/model/src/clip.rs`) bounds a clip start to ±`MAX_POSITION`, not to zero, and MIDI notes already carry negative ticks after a start trim of a looped clip (ADR 0019 decision 4). The player's count-in entry (`count_in` in `crates/playback/src/player/audio.rs`) accepts any start within ±`MAX_POSITION`. `position_param` (`crates/engine/src/cmd/mod.rs`) clamps protocol positions to ±`MAX_POSITION`.

**The floor at zero is policy, spread over call sites.** Commands clamp at zero one by one: `transport.play`, `transport.locate`, `transport.rewind` and `transport.loop` (`crates/engine/src/cmd/transport.rs`); clip moves (`move_clips` in `crates/engine/src/edit.rs`, `c.start.saturating_add(delta).max(0)`) and the ripple floor (`ripple_spans`); the edit selection (`crates/engine/src/cmd/edit.rs`); `view.scroll` (`crates/engine/src/cmd/view.rs`, `clamp(0, MAX_POSITION)`); markers and automation points (`crates/engine/src/cmd/event.rs`, `crates/engine/src/cmd/mix.rs`); MIDI clip creation (`crates/engine/src/cmd/midi_time.rs` on its `length` path, `crates/engine/src/cmd/event_more.rs`); the bounce default range `Range::new(0, content_end)` (`crates/engine/src/cmd/file.rs`, `crates/engine/src/cmd/realtime_render.rs`); `bounded_to_track` (`crates/engine/src/io.rs`). In the UI: `drop_start` (`crates/ui-studio/src/arrange.rs`, "never before zero"), `click_ruler` (`crates/ui-studio/src/actions.rs`), `follow_playhead`, the grid overlay's first bar (`crates/ui-studio/src/arrange/grid_overlay.rs`, `.max(0)` and `.bar.max(1)`), `begin_pass` (`crates/ui-studio/src/host/recording.rs`, pre-roll start `.max(0)`), `recording_pass_inspect` (`capture_start` clamped at 0), the edit cursor (`cursor` and `set_cursor` in `crates/ui-studio/src/lib.rs`), the arranger's snap helpers (`automation::snap`, `snap_delta`), the transport counter (`bars_beats`, `min_sec` in `crates/ui-studio/src/transport.rs`) and nudge (`nudge_plan`). MIDI file export clamps negative ticks to 0 (`clamp_tick` in `crates/midi/src/smf.rs`), and `midi_time::origin` clamps a clip's origin tick. The timeline click (`render` in `crates/mix/src/click.rs`) starts its scan at `.max(0)` ticks, so it never sounds before bar 1. A grep for `.max(0)` finds about 50 non-test sites in `crates/engine/src` and about 60 in `crates/ui-studio/src`; not all are positions.

**Conventions.** Logic is the only reference for anything specific to the zone. Ableton Live does not record during its count-in (its manual: Live "will not begin recording until the count-in is complete"; notes played early are recovered with Capture MIDI), so Live is cited only for general clip behavior: with MIDI Arrangement Overdub on, a new recording mixes into what is already on the track (Live manual), which is a merge. Verified for Logic: its count-in plays before the playhead and switches to record when it reaches it (Apple's Logic Pro help), and its project start marker can be dragged left in the ruler, giving bars before bar 1 (Apple's manual for the marker). Seen only as excerpts of Apple's text, not read in full: Logic's Recording settings offer Merge, Create Take Folder and Overlap for overlapping MIDI recordings, and Merge extends the existing region; notes outside a shortened region are muted, not deleted, and play again when it is lengthened (the iPad guide); the metronome has a "Click while playing" setting. Unverified for Logic: the numbering of bars before a moved project start (forum reports put the limit at bar -8); that notes played during the count-in are recorded into a region that starts before the project start (this ADR takes it as the maintainer's decision, #327 and #441, not as a cited fact); where a MIDI region starts when notes were played during a count-in in the middle of a project (at the first note, at the bar line before it, or at the count-in start; the maintainer's rule, decision 1.2, does not depend on it); whether the click sounds in bars before a moved project start; how bars before the project start are drawn; Logic's default for overlapping MIDI recordings; how the piano roll shows notes outside a region; and what Go to Beginning does with a moved project start. For audio, Apple's Logic Pro 8 manual says "Any audio present during the count-in will be recorded"; that the recorded audio region then starts at the record position and its left edge can be dragged back to reveal the count-in audio is unverified. Whether Live's Arrangement can hold a clip before 1.1.1 is unverified and not relied on.

## Decision

### 1. Decided by the maintainer (fixed)

1. People play into the downbeat while the click counts them in. What they play during the count-in is saved into the clip.
2. **One rule everywhere.** When something was played during the count-in, the clip covers the whole count-in, whether the recording starts at the session start or later in the session. One bar of click gives one bar before the record start; a longer count-in gives as many bars as it lasts. At the session start this is the pre-count zone: the zone's length is derived from the count-in length. This changes #327, where the clip starts at the first pickup (decision 9 lists the tests that change).
3. **Only when something was played.** The zone, and the early clip start, appear only when something was played during the count-in. A take with nothing played early starts at the record start, as today.
4. **Bars count down before bar 1, as Logic's bars before a moved project start do** (Apple's help for the project start marker; the numbering itself is from forum reports, not verified in Apple's documentation): bar 0, bar -1, and so on. Bar 1 stays where the song starts.
5. **MIDI first.** This ADR covers MIDI pickups only. Audio played during the count-in is wanted and is tracked as #442; decision 18 (amendment 2026-11-26) decides it.
6. Workflow follows what Logic and Ableton agree on unless transit can do clearly better; no inherited Pro Tools construct is binding.
7. Alpha: no migration shims. A session with content before bar 1 is a clean break, said loudly (decision 13).
8. **One capture model for MIDI and audio.** Everything from the start of the count-in is captured; the clip's left edge decides what is heard. Only the default edge differs. MIDI (this ADR): when something was played during the count-in, the edge opens to the count-in start, so an early note is seen and heard at once. Audio (decision 18): the edge stays at the record start, because count-in audio is mostly room bleed and floor noise; dragging the edge back reveals it (decision 14).
9. **Trimming a MIDI clip's left edge hides the early notes; it does not destroy them.** Dragging the edge back out restores them (decision 17).
10. **No catch range.** Nothing moves slightly early notes onto the clip start: notes stay where they were played.

"Something was played" means a note-on during the count-in, which is what `pickup` keys on today (decision 8 says what happens to controllers).

### 2. Representation: signed positions, a derived session start

**Positions before bar 1 are negative samples and negative ticks, through the model and the saved file.** Sample 0 stays bar 1 and tick 0 stays bar 1. Nothing new is stored: the zone is where the earliest clip starts.

**`Session::start()`** (new, `crates/model/src/session.rs`) is the earliest `start` of any clip on any playlist of any track, or 0 when that is later than 0. It is never after 0. Every playlist counts, not only the active one, so choosing a take (ADR 0039) never moves the session start. The zone is `[Session::start(), 0)`; it is empty in every session that exists today. It sits beside `content_end()`. `content_end()` counts the active playlist only; `start()` counts every playlist, so a pickup on an inactive take keeps a silent zone. Accepted: a take choice never moves bar numbers or the bounce start.

**The floors move from 0 to `Session::start()`** where a position may address the zone (decisions 5 to 8, 10, 12), and stay at 0 where it may not (decision 11). Each site is changed on purpose, never by a global search and replace.

**Why this one.** The brief asked for an honest comparison of three:

- **(a) Signed positions.** The types, the tempo map, the bar numbering, the formats, the grid, clip sanitizing and the player's position check are already signed (Context). ADR 0019 and its 2026-11-09 amendment hold across zero: before the first tempo event the tempo map is one linear segment through tick 0, so `tick_to_samples` stays monotonic and one conversion per position; `grid_start` and `grid_end` round a clip edge to the nearest tick on either side of zero (`to_samples` rounds half away from zero symmetrically, which keeps monotonicity); a looped clip's `LoopFrame` origin is a tick, negative or not; half-open ranges compare the same way. The cost is the floor sites above, each a one-line change with a test per class, plus the UI drawing that starts at bar 1.
- **(b) A session-start offset** (sample 0 is the zone start, bar 1 is a displayed offset, every stored position non-negative). `TempoMap` places bar 1 at tick 0 and sample 0 (`sanitize` forces a tempo and a meter at tick 0), so either every conversion gains an origin term or bar 1 moves off tick 0. Creating a zone after content exists rewrites every stored sample position (clips, automation points, markers, key signatures, loop range, selections, playhead, `timecode_start`, the recording plan and journal), which is (c) in another name, and changes every Min:Secs reading of the song. A fixed headroom given to every session from the start would change every existing file and is a Pro Tools-style construct.
- **(c) Shift content later and renumber.** The code already has this: `event.move_song_start` (`crates/engine/src/cmd/event_more.rs`) rebuilds the tempo map and moves musical material through `retime::move_material`. It moves only ticks-timebase tracks, so audio and samples-timebase material would part from MIDI, one record pass would become a whole-session edit inside the "Record" undo step, and time readings (Min:Secs, timecode, a bounced file's sync) would move under the user.

(a) keeps the invariants with the least risk. It is chosen.

### 3. Tempo and meter in the zone

The zone has the tempo and meter in effect at bar 1: the first tempo event and the first meter event, extended backward, as `TempoMap` already does. No tempo or meter event can be placed before bar 1 (`set_tempo` and `set_meter` clamp to tick 0, `sanitize` drops negative ticks; unchanged). A record start at bar 1 counts in at bar 1's tempo and meter (`count_in_for` in `crates/ui-studio/src/metronome.rs` measures "the bar containing `at`"), so the count-in and the zone agree. A change of bar 1's tempo re-places the zone's clips through `retime` like any other ticks-timebase clip; their samples change, their ticks do not (proposed test under Evidence).

A count-in from a later record start whose bar has another tempo can reach back across bar 1 (for example a two-bar count-in from bar 2 after a tempo change at bar 2). Its clicks were at that bar's tempo; the zone's grid is at bar 1's. The notes stay where they were played in time, as every pickup does today; they may sit off the zone's grid lines. Accepted.

### 4. The ruler, bar numbers, grid and snapping

- The ruler, the grid lines and the arranger lanes start at the session start. `grid_overlay::lines` starts from the bar containing `Session::start()` instead of `.max(0)` and `.bar.max(1)`; bar labels come from `bar_beat_at_tick`, which already counts 0, -1, ... (decision 1.4).
- Snapping in the zone: the arranger's snap helpers (`automation::snap`, `snap_delta` in `crates/ui-studio/src/automation.rs`) drop their `.max(0)` clamps and floor at the session start. Their rounding (`f64::round` of a tick ratio) is already symmetric. The engine's `GridValue` already handles negative positions. The `loopbar.rs` test that pins `snap(-400) == 0` stays (no zone); a zone case pins the session-start floor.
- Start-trim gestures use the clip-specific floor of decision 7, including snapping, the drag preview and the submitted target. `arrange::trim_edge` (`crates/ui-studio/src/arrange.rs`, which today clamps the target with `.max(0)` before `automation::snap`) and the `DragKind::TrimStart` preview (which clamps again with `.clamp(0, end - 1)`) must not clamp first at zero or at the session start. Other position gestures keep their stated floors. The UI exception lands with the hidden-content trim floor (Slices).
- The view can scroll to the session start (`view.scroll` floors at `Session::start()`, as do `follow_playhead` and the scroll gestures), and no further. After a recording whose count-in pickups start the take before the view's left edge, the first take that makes the zone and later ones alike, the view scrolls back to the take's start; a take that starts in sight, or at its record start, leaves the view where it is (#707).
- The transport counter (`bars_beats` and `min_sec` in `crates/ui-studio/src/transport.rs`) drops its `.max(0)`: Bars|Beats shows bar 0 and negative bars, and Min:Secs gets a sign-aware formatter (`-0:01.000`), the same as `transit_time::format_position`.
- The zone is drawn on a slightly darker lane background so bar 1 reads as where the song starts (decided by the maintainer). The color is a token added under ADR 0045 in the same landing.

### 5. Transport

- **Return to Zero** (`transport.rtz`, Home) goes to the session start: the zone start when there is one, else bar 1. This is decided by the maintainer. Play from there plays the pickups.
- `transport.play {from}`, `transport.locate`, `transport.rewind` and `click_ruler` floor at the session start, and so do the edit cursor (`StudioApp::cursor` and `set_cursor` in `crates/ui-studio/src/lib.rs`), `play_from_cursor`'s pre-roll start (`crates/ui-studio/src/host/transport.rs`), `click_empty`, `copy_clip_to` (`crates/ui-studio/src/actions.rs`), and nudge (`nudge_plan` in `crates/ui-studio/src/edit_tools.rs`, which floors at the session start instead of tick 0; today nudge-left of a clip before tick 0 would move it right, onto bar 1).
- **The click sounds in the zone** during playback when Click is on: `render` in `crates/mix/src/click.rs` drops its `.max(0)` and nothing else: it clicks wherever the transport is, and the floors keep the transport at or after the session start. Without this, playing from the start would be silent until bar 1 although the music started a bar earlier. Decided by the maintainer.
- **Pre-roll** at bar 1 still starts at bar 1 when there is no zone (the pre-roll start floors at `Session::start()` in `begin_pass`). With a zone, pre-roll may start in it. Proposed.
- **Hardware sync** (ADR 0043): Song Position counts sixteenths from 0 and cannot address the zone. A followed Start or Song Position locates at or after bar 1, unchanged. A sync output started inside the zone is out of scope here; it belongs to an ADR 0043 amendment when that ADR's output slices land.

### 6. Loop and punch

- The loop range and the punch range floor at the session start instead of 0 (`transport.loop`, the loop strip, `options.loop_playback`'s four-bar default). With no zone this is today's behavior.
- A loop that starts at bar 1 with Cycle on and a count-in: the count-in clicks before bar 1. When something is played during it, the first lap's clip covers the whole count-in (decision 1.2) and starts in the zone; later laps are whole loops, as `build_wrapping` already does for pickups. The transport loop itself stays where the user set it; playback loops back to bar 1, never into the zone.
- A punch takes no pickups (unchanged): a punch keeps its range.

### 7. Editing

- **MIDI clips may sit in the zone.** A MIDI clip may be moved, split, pasted, copied or drawn anywhere at or after the session start; a start trim may reach further (next bullet). A move, paste or copy never goes before the session start: it stops there, as moves and copies stop at sample 0 today (a protocol `edit.paste` had no floor before slice 1). So a drag does not grow the zone: the user cannot extend the zone by hand (decided by the maintainer; Logic's draggable project start is a later decision, see Reopen when). A zone clip moved to bar 1 or later therefore returns to the zone only by undo.
- **A start trim may reach the clip's own hidden content.** A start trim of a MIDI clip (`trim_clip` in `crates/engine/src/edit.rs`, whose left bound today is `lo = lo.max(0)`; a MIDI clip has no `material_len`, so that floor is its only bound) floors at the earlier of the session start and the clip's hidden-content position. For an unlooped MIDI clip, let `base = samples_to_ticks(clip.start)` and let `h` be the earliest negative stored note or controller tick. Its hidden-content position is `tick_to_samples(base.saturating_add(h))`, bounded by `-MAX_POSITION`; do not add a tick duration converted at tick 0 to `clip.start` (across a tempo change that lands far from the content: at 48 kHz, 120 BPM in bar 1 and 60 BPM from bar 2, a clip trimmed to bar 3 starts at sample 288,000, tick 7,680, and its hidden note at session tick -960 has relative tick -8,640; its position is sample -24,000, not `288000 + tick_to_samples(-8640) = 72000`). The start-trim floor is the earlier of that position and the session start. A looped MIDI clip's start-trim floor is the session start: its negative ticks are material for later cycles, not hidden content. `trim_clip`, `arrange::trim_edge` and the `TrimStart` preview compute the floor with one engine function, so the drag, its preview and the submitted command agree. Existing neighbor and shuffle constraints still apply. A trim that reaches before the session start grows the zone to it. This is not a handle for the zone: only content that was captured can be revealed. Decision 18.1 applies the same rule to an audio clip's file start. Without this, a count-in take trimmed to bar 1 would leave `Session::start()` at 0 and its pickups out of reach except by undo, against decision 1.9.
- **Stored positions are not rewritten** when the zone shrinks or goes. A command or gesture that reads a stored position before the session start floors it there: Play and Cycle start the loop at `max(loop.start, start())` and ignore a loop that ends at or before it, and the cursor, selection and scroll floor on read. This covers UI consumers as well as protocol setters, for example `wanted_loop` (`crates/ui-studio/src/host/transport.rs`). Undo restores the zone, and the stored positions mean what they did (`retime::same_material` in `crates/engine/src/retime.rs` lists the stored selections and loop range).
- **A move of several clips** stops for all of them when the first one reaches its floor, keeping their spacing (`ripple_spans` already keeps spacing at its floor). An audio clip's move floor is the session start too (decision 18.1, superseding the bar-1 floor of decision 11), so a mixed selection stops when its first clip reaches the session start.
- **The zone disappears with its content.** Delete the zone's clips, or move them to bar 1 or later, and the session start returns to 0. Undo brings it back, because it is derived from the clips undo restores.
- Notes inside a MIDI clip keep their clip-relative ticks; nothing in the piano roll changes, since a clip's own tick 0 is its start.
- **`event.move_song_start` is retired when the pre-count zone feature lands.** Until that landing, the command refuses while the session start is before 0, with a message naming the zone (its `.max(0)` would crush zone clips onto bar 1). Retirement is decided by the maintainer; there is no compatibility alias or migration shim.

### 8. Recording

**The capture.** Nothing changes on the audio thread: MIDI capture already runs from the count-in start on the device-frame clock and stamps events against the latch (`crates/playback/src/player/audio.rs`). The latch is the output frame that presents the record start's first sample, at a converted device rate too, to the nearest output frame (within half an output frame when the frames rendered since the converter started do not convert to a whole number of output frames), and the count-in bar keeps its full length there (amended 2026-11-16, #724: at a converted rate the latch was the output frame being produced, early by the output converter's lead). The three floors go:

- `MidiTake::timed` drops `.max(floor)`.
- `Journal::events` drops `.max(floor)`.
- `taken` (on `build_wrapping`'s path) drops `floor`; `lead` no longer clamps at `-cut.start`.

**The count-in length reaches the take builder.** `Cut` (`crates/engine/src/midi_take.rs`) gains `count_in: Option<Samples>`. `Recording` (`crates/engine/src/io/recording.rs`) and the journal `Header` (`crates/engine/src/midi_journal.rs`) gain `count_in: Option<Samples>` with `#[serde(default, skip_serializing_if = "Option::is_none")]`, written as `Some(frames)` by `plan_recording` from the plan's `CountIn::frames`, or `Some(0)` for a pass without a count-in. `VERSION` stays 1, and older builds ignore the field (neither type denies unknown fields). `None` means a journal written before this change: recovery uses #327's earliest-pickup start. With `Some(n)`, a pickup is a note-on with an offset in `[-n, 0)`. Events before `-n` are dropped (the capture is cleared at arm time in `prepare_midi_recording`, before the count-in starts, so a note-on in that gap is outside the count-in), and with `Some(0)` nothing before the latch is a pickup.

**The clip start.** In `build_wrapping`, when the pass has no punch and a pickup falls in the count-in, the first stretch starts at `-n`: the clip starts at the record start less the whole count-in, wherever the record start is. When nothing was played during the count-in, the first stretch starts at the latch, as today (decision 1.3).

**Events kept.** With a pickup, every event from the count-in start is kept and visible, controllers included, so a sustain pedal pressed before the first note is in the clip and sounds. Today `build_wrapping` keeps only events at or after the earliest note-on. Without a pickup, the clip starts at the latch (decision 1.3), and controllers from the count-in are kept at negative ticks, hidden by the left edge (decision 17): a pedal pressed during a count-in where nothing was played is in the file and does not sound. This follows from decision 1.8 (capture hides, never destroys). Its cost: a controller that streams during the count-in (a mod wheel, aftertouch, a pedal) puts hidden controllers into many takes, and each such take lists `midi_hidden_notes` (decision 17.8). A completed pass with captured controllers but no visible events retains them in a silent clip whose left edge stays at the latch; it does not open an early edge or create a new zone. A pass with no retained events still makes no clip. Creating no clip for a controller-only pass would discard those controllers (the journal is not permanent storage: recording completion disposes of it) and would need an explicit change to the keep-hidden ruling. Hidden describes an event relative to its containing clip's final edge: under the current overlap recommendation, merging into an earlier existing clip can reveal incoming count-in controllers as well as existing hidden material, even when the existing clip's start does not move (`merge` in `crates/engine/src/midi_take.rs` rebases the incoming events into the existing clip, where their ticks are positive). Keeping an incoming controller hidden independently of that final edge is not provided by this single-edge capture model. This consequence is accepted with the overlap and controller rules, both decided by the maintainer. `without_a_pickup_nothing_before_the_latch_is_kept_and_the_clip_starts_at_the_latch` changes: the clip range and its audible notes are as before, and the stray controller is now in the sequence at a negative tick.

**Where the clip lands.** The clip start is `cut.start - cut.count_in` in samples: the device-clock position of the count-in start. At a record start on bar 1 this is within half a sample per counted beat of bar `1 - N`'s tick, because `CountIn::frames` is a rounded beat times the beats (`count_in_for`). ADR 0019's grid start rounds the clip edge to its tick, so the clip sounds from the bar line. Placing the count-in's beats from the tempo map, so the clicks and the zone's grid agree exactly, is a follow-up issue, #703 ("Count-in clicks placed from the tempo map"); this ADR does not need it.

**Record start in the zone.** A recording may start from a cursor in the zone; its count-in reaches further back, and when something is played during it the zone grows to the new clip's start. Positions stay within `-MAX_POSITION` (`Clip::sanitize`). The zone has no other cap. `wrapped` in `midi_take.rs` drops its `cut.start >= 0` condition, so a record start in the zone that runs into a cycle still cuts its laps.

**Loop recording.** Pickups belong to the first take, whose clip covers the whole count-in; later laps are unchanged (ADR 0026 amendment, item 3).

**Overlap.** The clip's range decides the overlap rules, as today: one MIDI clip in the way merges (overdub); several, or a loop, keep the old ones as the previous take on a duplicated playlist (`place_midi_recording_wrapping`). Because the whole count-in is covered, a take recorded right after an earlier clip now overlaps it for the whole count-in instead of from the first pickup, and so merges into it, or duplicates the playlist, more often than before. This follows from decision 1.2. Today's rules on the clip's range stay, decided by the maintainer: merging loses nothing, while deciding from the first captured event would leave the new clip overlapping the old one, which `place_clip` resolves by trimming the old clip. A merge that moves the clip's start earlier reveals hidden notes the new start passes (decision 17.11).

**#440's stopgap, as it is on `main`.** `taken` in `crates/engine/src/midi_take.rs` places pickups, clamps events at the session start and calls `ended_before_start`, which finds every note whose note-on and note-off are both at or before the session start; `taken` drops them and counts them in `Taken::left_out`. `left_out_before_start` sums that count for the status line, which `crates/ui-studio/src/host/recording.rs` appends after placing a MIDI pass ("N count-in notes before the session start were left out"). The user guide's recording section (`docs/user-guide.md`) says how many are left out, and known issue `issue-440` (`docs/known-issues/entries/issue-440.md`, with its row in `docs/known-issues/README.md`) records the stopgap; `Journal::events`'s doc comment (`crates/engine/src/midi_journal.rs`) describes it too. The recording slice removes `ended_before_start`, `left_out_before_start`, `Taken::left_out` and the status line, folds what is left of `taken` into the one-rule placement, replaces the guide's sentence with one describing the zone, and closes `issue-440`. The tests `count_in_notes_that_ended_before_the_session_start_are_left_out`, `loop_recording_from_the_session_start_leaves_the_ended_count_in_notes_out_of_every_lap` and `journal_recovery_leaves_out_the_same_count_in_notes_as_the_live_take` (`midi_take.rs`) and `count_in_notes_left_out_at_the_session_start_are_reported_on_the_status_line` (`crates/ui-studio/src/midi_pickup_tests.rs`) are replaced by tests that place those notes in the zone.

### 10. Export and bounce

- **Bounce includes the zone by default.** Bounce, stems and real-time render start from the session start (`Session::start()`) when no range is given: `Range::new(s.start(), content_end)` in `file.bounce_mix` (`bounce_job`), `file.bounce_paths` (`bounce_paths_job`), `file.bounce_stems` and the real-time render (`crates/engine/src/cmd/file.rs`, `crates/engine/src/cmd/realtime_render.rs`). The Bounce dialog's whole-song range starts there too (`crates/ui-studio/src/finish.rs`), because the dialog passes its range explicitly. With no zone this is today's range. This is decided by the maintainer.
- Stems share that start, so they line up with each other and with the mix.
- `file.bounce_consolidated` starts at the zone (slice 2b): its MIDI files and its tempo file start at the bar holding the session start, as the plain MIDI file export does, and its stems start at that bar's first sample (`consolidated_range` in `crates/engine/src/io/consolidated.rs`), so every stem and MIDI file of one export shares one start and lines up when imported at one position; bar 1 falls a whole number of bars into each file. Without a zone they start at bar 1, as before. The DAWproject export follows the same origin (slice 2b): every arrangement time in the document (clips, markers, tempo and meter points; notes, controllers and loop points are clip-relative) moves later by those whole bars, bar 1's tempo and meter sit at time 0, and its stems render from that bar, so no time is negative; transit's importer reads such a project back with no zone, its first bar being the zone's first bar.
- `bounded_to_track` (`crates/engine/src/io.rs`) floors at the session start, so the audio-track tools that render a track's material (transients, Strip Silence, Audio as MIDI) accept a range in the zone. **Superseded by decision 18.8 when slice 9 lands; until then the rest of this bullet describes the code.** Bounce in Place prints the clips' spans and already reaches the zone; a whole-track print (`track.bounce`, Commit) renders from bar 1. Where a print of zone content lands is decided together with #442 (decision 11). Until then (slice 2b): Commit's limit (a whole-track print and Commit leave the zone out) is documented in the user guide, and Bounce in Place of a zone clip starts its audio at bar 1: the span is rendered whole and the printed audio clip starts at bar 1, with the zone's audio before its left edge in the file, hidden as decision 1.8 hides count-in audio (`bounce_track_range` in `crates/engine/src/io.rs`). Clips that end before bar 1, their two-second tail included, would print nothing that sounds, so Bounce in Place refuses them with a message before anything renders. When the print hides audio before bar 1 and the source choice silences the source (Mute, Mute and deactivate or Hide), that part no longer plays, and `clip.bounce` says so in its reply's `notice`, which the status line shows; with Leave the source keeps playing it.
- The session length shown anywhere is `content_end - start`, through one function, `Session::length()` (`crates/model/src/session.rs`): the session-open log line (`crates/engine/src/io/session.rs`) and `session.inspect`'s `length_samples` read it (slice 2b).
- `transport.go_to_end` is unchanged.
- **MIDI file export.** `file.export_midi` (`export_midi` in `crates/engine/src/io/midi.rs`) writes absolute ticks today, and `write_smf` clamps every negative tick to 0 (`clamp_tick` in `crates/midi/src/smf.rs`), which would stack every zone note on tick 0. It writes from the session start instead: when the session start is before 0, every event, including the conductor track's tempo, meter and marker events, moves later by `-bar_start_tick(b)`, where `b` is the bar holding the session start, so the file's first bar is the zone's first bar. It follows what plays: each clip is written through `clip_as_played` (`crates/mix/src/midi.rs`), which gives the clip's own notes and controllers from its grid start to its grid end (decision 17.1); today it also writes notes past a clip's end. The export writes each clip's own events only: the track's real-time properties, MIDI Track Offset and MIDI effects are not applied. Muted clips are left out (a file cannot mark a clip muted, so it would sound wherever the file is opened); muted tracks are still written. The exported conductor track also establishes the tempo and meter in effect at the export origin at file tick 0. For a zone, these are the session's bar-1 tempo and meter, extended backward. Shifting the original conductor events is not sufficient: `export_midi` hands the session's tempo and meter events to `write_smf`, which writes them at their supplied ticks and does not initialize tempo or meter at file tick 0, so their first events would otherwise occur after the exported zone. Markers keep their shifted positions. An export with a looped clip that would unroll to more than 2,000,000 events is refused with a message naming the track (`unroll_midi_loop`'s limit, in `export_midi_session` in `crates/engine/src/io/midi.rs`), and the consolidated export refuses a track that would play more than 2,000,000 events (`sequence_as_played`). "Only what sounds" follows playback's rules, not a filter of the raw sequence: note-offs clipped at the clip's grid end, and a valid loop's repetitions written out. Test: a 90 BPM, 3/4 session with a one-bar zone exports tempo and meter at file tick 0, later changes shifted by one 3/4 bar, and the pickup at its tick from the zone's bar line with its length (negative control: the base commit writes the pickup at tick 0). Including the zone by default, starting the MIDI file at the bar holding the session start, and writing only what sounds are decided by the maintainer.

### 11. Audio clips, automation, markers and the other lanes

Narrowest rule for now (proposed): **only MIDI clips may start before bar 1.** Superseded for audio clips by decision 18 (amendment 2026-11-26).

- Audio clips may start before bar 1 through a start trim, a move, paste or copy within the zone, a print or a recording (decision 18). `clip.place_source`, imports and file drops keep their floor at bar 1.
- Automation points stay at or after bar 1 (`automation.set_point`, `l.set_point(at.max(0), ...)`). In the zone a lane reads its value at bar 1 (its first point's value), so a MIDI pickup plays through the mixer as bar 1 sets it.
- Markers, key signatures, tempo and meter events stay at or after bar 1.
- A MIDI clip in the zone plays through its track's instrument and inserts like any clip; nothing in `crates/mix/src/midi.rs` assumes a non-negative clip start (`base` is the clip start's tick, positive or negative; the `.max(0)` sites there are clip-relative ticks).

### 12. The control protocol

- Positions are already signed within ±`MAX_POSITION` and parse as negative bars (`"bars_beats:-1|1|000"`) or negative Min:Secs.
- Floors at the session start: `transport.play`, `transport.locate`, `transport.rewind`, `transport.loop`, `transport.rtz` (to the session start), `view.scroll`, the edit selection, clip moves and pastes of MIDI clips, `edit.copy_clips` (whose `by.max(-src[0].1.start)` floors the earliest copy at 0 today; it floors at the session start, for an audio clip too since decision 18.1), MIDI clip creation in `midi_time.rs` and `event_more.rs`, and the default `start` of `file.bounce_mix`, `file.bounce_paths`, `file.bounce_stems`, real-time renders and `file.export_midi`. `midi_time::origin` (`crates/engine/src/cmd/midi_time.rs`) returns the signed absolute tick of the clip start. `midi_time::parse` accepts a negative origin (today it rejects `origin < 0`) while retaining positive, one-based clip-local bar and beat components and its checked arithmetic. Musical note starts and lengths remain clip-local; this change does not introduce absolute session-bar addressing. Clip creation and musical lengths in the zone use the same signed-origin support.
- Floors at bar 1 (unchanged): `clip.place_source`, imports, `automation.set_point`, markers, tempo and meter commands. Before its retirement, `event.move_song_start` also refuses while a zone exists (decision 7).
- `ui.inspect`'s recording pass reports `capture_start` unclamped and gains `count_in` as the plan carries it.
- A read that reports the session's extent reports `start` beside the end (slice 2b): `session.inspect` (and `file.get_info`, the same reply) gives `start_samples` (the session start), `end_samples` (the content end) and `length_samples` (`content_end - start`, decision 10; it was the content end before, which it still equals without a zone).
- `docs/` protocol pages say which commands accept the zone.

### 13. The saved file and older builds

- No new field on the session, no `format_version` change, no migration: a clip's `start` is already a signed number in the file.
- **A `pre_count` need (ADR 0023).** `Session::needs()` lists `pre_count` when `Session::start()` is before 0, and `KNOWN_NEEDS` gains it. A build with the marker and without this entry warns on load that parts of the session may be missing or sound different, and that saving can drop them. The marker is a warning, not a shim: alpha's no-migration rule stands.
- **What an older build does with a session that has content before bar 1.** It loads the file; `Clip::sanitize` keeps the negative start. Its ruler and scroll stop at bar 1, so the zone is out of sight and out of reach; Return to Zero and Play go to bar 1, so the pickups do not play (a clip starting in the zone plays only its part after bar 1). Its bounce starts at bar 1 and leaves the zone out. Saving without touching the clip keeps it whole. Moving the clip, or anything else that runs `move_clips` over it, clamps its start to bar 1 and shifts every note later by the zone's length: silent damage. Builds since the marker (ADR 0023) warn first; builds before it do not. The release notes say this loudly.
- A clip with hidden notes (decision 17) plays them at its first tick in an older build; the `midi_hidden_notes` need warns builds since the marker.
- An audio clip before bar 1 adds the `audio_pre_count` need (decision 18.9).

### 14. Audio during the count-in (#442, not decided here)

**Superseded by decision 18 (amendment 2026-11-26).** The paragraph below is the state before it. One statement in it was wrong at the time: the input is rolling before the latch (capture starts when the take is armed), and the take writer discards the count-in audio when the start latches (decision 18.7).

Under the one capture model (decision 1.8) audio differs only in its default edge: the take file holds everything from the count-in start, and the clip's left edge stays at the record start, so the count-in audio (mostly room bleed and floor noise) is hidden until the user drags the edge back. An audio clip's left edge already hides rather than destroys: a start trim moves the clip's offset into its file (`trim_start`, "audio clips advance into the file"), so the hidden audio is still in the file. What #442 would have to change: the audio recorder keeps input from the count-in start (today the audio take starts at the latch, and the input may not be rolling before it); the take file then begins before the latch, so the clip is placed with a positive source offset equal to the count-in; dragging that edge back before bar 1 needs audio clips in the zone (decision 11's bar-1 floor lifted for audio); and disk-backed sources (ADR 0035) prime from that offset. Audio has no note-on, so decision 1.3 does not apply: the edge does not open by itself. #442 decides these.

### 15. Retrospective MIDI capture (#330)

#330 places a captured phrase at the cursor with the first note on the nearest beat. With the cursor at bar 1, notes before that first beat land before bar 1; they go into the zone under the same rule as pickups (MIDI clips may start before bar 1, the session start follows the clip). Nothing in #330's design changes.

### 16. Real-time rules

Nothing here adds allocation, locking or blocking on the audio thread. Positions on the audio thread are already `i64` and the player already accepts any start within ±`MAX_POSITION`. `Session::start()` is computed on the control and UI threads, over the clip lists they already walk, and never reaches the audio thread except as a position it can already receive. The click change in `crates/mix/src/click.rs` removes one clamp and reads nothing new; in particular it does not read `Session::start()`, which walks every clip. The capture changes only remove clamps in code that runs on the control thread (`MidiTake::timed` on the main-thread facade, the journal and the take builder). Decision 17's playback change replaces a clamp by a skip in `played_note`, which allocates nothing.

### 17. A MIDI clip's left edge hides; it never destroys

Decision 1.9 is not true today for a clip that is not looped (Context): a start trim drops the notes it cuts off, and a note left at a negative tick sounds at the clip's first tick. The right edge already hides. The rule:

1. **The sequence keeps every note; the edges decide what sounds.** A note or controller of a MIDI clip that is not looped sounds only when it starts at or after the clip's grid start and before its grid end (ADR 0019's amendment, item 4). The rest is hidden: kept in the file, not played, not sent to an external output, not chased, not consolidated, not bounced.
2. **`trim_start` keeps what it cuts off** (for the trims named in item 10). It drops its `retain` for clips that are not looped, so the cut-off notes and controllers stay at negative ticks, as a looped clip's already do. Dragging the edge back out (a start trim with a negative delta, which already shifts notes later by the same ticks) brings them back where they were played.
3. **`played_note` skips a note whose stored tick is before 0** in a clip that is not looped (`n0.start < 0`), instead of clamping it. A visible note that the track's Delay moves before tick 0 still clamps to tick 0, as today, the same as controllers (`c.tick >= 0`, then the delayed tick clamped). The same function serves playback and the external output and chase (`crates/mix/src/external_midi.rs`), so both follow. Controllers already skip negative ticks. A note that starts before the left edge is hidden whole, even if its release is after the edge. This is decided by the maintainer. Accepted: a chord played during the count-in and held through the downbeat is silent after trimming the left edge to bar 1.
4. **The piano roll hides what is before the left edge.** A note or controller before the clip's left edge (a stored tick before 0 in a clip that is not looped) is not drawn, not selected by Select All and not touched by quantize, transpose, duplicate or delete. Notes past the right edge keep today's treatment in the piano roll, the note commands and copies (the roll draws them as outside the clip, `paint_notes`); they are already silent in playback, export and bounce. Showing left-hidden notes (for example dimmed outside the edge) is a later view option, not part of these slices (decided by the maintainer).
5. **Split stays a partition.** `split_clip` gives each half the notes on its side, as today; a split is a cut, not a trim (decided by the maintainer).
6. **Consolidate** (`consolidate_midi`) already keeps only notes inside `0..len` and so writes the visible notes only; unchanged.
7. **ADR 0019's amendment, item 4,** says a trim that clears a loop under `MIN_CYCLE` leaves the notes it moved to negative ticks "where playback starts them at its first tick, all at once". Under this rule they are hidden instead. That clause is updated in the same change.
8. **Older builds.** A build without this rule plays a hidden note at the clip's first tick. `Session::needs()` lists `midi_hidden_notes` when any MIDI clip that is not looped holds a note or controller before tick 0, and `KNOWN_NEEDS` gains it (ADR 0023), so builds since the marker warn.
9. **Baking real-time properties** (`crates/engine/src/cmd/track_more.rs`, today `n.start.saturating_add(delay).max(0)` for every note) preserves the distinction between hidden stored events and visible events. In an unlooped clip, hidden notes remain unchanged. Visible notes bake Delay with the same tick-zero clamp used by playback, so a visible note at tick 0 under negative Delay remains audible at tick 0 after baking. Valid looped clips retain their loop semantics; a negative stored tick alone does not make their content hidden. A validly looped clip bakes Delay without the tick-zero clamp, as playback plays it, and an unlooped clip's visible notes clamp at tick 0.
10. **A copy is a cut, not a trim.** `copy_range` (`crates/engine/src/edit.rs`) drops, for a clip that is not looped, the notes and controllers before the copied range's start (it filters after `trim_start`), so copy, paste, duplicate and consolidate never carry notes hidden by the left edge; what lies past the copied range's end stays hidden by the copy's right edge, as today (consolidate already writes only `0..len`). `trim_to`, Trim Start to Insertion, the trim drag and the retime squeeze (`crates/engine/src/retime.rs`) keep them: they are trims. This rule also covers whole-clip copy gestures. `edit.copy_clips` (`crates/engine/src/cmd/edit.rs`, which clones complete clips), including arranger Ctrl/Alt-drag through `StudioApp::copy_clips`, drops each unlooped source's notes and controllers before tick 0 before placing its copy. Filtering only `copy_range` is insufficient. Valid looped copies retain the material required by their repeats. Whole-track copies follow the same line between a verbatim copy and new content: `track.duplicate` keeps hidden events (it is a verbatim copy of the track, like a playlist duplicate), while `track.extract_midi` and range copies drop them (they make new content from what sounds). This is an engineering decision.
11. **Overdub reveals what its new start passes.** When a take merges into a clip and moves its start earlier (`merge` in `crates/engine/src/midi_take.rs`), hidden notes at or after the new start sound, as if the edge had been dragged back (decision 1.8). Hidden describes an event relative to its containing clip's final edge, so a merge into an earlier existing clip can also reveal the take's incoming count-in controllers even when the existing clip's start does not move (decision 8). Keeping an incoming controller hidden independently of that final edge is not provided by this single-edge capture model; this is accepted with the overlap and controller rules decided by the maintainer.
12. **The trim floor** reaches the clip's earliest hidden event (decision 7).
13. **A command that addresses an event by index treats a hidden index exactly as it treats an out-of-range index**: it refuses where it refuses an out-of-range index and ignores where it ignores one, per command. A command that refuses validates the whole selection before it writes, so a refused command changes nothing.

**How much work.** The engine core is small: two `retain` lines removed in `trim_start`, a clamp turned into a skip in `played_note`, the filter in `copy_range`, the bake, the trim floor, the need, the ADR 0019 clause. The audit covers every walker of a clip's notes: the piano roll (`crates/ui-studio/src/keys/`), the arranger thumbnail (`pitch_span` in `crates/ui-studio/src/arrange/clips.rs`), the engine's note commands (`cmd/midi.rs`, whose `(n.start + dt).max(0)` would move an addressed hidden note to tick 0; quantize and the duration ops in `cmd/event.rs`; `cmd/track_more.rs`), `takes_join`, `score` and `inspect`, and MIDI file export (decision 10). Each one skips events before the left edge or is listed as deliberately seeing them; events past the right edge keep today's treatment (item 4). The audit also found walkers this list missed: `track.extract_midi` (a copy, item 10), the step input tie, Extract Chords and Tab to transients skip events before the left edge like the rest, and DAWproject export and clip group file export skip them too, in slice 6a (an engineering decision). Deliberately seeing hidden events: `midi.notes` and inspect's `note_list` (they are the index map the note commands address, so a hidden note shows its negative start), `remove_duplicate_notes`, `select_split_notes` (a partition, like split), `playlist_duplicate`, restore and flatten performance, retime, `split_clip`, `sanitize`, `session.save_copy` and `export_selected_tracks_as_session` (session files keep everything), and `export_sibelius`, which goes through `score` and already leaves them out. Engine preparation may land first, but non-destructive trimming and hidden-note playback semantics are not activated until the UI's visibility, selection, copying and source-index mapping are ready: today the piano roll clones every note (`clip_view` in `crates/ui-studio/src/keys.rs`), Select All selects them all, and Duplicate submits copies as new notes through `midi.note_add`, which cannot know its source was hidden. UI filtering preserves the original sequence indices used by note commands (`crates/ui-studio/src/keys/multi.rs` derives local indices from sequence order). No intermediate landing allows ordinary piano-roll actions to duplicate or modify hidden content. The audit is done before the landing sizes are fixed (Slices). Activation lands before recording, because a take whose clip opens to the count-in start must be trimmable without losing the early notes.

**Recording rarely creates hidden notes.** A take's clip opens to the count-in start when a note was played (decision 1.2), so every captured note is visible. The exception is a count-in with controllers and no note (decision 8, Events kept). Otherwise hidden notes come from a start trim (item 10 lists which edits are trims), which hides them only once slice 6a lands. Before it, a session made by transit can already hold hidden content: a start trim of a looped clip followed by `clip.clear_loop` leaves negative-tick notes in an unlooped clip (slice 4). No catch range (decision 1.10): a note played a few ticks before the downbeat stays a few ticks before it.

## Evidence an implementation must carry

Deterministic tests on the existing fixtures, no wall-clock assertions, no device access, no pinned hashes (click waveforms are compared by events or in process, because `click::blip` uses platform math). Each negative control names the base path that fails; these are static readings of ac370f78 and, for #440, of `main`, to be confirmed against the commit each slice is built on when each test is written.

- **Model.** `Session::start()` is 0 for an empty session and for one without negative clips, the earliest clip start otherwise, and counts clips on inactive playlists. `needs()` lists `pre_count` exactly when it is negative; a session with a zone round-trips through save and load with the clip start and its notes unchanged; a build that removes `pre_count` from `KNOWN_NEEDS` warns on load (the ADR 0023 pattern).
- **Take builder** (`crates/engine/src/midi_take.rs`). A pickup at the session start places the clip at `-n` with every note where it was played; a note played wholly during the count-in keeps its length and is in the take (negative control: `main`'s `ended_before_start` leaves it out; the base commit gives a one-tick sliver); a pass with nothing played early starts at the latch; a later record start with a pickup covers the whole count-in (negative control: the base commit starts the clip at the first pickup); a punch takes no pickup; loop recording gives the pickup to the first lap only, at the session start and later; a record start in the zone grows the zone; with a pickup, controllers from the count-in start are visible; without one, they are kept hidden at negative ticks; a pass with captured controllers and no visible events gives a silent clip whose left edge is at the latch, and a pass with no retained events gives none; with `count_in: Some(n)`, a note-on before `-n` is not a pickup; a take merged into an existing clip that starts two bars earlier sounds the take's count-in controller (decision 8).
- **Journal.** A header with `count_in: Some(n)` recovers the same clip the live path placed; a header with `None` falls back to the earliest pickup; nothing is clamped at sample 0.
- **Player** (`crates/playback/src/player/audio/midi/tests.rs`, `count_in.rs`). A pickup before the session start keeps its full offset from the latch (negative control: the base commit's `MidiTake::timed` clamps it). Playing from a negative position renders a zone clip's notes on their samples at block sizes 1 and 512. Negative control: at the base commit `transport.play {from: <negative>}` starts at 0. ## Consequences

- A count-in take keeps what the player played, where they played it, at the session start and later alike, and playing from the start plays it.
- Takes started later in the session now start a whole count-in early when something was played early, so they overlap the previous clip more often and merge into it, or start a take stack, more often than under #327.
- Every position floor becomes a choice between 0 and the session start; a new command that takes a position must make that choice. The review checklist gains "does this position floor at 0 or at the session start?".
- A file with a zone is damaged by moving its zone clips in a build that predates this ADR (decision 13).
- A MIDI clip's left edge becomes non-destructive, matching its right edge and audio clips' left edge; a clip file can carry notes nobody hears, which the piano roll does not show until a view option does.
- Count-in controllers with no note played stay in takes as hidden content, so such takes list `midi_hidden_notes`.
- The zone's grid can differ from the clicks a count-in played when the record bar's tempo is not bar 1's (decision 3).

## Alternatives rejected

- **A session-start offset with non-negative stored positions** (decision 2, b): moves the tempo map's origin or rewrites every stored position when a zone appears.
- **Shifting content later and renumbering** (decision 2, c): `event.move_song_start` already does it for ticks-timebase material; it parts audio from MIDI, makes a record pass a whole-session edit, and moves time readings.
- **A stored zone length** (a `pre_count` field on the session): a second source of truth beside the clips, a field to keep in step on delete, move and undo, and a zone that can outlive its content. Deriving it from the clips gives decision 1.3 for free.
- **A zone from the first pickup only** (#327's rule at the session start): the maintainer decided the whole count-in (decision 1.2).
- **A catch range** that moves notes played slightly before the clip start onto it: notes stay where they were played (decision 1.10).
- **Keeping the destructive left trim** for clips that are not looped: a take that opens to the count-in start could then not be tidied without losing the early notes (decision 1.9).
- **A cap on the zone** (for example the longest count-in, 16 bars, `count_in_for`'s clamp): positions are already bounded by `MAX_POSITION`, and a cap would drop captured content.
- **Ableton's model** (no recording during the count-in, Capture MIDI afterward): the maintainer chose Logic's for pickups (#327); Capture MIDI stays planned as #330.

## Settled choices

On 2026-11-10 the maintainer accepted the recommendations of the earlier open list: the click sounds in the zone, today's overlap rules stay with the longer lead, count-in controllers are visible with a note and hidden without one, there is no handle to extend the zone, the zone gets a darker lane token, a split stays a partition, and hidden notes are not shown in these slices. Each stands in the decision text above. Return to Zero, default inclusion of the zone in bounce and MIDI file export, whole-note hiding across the left edge, and retirement of `event.move_song_start` were decided earlier. The zone's cap, the count-in clicks (a follow-up issue) and a sync output in the zone (out of scope, an ADR 0043 amendment later) are decided above as engineering.

## Amendment 2026-11-16: the latch at a converted device rate (#724)

Accepted 2026-11-16 after three judging rounds (proposed the same day), together with the 2026-11-16 amendments of ADR 0015, 0017 and 0020. It records what the code that landed for #724 (1af45806..12e06b36) does and changes no decision. Decision 8 says capture stamps events against the latch; that sentence gains, in place, which frame the latch is at a converted device rate.

- **What changed.** At a converted device rate the latch was the output frame being produced when the take's first block was rendered. The output converter presents that block its lead later, so the latch was early by the converter's lead against the frame where the record start is heard, and the take landed that much late against what was heard (the commit message of 251729a0 gives 15 output frames at 48 kHz on a 44.1 kHz device as an example; no test pinned it). Now the converter runs on through the count-in end: the block that starts the take is presented its lead after the next consumed output frame, that frame is the latch, and the timeline reaches the record start on it (`Transport::record_ahead` and `Timeline::lead_in`). The lead is `Phase::ahead`, which rounds the converter's lead to the nearest output frame (a half rounds up), so the latch is within half an output frame of the frame presenting the start sample, and exact when the frames rendered since the converter started convert to a whole number of output frames (a count-in bar of 96,000 frames at 48 kHz is 88,200 at 44.1 kHz). At equal rates the lead is 0 and nothing changes.
- **What it means for a take** (tested with whole bars at 120 BPM, which convert exactly). The count-in bar keeps its full length in output frames (96,000 session frames at 48 kHz are 88,200 output frames on a 44.1 kHz device and 192,000 on a 96 kHz device); the take starts on the frame where the record start is heard; a pickup played on a count-in click lands on that click's place before the record start; and what sounds across the latch (a monitored input, a held note, a tail) stays continuous.
- **Evidence.** `the_latch_presents_the_start_sample_at_a_converted_rate_too` and `a_tone_sounding_across_the_latch_has_no_step_at_any_rate` (`crates/playback/src/player/audio/tests/count_in.rs`, devices at 44.1, 48 and 96 kHz under a 48 kHz plan, callbacks of 128 to 700 frames); `a_pickup_on_a_count_in_click_lands_on_that_click_at_a_converted_rate_too` (`crates/playback/src/player/audio/midi/tests.rs`).
- **Not covered.** A count-in whose length does not convert to whole output frames has no test (by reading, the latch is then within half an output frame). Since v0.7.4 Play and Record without a count-in run the converter on through a start from a stop, so audio already sounding is not cut (#725). What still restarts it, each a stated limit (decided 2026-11-26): the count-in start at a converted rate, where the frames the converter had rendered ahead are skipped and the filter starts from silence on the output frame where the first click starts, a splice rather than a gap (about 17 to 19 session frames, 0.35 to 0.4 ms, with a 48 kHz session on a 44.1 or 96 kHz device; the size depends on the rate pair, since the reader's reach is 16·max(1, session rate / device rate) session frames, 32 with a 96 kHz session on a 48 kHz device), while the first click's timing stays as this amendment pins it (running the converter on there would move that click by the reader's lead); Locate while playing, which discards the pending audio at once and restarts the converter (that block holds the whole mix, so keeping a live input continuous across a locate would mean either a delayed locate or audio from the old position after it); and Stop and the transport's end, whose restart hardware-insert latency compensation relies on ([ADR 0015](0015-io-routing-abstraction.md), the 2026-11-16 amendment on the #709 converter term, rule 10). A Play or Record with a position while already playing is not a Locate: it plays out the pending remainder, the converter's lead (`Phase::ahead_after`), and then jumps. That lead is bounded by the reader's reach, not by the callback: about 16 output frames when the device rate is at or below the session rate and 16 × device rate / session rate above it (up to about 32 with a 48 kHz session on a 96 kHz device), so with small callbacks it can span more than one callback.

## Amendment 2026-11-26: audio in the zone and audio during the count-in (#442)

Proposed 2026-11-26. The maintainer decided nine points on 2026-11-26 (#442, checked by a second reviewer); this amendment states them as decision 18, one item per point. It supersedes decision 11 for audio clips, decision 14, the print sentences of decision 10 and the audio move floor of decision 7, each marked in place. File and line references are readings of 5233b087.

**Terms.** All lengths and positions in decision 18 are session samples unless they are named file frames. A take file's **lead** is its frames before the frame that holds the record start (the latch). `session_len(f) = round(f × session rate / plan.rate)` is the length in session samples of `f` file frames at the plan's rate `plan.rate` (the take file's rate: `TakeWriter::create` writes at the recorder's rate, which `plan_recording` copies into the plan): it is the length `add_source` gives a decoded take (`crates/engine/src/io.rs:168-172`; `transit_dsp::offline::resample` rounds at `crates/dsp/src/offline.rs:219`), and `f` itself for a disk-backed take, which streams only at the session rate (`crates/engine/src/io/disk.rs:53`). **The lead is never inferred from `count_in`:** today's builds already write `count_in: Some(n)` for every pass (`crates/ui-studio/src/host/recording.rs:128`) while the writer starts the file at the latch (`crates/playback/src/record.rs:776-781`). `Recording` (`crates/engine/src/io/recording.rs:105-110`) gains `audio_lead: Option<u64>`, the lead in file frames, with `#[serde(default, skip_serializing_if = "Option::is_none")]`. From slice 10, `plan_recording` writes `Some(L_in)` for every pass with audio takes, where `L_in = round(n × plan.rate / session rate)` (half up) for count-in `n`, or `Some(0)` without one. A pass armed without a start gate (`Recorder::arm`, `crates/playback/src/record.rs:572`, used when there is no player, `host/recording.rs:286`) has no lead and writes `Some(0)`. The plan Stop builds when none was kept (`host/recording.rs:420-431`, today `rate: 0`) carries the recorder's rate as `rate` and the same `audio_lead` the host published for the pass (18.7). Every other constructor or copy keeps both: `plan_recording` sets them (`host/recording.rs:115-131`), the autosave copies use the whole plan or struct update (`host/autosave.rs:31`, `:54`; `host/recording.rs:248`, `:304`), and crash recovery reads the saved plan with its fields (`plan_of`, `crates/engine/src/autosave.rs:488`). `Recording::new` and `add_recording` (`recording.rs:115`, `:206`) mean a file without a lead, as today. Absent means a file that starts at the latch: lead 0, today's layout, whatever `count_in` says. `L_s = session_len(L_in)`, which is `n` at equal rates, and `F = session_len(file frames)` is the take's length.

### 18. Audio clips in the zone, prints of zone content, audio during the count-in

1. **An audio clip's start trim reaches its file start, in the zone too; moves stop at the session start.** `start_trim_floor` (`crates/engine/src/edit.rs:528`) returns, for an audio clip, `min(Session::start(), c.start - c.source_offset())`, bounded by `-MAX_POSITION`, instead of 0: the same file-start expression as `file_span` (`edit.rs:596-598`), so the floor and the file bound agree (a recorded take has stretch 1). `trim_bounds` (`edit.rs:569`) keeps its neighbor bounds and the file bound (`file_span`), so a trim stops at the end of an earlier clip on the playlist and never passes the file start; in Shuffle an audio clip keeps only its file bound, as today. A trim before the session start grows the zone. The arranger's start-trim drag and preview read the same functions (`crates/ui-studio/src/arrange.rs:604`, `:631`). `start_floor` (`edit.rs:515-516`) returns the session start for audio clips as for MIDI, so `move_clips`, `edit.paste` and `edit.copy_clips` (`crates/engine/src/cmd/edit.rs:346`, `:979`), the paths in `cmd/edit_more.rs:455` and `:663`, nudge, and the arranger drags (`crates/ui-studio/src/actions.rs:219`, `arrange.rs:584`) stop an audio clip at the session start and never grow the zone. With the bar-1 floor kept, any move of an audio clip already in the zone would lift it to bar 1 on its own with its offset unchanged (`edit.rs:501-506`). `clip.place_source` (`crates/engine/src/cmd/clip.rs:163`, `.max(0)`), imports and file drops keep their floor at bar 1; automation, markers, key signatures, tempo and meter stay at or after bar 1 (decision 11).
2. **A take whose record start is in the zone is placed where it was recorded.** `from_bar_one` (`recording.rs:346`) and its calls (`:237`, `:276`) go, so a piece keeps `at < 0`, and a piece wholly before bar 1 is a clip in the zone. With it go `BEFORE_BAR_ONE_NOTE`, `before_bar_one_note` and `before_bar_one_laps_note` (`recording.rs:323-339`), the "recorded before bar 1" unplaced entry (`:277-282`), the early-take filter in `report_lap_notes` (`crates/ui-studio/src/host/recording.rs:540-542`) and known issue `issue-442`. An unplaced entry with that reason already saved in a session stays listed (no migration).
3. **Mid-session.** A take's single piece is `Piece { offset: L_s, at: plan.start, len: F - L_s }` (today `offset: 0, len: frames`, `recording.rs:380`), and a take with `F - L_s <= 0` is empty (the check at `recording.rs:229` reads `got.frames()` today): it gets today's empty-take message and no clip. The clip starts at the record start, the count-in audio is in the file before it, and a left trim reveals it down to the file start (18.1), into the zone when the count-in crosses bar 1.
4. **The clip never opens with the count-in showing.** No placement makes a piece whose range includes the lead. A pass's overlap decisions use the pieces placement makes, computed in session samples from `F` and `L_s` at both call sites: the new-take check (`recording.rs:234-237`, which today passes `got.frames()`, file frames at the file's rate, before `add_source` resamples) and placement (`recording.rs:272-274`, which passes `x.frames`, the source's length at the session rate). At unequal rates the check under-measures today, lead or not: a four-second take at 44.1 kHz under a 48 kHz session is checked as 176,400 and placed as 192,000, so a clip starting 180,000 after the record start escapes the take stack and is overwritten (a related defect, fixed by this rule). `takes_end` (`recording.rs:150-160`, which rounds up) uses `session_len` too, so `pass_end` and placement agree. So a lead lying over an earlier clip neither starts a take stack nor is written over that clip by `place_clip`, and revealing it later stops at that clip's end (18.1). The live take strip (`crates/ui-studio/src/arrange/recording_preview.rs:9-19`) draws the take's first sample `L_s` before the origin `live_span` returns (`recording.rs:508-511`; its length comes from the transport clock, which starts at the latch), clipped to the span `live_span` returns, so the count-in is never drawn. The issue body, which said otherwise, is corrected on GitHub.
5. **Punch.** A punch never shows the lead. Placement intersects each piece with the punch range itself: a piece `[at, at + len)` becomes `[max(at, punch.start), min(at + len, punch.end))`, its offset advanced by `max(0, punch.start - at)`, and a piece left empty makes no clip. The `edit.trim_to_fill_selection` calls after placement go (`recording.rs:173-177` and `:188-198`, with the undo squash folded around the second), because that command can also extend a clip back toward its file start (`trim_to_fill`, `crates/engine/src/cmd/edit.rs:752-756`, bounded only by the file and the neighbors), which would show the count-in. Example: `plan.start` 96,000, `L_s` 96,000, `F` 144,000 and punch `[48000, 144000)` place `[96000, 144000)` at offset 96,000; the trim command would move the edge to 48,000 at offset 48,000 and make one second of count-in audible. The count-in and pre-roll audio stay hidden in the file, and "a punch takes no pickups" (decision 6) holds for what is heard. The UI's `begin_pass` sets no punch (every branch, `host/recording.rs:50-85`); this is the protocol plan's and crash recovery's path.
6. **Loop recording: the count-in belongs to the first lap only.** `take_pieces` (`recording.rs:375`) cuts laps from the latch over `F - L_s` with `lead` 0 (`take_laps::laps`, `crates/engine/src/take_laps.rs:59`) and adds `L_s` to every piece's offset. Only the first lap's piece has the count-in before it in the file; a later lap's piece has the previous lap before it, as today. The audio part of a pass's end is one engine function, `max(0, takes_end - L_s)` over the plan's take files, used by every place that computes it: `pass_end` for a plan without `end` (`recording.rs:135-147`), reached by audio crash recovery (`autosave::recover`, `crates/engine/src/autosave.rs:403-404`) and by MIDI crash recovery, and Stop, which stores the furthest of the playhead, the take files and the last MIDI event in `plan.end` (`host/recording.rs:446-452`, which reads `takes_end` today). `pass_end` returns `plan.end` as it is (`recording.rs:136-137`), and the MIDI take builder cuts by it (`midi_pass_end`, `crates/engine/src/midi_take.rs:295-296`), so audio and MIDI laps are cut through one end (#567), live and recovered alike. MIDI crash recovery today forwards only the saved plan's `takes` (`autosave::recover_midi`, `autosave.rs:531-533`) into a plan rebuilt with `rate: 0` and no lead (`recover_with_takes`, `crates/engine/src/midi_journal.rs:310-325`): it forwards the saved plan's `takes`, `rate` and `audio_lead` together, and the rebuilt plan carries all three. A MIDI-only pass has no saved audio plan, or recovers through `midi_journal::recover` (`midi_journal.rs:293-295`), and has no audio part in its end. Without the subtraction at Stop, 96,000 of lead and 48,000 recorded at 44.1 kHz under 48 kHz store `plan.end` 144,000, and 96,000-sample laps gain a phantom second lap that a held MIDI note runs into, while recovery ends at 48,000. This mirrors ADR 0026's pickups amendment.
7. **The whole count-in is kept.** Today the input rolls from arm (`Shared::start_capture` in `arm_with`, `crates/playback/src/record.rs:641`), the take writer keeps a `start::History` of `RING_SECONDS` = 4 s (`record.rs:32`, `:595`) while the start is pending, evicting the oldest frames past that (`crates/playback/src/record/start.rs:516-519`), and at `Started` drains everything before the latch's input frame (`start.rs:503-504`): the take file starts at the latch and the count-in audio is discarded. The rule: the latch is at file frame `L_in` (input frames; the history already counts one input ordinal per file frame, `start.rs:503-509`).
   - **Publication before the count-in.** The count-in is computed in `begin_pass` (`host/recording.rs:77`, `:87`) after `Recorder::prepare` ran in `arm_audio_takes` (`:284`). Main stores `L_in` in the ticket's shared start state (`start::Shared`, `start.rs:108`) with Release in `Player::start_recording` (`crates/playback/src/player/device.rs:413-421`), before it sends `Command::Record`. The writer loads it (Acquire) before pushing each block and, once it is set, grows the history to `L_in` plus today's 4 s on the writer thread before that push. A count-in frame is captured only after the audio thread applies the request, which is sent after the store, so every count-in frame is pushed into a grown history and none is evicted. The audio thread's capture ring (`record.rs:480`) is unchanged.
   - **The file start, underflow included.** At `Started`, with the latch's input ordinal `a` (after the #587 move, `start.rs:484-496`, when it applies) and the first retained frame `r`, the file start is `s = a - L_in` in signed arithmetic, so `s` may be negative (the duplex estimate, `start.rs:295-302`, can give an early `a`). The writer first writes `max(0, r - s)` frames of silence, then the retained frames from `max(r, s)`, and logs once when it wrote silence. The latch is therefore always at file frame `L_in`, and placement and crash recovery need only the plan (`audio_lead`, `rate`).
   - No level detection, no automatic fade, no cap beyond the count-in length setting (`count_in_for` clamps at 16 bars). Stop during the count-in records nothing, as today. The lost-input report (`crates/playback/src/record/loss.rs:86-93`) measures from the latch, the file origin plus `L_in`, and a loss inside the lead reads "during the count-in".
