On Linux and macOS a CLAP plug-in file written over in place while transit has it loaded (`cp` onto it, some installers) changes the code its running instances execute: new bytes under code that is running are undefined, and on Linux the truncation also drops the loaded copy's relocated pages, which then come back from the file unrelocated even when the same bytes are written back; either can crash the app (#348 saw zero plug-ins and a segmentation fault on Linux). A file replaced by a rename (a linker's output, `mv`, `install`, most installers) is safe: the old file lives on while transit keeps it loaded. Windows refuses to write a loaded DLL. Since #348 transit never hands out the loaded copy of a changed file: a new instance of it fails to load (the log says "changed on disk or was removed since transit loaded it; restart transit to load it again"), while a rescan (in a child process) lists the new file's plug-ins. The check compares the binary's size and modification time, and on Linux and macOS its device and inode: a `touch` also counts as a change, and a same-size copy that carries the loaded file's own modification time does not when it is written in place, nor on Windows when it replaces the file. Running instances keep the old code, and transit never unloads a plug-in, so the new file loads only after a restart.
