Linux recording through cpal ALSA under PipeWire (#429). The "recording start fell outside retained input history" refusal a tester saw at a 2048-frame period is not an undersized history (it holds 4 s at any period and channel count): with consistent device clocks the start cannot precede the first input frame captured after arm, so it means the output's playback-time estimate and the input's capture-time estimate disagree on that machine; the refusal now logs the start, the first retained frame and the gap, and both clocks' figures and latencies. A start more than the input clock's 100 ms projection ahead now waits for the input instead of failing, but an input period of 100 ms or more (a PipeWire quantum of 4800 frames or more at 48 kHz) lets the input clock map go stale between callbacks, so a record start can still fail to map. The input of an ALSA server or default PCM ("default", "pipewire", "pulse", sysdefault) whose widths run contiguously from 1, a converting plug-in, opens stereo (else mono): those widths are an upmix of one source, not separate inputs. Every other device keeps its widest width as before, including a card (cpal lists it as plughw) and an interface whose widths change per rate band; where that widest width does not exist at the chosen rate the input does not open (an older limit, unchanged).
