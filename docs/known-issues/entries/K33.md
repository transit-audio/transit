Native ASIO MMCSS: when the driver does not call back after the stop request, the buffer-switch thread's registration is reverted from the host thread, against Microsoft's rule that the registering thread reverts. The slice d1 review's probe (Windows 11 26200) found this best-effort path safe: the handle is a process handle-table entry, a revert from another thread returns TRUE and restores the thread's priority, a second revert fails with error 6, and a registration never reverted is a leaked handle, not undefined behavior; transit reverts each handle at most once. A driver that registers its own callback thread cannot get a second registration from transit (Windows refuses it with error 1552, which transit takes as "the driver's", reported `DriverRegistered`, "MMCSS by driver" in Audio Devices, before and after the stop, nothing to revert), so ours never ends the driver's. Until ASIO slice d2 that case read `Unobserved`, as did a driver calling back on the host thread; the Scarlett 2i2's hardware run of 2026-10-22 read `Unobserved` (the Model 12 read `MmcssProAudio`, then `Released`), and the d2 states tell the two apart on the next run. The host-thread revert is not yet seen on the reference interfaces' drivers.
