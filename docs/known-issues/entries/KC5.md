Native JACK library choice (#230, #430). Until #430 every JACK call went through a static table that resolved each function from `dlopen("libjack.so.0")`, which the loader answers with the first object of that soname already mapped in the process, jackd2's library whenever anything loaded it first. PipeWire's library then could not serve the process and Audio Devices said "... connected, but another libjack was already loaded in this process; start transit with pw-jack" (#429). Fixed: transit declares the JACK functions itself and resolves them with `dlsym` on the handle of the library whose probe client connected, bound once for the process and never replaced; no library it loads is ever unloaded; PipeWire's library is found the way `pw-jack` finds it. Confirmed on Kubuntu with PipeWire, started without `pw-jack`: the log names PipeWire's libjack as the only JACK library mapped, and the client is active in the graph (#430). What remains: a library loaded by another component stays mapped beside ours and no longer decides which library serves transit (one in the process's global scope could still receive calls the chosen library makes to its own exported functions; no such component is known); when no PipeWire JACK library is found to try, Audio Devices offers `pipewire-jack` or `pw-jack` as the fallback; and with a PipeWire socket present while PipeWire's library does not connect (a stale socket) and `jackd` running, jackd2's library is never probed, because the loader answers `libjack.so.0` with PipeWire's still-loaded object (`TRANSIT_JACK_LIBRARY=libjack.so.0` is the way out).
