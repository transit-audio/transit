Native JACK library choice (#230, #430). Until #430 every JACK call went through `jack-sys`'s static table, which resolved each function from `dlopen("libjack.so.0")`; the dynamic loader answers that with the first object of that soname already mapped in the process, which is jackd2's libjack whenever anything loaded it first (an earlier probe with no PipeWire socket seen, or another component such as, plausibly, ALSA's JACK plug-in during ALSA device listing; which one was not established), so PipeWire's library could not serve the process and Audio Devices said "... connected, but another libjack was already loaded in this process; start transit with pw-jack" (a tester on Ubuntu 26.04 with jackdmp 1.9.22 and PipeWire, #429). Fixed: transit declares the JACK functions itself and resolves them with `dlsym` on the handle of the library whose probe client connected, bound once for the process and never replaced; no library it loads is ever unloaded; PipeWire's library is found the way `pw-jack` finds it, with no distribution path written in. What remains: a library loaded by another component stays mapped beside ours and no longer decides which library serves transit (one in the process's global scope could still receive calls the chosen library makes to its own exported functions; no such component is known, ADR 0021 Amendment 2026-11-10, Open), and when no PipeWire JACK library is found to try, Audio Devices offers `pipewire-jack` or `pw-jack` as the fallback; and with a PipeWire socket present while PipeWire's library does not connect (a stale socket) and `jackd` running, jackd2's library is never probed, because the loader answers `libjack.so.0` with PipeWire's still-loaded object (`TRANSIT_JACK_LIBRARY=libjack.so.0` is the way out).
