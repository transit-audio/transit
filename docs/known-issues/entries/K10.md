Closed on Windows and Linux: a heavy plug-in's create call blocked the UI thread for its duration (SDK main-thread rule). Hosted instances are now created, restored, edited and destroyed on a plug-in host thread ([ADR 0018](../../adr/0018-plugin-host-thread.md)); the slot reads "Loading…", and "Not responding" after 10 s. Since issue #56: an instance staging did not predict loads the same way (its document is compiled again when it is ready); a save waits for a plug-in held by a modal dialog at most 500 ms (still waiting for plug-ins that are answering, and for one never captured) and names any plug-in whose stored state it kept; a never-loaded type's parameter table is read on the host thread with a 500 ms bound. Remaining: macOS still creates on the UI thread (AppKit); on Windows the editor window still has no owner, but since issue #173 transit groups the editors with the main window by hand ([ADR 0030](../../adr/0030-editor-window-cohesion.md)): they hide and return with it when it is minimized and restored, come above it when it is activated, have no taskbar button (Window > Plug-in Windows Follow transit off keeps them apart, with their own buttons), and a plug-in that stops answering only stops its own window following; a plug-in's own extra windows and floating CLAP editors are not grouped; returning to transit by clicking an editor brings up only that editor, and the rest come up on the next click on the main window; Linux hosts editor windows on X11 since #147 (K92 to K94 for what is left); offline renders (bounce, stems, freeze) still make their instances on the thread that builds the render (ADR 0018 says why).
