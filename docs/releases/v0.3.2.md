# transit v0.3.2

This is a patch release following v0.3.1 with the fixes from the first Linux diagnostics report and from Discord feedback on FX channels, plus two small polish items. transit is alpha-quality software and the session format may still change, so back up anything you care about.

## Highlights

- **FX channels.** A new FX channel no longer picks up a send from whichever track was selected. Add one plain, or use + Send > New FX Channel on a track to get the channel and the send together. Escape, or a click on empty mixer space, clears the mixer highlight.
- **Step input idles quietly.** With Step on and nothing played, the piano roll polls MIDI every 30 ms instead of repainting at display rate, so a laptop left in Step mode stays cool.
- **Diagnostics on Linux.** The report no longer prints the WASAPI-only setting on Linux, the JACK note appears once, and every backend names its wake figure the same way. The Audio Devices window shows the JACK buffer note once under the device list.
- **MIDI Mappings.** Table cells are centered vertically, so text lines up with the Range fields and buttons.

## Fixes

- Mixer: + FX Channel (mixer button, Track menu, arrange quick-add) creates the channel with no send; + Send > New FX Channel on a track creates the channel and a -12 dB send from that track as one undo step; Escape and a click on empty mixer space clear the selection and the focused track, and the highlight follows an explicit focus or selection only (#145).
- Piano roll: while Step is on and nothing is pending, the editor polls MIDI at 30 ms instead of requesting a repaint every frame; a held key, pedal or pending chord brings the full rate back (#144).
- Diagnostics report: the Shared device (WASAPI) line prints only on Windows; the JACK server note (rate, buffer, how to pin it) prints once under the JACK heading instead of once per device; the wake figure reads "gap over period" on WASAPI render, ASIO and JACK (WASAPI capture keeps "late", which is what it measures, see docs/troubleshooting.md); a wake rate not yet sampled is left out instead of a dash (#146).
- Audio Devices: a system-wide note such as the JACK buffer hint shows once under the device list of the selected system; notes about one device stay under that device (#146).
- MIDI Mappings window: every cell is centered vertically, header included (#148).
- Repository: the timing lint treats a same-function helper that installs a clock as injected-clock evidence and reports a nested loop pair once. This has no user-facing change (#135).

## Known issues

Full list: [docs/known-issues](https://github.com/transit-audio/transit/blob/main/docs/known-issues/README.md).

- K87: the MIDI Mappings window's fixed columns need about 970 points of width, so on narrower screens the window can run past the screen edge.
- #139: a fast sustain pedal tap with no key held reportedly inserted no rest on one machine; it could not be reproduced and the timing path was reworked in v0.3.1. Please report if you see it.

| Linux (x86_64) Fedora and RPM package | `transit-0.3.2-linux-x86_64.rpm` |

A `.AppImage.zsync` file sits next to the AppImage for delta updates. Every archive carries `audio-bench`, which measures your interface (round trip, jitter, xruns).

All builds are unsigned. On Windows, SmartScreen shows "More info", then "Run anyway"; the Windows build includes native WASAPI and native ASIO. The macOS app is ad-hoc signed and not notarized; if macOS blocks it, run `xattr -dr com.apple.quarantine /Applications/transit.app`, or right-click it and choose Open. On Linux, make the AppImage executable (`chmod +x`) and run it, or install the .deb or .rpm with your package manager; none of the Linux packages are signed. The Linux builds carry the native JACK backend (#55): it talks to a running JACK 2 or PipeWire server (transit never starts one), and Auto prefers it when a server is up. On Debian and Ubuntu with PipeWire, start transit as `pw-jack transit` so PipeWire's JACK library is found. The first tester report (Ubuntu 24.04, PipeWire, 128 samples at 48 kHz) ran clean apart from one overload; more reports are wanted in #55: run `transit --report` and tell us how it went.
